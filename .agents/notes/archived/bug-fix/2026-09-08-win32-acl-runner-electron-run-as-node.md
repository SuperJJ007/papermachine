# Agent Note: the win32 ACL sandbox runner invocation carries its own required env, not the caller's guess

Status: implemented
Archived: 2026-09-10

English | [中文](2026-09-08-win32-acl-runner-electron-run-as-node.zh.md)

## Problem

Every Windows Science task timed out. `packages/sandbox/sandbox-local/src/index.ts`'s `windowsAclRunnerInvocation()` re-execs `process.execPath` to run `@deepseek-ai/dsh-sandbox-windows-acl`'s `runner` as a Node script — on a packaged desktop build, `process.execPath` is `PaperMachine.exe`, an Electron binary. Every spawn site (`science-runtime`'s `probeEnvironment`/`installEnvironment`/`kernelEnvironment`, all `environmentBase: 'empty'`) gave that re-exec only `HOME`/`TMPDIR`/`PATH`/locale — never `ELECTRON_RUN_AS_NODE=1`. Without it, the packaged binary does not run `runner` as Node; it boots itself as a second, complete desktop app instance (its own gpu-process, network-service utility process, and renderer), confirmed by two independent process-tree reproductions on a real Windows Server 2022 host: each science probe spawn produced two full app-shaped process trees (not a single Node child), which then each attempted to launch their own Host webserver — first against the port `host-port.json` remembered (colliding with the real, never-restarted Host: `EADDRINUSE`), then falling back to an OS-assigned port. `apps/desktop/src/main.ts:81` and `:341` already set `ELECTRON_RUN_AS_NODE: '1'` on their own `process.execPath` re-execs (the Host launch and the watchdog); the win32 ACL sandbox re-exec was the one call site nobody set it on. The real `python.exe`/`Rscript.exe` this probe was supposed to spawn never ran: the phantom instance is what hung, all the way to `DEFAULT_TIMEOUT_MS` (120000ms), at which point the fused abort signal killed the whole phantom tree — the two identical `aborted before spawn: TimeoutReason: SCIENCE_RUNTIME_TIMEOUT after 120000ms` messages users saw are `observePrepared()`'s next sequential probe (`utf8`) hitting `subprocess-local/spawn.ts`'s synchronous already-aborted guard, one per language. Whether the EADDRINUSE collision itself happened was port-allocation luck (one reproduction hit it, the other did not) — irrelevant to the outcome, since the science task timed out 100% of the time either way.

## Decision

`ConfinedArgv` (`packages/sandbox/sandbox/src/index.ts`) gains a required `env: Readonly<Record<string, string>>` field: environment entries the selected backend's runner invocation itself requires, which the caller merges OVER its own base env before spawning `argv`. `packages/sandbox/sandbox-local/src/index.ts`'s win32 ACL branch returns `env: { ELECTRON_RUN_AS_NODE: '1' }` (both the built-entry and the tsx-source-launch forms of `windowsAclRunnerInvocation()`, since both re-exec `process.execPath`); every POSIX branch, and the operator-configured `runnerCommand` override, returns `env: {}`. Every confined-argv spawn site merges `confined.env` last, so the backend's requirement wins on any key collision: `science-runtime`'s `runProbe`/`runMicromambaInstall`/`KernelProcess.start`, `bash-sandbox`/`pwsh-sandbox`'s `run()`/`start()` (merged into `spec.env`, which sits under the executor's own trusted `dshEnv` layer — safe because `dshEnv` is typed to managed `DSH_*` keys and can never collide with a backend-required key like `ELECTRON_RUN_AS_NODE`), and `terminal-bash`'s PTY spawn (merged into `childEnvironment(...)`'s result). The field is required, not optional, so every existing and future backend must state its answer explicitly (`{}` is a valid, deliberate answer) rather than the type silently defaulting one in.

The env requirement lives on the seam result, not inside `science-runtime`: the decision to re-exec `process.execPath` is the win32 ACL backend's own, made without any input from `science-runtime`, `bash-sandbox`, or any other consumer, so the environment that decision requires is the backend's fact to declare — a capability-seam split matching `denialSignatures`/`runnerFailureRules`, which already carry backend-owned classification facts the caller cannot know on its own.

## Alternatives considered

- **`science-runtime` reads `process.env.ELECTRON_RUN_AS_NODE` and forwards it.** Rejected: this makes a supposedly platform- and Electron-agnostic package (`science-runtime`, and transitively `dsh-subprocess`/`dsh-sandbox-local`) know that its own `process.execPath` might be an Electron binary — a fact that belongs to the win32 ACL backend, which is the party that chose to re-exec `process.execPath` in the first place. It also only fixes `science-runtime`: `bash-sandbox`, `pwsh-sandbox`, and `terminal-bash` all confine through the same seam and would still boot phantom app instances on Windows the next time any of them ran a confined command, since none of them has a reason to guess an Electron-specific env variable either.
- **Hardcode `ELECTRON_RUN_AS_NODE: '1'` inside `windowsAclRunnerInvocation()`'s own spawn call.** Not applicable: `sandbox-local` does not spawn the runner itself — `confine()` only returns the argv for the caller to spawn under its own subprocess seam (with its own stdio, cancellation, and process-tree lifecycle). The backend has no spawn call of its own to hardcode the variable into; it must communicate the requirement back through its return value.
- **Give `ConfinedArgv.env` a default of `{}` (optional field) instead of required.** Rejected per this repository's explicit-over-implicit convention: an optional field with an implicit empty default is exactly the kind of caller-side guess this fix removes elsewhere in the type. A required field forces every backend implementation (current and future) to state its answer, including the deliberate `{}` on every POSIX rung and the `runnerCommand` override.

## Consequences

Every confined-argv spawn site across `science-runtime`, `bash-sandbox`, `pwsh-sandbox`, and `terminal-bash` now merges `confined.env`; a future `.confine()` consumer that drops the field on its way to a real spawn call reintroduces this bug for itself. `apps/desktop/src/main.ts` additionally requests the single-instance lock (`app.requestSingleInstanceLock()`, quitting immediately without it, focusing the existing window on `second-instance`) as defense in depth: with the env fix in place, the win32 ACL runner invocation never reaches `main.ts`'s app code at all (`ELECTRON_RUN_AS_NODE=1` makes the packaged binary run as plain Node instead of booting Electron's app lifecycle), so the lock guards only a genuine second user launch or a future `process.execPath` re-exec that forgets the env variable — it does not, by itself, fix a missing env variable, since a locked-out phantom instance still would not run `runner` as Node before quitting. Real-device reconfirmation on Windows is a separate, still-pending step (this fix ships with unit-test coverage only, per the win32-no-CI testing policy).
