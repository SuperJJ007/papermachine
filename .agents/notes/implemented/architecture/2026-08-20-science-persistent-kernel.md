# Agent Note: A persistent per-language kernel replaces one-shot Python/R execution

Status: implemented

English | [中文](2026-08-20-science-persistent-kernel.zh.md)

## Problem

Claude Science keeps interpreter state alive across `run_python`/`run_r` calls within one session: variables, imports, and inline package installs (`pip install`, `install.packages()`) persist until a kernel ends by idle timeout, environment rebind, or session end. A fresh-process-per-run execution model cannot express that: every call started from a blank interpreter, so a user watched every earlier assignment vanish between calls, and there was no durable fact recording that a kernel had ever existed or ended.

A user-configured Conda prefix cannot be assumed to contain any notebook-kernel dependency, and the Runtime does not install into a prefix. A kernel therefore has to run with zero added dependencies, inside the same full-enforcement sandbox a one-shot process used, while giving the model and every later reader a durable, replayable account of when a kernel started, when and why it ended, and which runs shared its memory.

## Decision

This note owns the kernel process, its wire protocol, its durable lifecycle vocabulary, and every runtime behavior that depends on a kernel surviving past one run. The [Science Session decision](../feature/2026-08-15-dsh-science-v01-r1-science-session.md) continues to own the durable-event and replay mechanics this note's own event follows; the [Science Runtime decision](../feature/2026-08-15-dsh-science-v01-r2-science-runtime.md) continues to own the folded service's configuration strictness, prefix observation, and exact-Session lease and quarantine machinery this note extends rather than replaces — this note supersedes only its one-shot execution-mechanism paragraphs, rewritten in place to point here.

### Kernel process and wire protocol

A kernel is one long-lived confined subprocess per `(session, language)`: `kernel_python.py`, Python standard library only, run under `python -B -u -X utf8` (no `-I`: dropped so an inline `pip install`'s user-site fallback is importable within the kernel — see the [kernel-scoped inline installs Agent Note](2026-08-22-science-kernel-scoped-inline-installs.md)); `kernel_r.R`, base R only (no `jsonlite`, matching the R package-inventory probe's own TSV choice), run under `Rscript --vanilla --encoding=UTF-8`. Both ship as package assets under `packages/science/science-runtime/assets/`, resolved by a small module relative to its own `import.meta.url` so resolution is correct from both source and built execution. Neither driver needs a notebook-kernel package such as `ipykernel`/`IRkernel` — an assumption a user-configured prefix cannot support — and Jupyter's ZMQ transport would conflict with the sandbox's deny-by-default network posture. Each driver instead executes source in one persistent namespace (a module-level globals dict in Python, the global environment via `source()` in R).

Three channels carry the protocol, all inside the sandbox's writable scratch or the standard stdio pipes: the host writes single-line, tab-separated requests to the kernel's stdin; the driver writes single-line responses to a response FIFO the host creates with the POSIX `mkfifo` binary in the kernel's own scratch directory before spawn (a FIFO because base R can neither open a Unix domain socket nor `dup2` a file descriptor, and the sandbox denies TCP outright); a run's stdout/stderr go to per-run capture files the request names, never to the kernel's own stdio. Source travels by path, not by value — the host writes the run's exact UTF-8 source into the run directory before commit, and the driver `exec(compile(...))`s or `source()`s that file, reusing the same source-flush machinery a one-shot run always used.

FIFO response reads use an owned forwarding process so idle kernels cannot exhaust the Host filesystem pool; the [reader-isolation decision](../bug-fix/2026-08-31-science-fifo-reader-isolation.md) owns transport cleanup.

Python redirects a run's output at the file-descriptor level (`os.dup2`), so C-extension and child-process writes land in the correct capture file. R captures only through `sink()`: R-level `print`/`cat`/`message` output is attributed correctly, but C-level or child-process writes bypass `sink()` and land in the kernel's own long-lived, bounded stdout/stderr collectors, never attributed back to any run. When a driver detects it could not fully restore or attribute a run's capture, its response frame carries a degradation flag and the run's terminal event carries `outputDegraded: true`; the run's own result still stands, only its captured tails may be incomplete.

Both drivers harden crash paths that only matter once a kernel outlives a single run. Python rebinds `sys.stdout`/`sys.stderr` around every redirect and restore to `closefd=False` wrappers, so user code calling `sys.stdout.close()` cannot kill the kernel's own I/O. R records `sink.number()` before every push and unwinds every pop inside `tryCatch`, so a user `close(stdout())` or an unbalanced `sink()` call cannot desynchronize output routing for the next run. R's interrupt handling has a hard asymmetry from Python's: `tryCatch(interrupt = ...)` reliably catches `SIGINT` delivered during `Sys.sleep()` and CPU-bound loops, so a mid-run interrupt is safe, but an idle-time `SIGINT` either kills the R process outright or latches and misclassifies the very next run as interrupted — R has no idle-safe handler the way Python's default-ignored-until-`exec` handler does. The interrupt rule below exists specifically to keep that idle-time hazard unreachable.

Every kernel spawns under the same `workspace-write` sandbox policy a one-shot process needed — full enforcement, prefix read-only, empty subprocess environment base, owned `HOME`/`SCIENCE_STATE_DIR` — held for the kernel's entire lifetime instead of freshly reapplied per run; only `TMPDIR`/`SCIENCE_ARTIFACT_DIR` become per-run values the driver itself sets for each request, since one process serves every run across the kernel's whole lifetime.

### Lifecycle, epochs, and kernel ends

At most one kernel exists per `(session, language)` — Python and R kernels may coexist — starting lazily on the first run that needs it. `kernelEpoch` is a session-local counter strictly monotonic across both languages, allocated from the durable projection's own watermark rather than in-memory-only state, so it survives Host restarts; two runs sharing an epoch share the kernel's in-memory state, and a run naming an earlier epoch never saw what a later one produced. A dedicated kernel-set registry owns every live kernel keyed by the exact `Session` object, parallel to the existing per-operation lease registry: runs stay serialized through that lease exactly as before, but a kernel is a held resource rather than an operation, so holding one does not itself put a session's lease into a busy state.

A kernel ends for one of a closed set of reasons, switched on exhaustively everywhere it is consumed: `idle` (the idle timer fired with no run since its last reset), `session-end` (the owning session detached), `environment-rebound` (a newer applied environment revision exists for the kernel's language), `run-escalation` (an interrupted-but-unproven run left the kernel's state unknown), `protocol` (the driver broke the wire protocol), `crash` (the process exited uncommanded with no protocol violation observed), and `service-disposed` (the Runtime itself shut down). Every end path sends a cooperative exit request when the process is alive, then applies the same bounded-wait/`terminate()`/bounded-wait/eventual-quiescence escalation the rest of the Runtime already uses for process teardown; a same-id successor session stays quarantined until every kernel the prior lifecycle owned is proven quiescent, reusing the existing quarantine machinery rather than a second one. Two same-id registry entries racing to spawn concurrently still resolve to exactly one live, acquirable kernel: the losing entry's own kernel goes through that identical cooperative-exit/quiescence path rather than being left running unregistered outside the kernel-set's teardown discipline. The idle timer resets on every completed run and is disarmed for the whole window a run is in flight — from kernel acquisition through the run's own terminal commit — so it can never fire mid-run and kill a busy kernel.

### Durable events and the fold's relation set

One `SessionEventMap` member, `science/kernel-state`, carries a whole kernel-lifecycle transition: `kernelEpoch`, `language`, `state: 'started' | 'exited'`, `reason` (present iff exited), `startedAt` (present iff exited — the matched `started` fact's own `at`), `environmentRevision`, `environmentFingerprint`, `at`. Both directions reuse one shape rather than a started/terminal pair, because a kernel-state fact never repeats a field its own prior transition already fixed — with one deliberate exception. The `exited` direction restates `startedAt` so a closed kernel's own record never drops its start time; without it, a reader could not answer "how long did this kernel live" — the natural provenance question anchoring epoch-based state continuity — from the closed record alone. The fold asserts that restated value equals the matched `started` fact's own `at`, turning a false restatement into a decode-time rejection rather than a silent projection inconsistency.

The fold ties an `exited` fact to its open `started` fact by more than a `kernelEpoch`/`language` lookup: `environmentRevision` and `environmentFingerprint` must match exactly, mirroring the run terminal's own identity rule that a terminal record never rewrites its start-owned provenance in place. Both `kernel.at` never exceeding the folding event's own time and `exited.at >= started.at` are enforced as interval facts, the same class of check already applied to run terminals. The `started` direction additionally requires the environment relation a run already asserts — the kernel's `environmentRevision`/`environmentFingerprint` must resolve to the language's latest applied binding — while the `exited` direction is deliberately free of that "latest revision" requirement, because an `environment-rebound` exit legitimately names a revision a newer one has since superseded; its identity is pinned by the started-fact match instead of by being current.

`ScienceRunIdentity` carries a required `kernelEpoch`, naming the kernel instance that executed the run — the provenance backbone letting a reader or the model itself tell which runs shared memory: two runs sharing an epoch shared state, and a run whose epoch differs from an earlier one never saw it. The fold rejects a run naming an epoch that was never started, is already exited, or resolves to different provenance than the kernel record it claims.

Replay derives an interrupted kernel record for any kernel still `started` at the session's end-seed boundary, mirroring how an unmatched running run is handled — after a Host restart no kernel is ever presented to a reader or the model as running. This also covers the one path with no durable `exited` fact to derive from: ending a kernel after its owning session has already detached targets an in-memory log that is never published or persisted, so replay is what recovers that kernel as interrupted for every later reader.

The run→epoch reference invariant, the run terminal's `outputDegraded?: true` field, and the kernel-state event itself are all additions to an already required-on-read event stream, so a build that does not know them refuses to read a session carrying kernel execution rather than silently reconstructing an incomplete one. That refusal is exactly what the per-event `ignorable` marker exists to make survivable without a structural format bump — see the [session log versioning decision](2026-08-10-session-log-version-mechanism.md): the marker defaults to required, and an unrecognized or incompatible required event refuses the whole read, which is the correct failure mode for a field that changes how execution provenance is understood. `SESSION_FORMAT_VERSION` stays at `0` through this whole delivery: every change here is vocabulary growth on required-on-read events, never a change to the log's header, envelope, or surface mechanism. The private projection's own cache format is a different, lower-stakes version, governed by the session-projection registry's own rule (bump whenever the serialized state shape or fold semantics change); its value is `8`, incremented independently each time the fold's own shape changed — first to carry the kernel list and epoch watermark at all, then again for each field the relation-set rules above added.

### Interrupt-first control and taint-retirement

Each run still carries an operation control bounded by the configured per-run timeout. On abort — cancellation or timeout — the Runtime sends the kernel process `SIGINT` and waits a fixed grace window (the same constant that already governs process-tree settlement elsewhere in the Runtime) for the kernel to reply that it caught the interrupt. If it does, the kernel proved it recovered cleanly and survives; the run's own terminal is decided purely by what caused the abort (`cancelled` or `timed-out`), never by what happened to the kernel. If the kernel instead finishes the run normally — its own code raced the interrupt, or caught and swallowed it — or does not reply within the grace window, its state is no longer trustworthy: for R specifically, an idle-time `SIGINT` can kill the process or latch a stale interrupt that misclassifies the very next run. The Runtime retires the kernel once the run settles — a best-effort cooperative exit request, the same quiescence escalation used everywhere else, and a `kernel-state(exited, reason: 'run-escalation')` fact — and the next run for that language starts a fresh epoch.

The Runtime never sends `SIGINT` outside a run in flight: every idle-path end (idle timeout, environment rebind, session end, service disposal) always uses the cooperative exit request, so R's idle-time interrupt hazard never has an opportunity to fire. Because that is what makes the hazard unreachable, both the retirement decision and the idle-timer re-arm have to survive every exit from run settlement, including one where the run's own terminal commit is itself rejected: both derive from the run's own outcome in a scope that always executes, so a kernel the Runtime already judged untrustworthy is never left registered for reuse, and a kernel that survived an interruption is never left with its idle timer permanently disarmed by an unrelated commit failure.

A kernel that dies uncommanded mid-run, with no interrupt ever sent, settles that run `failed` with a dedicated kernel-death failure code and a `kernel-state(exited, reason: 'crash')` fact; a mid-run protocol break settles the run with the same failure code but a `protocol` kernel-state reason.

### Package permanence and the provisioning handoff

Inline installs need no Runtime code: they mutate the live kernel process and its writable caches, and vanish the moment that kernel ends, purely because the kernel is a real persistent process. Environment-level installs — a new applied environment revision, via micromamba or any other mechanism — are a different track's responsibility; this Runtime implements only the rule that track depends on: once a newer applied revision exists for a language, the next run for that language ends the stale kernel with reason `environment-rebound` and starts a fresh epoch against the new revision, independent of how the revision came to be.

That rule is real and provable without a producer: the Science Session fold already accepts an applied environment revision superseding an earlier one once no run for that session is currently in flight, verified by appending a later revision directly to the durable log and observing the fold-level rebind. What is genuinely missing is a caller: `bindEnvironment` itself still rejects a second call once the session has any run at all, a stricter, Runtime-owned guard than what the fold requires. A provisioning implementation reaches `environment-rebound` by calling `bindEnvironment` again after runs exist, so lifting that guard — not building new fold-level support — is the only work required to make a real rebind reachable through a product API.

### Configuration, platform scope, and errors

Two configuration fields govern kernel timing, both validated safe integers changeable from `cordis.yml`: an idle timeout defaulting to 1,800,000ms (30 minutes, matching Claude Science's own documented default; range 60,000–86,400,000) and a spawn-to-ready deadline defaulting to 30,000ms (range 1,000–600,000). The existing per-run timeout keeps its meaning and is fused into a fresh kernel's spawn: the caller's own operation signal feeds the spawn's `READY` wait, so a spawn is bounded by whichever of the caller's deadline or the spawn-to-ready deadline fires first. The spawn spec handed to the subprocess capability itself deliberately carries no signal, so the kernel process outlives the one run that started it. Protocol constants — the frame grammar, protocol version, and the shared grace window — stay fixed: they describe the wire protocol itself, not a deployment choice.

Kernel execution requires POSIX (a FIFO, `SIGINT`, and the `mkfifo` binary): darwin and linux only. A run rejects pre-publication on every other platform with a dedicated unsupported-platform code, before any scratch or process work — matching Claude Science's own platform coverage, which ships no native Windows build. A per-run spawn kept only as a Windows fallback was rejected: one execution model, honestly scoped, is preferable to two execution models with different persistence semantics.

Rejection codes cover the kernel's own failure modes: a dedicated start-failure code for a spawn, handshake, or start-time confinement failure, naming the language and cause class in task vocabulary — no FIFO, stdin, subprocess, or transport term reaches a model- or user-facing message. A driver-reported error response settles a run `failed` with an execution-failure code, replacing the one-shot model's exit-code/signal-based failure codes outright: a kernel run has no per-run exit code or signal of its own, so `ScienceRunTerminal` carries no such fields, and the model-facing run-tool schemas, result rendering, and state summaries all match that absence rather than advertising fields a kernel run can never populate. A same-session kernel-set conflict surfaces as the same busy-session rejection an operation lease conflict already produces; a kernel epoch allocator regression reaching a caller — not expected in normal operation — surfaces as an infrastructure-failure rejection.

## Alternatives considered

**Adopt a Jupyter-compatible kernel (`ipykernel`/`IRkernel` over ZMQ).** Rejected: a user-configured prefix cannot be assumed to contain either package, the Runtime does not install into a prefix by design, and ZMQ's transport conflicts with the sandbox's deny-by-default network posture. A zero-dependency stdlib/base-R driver needs neither assumption.

**Speak the protocol over a Unix domain socket instead of stdin plus a FIFO.** Rejected: base R can neither open nor `dup2` a Unix domain socket, and the sandbox denies TCP outright; a FIFO is a plain filesystem path both a Python `open()` call and base R's `fifo()` can reach with no new capability.

**One process serving every language, or every session.** Rejected: a single process cannot host two different language interpreters, and routing multiple sessions through one process would move lifecycle and isolation reasoning out of the durable event stream and into ad hoc in-process state instead.

**Kill on abort, never interrupt.** Rejected: it would discard every earlier variable on the first timeout or cancellation, which regresses behind the one-shot model rather than improving on it — Claude Science's documented parity requires state to survive an interrupted run whenever the kernel itself can prove it recovered.

**Track R's idle-interrupt hazard per language instead of one taint-retirement rule.** Rejected: it would require the host to model a live behavioral difference between interpreters rather than apply one rule — send `SIGINT` only while a run is in flight — that makes the difference irrelevant by construction, for both languages, without per-language branching in the host.

**Represent a kernel's started/exited transitions as two distinct event types.** Rejected: unlike a run, a kernel-state fact never repeats a field its own prior transition already fixed, aside from the one deliberate `startedAt` restatement; a second event type would carry no field the shared shape does not already need.

**Let the provisioning track own the environment-rebound fold rule as well as the `bindEnvironment` guard.** Rejected: representability in the durable log is independent of who calls `bindEnvironment`. Building and proving the fold-level rule once, ahead of any caller, means the provisioning track's own work reduces to calling an existing operation again rather than inventing a new durable transition.

## Consequences

Variables, imports, and inline package effects survive across `run_python`/`run_r` calls exactly as Claude Science documents, at the cost of every run committing at least one additional durable session event across a kernel's lifetime and the Runtime holding a live subprocess per active language for as long as the idle timeout allows, rather than only for the duration of one run.

R's output capture remains sink-level only: C-level and child-process writes bypass `sink()` and land in the kernel's own bounded, unattributed collectors rather than in the run that produced them; file-descriptor-level capture matching Python's redirection is not implemented. A kernel's real operating-system process state is not reconciled against a Host crash — replay always tells the model and every later reader that a kernel open at the last observed session boundary is not running, but the Runtime does not additionally verify what the interpreter process itself did across that restart. Both gaps are accepted for this delivery; each is a distinct, addable reconciliation pass rather than a change to the events or fold rules above. Both are recorded, alongside the provisioning handoff above, in `packages/science/science-runtime/README.md`'s Known Limitations.

The environment-rebound rule is real and durably provable — a later applied revision folds cleanly once no run is in flight — but unreachable through any shipped product path until the provisioning track lifts `bindEnvironment`'s own post-first-run guard; until then, only a direct log append exercises the fold-level behavior.
