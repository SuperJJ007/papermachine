# Agent Note: kernel-scoped user-install bases make inline `pip install`/`install.packages()` actually work

Status: implemented

English | [中文](2026-08-22-science-kernel-scoped-inline-installs.zh.md)

## Problem

`run_python`'s tool description and the science-runtime README already promised that an inline `pip install` inside a run affects the running kernel until it restarts — mirroring Claude Science. That promise never held. The Python kernel was spawned with `-I` (isolated mode). Under sandbox confinement the Conda prefix is read-only, so pip's install falls back to a user-site install under the kernel's `HOME` (verified: `openpyxl` landed in `<session scratch>/home/.local/lib/python3.12/site-packages`, pip exit 0) — but `-I` excludes user site-packages from `sys.path`, so the very next `import` in the same kernel raised `ModuleNotFoundError`. The tool description was aspirational, not descriptive.

## Decision

**Drop `-I` for persistent kernels only; every probe keeps it.** `interpreterArgv` (`execution.ts`) is the kernel-only argv builder — an interpreter probe already builds its own direct argv (`probeArgv` in `environment.ts`) independently and was never touched. A probe never installs anything, so isolated mode stays the tighter default there.

**Give each kernel its own writable install base, not the session's `HOME`.** A Python kernel's fixed environment allowlist gains `PYTHONUSERBASE=<kernel scratch dir>/pyuser`; an R kernel's gains `R_LIBS_USER=<kernel scratch dir>/rlibs`. Both directories are created at kernel spawn (`ScienceKernelScratch.userLibrary`, `scratch.ts`) — R only adds `R_LIBS_USER` to `.libPaths()` when the directory already exists at startup, and pointing at a scratch-scoped path (rather than leaving pip to fall back to `HOME`-relative `.local`) is what makes the install kernel-scoped instead of session-scoped.

**Per-kernel, not per-session or per-environment.** `userLibrary` lives under the kernel's own `kernels/<language>-<epoch>/` directory, keyed by `kernelEpoch` the same way `tmp` already is. A fresh kernel — idle restart, crash, interrupt escalation, or `environment-rebound` — gets a fresh, empty base. This is load-bearing for `environment-rebound` specifically: once a newer applied environment revision exists, the next run for that language starts a fresh epoch against the new revision, and that fresh kernel must never see packages an inline install pulled into the *old* revision's kernel. Scoping to `HOME` (session-wide) or to a session-level directory would have let a stale inline install leak across an environment rebind; scoping to the kernel epoch cannot.

**Python needed a second, non-obvious fix: the kernel driver, not just the flags/env.** Dropping `-I` and setting `PYTHONUSERBASE` alone was not sufficient — real-acceptance testing against a live Conda prefix caught the same-kernel import still failing even with `-I` gone. Root cause: Python's `site` module adds the user site-packages directory to `sys.path` exactly once, during interpreter startup, and only if that directory *already exists* at that instant. `PYTHONUSERBASE` names the writable base, but the actual leaf pip installs into is a nested, version-dependent `PYTHONUSERBASE/lib/pythonX.Y/site-packages` that pip creates lazily on its *first* install — after `site.py` already finished its one-time scan. Pre-creating only the top-level `pyuser` directory (as the flags/env change alone would do) left that leaf directory absent at kernel startup, so it was never added to `sys.path`, and no later install in that kernel could retroactively fix it. `kernel_python.py` now calls `site.addsitedir(site.getusersitepackages())` once at driver startup (after `os.makedirs`, gated on `PYTHONUSERBASE` being set and `site.ENABLE_USER_SITE`), using Python's own understanding of its user-site layout instead of the Node side guessing a version-specific path. `sys.path` is process-global and persists for the kernel's whole lifetime, so this single startup call covers every later `RUN` frame. R never had this problem: `R_LIBS_USER` names the library directory directly (no nested nesting to construct), so pre-creating the one directory `scratch.ts` already creates is sufficient.

## Consequences

Verified end-to-end against real Conda prefixes (Python 3.12 `mesa` env, an R Conda env), bypassing an unrelated, pre-existing chart-curation/attachment-readback failure in `real-acceptance.ts` that blocks the full script from reaching `PASS` on this machine (reproduced identically against unmodified `main`; out of scope for this change): build a trivial dependency-free wheel / R source tarball locally (no network), `pip install --no-index` / `install.packages(repos = NULL, type = "source")` inside a kernel, import in the *same* kernel (succeeds), force an `environment-rebound` kernel restart, import again (fails: `ModuleNotFoundError` for Python, "there is no package called" for R). Both match the design exactly. `real-acceptance.ts` gained the same check sequence as a committed, opt-in extension (`DSH_SCIENCE_RUNTIME_REAL_ACCEPTANCE=1`), currently unable to complete end-to-end on this machine only because of the unrelated pre-existing blocker noted above.

The kernel-run README's "Confinement and environment" section and the `install.packages()`/`pip install` limitation bullet were corrected from an aspirational ("no code needed") to a truthful description of the actual mechanism. `run_python`'s and `run_r`'s tool descriptions needed no change — their wording already stated the now-true behavior; the keyless snapshot that pins them was reverified unchanged.

## Alternatives considered

- **Point `PYTHONUSERBASE`/`R_LIBS_USER` at the session's `HOME`-relative default (do nothing)** — this was the pre-fix state for Python (pip's own fallback) and is exactly what leaks a stale install across `environment-rebound`; rejected as the bug this change closes.
- **Scope the install base to the Science Session instead of the kernel instance** — survives a kernel restart within the same environment revision, which sounds convenient but breaks the `environment-rebound` invariant: a fresh kernel against a newer revision must never carry forward a package installed against the old one.
- **Add `-P` (Python's "safe path" flag) instead of dropping `-I`** — rejected per the task brief: `-P` does not exist on older interpreters a user-configured Conda prefix may still carry, and this Runtime targets whatever prefix the operator points at, not a pinned Python version.
- **Fix the `sys.path` gap by re-running `site` processing from Node before spawn** — not possible from the host side without duplicating Python's own version-specific site-packages layout logic; doing it once inside the driver, using `site.getusersitepackages()` itself, is both simpler and correct across every Python version the driver may run under.
