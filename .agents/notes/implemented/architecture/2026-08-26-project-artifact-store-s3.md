# Agent Note: Project artifact store — S3 cross-session continuity

Status: implemented

English | [中文](2026-08-26-project-artifact-store-s3.zh.md)

## Problem

[S1](2026-08-26-project-artifact-store-s1.md) shipped the project artifact store package; [S2](2026-08-26-project-artifact-store-s2.md) wired `science-runtime`/`science-session`/`tool-science` onto it, but every capture, curation, and run-input reference still resolved only against the acting session's own live projection or fold-local history — a second Science session opened against the same project workspace could not continue, reference, or extend an artifact a first session had already produced, even though the store itself (S1) already indexed artifacts per project, not per session. [S0](../../implemented/architecture/2026-08-25-project-artifact-store.md) specifies this as spec item 5: a second session in the same project reads, references, and appends versions to a first session's artifact, with artifact identity unchanged and the new version's producer naming the new session.

## Decision

**Auto-capture consults the project store, not just this session's own fold, when deciding create-vs-append.** `captureRunArtifacts` (`science-runtime/src/capture.ts`) still uses this session's own live projection first — most walks recapture a path this same session already knows about, and that needs no store round trip. Only when a captured path's logical name has no local record does the walk call `store.listArtifacts(projectId)` (fetched once per walk, lazily, and cached) to check whether a different session in the same project already owns that logical name. Finding one extends its existing `artifactId` — the new version's producer is this session, its content is deduplicated against that artifact's cross-session latest exactly like a same-session rerun — instead of forking a second artifact under the same name. Deduplication against a direct human edit's own ancestor chain stays scoped to this session's own local history; project-wide history for that specific check is not needed by any current acceptance path. This mechanism was briefly deleted (`b0524e2c64`) and then restored, plus its natural create-race follow-on, by the [runtime provenance-writes note](2026-09-02-science-runtime-provenance-writes.md), which this paragraph still accurately describes at the design level; that note owns the current store-read details (`store.getLatestVersion`/`store.listVersions` replacing the session's own slimmed projection) T1/T2's artifact-authority migration made necessary.

**`artifactInputs` (`run_python`/`run_r`) resolves cross-session references, `editBaselines` does not.** `prepareRunArtifacts` (`science-runtime/src/inputs.ts`) resolves each input first against the session's own live projection; on a miss, it falls back to `store.listVersions(projectId, artifactId)` and matches by ordinal — the store is the authority a session's own projection can never independently reconstruct for an artifact another session produced. `editBaselines` keeps its session-local-only resolution: extending it would also require `science-session`'s fold to accept an unresolved `parent` reference on replay, which the human-edit invariants (parent logical name, media type, environment-provenance equality) cannot check without a local copy of that version — a real design nobody has reviewed, and out of this slice's scope (spec item 5 names artifact reads/references/appends, not lineage).

**The strict fold trusts a cross-session reference it cannot independently verify, instead of rejecting it.** Two checks in `science-session/src/transition.ts` previously assumed every artifact reference was resolvable from this session's own accumulated fold state — true only because, before S3, every reference legitimately was. The acceptance rule is relative to this session's own locally-recorded maximum version for the referenced artifactId: a version strictly ahead of that maximum is trusted, because the store's own transaction already proved it real before the referencing event committed — this covers both an artifactId this session has never recorded at all and one it has recorded only up to some lower version (a concurrent session's own interleaved append may hold the intermediate ordinals). A version at or below that local maximum is fully verifiable from the log alone, and is never trusted from the store:
- `applyArtifactSaved`'s version check accepts any version strictly greater than the highest version this session's own fold has already recorded for that artifactId — whether this session has never recorded that artifactId at all (the highest is undefined, so any positive ordinal the codec's own `POSITIVE_INTEGER` schema admits qualifies), or has recorded some versions and this one lands beyond all of them (a concurrent session's own interleaved append may have taken an intermediate ordinal). A version at or below that local maximum which does not exactly match a locally recorded version is a same-session inconsistency the log alone can verify, and still throws.
- `applyRunStarted`'s run-input check (`requireRunInputArtifactVersion`, replacing the shared `requireArtifactVersion` for this one call site) applies the identical rule: it returns without throwing when the referenced version exceeds this session's own locally-recorded maximum for that artifactId (including when there is no local record at all), and throws only when the referenced version is at or below that maximum and does not exactly match a local record.

Both relaxations trust a fact the live Runtime already validated against the store before the referencing event committed (the Host-side pre-commit invariant S0 specifies); pure fold replay, which never reaches the store, carries that validated fact forward rather than re-deriving it. `artifact.parent` resolution (`requireArtifactVersion`, used by both the parent self-reference check and the human-edit invariants) is unchanged and stays strict — no caller can produce a legitimate cross-session `parent` today, since `editBaselines` resolution above stays same-session-only.

**Files listing is a store-level fact already, not a new mechanism.** S1's `listArtifacts(projectId)` already returns one row per artifact, `latestVersionId` pointing at whichever version is current regardless of which session produced it — S3 adds no new listing API. What S3 changes is capture's own create-vs-append decision (above): before this slice, a second session's recapture of an existing logical name would have called `createArtifact` and produced a second row for the same name, because capture only ever asked its own session's fold. A dedicated `science-runtime` test proves the store still shows exactly one row, with the new session as the latest version's producer, after a cross-session continuation — this is what "Files still shows one Artifact/latest" (spec item 5) reduces to at the store layer. The Files-as-UI-surface (`ProjectLibrary`, `packages/client/ui-science`) now renders this same one-row-per-artifact listing directly, reading it through `sessions.scienceLibrary`/`scienceVersions`.

**A Host restart continues writing to the same on-disk store.** No new mechanism: `ScienceArtifactStore.openProject` already derives a project's store path deterministically from `dshHome`+`projectId` (S1), so a fresh Cordis Context pointed at the same `dshHome` reopens the same on-disk index and blobs. A dedicated test disposes one harness's Context after a first session's capture and creates a second, fully independent harness (fresh Context, fresh `ScienceArtifactStore`, fresh `ScienceRuntime`) against the same `dshHome`, proving the second session's continuation carries no in-memory state forward — only what was durably committed.

## Alternatives considered

**Extend `editBaselines`/parent lineage cross-session in this slice too** — rejected: it needs `science-session`'s fold to accept an unresolved `parent` on replay the same way run inputs now do, but the human-edit invariants that consume the resolved parent (logical name, media type, environment-provenance equality) have no fallback when the parent is a bare reference with no local copy to check those facts against. Making the fold trust an *entire* forwarded artifact-metadata bundle it cannot verify is a materially different and larger trust boundary than trusting a single-field "this reference exists" fact for run inputs, and was not designed or reviewed here.

**Rewrite capture's create-vs-append decision entirely off the store** (drop the session-local fast path) — rejected: the session-local live projection already correctly answers "does an artifact for this logical name exist" for every file a prior run of THIS session captured, with no I/O; discarding that path for a store round trip on every captured file would only slow down the overwhelmingly common case (single-session repeated runs) to correctly handle the rarer cross-session one.

**A dedicated project-level "Files" listing tool or RPC** — rejected: the store's existing `listArtifacts`/`getVersion` methods (S1) already answer "one row per artifact, latest version" completely. The later [Session-authorized read path](2026-08-26-session-authorized-science-artifact-reads.md) restores exact-version browser content without adding that separately scoped project-wide surface.

## Consequences

`science-runtime`'s auto-capture walk and `prepareRunArtifacts` now depend on `ScienceArtifactStore.listArtifacts`/`listVersions` in addition to the read/write methods S2 already used; no public method signature on the store changed. `science-session`'s strict fold accepts a narrower set of previously-rejected `science/run-started`/`science/artifact-saved` values — a reference at or below this session's own locally-recorded maximum version for an artifactId that does not exactly match a local record is still rejected exactly as before; a reference strictly ahead of that maximum is now accepted, whether or not this session's own fold has recorded any version of that artifactId at all. `packages/science/science-session/tests/fold.spec.ts`, `fold-transitions.spec.ts`, and `invariant.spec.ts` cover both directions: acceptance of a version ahead of the local maximum (including a gap left by a concurrent session's interleaved append, not just the immediate next ordinal) and rejection of an in-range mismatch; `science-runtime/tests/capture.spec.ts` proves the same rule end to end through two real interleaved sessions against one real project store.

`editBaselines`/parent lineage, human-edit continuation, and `annotate_artifact` curation all remain resolvable only against the acting session's own fold-local history — naming a version a different session produced still rejects for those paths. Browser content reads now use the later Session-authorized exact-version RPC; a genuine project-level "Files" UI (one section listing every project artifact, distinct from session transcript occurrences) remains outside this mechanism. No new keyless ACP/headless snapshot scenario was added: the tool-facing schemas (`run_python`/`run_r`'s `artifact_inputs`, `get_science_state`) are byte-identical to before this slice — what changed is which previously-rejected calls now succeed, verified through real `ctx.plugin`-composed `science-runtime` tests (real `ScienceArtifactStore`, real sessions, no mocked store in the new coverage) rather than a new multi-session headless-agent scenario, which would need new fixture scaffolding to express two sessions in one recorded example; this is flagged as a gap for whoever next extends the headless-agent example suite, not fixed here under this slice's budget.

`packages/science/science-session/src/applicability.ts` and `transition.ts` are both at 100% per-file coverage.
