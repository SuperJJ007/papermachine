# Agent Note: Project artifact store — S3 cross-session continuity

Status: implemented

English | [中文](2026-08-26-project-artifact-store-s3.zh.md)

## Problem

[S1](2026-08-26-project-artifact-store-s1.md) shipped the project artifact store package; [S2](2026-08-26-project-artifact-store-s2.md) wired `science-runtime`/`science-session`/`tool-science` onto it, but every capture, curation, and run-input reference still resolved only against the acting session's own live projection or fold-local history — a second Science session opened against the same project workspace could not continue, reference, or extend an artifact a first session had already produced, even though the store itself (S1) already indexed artifacts per project, not per session. [S0](../../implemented/architecture/2026-08-25-project-artifact-store.md) specifies this as spec item 5: a second session in the same project reads, references, and appends versions to a first session's artifact, with artifact identity unchanged and the new version's producer naming the new session.

## Decision

**Auto-capture consults the project store, not just this session's own fold, when deciding create-vs-append.** `captureRunArtifacts` (`science-runtime/src/capture.ts`) still uses this session's own live projection first — most walks recapture a path this same session already knows about, and that needs no store round trip. Only when a captured path's logical name has no local record does the walk call `store.listArtifacts(projectId)` (fetched once per walk, lazily, and cached) to check whether a different session in the same project already owns that logical name. Finding one extends its existing `artifactId` — the new version's producer is this session, its content is deduplicated against that artifact's cross-session latest exactly like a same-session rerun — instead of forking a second artifact under the same name. Deduplication against a direct human edit's own ancestor chain stays scoped to this session's own local history; project-wide history for that specific check is not needed by any current acceptance path.

**`artifactInputs` (`run_python`/`run_r`) resolves cross-session references, `editBaselines` does not.** `prepareRunArtifacts` (`science-runtime/src/inputs.ts`) resolves each input first against the session's own live projection; on a miss, it falls back to `store.listVersions(projectId, artifactId)` and matches by ordinal — the store is the authority a session's own projection can never independently reconstruct for an artifact another session produced. `editBaselines` keeps its session-local-only resolution: extending it would also require `science-session`'s fold to accept an unresolved `parent` reference on replay, which the human-edit invariants (parent logical name, media type, environment-provenance equality) cannot check without a local copy of that version — a real design nobody has reviewed, and out of this slice's scope (spec item 5 names artifact reads/references/appends, not lineage).

**The strict fold trusts a cross-session reference it cannot independently verify, instead of rejecting it.** Two checks in `science-session/src/transition.ts` previously assumed every artifact reference was resolvable from this session's own accumulated fold state — true only because, before S3, every reference legitimately was:
- `applyArtifactSaved`'s contiguity check no longer requires a logical name this session has never recorded to open at version 1. It may be a genuinely new artifact, or it may continue one a different session already versioned in the same project — this session's fold, replaying only its own log, cannot tell those apart without the store, so it accepts any ordinal the codec's own `POSITIVE_INTEGER` schema already admits. A same-session continuation (a logical name this session HAS recorded) still enforces exact contiguity: the log alone can verify that case, and does.
- `applyRunStarted`'s run-input check (`requireRunInputArtifactVersion`, replacing the shared `requireArtifactVersion` for this one call site) now returns without throwing when the referenced artifactId is not in `state.artifacts` at all. An artifactId this session's fold HAS recorded, named at the wrong version, still throws — the log alone can catch that same-session inconsistency.

Both relaxations trust a fact the live Runtime already validated against the store before the referencing event committed (the Host-side pre-commit invariant S0 specifies); pure fold replay, which never reaches the store, carries that validated fact forward rather than re-deriving it. `artifact.parent` resolution (`requireArtifactVersion`, used by both the parent self-reference check and the human-edit invariants) is unchanged and stays strict — no caller can produce a legitimate cross-session `parent` today, since `editBaselines` resolution above stays same-session-only.

**Files listing is a store-level fact already, not a new mechanism.** S1's `listArtifacts(projectId)` already returns one row per artifact, `latestVersionId` pointing at whichever version is current regardless of which session produced it — S3 adds no new listing API. What S3 changes is capture's own create-vs-append decision (above): before this slice, a second session's recapture of an existing logical name would have called `createArtifact` and produced a second row for the same name, because capture only ever asked its own session's fold. A dedicated `science-runtime` test proves the store still shows exactly one row, with the new session as the latest version's producer, after a cross-session continuation — this is what "Files still shows one Artifact/latest" (spec item 5) reduces to at the current, UI-less layer; a `Files`-as-UI-surface still awaits S4's browser read path.

**A Host restart continues writing to the same on-disk store.** No new mechanism: `ScienceArtifactStore.openProject` already derives a project's store path deterministically from `dshHome`+`projectId` (S1), so a fresh Cordis Context pointed at the same `dshHome` reopens the same on-disk index and blobs. A dedicated test disposes one harness's Context after a first session's capture and creates a second, fully independent harness (fresh Context, fresh `ScienceArtifactStore`, fresh `ScienceRuntime`) against the same `dshHome`, proving the second session's continuation carries no in-memory state forward — only what was durably committed.

## Alternatives considered

**Extend `editBaselines`/parent lineage cross-session in this slice too** — rejected: it needs `science-session`'s fold to accept an unresolved `parent` on replay the same way run inputs now do, but the human-edit invariants that consume the resolved parent (logical name, media type, environment-provenance equality) have no fallback when the parent is a bare reference with no local copy to check those facts against. Making the fold trust an *entire* forwarded artifact-metadata bundle it cannot verify is a materially different and larger trust boundary than trusting a single-field "this reference exists" fact for run inputs, and was not designed or reviewed here.

**Rewrite capture's create-vs-append decision entirely off the store** (drop the session-local fast path) — rejected: the session-local live projection already correctly answers "does an artifact for this logical name exist" for every file a prior run of THIS session captured, with no I/O; discarding that path for a store round trip on every captured file would only slow down the overwhelmingly common case (single-session repeated runs) to correctly handle the rarer cross-session one.

**A dedicated project-level "Files" listing tool or RPC** — rejected for this slice: the store's existing `listArtifacts`/`getVersion` methods (S1) already answer "one row per artifact, latest version" completely; a new model- or browser-facing surface over that data is S4's UI-wiring job (`packages/client/ui-science` does not compile today and is explicitly deferred there), not a new backend mechanism this slice needs to invent.

## Consequences

`science-runtime`'s auto-capture walk and `prepareRunArtifacts` now depend on `ScienceArtifactStore.listArtifacts`/`listVersions` in addition to the read/write methods S2 already used; no public method signature on the store changed. `science-session`'s strict fold accepts a narrower set of previously-rejected `science/run-started`/`science/artifact-saved` values — a same-session reference at the wrong version, or a same-session contiguity skip, are still rejected exactly as before; only a reference this session's own fold has never recorded at all is now accepted. `packages/science/science-session/tests/fold.spec.ts` and `invariant.spec.ts` updated their fixtures accordingly (a wrong-version-but-known-locally case replaces what used to be an unknown-artifactId case, which no longer throws).

`editBaselines`/parent lineage, human-edit continuation, and `annotate_artifact` curation all remain resolvable only against the acting session's own fold-local history — naming a version a different session produced still rejects for those paths. Browser artifact reads (`packages/client/ui-science`) remain dark; a genuine project-level "Files" UI (one section listing every project artifact, distinct from session transcript occurrences) is S4's job over the same store data this slice already proves correct. No new keyless ACP/headless snapshot scenario was added: the tool-facing schemas (`run_python`/`run_r`'s `artifact_inputs`, `get_science_state`) are byte-identical to before this slice — what changed is which previously-rejected calls now succeed, verified through real `ctx.plugin`-composed `science-runtime` tests (real `ScienceArtifactStore`, real sessions, no mocked store in the new coverage) rather than a new multi-session headless-agent scenario, which would need new fixture scaffolding to express two sessions in one recorded example; this is flagged as a gap for whoever next extends the headless-agent example suite, not fixed here under this slice's budget.

Pre-existing, not touched by this slice: `packages/science/science-session/src/applicability.ts`'s presetId self-consistency branches (added by S2's presetId rider) are below the per-file 100% coverage gate — S2's own handoff already flagged that coverage was not run for that rider; this slice's own changed files (`transition.ts`, `capture.ts`, `inputs.ts`) are at 100%.
