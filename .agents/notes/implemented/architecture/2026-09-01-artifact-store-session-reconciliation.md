# Agent Note: Store ↔ session reconciliation, and W2/W3 narrowing at every append site

Status: implemented

English | [中文](2026-09-01-artifact-store-session-reconciliation.zh.md)

## Problem

[T1](2026-09-01-project-artifact-store-schema-v2.md)'s authority rule made the project artifact store the sole authority for a version's provenance, and the audit that motivated it (`audit.md` D12) also found five crash windows across the "blob → SQLite transaction → session.append" write sequence with **no reconciliation code anywhere in the repository** (`grep -rn "reconcil" packages/science packages/host/apiproxy/src` hit three unrelated comments): a store row committed with its `science/artifact-saved` append then rejected leaves an orphan row the Files panel lists but no session ever explains (W1/W2); an `annotateVersion` write followed by a rejected curation event leaves the two faces permanently disagreeing (W3, already documented as accepted in T1's own JSDoc); and two windows around auto-capture (a run finishing with no capture attempt, and a capture walk crashing partway through) leave files uncaptured with no retry and no report (W4/W5). T2's own writes already fixed the *causes* of some of these (T1's schema, T2a's event slimming, T2b's store-authority reads); none of them fixed the *lack of any pass that discovers and repairs the syncing gap once it happens*.

## Decision

**The store's write transaction stays the sole authority; reconciliation only ever repairs the store, never the session log.** A session log is append-only and its replay contract depends on that — rewriting history to "fix" a stale event would break every consumer that trusts seq-ordered replay. Concretely, `dsh-science-artifact-store`'s new `reconcile.ts` module classifies every version the store holds against the `science/artifact-saved` events a caller has already read and folded, and only ever calls the store's own `setVersionHealth`/`reconstructVersion` — it never calls anything that appends to a session.

**Six cases, decided per version, by comparing `sha256` and the current annotation snapshot — never by trusting which side committed first:**

| Case | Condition | Handling |
|---|---|---|
| Consistent | store row and event both name this `versionId`, same `sha256`, same title/caption | no write |
| Orphan (W1/W2) | store row exists, no event names this `versionId` | `version_health.orphan = 1`; the row and its bytes are untouched — a real, complete version with no session claiming it |
| Dangling event | an event names a `versionId` the store has no row for | `reconstructVersion` rebuilds a version row (and its artifact row, if that's also missing) from the event's fallback fields; `version_health.reconstructed = 1` |
| Content conflict | same `versionId`, different `sha256` | not reachable through any normal write path; recorded as a diagnostic, store row marked `orphan`, event untouched |
| Metadata divergence (W3) | same `versionId`/`sha256`, event's title/caption snapshot is stale | no write — the store's latest annotation already is the current fact; a stale event is a correct historical record of what the model saw, not an error |
| Missing blob | row exists, `blobs/sha256/…` absent | `version_health.missingContent = 1`; the row is never deleted |

Deviation from the task book worth flagging explicitly: the task's table describes "库赢，事件不动" for metadata divergence as a *repair*; there is in fact nothing to repair on either side — the store's `latestAnnotation` already is current, and the event is already a correct point-in-time record — so this case is classified for visibility (tests, `ReconcileResult.outcomes`) but produces no store write at all, which is the correct reading of "the store wins" rather than a gap.

**`reconstructVersion`'s `contentOrigin` is fixed to `'import'`, never guessed as `'run-auto'`.** A reconstructed row's real content origin (a run, or a human edit) is exactly the fact this reconstruction cannot recover — `'import'` is the one `ContentOrigin` value that does not claim otherwise, matching the store-honesty stance T1 already established for its own v1→v2 migration (never inventing certainty it doesn't have). `mediaType` is inferred from the dangling event's `logicalName` extension (the event no longer carries `mediaType` after T2a's slimming), falling back to `application/octet-stream` for an unrecognized one; `byteCount` is the blob's real size when present, or an explicitly-sentinel `0` when also missing (paired with `missingContent: true`, so a caller checks that flag before trusting the byte count rather than being silently lied to).

**`reconcileMaxVersions` (store package, default 2000) and `reconcileMaxSessions` (runtime package, default 500) are two separate bounds because they bound two separate kinds of work owned by two separate packages.** The store bounds how many of *its own* version rows and dangling events one `reconcileProject` call processes (batching, `truncated: true` on overflow); the runtime bounds how many *session logs* one project's reconciliation trigger reads before folding events (`collectProjectArtifactEvents`'s own `truncated`). Neither bound bootstraps a resumable job across Host restarts: `ScienceRuntime` triggers reconciliation once per project id per Host lifetime (a `Set<string>` cache in `sessionProject`), so a project whose first pass was truncated does not get a second pass until the next Host restart — accepted for this task, since "bounded and non-blocking" was the hard requirement, not "complete in one pass."

**The runtime reads session logs exactly once, in exactly one place, and hands the store a same-process typed value — the store package never touches session-log format.** `dsh-science-runtime/reconcile-trigger.ts`'s `collectProjectArtifactEvents` lists every session whose header `cwd` resolves to the project's canonical workspace path (`OpenedProject.workspacePath`) and reads each through `@deepseek-ai/dsh-session-persistence`'s `SessionPersistence.inspect()` — per the T2b-1 Note's own finding, this returns each event's *raw, undecoded* `data`, bypassing `dsh-science-session`'s codec (which is deliberately non-strict and would silently drop exactly the fallback fields a dangling-event reconstruction needs). Because this is a genuine durable/file boundary — not a same-process typed value — `extractReconcileEvent` validates the raw shape field-by-field rather than trusting the `SessionEventMap` static type, and skips (with a warning) anything malformed rather than throwing. `sessionPersistence` is consulted through `ctx.get('sessionPersistence')` (optional), never added to `ScienceRuntime`'s required `inject` array: making it required would have broken every existing test and any deployment that runs Science without a persistence backend mounted, for a self-healing pass the Runtime does not itself depend on to function.

**W2/W3 narrowing extends the existing capture-side pattern to every other store-commit-then-event-append site.** T2 already made `capture.ts` mark `orphan` immediately when its own `science/artifact-saved` append is vetoed after the store row committed. This task adds the same behavior — via one shared `appendArtifactSavedOrMarkOrphan` helper — to `annotateArtifact` (the store's annotation already committed), `performChartEdit`'s human-edit commit, and `saveArtifactAs` (the third call site, not named in the task book but structurally identical — added for symmetry rather than left inconsistent). A health-marking failure on top of an already-failed append is logged and swallowed, not thrown: the append's own error is what the caller needs to see, and an unmarked row is still recoverable by the next full reconciliation pass either way.

## Alternatives considered

**Detecting W4 (a run reaching terminal status with zero captured versions) and W5's "capture crashed before writing anything" residual case** — scoped by the task book but **not implemented**: both require reading `science/run-started`/`science/run-finished` events and cross-referencing terminal `runId`s against every version's `producerRunId`, a structurally different comparison (run facts vs. artifact facts) from the six-case version-vs-event table this task built, and genuinely undetectable in the cases that leave literally no trace in either V or E (scratch already cleaned, nothing captured, nothing to reconstruct from). Documented here as an explicit, deliberate scope cut rather than silently dropped; the two `dsh-science-runtime` README "Known Limitations" bullets describing W4/W5 are intentionally left unedited rather than falsely claiming coverage they don't have.

**Making `reconstructVersion` guess `content_origin: 'run-auto'`** (the common case) instead of `'import'` — rejected: a dangling event's own producer session is known (the session whose log carried it), but whether the ORIGINAL commit was a run or a human edit is not recoverable from the event at all after T2a's slimming; guessing the common case would silently fabricate a fact this reconstruction cannot prove, exactly what T1's whole authority-rule effort exists to stop doing.

**Requiring `sessionPersistence` in `ScienceRuntime`'s `inject` array** — rejected: this Runtime's own test harness (and any deployment scoped to run Science without durable session persistence) would fail to load the service at all rather than degrading gracefully; `ctx.get` is the established optional-service pattern this repository already uses for the same backend elsewhere (`agent-loop`, `apiproxy`, `subagent`, `hooks-*`).

## Consequences

Scope: `packages/science/science-artifact-store` (new `reconcile.ts`; `reconstructVersion`/`blobByteCount`/`getReconciliationSummary`/`reconcileProject` on the engine and the Cordis service; `insertAnnotation` factored out of `annotateVersion` for reuse with `derived: true`; new `RECONCILE_ORDINAL_CONFLICT` error code; new `reconcileMaxVersions` Config) and `packages/science/science-runtime` (new `reconcile-trigger.ts`; the `sessionProject` trigger and its once-per-project-per-Host-lifetime cache; `appendArtifactSavedOrMarkOrphan`; new `reconcileMaxSessions` Config; new peer/dev dependency on `@deepseek-ai/dsh-session-persistence`, dev-only on `@deepseek-ai/dsh-session-persistence-jsonl` for the end-to-end test). Both packages carry 100% per-file coverage on the changed surface.

The public read interface T3b's `dsh-api-proxy`/`ui-science` pass-through needs already exists: `ScienceArtifactStore.getReconciliationSummary(projectId): Promise<ReconciliationSummary>` (`{orphanCount, reconstructedCount, missingContentCount, items}`, a pure read of the last recorded `version_health` state) and `ScienceArtifactStore.reconcileProject(projectId, events): Promise<ReconcileResult>` (the entry point, called by `dsh-science-runtime`, not by the BFF directly). T3b's own scope — the `scienceLibrary` response's `health` field, the Files-panel banner, and the `orphan`-is-never-surfaced UI rule — is unaffected by anything decided here beyond consuming this read interface.

`packages/science/science-artifact-store/tests/*.spec.ts` and `.../fixtures/concurrent-append-worker.ts` all gained `reconcileMaxVersions: 2000` at their direct `new ProjectArtifactStoreEngine(…)` construction sites (the field became required on `ProjectArtifactStoreOptions`); this is a mechanical, symmetry-only change with no behavior implication for those suites.
