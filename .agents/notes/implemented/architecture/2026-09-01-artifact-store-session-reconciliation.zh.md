# Agent Note: store ↔ session 对账,以及每个追加点上的 W2/W3 收窄

Status: implemented

[English](2026-09-01-artifact-store-session-reconciliation.md) | 中文

## 问题

项目数据库与会话日志分开提交且生命周期不同。对账必须区分证据不足与已证明不存在，不能覆盖权威溯源。

## 决策

对账处理七种情况：引用一致不操作；不完整日志中缺失则保留为未验证；完整扫描中缺失则标为孤立；悬空日志引用重建库行；hash 冲突产生诊断及孤立状态；元数据差异不覆盖历史快照；缺少 blob 字节则保留该行并标记 missing。重建优先使用实际 blob 大小，缺失时用零哨兵，并保守推断媒体类型。

库与 Runtime 分别配置版本和会话限制。Cursor 同时限制已有版本及悬空引用的工作量；失败项轮转，避免一个错误阻塞其余项目。会话集合 revision 和完整性决定结果复用。只有完整、无错误且无 cursor 的扫描才能抑制后续工作；延迟重试发生在后续解析时，不是自动后台循环。

捕获、注释、图形保存及另存共用追加失败后标孤立的处理。若标记也失败，诊断保留最初追加错误。健康汇总包含所有版本，不只最新行。普通孤立状态不冒充字节缺失；当前 Remote 分别暴露 reconstructed 和 missing 健康信息。

## 考虑过的替代方案

**把未观察到事件一律当成不存在。** 有界或失败扫描会错误地把合法版本标为孤立。

**用会话快照改写库存溯源。** 历史快照可以合法地落后于后续注释。

**立即无限重试整个项目。** 会产生无界工作，并让一个损坏项阻塞进展。

**只统计最新版本健康。** 旧版缺失或重建版本仍可寻址，不能从诊断消失。

## 后果

可选 persistence 不能变成加载前提。原始日志检查仍验证耐久字段，不把错误输入当作可信数据。对账不恢复零输出的终止运行，也无法发现建立任何库行前的捕获失败；这些需要独立的运行与版本比较。修复元数据不能恢复缺失 blob 内容。
