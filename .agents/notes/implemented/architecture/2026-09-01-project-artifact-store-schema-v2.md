# Agent Note: Project artifact store — schema v2 and its migration

Status: implemented

English | [中文](2026-09-01-project-artifact-store-schema-v2.zh.md)

## Problem

An audit of the two Science artifact persistence faces — the project SQLite store (`@deepseek-ai/dsh-science-artifact-store`) and the session event log — found 14 concrete disagreements between them (D1–D14 in the audit that motivated this change; see the coordinating task's `audit.md` for the full list and reproduction steps). The two faces each held a partial, sometimes contradictory copy of the same facts: `createdAt` diverged after curation (D1), the authorizing `toolCallId` diverged after curation (D2), `parent`/`base version` used two different addressing schemes and two different defaulting rules (D3), one `origin` column carried two unrelated facts and was overwritten in place (D4), the environment fingerprint was truncated to a 12-character preview in the store but kept in full in the event (D5), the live-figure-object state existed only in the event log (D6), a same-`logicalName` collision could silently split one artifact into two rows (D7), `caption` could never be cleared once set (D8), the Files panel and the session-scoped detail view disagreed about a version's own title (D9), and user notes existed only in the event log (D10). Underneath all of this, `PROJECT_ARTIFACT_STORE_SCHEMA_VERSION` had never actually been bumped since the package shipped: `schema.ts` rejected any on-disk value other than `0` or the current one, with no upgrade path at all (D14) — the very first DDL change after release would have made every existing user's store unopenable.

## Decision

**Authority rule: the project store's write transaction is the sole authority for a version's provenance; the session event log records only `versionId` + `sha256` + the presentation snapshot the model saw at that moment.** An artifact's lifecycle is designed to outlive any one session (project-scoped, not session-scoped), and a session log is a user-deletable artifact — a deletable medium cannot be the authority for a longer-lived object. Concretely: `versionId`/`artifactId`/`ordinal`, `contentOrigin`, the full `producer{sessionId,runId,toolCallId,requestHeaderSeq,turn}` group, `baseVersionId`/`baseExplicit`, and `createdAt` live in the store ONLY — the event no longer carries them. `sha256` stays on the event too (a content pin, letting a reader verify the bytes the model saw without re-trusting the store). The CURRENT `title`/`caption` lives in the store's newest `version_annotations` row; the event still carries the title/caption snapshot the model saw at THAT call — a presentation fact, not a provenance fact, and correctly a per-event historical record rather than a live pointer.

**Metadata edits append a row; `versions` itself has exactly one mutable column.** `version_annotations` gets a new row on every `annotateVersion` call; `versions.latestAnnotationId` is the only column on an immutable version row that ever changes, and it is a cache pointer recomputable from `version_annotations` if it were ever wrong. Three reasons, not one:

1. A metadata edit has its OWN provenance (who changed it, when, which call) distinct from the content's provenance. In-place update has nowhere to put those three facts without either losing them (today's store) or smuggling them into the content-producer columns (today's event, D2's root cause).
2. Real data proved in-place update destroys facts irrecoverably: `mimic_iii_overview.png` v1's store row shows `origin='model'`, a Chinese title — the fact that it was ONCE an auto-capture with a basename title is gone from the store forever, recoverable only from a session log that might already be deleted.
3. Append naturally supports clearing a caption (`caption: null` on a new row — D8) and lets a human edit and a model curation coexist as two DIFFERENT rows without one silently overwriting the other's provenance.

**`content_origin` and `actor` are two different enums for two different facts (fixes D4).** `versions.content_origin` (`'run-auto' | 'human-edit' | 'import'`) is immutable — how the BYTES came to exist. `version_annotations.actor` (`'capture' | 'model' | 'human'`) — who wrote THIS metadata edit — changes with every new row. v1's single `origin` column conflated these; migrating it apart is D4's fix.

**`baseVersionId` is an explicitly-declared fact, never defaulted (fixes D3).** `base_version_id` (nullable, may name a version of a different artifact) + `base_explicit` (`0`/`1`) replace `parent_version_id`. The chain predecessor is always derivable from `(artifactId, ordinal - 1)` and is deliberately never stored — storing it invites exactly the "does no-base mean no-parent, or model-defaulted-parent" ambiguity that D3 documented. `appendVersion`/`createArtifact` set `baseExplicit` from whether the caller supplied `baseVersionId` at all; there is no independent "explicit" flag a caller can set inconsistently with whether a baseline was given.

**Migration mechanism: an ordered upgrader chain, mirroring the session-log direction-aware mechanism** ([`2026-08-10-session-log-version-mechanism.md`](2026-08-10-session-log-version-mechanism.md)) rather than the store's previous "reject anything but 0 or current." `STORE_MIGRATIONS: readonly StoreMigration[]` holds `{from, to, apply}` steps; `resolveMigrationChain` walks from the on-disk version to the target, throwing `SCHEMA_UPGRADE_UNAVAILABLE` at the first missing step (a pure function, independent of the module-level export, so a gap is unit-testable without seeding a real gap in the shipped chain). Opening branches on the on-disk `user_version`: `0` builds fresh and stamps last; `= current` is used as-is (idempotent DDL re-applied as a safety net); `< current` with an unbroken chain checkpoints WAL and copies `store.sqlite` to `store.sqlite.v<N>.bak` (retention via the new validated `storeBackupRetention` Config field, default 1 — a deployment-varying choice, not a `DEFAULT_*` constant), then runs each step in its own write transaction with `PRAGMA foreign_keys = OFF` for the rebuild, `PRAGMA foreign_key_check` BEFORE that step's own `PRAGMA user_version = <to>` and `COMMIT` (a violation throws and the transaction genuinely `ROLLBACK`s — stronger than a post-commit file restore, since an invalid state is never durably committed in the first place), and `ON` again once the whole chain completes; `> current` throws `SCHEMA_VERSION_NEWER`, naming that the blob directory is still recoverable by hand.

**v1 → v2's six steps map old data honestly, never inventing certainty it doesn't have:**

| v1 fact | v2 destination | Mapping |
|---|---|---|
| `artifacts` (no `kind`, no uniqueness) | `artifacts` + `kind`, `UNIQUE(owningProjectId, logicalName)` | `kind` inferred from the artifact's latest version's `mediaType` (`image/png`→`figure`, `text/csv`→`dataset`, everything else→`document` — the only three cases any producer in this build ever writes). A same-name collision keeps the earliest-created artifact's name and renames the rest `<name>#<short artifactId>`, with an explanatory `artifact_notes` row; version chains are never merged (merging would fabricate a false ordinal history). |
| `versions.parent_version_id` | `base_version_id` + `base_explicit` | Copied straight into `base_version_id`; `base_explicit` is **always `0`**, never `1` — v1 had no column distinguishing an explicit `edit_of` from `store.ts`'s old default-to-latest behavior (D3's root cause), so this migration does not guess which migrated rows were "really" explicit. |
| `versions.origin` | `content_origin` + one derived `version_annotations` row | `'human-edit'` stays; `'auto'`/`'model'` both become `content_origin: 'run-auto'` (origin's OLD meaning conflated content and metadata provenance — D4). One annotation row is derived per version: `actor: 'model'` when v1's `origin` was `'model'`, `'capture'` otherwise; `title`/`caption` carried over verbatim; `derived: true`; `createdAt` = the version's own `createdAt` (the only timestamp v1 had). |
| `versions.environment_fingerprint_preview` (12 hex chars) | `versions.environment_fingerprint` (64 hex chars) | **Not promoted** — a 12-character preview cannot honestly become a full digest, so the column starts `NULL` and is recoverable only through step 4. |
| `versions.environment_revision` (`TEXT`) | `versions.environment_revision` (`INTEGER`) | Parsed with `Number()` — every known producer wrote this as `String(revision)` of a real integer, so this always round-trips; this also fixes a pre-existing type mismatch against every other Science package, which has always treated `environmentRevision` as a `number`. |
| (nothing — v1 had no column) | `versions.producer_turn`, `figure_state`, and the derived annotation's real `toolCallId`/`createdAt` | **Optional step 4, the one exception to "the store never reads session logs":** a caller-supplied `backfillProvenance(projectId, rows) => Promise<Map<versionId, {...}>>` hook may recover these from that project's v1-era session logs, the only place these facts still exist. A missing hook, a rejected hook, or a `versionId` absent from the result all degrade that data to its already-migrated default and log one `onWarning`; none of them fail the migration. |

## Alternatives considered

**Keep the event log as (co-)authority for provenance, letting the store degrade to a rebuildable cache** — rejected: this is the audit's option (b). It passes "model-visible ⟺ logged" for free but fails "deleting the producing session still explains the artifact" (the actual S0 requirement — project artifacts must outlive sessions) unless deletion first "solidifies" the facts into the store, which is (a) with an extra, easy-to-forget migration step. It also keeps D1/D2/D3's actual mechanism (two homes for one fact) instead of fixing it.

**In-place metadata update with an explicit-null-capable patch (fix D8 without appending rows)** — rejected: still loses the metadata edit's own provenance (who, when, which call) and, per the real `mimic_iii_overview.png` evidence, still destroys the content's original curation history irrecoverably. Append-only is not extra ceremony here — it is the only representation that has anywhere to put facts the in-place version had nowhere to keep.

**Monotonic rejection, permanently (keep D14's current behavior, just document it better)** — rejected outright: with the product shipping tonight, the very next DDL change would make every existing user's store unopenable while their blobs sit untouched and unreachable underneath it. This is the one item in the audit rated "data unavailable," not merely "inconsistent," and the codebase already has a proven, direction-aware upgrade mechanism (the session log's) to mirror instead of re-inventing a weaker one.

**Defaulting `baseVersionId` to the artifact's current latest version on a plain continuation (restore the old `store.ts:241` behavior)** — rejected: this IS D3. The whole point of the split is that "no base declared" and "base defaulted to latest" are different facts a single nullable column cannot distinguish, and every consumer that reads `baseVersionId` (the version stepper's lineage line, `get_science_state`'s valid-reference set) needs to tell them apart.

## Consequences

This task (T1) delivers the store package only — new tables, the migration, and the adjusted public interface (`createArtifact`/`appendVersion` drop `title`/`caption`, gain `kind`/`baseVersionId`/`producerTurn`/`environmentFingerprint`/`figureState`; `annotateVersion` gains `actor`/`sessionId`/`toolCallId`/`requestHeaderSeq` and append semantics; new `listNotes`/`putNote`/`removeNote`/`getFigureState`/`setVersionHealth` methods) — with no consumer wired up yet, matching S1's original shape. `science-runtime`, `science-session`, and `tool-science` still write through the OLD `origin`/`title`/`caption`/`editBaselines` shape until a later task updates them; that update also owns implementing the `backfillProvenance` hook (this package only defines and calls it), the store↔session reconciliation algorithm that calls the new `setVersionHealth`, and the `SESSION_FORMAT_VERSION` bump-or-tolerate decision for `science/artifact-saved`'s slimmed payload. The three-artifact/dataset/document/job-output `kind` split and the `figure_state`/future `dataset_schema`/`jobs` side-table shape are designed to admit Figure/DataAsset/Jobs objects later without another authority-rule migration — new object kinds get a side table in the store and their conversational facts in the session log, never a second copy of provenance in both places.
