# Agent Note: Science artifact raw-byte reads over HTTP, not JSON-RPC base64

Status: implemented

English | [中文](2026-09-01-science-artifact-raw-byte-reads.zh.md)

## Problem

Every Science artifact read went through `session.scienceArtifact`, a JSON-RPC method whose response schema carries `data: string` — the blob base64-encoded (`api-proxy.ts`'s `Buffer.from(data).toString('base64')`). Base64 inflates by exactly 4/3: the sampled corpus's largest blob (2.5 MB) becomes a ~3.4 MB JSON string field inside one RPC envelope, parsed as one JavaScript string before any byte reaches its consumer. A download or a large preview pays this inflation, plus a full decode/re-encode pass, on every read.

The browser side compounded this for text content specifically. `ScienceDetailsView.tsx`'s download path ran the base64 payload through `TextDecoder('utf-8', { fatal: true })` to recover a string, then `encodeURIComponent` to build a `data:` URI — decode, then re-encode, to move bytes the browser already had. Two real defects followed directly from this design, not from any implementation slip: a CSV encoded as GBK or Latin-1 (common for Science-workspace data exports) fails `TextDecoder`'s `fatal: true` mode immediately, and the failure's own `.catch(() => {})` swallowed it — a user clicking Download on a non-UTF-8 CSV saw nothing happen, with no error surfaced anywhere. Separately, a `data:` URI has a browser-enforced length ceiling; a large CSV that decodes cleanly can still fail to download for size alone, silently, through the same empty catch.

## Decision

**A second host-only download surface, `GET /api/science/artifact/:sessionId/:versionId`, joins `session.export` in the `DownloadsApi` domain (no wire envelope — `toFetchHandler` answers it as a physical route, exactly like `session.export`).** The path carries no `projectId` segment; authorization is the exact `authorizedScienceArtifact` function `session.scienceArtifact` already used (extended only to also carry `artifactId`/`ordinal`, both already present on every `VersionRecord` each of its three branches already holds), so a client cannot select an authorization domain of its own choosing — the session's own event-log fold derives the project, precisely as the JSON-RPC path does. The base64 RPC is unchanged and stays the read path for non-browser callers (see `readScienceArtifact` RPC consumer grep in this task's report); this endpoint is additive, not a replacement.

**The response body is the verified `Uint8Array` from `ScienceArtifactStore.readBlob` passed straight to `Response`, with no intermediate string of any kind.** No base64, no `TextDecoder`, no `data:` URI. `Content-Type` carries the stored `mediaType` verbatim with no `charset` parameter — this endpoint never inspects bytes to guess an encoding; the non-UTF-8 CSV defect above is exactly why guessing is worse than leaving the decision to the browser's own BOM/heuristic handling. `Content-Length` is the verified byte count, `Content-Disposition` names the owning artifact's current logical name with `-v<ordinal>` inserted before its extension (`chart.png` version 3 → `chart-v3.png`), doubly encoded per RFC 5987 (`filename*=UTF-8''…`) alongside an ASCII-safe `filename=` fallback for user agents that ignore the extended form, and `X-Content-Type-Options: nosniff` is always set.

**Integrity is verify-then-serve, not stream-then-abort, because the store package exposes no way to do the latter from outside its own module.** `@deepseek-ai/dsh-science-artifact-store`'s public `exports` map is `.`, `./ids`, `./invariant`, and a test-only `./src/*` — `blobs.ts`'s `readBlob` (the function that hashes a blob against its `sha256` before returning it) and the private `blobPath` helper that resolves a digest to its on-disk path are both unreachable from `dsh-host-apiproxy` except through `ScienceArtifactStore.readBlob`, the one already-public method, which returns the whole verified buffer rather than a stream. This task's scope was `packages/host/apiproxy` only — extending the store package's public surface with a streaming variant belongs to that package's own owners, not this change. The result is a strictly stronger guarantee than the streamed design would have given: this endpoint holds one fully verified buffer before writing a single response header, so no client can ever receive a partial response whose `Content-Length` promise it cannot keep, and no download is ever framed as complete when it silently was not. The cost is one buffer copy per concurrent download, acceptable at the corpus sizes observed; a genuinely streaming `readBlob` is future work for the store package.

**Three failure outcomes get distinct, documented codes; T3's `missingContent` health flag had named the fact but not this endpoint's wire vocabulary, so this task defines it.** An unauthorized or nonexistent session/version answers 404 with a fixed `not found` body — never a reason, never an echoed project id, so a client cannot use response content to enumerate what exists. A version whose blob is absent from the store (`ScienceArtifactStore.readBlob` throwing `BLOB_NOT_FOUND`) answers 410 Gone with an `x-science-artifact-error: missing_content` header — the same name T3's `VersionHealthRecord.missingContent` flag already uses, chosen for exactly that alignment (a follow-up client change can key off `missingContent` in both places without inventing a second vocabulary). A version whose blob fails SHA-256 verification (`BLOB_CORRUPT`) answers 409 Conflict with `content_corrupt` — a name T3 had no equivalent for, since content tampering is a different failure from "the row is unhealthy" reconciliation tracks. A deployment with no `scienceArtifactStore` service mounted answers 500.

## Alternatives considered

**Keep the base64 JSON-RPC path but chunk large blobs across multiple messages** — rejected. Chunking removes neither the base64 inflation nor the decode/re-encode pass; it only hides the same overhead behind reassembly logic on both ends, and does nothing for the non-UTF-8 text defect, whose root cause is decoding to a JS string at all, not message size.

**Fix the non-UTF-8 defect by having the client detect and re-decode with a guessed encoding before building the `data:` URI** — rejected as out of this task's scope, and rejected in principle: encoding detection from bytes alone is inherently a guess (T4's own task book calls this out explicitly), and a wrong guess silently corrupts data the same way the current `fatal: true` failure silently drops it, just less visibly. The correct fix is to stop needing a JS string at all for a binary transfer, which this endpoint does directly.

**Add a genuinely streaming disk read (`fs.createReadStream` against a resolved blob path) in this same task** — deferred, not rejected outright. It would need a new public accessor on `@deepseek-ai/dsh-science-artifact-store` (a path resolver or a streaming `readBlob`), which is a different package's public surface and this task's explicit boundary excludes it. Documented as a Known Limitation in `dsh-host-apiproxy`'s README rather than worked around with a private cross-package import.

## Consequences

Scope: `packages/host/apiproxy` only (`src/api/downloads.ts`, `src/api/downloads.schema.ts`, `src/fetch/handler.ts`, `src/api-proxy.ts`, `tests/science-artifact-download.spec.ts`, `README.md`/`README.zh.md`). No file under `packages/science/*`, `packages/client/*`, or `packages/api` changed — the store's read interface, the reconciliation mechanism, and every client consumer are unmodified. `session.scienceArtifact`'s base64 response schema, `authorizedScienceArtifact`'s three proof paths, and `ScienceArtifactStore`'s public methods are unchanged in behavior; `AuthorizedScienceArtifact` gained two fields (`artifactId`, `ordinal`) already available on every branch's existing `VersionRecord` read, so no additional store call was needed to add them.

Image/text preview switching to `<img src>`/`fetch()` and the Files-panel/detail-view unified-title rendering are separate work on this same migration and extend this Note with their own sections rather than opening a new file for the same endpoint.

`packages/host/apiproxy/tests/science-artifact-download.spec.ts` covers byte-identical passthrough for both a non-UTF-8 (GBK-shaped) CSV fixture and a 2 MB+ PNG fixture generated in-test (never committed as a binary), the `Content-Length`/`Content-Disposition`/`nosniff` header contract including RFC 5987 encoding of a filename carrying a `attr-char`-excluded mark (`!'()*`), the 404 authorization-failure path asserting the response body never contains the project id, the 410/409 error-code paths, and the store-unmounted/authorization-throws/read-failure 500 paths. `npx vitest run packages/host/apiproxy --coverage --coverage.include='packages/host/apiproxy/src/**'` reports 100% statements/branches/functions/lines (676/676, 201/201, 193/193, 640/640) across the package's full 404-test, 21-file suite.

## Batch version-summary read (`sessions.scienceVersions`)

The unified-title fix needs a Host read that returns a version's CURRENT title/caption/content-origin — the same store row `scienceArtifact` and the download endpoint already read for authorization, not a session-log snapshot taken when the version was captured. A Files-panel page or a version stepper needs this for several versions at once, so the read is batched rather than repeated per version: `sessions.scienceVersions(sessionId, versionIds[])` returns `{ versions: ScienceVersionSummary[] }`, each entry `{ versionId, artifactId, logicalName, ordinal, title?, caption?, contentOrigin, createdAt, mediaType, byteCount, health? }`.

**A new RPC, not a wider `scienceLibrary`, because the two calls answer different questions with different authorization shapes.** `scienceLibrary` lists one latest row per artifact in a whole project — its caller supplies no version identity at all, and every row it returns is by definition visible to the caller (the caller asked for "the project"). `scienceVersions` answers "what are the current facts for exactly these versions", a caller-chosen set that can span any mix of latest and historical versions across the project's artifacts, each requiring its own independent authorization proof through `authorizedScienceArtifact` (a version a session's fold cannot prove must not leak into a response the caller can already read because `scienceLibrary` happened to authorize the project as a whole). Folding this into `scienceLibrary` would mean either always returning every historical version for every artifact (paid on every Files-panel load, needed by almost no caller) or growing that RPC an unrelated optional request shape, `{ projectId }` plus `{ versionIds }`, splitting its own authorization story into two conditionally-applicable rules on one wire method. A second RPC keeps each contract's authorization rule singular and lets a caller that only ever needs `scienceLibrary` stay unaware the batch path exists.

**Authorization reuses `authorizedScienceArtifact` per id, unauthorized ids drop silently.** Each requested `versionId` is resolved through the same three proof paths the raw-bytes endpoint and `session.scienceArtifact` already use; an id the session's fold cannot prove is omitted from the result array rather than failing the whole call. This mirrors `scienceLibrary`'s own established rule (a version whose media type this build cannot render is silently absent from that listing too) — a caller renders a batch where partial visibility is the normal outcome of individually-authorized items, not a client-visible fault, and the omission also carries no information (a client cannot tell "not authorized" from "no longer exists" from the missing entry, matching `scienceArtifact`'s reason-free 404). A fixed 200-id cap, enforced by the request schema before any store lookup runs, bounds one call's authorization and store work.

**`AuthorizedScienceArtifact` (the shared authorization result type `scienceArtifact`, the download endpoint, and this RPC all build from) grew `title`/`caption`/`contentOrigin`/`createdAt`.** Every one of its three resolution branches already holds the full `VersionRecord` the store returned before this change (the earlier `artifactId`/`ordinal` widening established the same pattern), so naming these four already-fetched fields on the shared type costs no additional store round trip; only `logicalName` needs a fresh `getArtifact` call, cached per distinct artifact within one batch call since a version stepper's requests are dominated by repeats of the same artifact.

**Consequences**: `packages/host/apiproxy/src/api/sessions.ts` (the `ScienceVersionSummary`/`ScienceContentOrigin` types and the `scienceVersions` method declaration), `src/api/sessions.schema.ts` (request/value schemas, the `SCIENCE_VERSIONS_BATCH_LIMIT` constant), `src/api/rpc-map.ts`, `src/fetch/handler.ts`, `src/fetch/client.ts` (also exports `resolveApiOrigin`, factored out of `AbstractApiClient.resolveBase` so a same-origin URL builder outside the carrier — the client runtime's raw-bytes preview/download helper — resolves the identical origin without hardcoding one), `src/api-proxy.ts` (the `scienceVersions` handler and the `AuthorizedScienceArtifact` widening), and their tests. `packages/client/runtime` gained `Session.readScienceVersions`, a `scienceArtifactUrl(sessionId, versionId)` helper built on the exported `resolveApiOrigin`, and a `health: ScienceLibraryHealth` field on `readScienceLibrary`'s declared return type (the wire already carried it; only the client-side type had not caught up). `readScienceArtifact` and its base64 RPC are unchanged and remain for callers that are not a browser preview or download.
