# Agent Note: a client-facing read path for `ScienceChartState`

Status: implemented

English | [中文](2026-09-02-science-client-chart-state-read-path.zh.md)

## Problem

[T1/T2](2026-09-01-project-artifact-store-schema-v2.md) moved a version's live-figure chart state (`ScienceChartState`: addressable elements, the direct-edit operation log, pixel-space hit regions) into the project artifact store's `figure_state` table, keyed by `versionId`. `ArtifactContent.tsx`'s live chart-edit panel had read this state synchronously off the session projection's own `ScienceClientArtifactVersion.chart` field; that field is gone with the migration, and no RPC read it from the store instead — [the raw-byte-reads Note](2026-09-01-science-artifact-raw-byte-reads.md) (its own "ui-science read-path migration" section) documents the resulting regression at its exact call site rather than working around it: the panel never mounted, and `previewChartOps` could not substitute for a dedicated read because it rejects an empty operation list.

## Decision

**A new single-version RPC, `sessions.scienceChartState(sessionId, versionId)`, joins `scienceArtifact`/`scienceVersions` in `SessionsApi`, authorized through the exact same `authorizedScienceArtifact` three-proof-path function.** It answers `{ chart: ScienceChartState | null }`: `null` for a non-PNG version, and for a PNG version whose `figure_state` row is absent (imported or legacy content) — a caller cannot distinguish the two and shows no edit affordance either way, so no distinction is drawn on the wire. Unlike the batch `scienceVersions` read, an unauthorized or nonexistent `versionId` fails loud with `science-artifact-error`/`VERSION_NOT_REFERENCED` rather than a silent omission: this RPC always names exactly one version an already-open artifact tab is rendering, not a batch where partial visibility is the expected outcome. The implementation is the tool-science `edit-message.ts` `submit` Remote's own `figureState` resolution (`store.getVersion` → check `mediaType === 'image/png'` → `store.getFigureState` → `decodeScienceChartState(JSON.parse(...))`), reused as the read path's actual body rather than a new mechanism.

**The wire response schema is structural, not a re-implementation of `dsh-science-session`'s own `decodeScienceChartState` cross-field checks** (element/hitmap id references, bbox ordering, byte-size cap) — the Host already ran that validation before writing the `figure_state` row, so `sessions.scienceChartState`'s wire schema shapes the parsed client-side value only, mirroring `sessionProjectionsBlockSchema`'s and `toolEventViewSchema`'s own already-host-validated passthroughs elsewhere in this same schema file. `ScienceChartState` itself is imported directly from `@deepseek-ai/dsh-science-session/types` rather than redeclared field-for-field (the pattern `ScienceContentOrigin` uses for `dsh-science-artifact-store`, which exposes no browser-safe subpath) — `dsh-science-session/types` is already a zero-Node type-only subpath, and `sessions.ts` already imports `ScienceArtifactMediaType` from it the same way. `packages/host/apiproxy/src/api/index.ts` re-exports the name directly from that subpath (not from `./sessions.ts`, which never declares it) so `dsh-client-runtime` can name it without adding its own dependency on `dsh-science-session` — `ScienceChartState` reaches `ISession.readScienceChartState`'s return type entirely through the existing `dsh-host-apiproxy` peer dependency.

**`ArtifactContent.tsx` fetches chart state once when a PNG version's content mounts, not on a separate "expand the panel" gesture — there is no such gesture.** `ScienceChartEditPanel` has always rendered as one always-visible form the moment its artifact tab opens (no internal collapse/expand toggle exists on the panel itself, only smaller internal disclosures like the annotation-overflow control), so "the PNG tab opens" is the only mount trigger this component actually has. `ChartEditSlot` (new, in `ArtifactContent.tsx`) wraps a `useLoadedChartState` hook (mirroring `useLoadedText`'s loading/ready/error states, keyed by `content.versionId`) around `ScienceChartEditPanel`, rendering nothing while loading, on a fetch error, or once resolved with `chart === null`. The fetch fires exactly once per opened version: `ArtifactContent`'s own call site (`ScienceDetailsView.tsx`'s `ArtifactTab`) already remounts it fully on every tab switch or version step via a `key={artifactId:version}`, so no additional dedupe or caching is needed for this single-consumer read — `science-chart-state-loader.ts`'s own doc comment names `loadImage`/`loadText`'s memoization as the template a future cache should follow if a second consumer appears.

**`ReadOnlyPreview` (the Files-panel workspace-file preview and the library-artifact preview modal) passes an inert `loadChartState` that resolves `null` without a request, not the real loader.** Both call sites synthesize their `ScienceRenderableVersion` through `previewChart()`; one (`WorkspaceFilePreview`) uses the workspace-relative file path as a fake `versionId` that the RPC would always reject, and the other (a library row opened outside its own live-session tab) can carry a real store `versionId` but never did carry chart state before this task either (the pre-migration `ScienceClientArtifactVersion.chart` field was never populated by either `previewChart()` call site). Matching that existing behavior — read-only previews never show the edit panel — costs one inert closure instead of a request this build already knows would find nothing to edit.

## Alternatives considered

**Batch the read into `sessions.scienceVersions`, adding a `chart` field to `ScienceVersionSummary`** — rejected. That RPC's whole design (`2026-09-01`'s own Decision) is a caller-chosen batch where partial visibility is normal and every field is comparatively small (title, caption, a few scalars); `ScienceChartState` carries `elements`/`ops`/`hitmap` arrays up to `MAX_CHART_STATE_BYTES`, paid on every batched call (a version stepper's whole visible set) even though only the one currently-open version ever needs it. A caller that only needs a batch of light facts would also start paying for chart-state parsing it never asked for.

**Substitute `previewChartOps` with an empty `ops` array as the read** — rejected in the parent Note already, and confirmed here: the Remote explicitly rejects an empty operation list, and even if it did not, a preview call is designed to render a hypothetical edited PNG, not to answer "what is the current addressable state" — reusing it would couple an unrelated capability's contract to this read's needs.

**Cache chart state across renders the way `useScienceVersionSummaries` accumulates version facts** — deferred, not rejected: `ChartEditSlot` has exactly one consumer today (the currently open PNG tab), so a session-lifetime cache would add a data structure with nothing to share across. `science-chart-state-loader.ts`'s own doc comment names the memoization pattern to reach for once a second consumer exists.
