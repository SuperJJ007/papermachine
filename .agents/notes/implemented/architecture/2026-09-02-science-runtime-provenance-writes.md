# Agent Note: `science-runtime` writes provenance to the store, not the event

Status: implemented

English | [中文](2026-09-02-science-runtime-provenance-writes.zh.md)

## Problem

[T1](2026-09-01-project-artifact-store-schema-v2.md) made the project artifact store's write transaction the sole authority for a version's provenance, and [T2a](2026-09-02-science-artifact-event-slimming.md) slimmed `science/artifact-saved` and its fold to match. `science-runtime` still wrote the old shapes: `capture.ts` passed a 12-character `environmentFingerprintPreview` and a `title`/`origin` pair straight into `createArtifact`/`appendVersion`, and rebuilt a full old-style `ScienceArtifactVersion` (with `origin`, `chart`, `mediaType`, `byteCount`, `parent`, `runId`) for the event; `annotateArtifact` fabricated `createdAt: Date.now()` and let the curating call's own `toolCallId` stand in for the content's producer (D1/D2); `performChartEdit`'s human-edit commit read `parent.chart`/`parent.mediaType`/`source.runId` directly off the session projection, fields T1 had already moved into the store. None of this compiled against T1/T2a's new interfaces.

## Decision

**`capture.ts` writes full provenance to the store and a slim presentation snapshot to the event.** `producerTurn` is read once per walk from the local fold's own `state.toolCalls` index (looked up by the authorizing run's `toolCallId`; `tool/call` events are unaffected by the event slimming) rather than per file. `environmentFingerprint` is passed through unchanged (full 64-hex digest; the old 12-character preview truncation is gone with the store column it existed for). A captured PNG's chart state becomes a `figureState: { figureKey, dpi, stateJson: JSON.stringify(chart) }` input instead of a `chart` field on the event. `baseVersionId` is supplied only when `editBaselines` names one (never latest-defaulted — the store never defaults it either). The title (the file's basename) is written as a separate `actor: 'capture'` annotation after the content commits, not as a `versions` column (T1 dropped that column). The event itself carries only the new field set (`artifactId`/`versionId`/`version`/`logicalName`/`sha256`/`title`/`caption?`/`projectId`/`seenAt`).

**Cross-session continuation (D7) is restored, plus its natural follow-on: a create race.** `b0524e2c64` had deleted the lazy `store.listArtifacts` lookup capture used before D7 to decide create-vs-append, to sidestep the strict-fold-era ambiguity T2a's loosened checks and T1's `UNIQUE(owningProjectId, logicalName)` constraint now resolve honestly. It is back: a logical name this session's own fold has never recorded still resolves against a project-wide `listArtifacts` snapshot (fetched once per walk, lazily, and memoized) before falling through to `createArtifact`. Because the store — not local session history — is now genuinely the authority for a version's `sha256` and `contentOrigin`, the same-content skip and the human-edit stale-skip both read `store.getLatestVersion`/`store.listVersions` directly instead of the session's own (slimmer, provenance-free) projection; this is strictly more correct than the pre-D7-deletion version, which could still be fooled by a locally stale head. The restoration's direct consequence — two sessions racing the same brand-new logical name into existence between one walk's `listArtifacts` snapshot and its own `createArtifact` call — is handled by catching `ProjectArtifactStoreError('LOGICAL_NAME_CONFLICT')` specifically, re-resolving the winner, and appending onto it rather than failing the file; any other store error still propagates unchanged.

**`annotateArtifact` calls `store.annotateVersion` and stops rebuilding a version value.** It resolves the target from the session's own projection (unchanged: `logicalName`/optional `version` against `projection.artifacts`), reads the store's current `contentOrigin` to reject a human-edit target (`ARTIFACT_NOT_CURATABLE`; this fact left the session projection with T2a, so it is a store read now, not a field check), then appends one `version_annotations` row via `annotateVersion({ actor: 'model', sessionId, toolCallId, requestHeaderSeq, title, caption: request.caption ?? null })`. `caption ?? null` reproduces the old full-replace semantics (an annotate call is authoritative for both fields; omitting `caption` clears a prior one — D8) using the store's tri-state input (omit = carry forward, `null` = clear, string = set). Neither `createdAt` (D1) nor the curating call's own identity (D2) reach the version row at all now — they never did after this change, because the version row is never touched by curation; only the annotation's own `sessionId`/`toolCallId`/`requestHeaderSeq` record who curated.

**A toolCallId cannot authorize two `annotate_artifact` curations, checked at the store write.** T2a's slimming removed `science/artifact-saved`'s own `toolCallId` field, so the fold-level "no two Science facts share one authorizing call" check has nothing left to gate on for curation (documented as a residual gap in that note). `assertAnnotateToolCallUnused` closes the reachable part of it before the write: for every distinct `artifactId` this session's own projection already knows, it reads `store.listVersions` and rejects if any version's current `latestAnnotation.toolCallId` matches. This is durable (a store read survives a Host restart; an in-memory Runtime `Set` would not) and bounded to what a curation call could plausibly target (its `logicalName` must already be in this session's own projection). It is deliberately not a whole-project scan: two narrowings are accepted and documented in the package README rather than silently dropped — a `toolCallId` a later annotation has superseded is no longer visible (the store's public API exposes only the current annotation per version, not its full history), and an artifact this session has never loaded is not scanned.

**`commitStyleEdit` (the human-edit branch of `performChartEdit`) resolves every fact `parent.chart`/`parent.mediaType`/`source.runId` used to carry from the store.** `store.getVersion`/`store.getFigureState` replace the parent's `mediaType`/`chart` fields; the nearest run-origin ancestor ("source") is found by scanning `store.listVersions(projectId, artifactId)` for the last `contentOrigin !== 'human-edit'` row (the artifact's FULL ordinal history, not just what this session's own fold happens to know — the store is the authority for `contentOrigin` now, so this scan is honestly the same store round trip a cross-session-aware search would need anyway) rather than filtering the session's local `versions` array by a removed `origin` field. The appended human-edit version's `environmentRevision`/`environmentFingerprint` are ASSIGNED from the edited version's own store row (never re-derived or fold-checked — the store row already is the fact), `baseVersionId` names the edited version explicitly (`baseExplicit: true`, matching every other editBaselines caller), and no producer run/tool-call fields are set (a human edit has no authorizing run), beyond `producerTurn` — the session's last started turn, read once when `applyChartEdit` is called ([producer.turn attribution](../bug-fix/2026-09-03-science-viewer-write-turn-attribution-and-data-loading-guidance.md)). Title/caption are inherited via a separate `actor: 'human'` annotation that copies the edited version's current values forward, mirroring `capture.ts`'s basename annotation and `annotateArtifact`'s curation annotation — three different actors, three different call sites, one mechanism.

**The `backfillProvenance` hook (T1's v1→v2 migration step 4) is deferred, not implemented, with the reusable reader identified.** The hook signature is `(projectId: string, rows) => Promise<Map<versionId, BackfillProvenanceValue>>` — no `workspacePath`. Resolving "which session logs belong to this project" from `projectId` alone needs `dsh-science-artifact-store`'s own (unexported) `resolveProjectIdentity`, which this task's scope forbids touching. The correct sidestep — not requiring that resolution at all — is that each `BackfillProvenanceRow` already names its own `producerSessionId`: grouping rows by that field and reading each session directly through `@deepseek-ai/dsh-session-persistence`'s backend-agnostic `SessionPersistence.inspect(sessionId)` (not the JSONL backend's own internals, which are not part of its public compiled surface) returns each event's ORIGINAL stored `data`, unprocessed by `dsh-science-session`'s codec — the exact old fields (`environmentFingerprint`, `toolCallId`, `origin`, `createdAt`, `chart`) T2a's tolerant codec now silently drops on read. `producerTurn` is recoverable the same way capture.ts recovers it live: scan that session's own `tool/call` events (a generic, Science-independent event shape) for the annotate/producer call's `turn`. This is a real, buildable design, not a dead end — it is left unimplemented here because it is additional scope beyond this package's own write-path migration, needs a new peer dependency on `@deepseek-ai/dsh-session-persistence`, and the store's own migration already treats an absent hook as a documented, non-fatal degradation (`onWarning`, never a failed migration). `ScienceArtifactStore`'s `backfillProvenance` config field is left unset by every composition this task touches.

## Alternatives considered

**Keep `producerTurn` optional and spread it conditionally, matching every other optional producer field** — rejected: the authorizing run's `tool/call` event is provably always present in `state.toolCalls` by the time capture runs (the run's own `science/run-started` required it to validate the same `toolCallId` before it could commit), so treating it as possibly absent would hide a real invariant violation behind a silently-omitted field instead of failing loud, and would also have left an ultimately-uncoverable branch in the object literal.

**Scope the toolCallId-reuse check to a whole-project `listArtifacts` scan instead of this session's own known artifacts** — rejected: `annotate_artifact` can only ever name a `logicalName` this session's own projection already resolves (`resolveAnnotateTarget` requires it), so a version outside that set could never be the call's actual target; scanning every artifact in the project would cost an unbounded number of `listVersions` calls for no additional coverage of the actual threat (one authorizing call backing two curations from the same session).

**Keep `prepareRunArtifacts`'s `declaredBytes` pre-check by fetching `byteCount` per resolved input from the store** — rejected: it would reintroduce exactly the store round trip the function's own JSDoc says a same-session reference should never need, to preserve an optimization (failing fast before any blob read) that the existing per-blob `actualBytes` accumulation already makes redundant for correctness; only the early-exit timing was lost, not the byte bound itself.

**Recover the store's authority for the human-edit stale-skip check by asking only the specific artifact in question, not the store's current head, when this session's local `sha256` already looks unchanged** — rejected: local `latest.sha256` alone cannot distinguish "unchanged" from "a different session already advanced this artifact past what I know," so skipping the store read whenever local knowledge appears sufficient would silently reintroduce exactly the staleness D7 exists to prevent.

## Consequences

Scope: `packages/science/science-runtime` only, per T2's own package boundary (`packages/science/science-artifact-store`, `packages/science/science-session`, `packages/science/tool-science`, and `examples/` are other tasks' territory). `packages/science/tool-science` does not compile against this package's new `ScienceArtifactVersion`/store-input shapes yet (`annotate-artifact.ts`, `artifact-schema.ts`, `edit-message.ts`, `run.ts`, `state.ts` all reference removed fields — `origin`, `chart`, `mediaType`, `byteCount`, `parent`, `runId`, `environmentRevision`, `environmentFingerprint`); that migration is T2b-2's.

The [2026-08-30 per-session artifact identity](../../rejected/architecture/2026-08-30-science-artifact-identity-per-session.md) proposal is rejected by this change: its core mechanism (a fresh artifact per session even for an identical logical name) is the D7 regression this change reverses, superseded by T1's store-level `UNIQUE(owningProjectId, logicalName)` constraint plus the lazy cross-session lookup this note restores.

`science-runtime`'s own test suite is fully updated: `capture.spec.ts`, `annotate.spec.ts`, and `chart-edit.spec.ts` assert store-read provenance (`content_origin`, producer fields, `base_version_id`/`base_explicit`, `figure_state`) instead of removed event fields; the two cross-session tests are rewritten from asserting D7's absence to asserting its restoration (continuation on new content, skip on identical content, plus a new dedicated create-race-recovery test and a same-code-different-error negative test); `inputs.spec.ts`'s aggregate-byte pre-check test drops its `declaredBytes` sub-case. `real-acceptance.ts`, `chart-kernels.real.spec.ts`, and `chart-fidelity.spec.ts` (real-interpreter suites, gated behind `DSH_SCIENCE_RUNTIME_PYTHON_PREFIX`/`DSH_SCIENCE_RUNTIME_R_PREFIX` or the standalone `test:real-acceptance` script) read figure state and content origin from the store the same way, through small per-file `chartOf`/`contentOriginOf` helpers.

**A `/* v8 ignore */` comment placed above a ternary-expression variable initializer (`const x = cond ? a : b`) is not honored by `@vitest/coverage-v8`'s own threshold check on this version, even though every istanbul-remapped report (`text`, `html`, the repository's own `uncoveredLocationsReporter`) correctly shows it as covered.** Converting the same unreachable-branch guards to `if (cond) { throw … }` statements ahead of an unconditional access — matching every other invariant guard already in this file — makes the threshold check agree with the reports. `pnpm run test:coverage`'s v8 provider is architecturally a step removed from istanbul (V8's own bytecode-level branch counters, remapped through `v8-to-istanbul`), and this repository's own `coverage-final.json` branch-count data confirmed the discrepancy was specific to the ternary form, not a general ignore-comment failure or a package-scoped `--coverage.include` artifact.
