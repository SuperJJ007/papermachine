# Agent Note: Science Runtime queues a second concurrent run instead of rejecting it

Status: implemented

English | [中文](2026-08-25-science-runtime-queue-concurrent-runs.zh.md)

## Problem

A real desktop session had the model issue `run_python` and `run_r` together in one assistant step ("Let me run a quick Python and R sanity check in parallel"). Python completed in 1.4s; `run_r`'s tool result was `Error: Science Runtime operation was cancelled`, with no `science/run-started` event for it at all. Tracing the session log (`science/kernel-state` for `r` had a scratch directory but no `resp.fifo`, confirming `KernelProcess.start` began and was aborted) showed the exact chain: `run_python`/`run_r` declare no `isConcurrencySafe` classifier, so the tool scheduler (`packages/core/agent-loop/src/tool-calls.ts`) runs them as two exclusive barriers — `run_r`'s dispatch, and therefore its own `ScienceRuntime.startRun` call, does not begin until `run_python`'s full result has committed. In this session, a `session.cancel` RPC (`packages/host/apiproxy/src/api-proxy.ts`, `kind: 'user'`) arrived independently and won the race against `run_r`'s kernel spawn, which had only just started.

That exclusive scheduling is correct and intentional: `run_python`/`run_r` durably mutate the session (`science/run-started`/`science/run-finished`), and the parallel-tool-call safety contract (`packages/core/tools/src/index.ts`'s `isConcurrencySafe`, the [parallel-tool-call Agent Note](../feature/2026-07-10-parallel-tool-call-execution.md)) requires a `true` classifier's body not to mutate parent-owned state directly — the same reason filesystem writes and bash stay exclusive. The session log's own fold also hard-enforces "only one Science run may be running in a session" (`packages/science/science-session/src/transition.ts`'s `applyRunStarted`), so true concurrent kernel *execution* across languages is not on the table without a durable-format change.

Investigating the interaction surfaced a real, separate defect regardless of that one incident's genuine external cancel: `ScienceRuntime`'s `LeaseRegistry` (`packages/science/science-runtime/src/lifecycle.ts`) is a non-queuing, session-wide mutex. Any caller reaching `startRun` (or `bindEnvironment`/`annotateArtifact`) while another Runtime operation already holds the same Session's lease got an immediate `RUNTIME_BUSY` rejection (`packages/science/science-runtime/tests/run.spec.ts`'s `rejects a second concurrent run with RUNTIME_BUSY`, now rewritten) — not a queued turn. A genuinely racing second `startRun` call — from a retry, a second initiator, or a future scheduling change — got rejected outright instead of a real attempt once the first vacated.

## Decision

`ScienceRuntime.startRun` now calls a new private `reserveQueued(session, signal)` instead of `reserve` directly. `reserveQueued` retries `reserve` in a loop; on `RUNTIME_BUSY` it reads the blocking lease via a new `LeaseRegistry.blocking(session)` accessor and awaits that lease's own `settlement` promise (raced against the caller's `signal` aborting) before retrying. Every retry constructs a fresh `OperationControl`, so a queued caller's own operation deadline starts counting from when it actually acquires the lease, not from when it started waiting. `signal` aborting while queued, or the Runtime beginning disposal while queued, rejects immediately — with `OPERATION_CANCELLED` or `SERVICE_DISPOSING` respectively — before any `OperationControl` or lease is touched, so a caller cancelled or preempted while only queued never spawns anything.

`startRun`'s environment lookup and its durable open-run check move from before the lease reservation to after: they now read a **fresh** projection once the lease is actually granted, not the pre-queue snapshot, since a caller that queued behind another run has stale state by the time its turn arrives. The durable open-run check (`projection.runs.some(status === 'running')`) still throws `RUNTIME_BUSY` immediately rather than queuing — reaching it with a free lease means an orphaned run left by a crash before a Host restart re-attached the Session, not the in-process race `reserveQueued` already resolves; there is nothing to wait for.

`bindEnvironment` and `annotateArtifact` are unchanged: they still call the plain `reserve` and reject `RUNTIME_BUSY` immediately. They are rare, session-wide operations (bind happens once before any run exists; annotate is metadata-only), not the run-vs-run contention this fix targets.

## Alternatives considered

**Mark `run_python`/`run_r` `isConcurrencySafe`.** Rejected: they directly mutate durable session state (`science/run-started`/`-finished`), which the parallel-tool-call safety contract reserves for tools whose body does not mutate parent-owned state — the same reason bash and filesystem writes stay exclusive. It would also let two same-language calls race the fold's own single-open-kernel-acquire discipline (`kernel-set.ts`'s module doc: `KernelSet.acquire` assumes at most one call in flight per Session).

**Scope the lease per (Session, language) so Python and R execute genuinely concurrently.** Rejected: `transition.ts`'s `applyRunStarted` hard-enforces "only one Science run may be running in a session" at the fold level, independent of language — a durable, structural invariant, not an in-memory scheduling artifact. Loosening it is a session-log format change out of scope for this fix.

**Leave `RUNTIME_BUSY` as an immediate rejection and only improve its message.** Rejected: the task is "both must get real results" for a genuinely racing pair of calls; a clearer rejection message still denies the second caller a turn it is entitled to once the first vacates.

## Consequences

A second `ScienceRuntime.startRun`/`bindEnvironment`-adjacent run call that genuinely races an in-flight one for the same Session now queues and gets a real attempt instead of an outright rejection, matching `run_python`+`run_r` issued together in one step. The original captured incident's own cancellation was a legitimate external `session.cancel` and is unaffected — a caller cancelled after the tool scheduler already lets it start still observes that cancellation correctly, now cleanly with no lease ever touched if the cancel arrives while still queued. Under today's exclusive tool-scheduler classification for `run_python`/`run_r`, `reserveQueued`'s loop rarely retries in practice (the scheduler already fully serializes their dispatch): the value is closing the gap for callers that reach the Runtime directly or concurrently outside that scheduler, and for any future scheduling change.

## Verification

`packages/science/science-runtime/tests/run.spec.ts`: `'queues a second concurrent run for the same session instead of rejecting or cancelling it'` (rewritten from the old RUNTIME_BUSY-rejects test) drives two `startRun` calls without an intervening await and asserts both settle successfully; `'cancels a queued run cleanly, without ever spawning a kernel, when its own signal aborts before its turn arrives'` pins the pre-lease cancellation path; `'rejects a queued run with SERVICE_DISPOSING, without acquiring a lease, once the Runtime begins disposing while it waits'` pins the disposal path; `'lets a Python and R run issued together (Promise.all, no await between them) both complete rather than cancelling whichever is second'` drives the real cross-language scenario end to end through fake Python and R kernels. `packages/science/science-runtime/tests/lifecycle.spec.ts` adds direct `LeaseRegistry.blocking()` coverage for both the exact-Session and same-ID quarantine map lookups. `packages/science/science-runtime/tests/harness.ts` adds `authorizeConcurrentRuns`, which appends the one shared `step/start`/`request/header` plus per-language `tool/call` facts that a real assistant step emitting both calls together produces (the existing `authorizeRun` opens a fresh turn per call and does not fit two calls issued together).
