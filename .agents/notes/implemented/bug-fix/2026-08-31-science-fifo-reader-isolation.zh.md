# Agent Note: 将持久 FIFO 读取移出 Host 文件系统线程池

Status: implemented

[English](2026-08-31-science-fifo-reader-isolation.md) | 中文

## 问题

Node 文件流读取空闲 FIFO 时，会一直占用一个 libuv 文件系统 worker，直到有字节到达。四个持久内核会耗尽默认线程池，使无关文件读取、产物捕获、会话持久化和运行收尾无法完成，即使解释器已经执行完毕。

## 决策

每个内核拥有一个 `cat` 子进程，将响应 FIFO 转发至普通子进程 stdout 管道。Host 通过事件循环读取该管道。阻塞式 FIFO 打开和读取由转发进程承担，解释器从未连接时也是如此。转发进程只接收确切的私有 FIFO 路径和空环境，不执行科学代码。启动失败会等待两个进程树退出后移除 FIFO。正常收尾返回两个进程树的有界或最终退出观测，使拥有者保持隔离，直至两个进程树均已确认静止。

[持久内核决策](../architecture/2026-08-20-science-persistent-kernel.zh.md)继续拥有解释器状态、隔离、epoch、协议和取消语义。此处仅改变响应传输的资源归属。

## 考虑过的替代方案

**增大 `UV_THREADPOOL_SIZE`。** 这只是把失败推迟到更多空闲内核时，持久读取仍会与无关 Host 工作争用线程。

**用 `net.Socket` 包装非阻塞 FIFO 描述符。** 本机 macOS 探针能够传输数据且不耗尽线程池，但写端关闭后不发出 EOF。现有异常 EOF 回归拒绝这种协议故障检测能力的丢失。

**把响应移到解释器 stdout。** Python 可以保留并重定向描述符；base R 若不增加运行时机制，就无法将原生 stdout 写入与协议帧隔离。FIFO 保留了不增加解释器依赖、禁止网络的 Python/R 协议。

## 后果

每个存活内核增加一个小型转发进程，并在 POSIX `mkfifo` 之外依赖 `cat`。Host 文件 I/O 不再取决于空闲解释器的数量。通信测试覆盖四个空闲内核、启动失败、协议 EOF、中断和销毁；实机验收在两个会话中同时保留 Python 与 R，执行无关文件读取、完成运行、取消，并证明测试所拥有的进程已清理。可运行的 Science 快照在产物读取和会话持久化期间保留四个内核。
