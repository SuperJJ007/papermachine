# Agent Note: kernel stdin EPIPE handling and honest install-timeout reporting

Status: implemented

English | [中文](2026-09-03-science-kernel-stdin-error-and-install-timeout.zh.md)

## Problem

Real-device acceptance surfaced two `science-runtime` defects. First (9.3), `KernelProcess`'s constructor never attached an `'error'` listener to the spawned kernel's `stdin` pipe. `subprocess-local`'s bare-pipe stdio gives that stream no batch-mode listener of its own, so a write racing kernel teardown — most commonly the EXIT message `performEnd` sends as the process is already exiting — surfaced as an async EPIPE with no listener, which Node turns into an uncaught exception and crashes the Host. Second (8.1), `install_science_packages` bounded a potentially multi-minute micromamba solve by the same generic `timeoutMs` used for ordinary kernel calls; when the deadline fired while `OperationControl.cause` was already `'timeout'`, `runMicromambaInstall` reported `timed-out` even on processes that had in fact exited 0 inside the grace window, and every successful install unconditionally appended a new environment revision and told the model the change "takes effect next run" even when a re-run had installed nothing new — prompting a model that saw a timeout to retry an install that had already landed, restarting the kernel for no reason.

## Decision

`KernelProcess` attaches one `'error'` listener to `this.stdin` for the kernel's lifetime, alongside the existing FIFO listener; both route through a shared `onStreamError(source, error)` that is a no-op once `exitSettled` and otherwise calls `failProtocol` with a `KernelProtocolError` naming the failing stream. `performEnd`'s `catch {}` around its own EXIT write only ever covered a synchronous throw; the async EPIPE this closes is caught by the new listener, not by that block, and the code comment now says so.

`installPackages` reserves its `OperationControl` with a new `installTimeoutMs` config field (default 900_000 ms, max 3_600_000 ms) instead of the shared `timeoutMs` (max 600_000 ms); the desktop overlay sets it to 3_600_000 ms, matching the Host's own provisioning bound for micromamba work. `runMicromambaInstall` now checks for a completed, signal-free, exit-0 process before it checks `control.cause`: a solve that finishes inside the deadline's SIGTERM grace window is `success` even though the control had already latched `'timeout'`; only a process that did not complete successfully is classified `timed-out` or `cancelled` from that cause. After a successful run, `installPackages` re-observes the environment and compares the observation against the currently bound one with a new `sameInstalledBinding` check — `sameObservation`'s existing fingerprint comparison (identity: kind, executable, version) composed with an explicit `packagesSha256` comparison, because `bindingFingerprint` deliberately excludes the packages hash. Nothing changed reports `status: 'success'` against the current revision with no new revision appended; something changed appends a revision as before. Both branches now return an `environmentChanged: boolean` field the model can read, and `tool-science`'s `formatInstallResult` renders "applied … takes effect next run" only when it is true, "unchanged … no kernel restarts" when false, and a new `timed-out` branch tells the model the environment may be partially or fully written, to check state or try importing before deciding, and to retry at most once.

## Alternatives considered

**Wrap every `stdin.write` call in a try/catch instead of a stream listener.** Rejected: `write` failures for a broken pipe surface asynchronously through the `'error'` event, not as a synchronous throw from `write` itself, so a call-site try/catch cannot observe them.

**Classify `timed-out` purely on `control.cause` and leave the redundant-retry problem to prompt guidance.** Rejected: the tool result already had every fact needed to say plainly that nothing changed; steering a retry away by wording alone leaves the previous run's silent success unreported and does not stop the model from restarting the kernel on a hunch.

**Detect no-op installs with `sameObservation` alone.** Rejected after the accompanying test showed it does not detect a packages change: `sameObservation` compares `bindingFingerprint`, whose own JSDoc excludes `packagesSha256` by design (identity is independent of what happens to be installed). Detecting a redundant install requires the packages hash explicitly, alongside the fingerprint's identity check.

**Give `installPackages` its own timeout constant hardcoded in `install.ts`.** Rejected per the no-hardcoded-tunables convention: deployment-varying durations are validated `Config` fields, not source constants; `installTimeoutMs` follows the same `resolveConfig`/`assertKnownKeys` path as `timeoutMs`.

## Consequences

A kernel whose stdin pipe closes during or after teardown no longer crashes the Host; `end()` still resolves and the failure — if any caller was still waiting on a live operation — surfaces through the existing `failProtocol` path instead of an uncaught exception. `install_science_packages` can run for up to an hour before being timed out instead of the shared multi-minute `timeoutMs`, and a run that completes just past a firing deadline is reported as the success it was rather than a false timeout. A model that retries after a genuinely redundant install sees `environmentChanged: false` and no new revision, so a second identical install no longer restarts the kernel; a model that retries after a real timeout is told the environment may already be partially written and to verify before trying again. Three pre-existing fake test harnesses — `science-runtime`'s `ControlledSubprocess.packagesOutput`, the shared Python/R prefix fakes, and headless-agent's `prepareScienceFixture` — returned a static package inventory regardless of what an "install" call did, so tests written against them were unknowingly exercising the redundant-install path; each now conditions its fake output on a marker file the fake installer writes, and the one affected keyless snapshot fixture (`stream-json.expected.jsonl`) was refreshed to match.

## Testing

`kernel-process.spec.ts` adds coverage for a stdin stream error carrying and not carrying a real `Error`, for an EPIPE-shaped stdin error racing `performEnd`'s own EXIT write never becoming an uncaught exception (spied via `process.on('uncaughtException', …)`), and for a stdin error arriving after the kernel already exited being ignored; all 48 tests in the file pass with 100% branch coverage on the changed lines. `install.spec.ts` adds a case where a zero-exit, no-signal settlement lands after the deadline has already set `control.cause` to `'timeout'` and asserts the outcome is still `success`; all 37 tests pass with 100% statement/branch/function/line coverage on `install.ts`. `environment.spec.ts` adds `installTimeoutMs` config-bound coverage (default, min, max, rejection, and independence from `timeoutMs`'s own bound) and splits the `installPackages` success test into a genuinely-changed-inventory case (`environmentChanged: true`, new revision) and a redundant case (`environmentChanged: false`, no new revision); all 84 tests pass. `tool-science.spec.ts` covers both `formatInstallResult` wordings and the new `timed-out` guidance text, and rewrites the install tool's success test to install a package the fake environment did not already have; all 140 tests pass.

## Deferred

`packages/extensions/tool-cordis/src/api-catalog.ts`'s `installPackages` catalog entry text was updated to match the conditional-revision behavior but has no dedicated test coverage in this change; it mirrors the `tool-science` schema already covered by `tool-science.spec.ts`.
