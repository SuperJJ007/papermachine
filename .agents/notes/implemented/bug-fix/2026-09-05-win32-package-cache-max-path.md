# Agent Note: The Windows micromamba package cache stays under MAX_PATH

Status: implemented

English | [中文](2026-09-05-win32-package-cache-max-path.zh.md)

## Problem

The first install of the bundled `general` environment failed on Windows 11 with `LongPathsEnabled=0` at `qt6-main`: `libmamba Error when extracting package: remove_all: The directory is not empty` (reported: [issue #4](https://github.com/SuperJJ007/papermachine/issues/4)). micromamba 2.x lays its package cache out per source host and channel — `<MAMBA_ROOT_PREFIX>/pkgs/https/<mirror host>/<channel path>/win-64/<package>/...` — and this application's default cache root, `<dshHome>/desktop-environments/micromamba/pkgs` (under the per-user `C:\Users\<user>\.papermachine\...`), left the longest such relative path at 285, 301, or 310 characters depending on the mirror, all above Win32's 260-character `MAX_PATH`. The reporter proved the identical `micromamba create` succeeds when `CONDA_PKGS_DIRS=C:\pm` is set instead (312 packages, all health checks pass). The bundled micromamba 2.9.0 exposes no option to flatten the layered cache layout.

A second, independent defect in the same report: `DesktopEnvironmentProvisioner`'s health-check step joined `prefix`, `'bin'`, and `check.executable` unconditionally. On win32-x64 the interpreters live at `<prefix>\python.exe` and `<prefix>\Scripts\Rscript.exe`, not `<prefix>\bin\python`, so even a successful `create` failed at the verifying phase.

## Decision

`resolvePackageCacheDir` (`apps/desktop/src/provisioning.ts`) resolves the package cache directory as a pure function of `{ platform, root, systemDrive }`, and `DesktopEnvironmentProvisioner.provision` passes its result as `CONDA_PKGS_DIRS` in every `create` attempt's environment, alongside the existing `MAMBA_ROOT_PREFIX`. On darwin it returns `<root>/micromamba/pkgs` — the same path micromamba would have derived implicitly, so darwin behavior is unchanged. On win32-x64 it returns `<SystemDrive>\pm\pkgs`, built with `node:path`'s `win32` submodule so the result is deterministic independent of the host OS running the function (tests exercise it on macOS). `systemDrive` comes from `process.env.SystemDrive`, falling back to `C:` only when that variable is absent (Windows sets it by default; an absent value is the one case with no better source of truth). The resolved win32 root is 10 characters, leaving the ~245-character longest known layered relative path safely under `MAX_PATH`. The directory is created with `mkdir(..., { recursive: true })` before the first `create` attempt; a creation failure throws an error naming the path, so onboarding surfaces it verbatim instead of silently falling back to the long default.

This cache directory sits outside `<dshHome>` on Windows. Nothing in this application deletes `<dshHome>/desktop-environments/micromamba` either — no uninstaller or reset path enumerates or removes the provisioner root's contents beyond a single environment prefix during re-provisioning — so this is not a regression in cleanup behavior, only a fact worth recording: the Windows package cache is not reclaimed by anything this application does today. `environment-binding.ts`'s `isWithinProvisionedRoot` is unaffected — it validates only bound environment prefixes (`<dshHome>/desktop-environments/environments/...`), never the package cache, on either platform.

The health-check step now resolves each check's executable through `interpreterLayout(isWindows)`, exported from `apps/desktop/src/interpreter-presence.ts` (previously a private, module-scoped `INTERPRETER_LAYOUT` built from `process.platform`), keyed by `check.language` (`'python' | 'r'`) rather than `check.executable`. `DesktopEnvironmentProvisioner` calls it with `this.options.platform.startsWith('win32-')`, not `process.platform`, so tests exercise the win32 layout on macOS. `qualifyingInterpreters` (`interpreter-presence.ts`) keeps building its own table from `process.platform`, since it runs in `main.ts` against the real host immediately after a real provisioning run completes there. The two call sites now read from one exported function instead of carrying independent copies of the same table, so provisioning's health checks and `qualifyingInterpreters`'s post-bind re-check can no longer name different paths for the same prefix. `EnvironmentHealthCheck.executable` remains a validated declaration field but no longer participates in path construction; it stays as the declarative name of which interpreter a check exercises.

## Alternatives considered

- **Set `LongPathsEnabled` via the Windows registry during install.** Rejected: it requires elevation this per-user, unelevated installer does not have, and depends on a machine-wide policy this application has no business changing for a single package cache.
- **Use the `\\?\` long-path prefix on the cache directory.** Rejected: the reporter's own evidence is that the identical `create` succeeds with a short `CONDA_PKGS_DIRS` and nothing else changed; the `\\?\` prefix is not universally honored by every tool in the micromamba/conda toolchain's own path handling, so it is a less-verified fix than the one already proven on real hardware.
- **A `subst`/junction mapping a short drive letter to the long `<dshHome>` path.** Rejected: it adds a second piece of machine-global state to create, verify, and tear down, for a problem the reporter's own evidence already solves with one environment variable.
- **Ship a newer micromamba with a flatter cache layout.** Rejected for this fix: the bundled 2.9.0 has no such option today (checked `create --help` and `config list`), and pinning to an unreleased or unverified newer version is a larger, independent change with its own risk.

## Consequences

The Windows package cache root is fixed at `<SystemDrive>\pm\pkgs` rather than living under `<dshHome>` like every other piece of this application's state. It is not currently cleaned up by anything, on either platform, which is consistent with existing behavior rather than a new gap. `resolvePackageCacheDir` and the win32 health-check layout are covered by unit tests in `apps/desktop/tests/provisioning.spec.ts` (pure-function resolution for both platforms and the `SystemDrive` fallback, the resolved value reaching `CONDA_PKGS_DIRS`, the loud failure when the directory cannot be created, and the win32 health-check executable paths) using a fake `ProcessRunner`, all runnable and passing on macOS. Windows behavior itself — the actual `micromamba create` succeeding under the new `CONDA_PKGS_DIRS`, and the health checks passing against the real win32 layout — has not been re-verified on real Windows hardware since this change; the reporter's original evidence covers the `CONDA_PKGS_DIRS` mechanism in isolation, not this exact code path.
