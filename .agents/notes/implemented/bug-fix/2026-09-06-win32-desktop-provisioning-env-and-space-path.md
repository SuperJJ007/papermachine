# Agent Note: win32 desktop provisioning gets an ambient environment, and a space-containing Harness home gets a recovery page

Status: implemented

English | [中文](2026-09-06-win32-desktop-provisioning-env-and-space-path.zh.md)

## Problem

A static review of the desktop carrier's Windows changes (range `papermachine/main..main`, `apps/desktop` and related) found two P0-severity gaps neither exercised by any test nor previously reported from a real device.

`buildProvisioningEnv` (`apps/desktop/src/provisioning.ts`) allowlisted only `PATH`/`HOME`/`TMPDIR`/`LANG`/`LC_*`/proxy variables — a purely POSIX-shaped list. On win32, the `micromamba.exe` and health-check interpreter children this application spawns got none of `SystemRoot`, `USERPROFILE`, `APPDATA`, or any other Windows system variable. science-runtime's own `kernel-process.ts` had already hit this exact problem and fixed it with a `WIN32_AMBIENT_ENVIRONMENT_KEYS` allowlist, documenting that a win32 process given none of these cannot initialize Winsock (`WinError 10106`) — a risk for both micromamba's TLS package download and a health-check interpreter's own networking. Desktop provisioning carried no equivalent.

Separately, `boot()`'s very first Harness-home resolution throws `HarnessHomeSpaceError` when the resolved path — by default `<osHomeDir>/.papermachine` — contains an ASCII space, which R's `TMPDIR` probe (science-runtime's `environment.ts` `prepareProbeAttempt`, `kernel-process.ts` `KernelProcess.start`) cannot tolerate. `classifyBootInstallLocationFailure` excluded this error from the recovery-window path entirely, so it rethrew straight into `app.exit(1)`: no window, no message. The page written specifically for this error, `harnessHomeSpaceErrorPage`, had an empty `actions` array and was unreachable from this path — its only caller was the general launch-error page, which a failure in `boot()`'s first resolution never reaches. A Windows account whose home directory contains a space (`C:\Users\John Smith`) hits this on every launch.

A real-device test pass surfaced a third gap in the same area: `micromamba.exe`, packaged under `resources/bin/win32-x64/` and spawned as a standalone child, depends on `vcruntime140.dll`/`msvcp140.dll`. Windows's DLL search order starts from the spawned executable's own directory, not Electron's; a bare Windows host with no Visual C++ Runtime installed fails the spawn with `STATUS_DLL_NOT_FOUND`. This was previously tracked only in a temporary task file under `.agents/tmp/`, deleted once its task completes.

A follow-up acceptance pass on this same change found two more defects in `buildProvisioningEnv` itself, undetected by the tests above because every test used POSIX-shaped keys. First, the allowlist's `PATH` check used exact-string equality (`key === 'PATH'`), but Node preserves Windows's own casing for environment variable keys, and Windows's own PATH variable is named `Path`, not `PATH`. On real Windows this exact match silently found nothing, so the child's `PATH` carried only the `dirname(process.execPath)` prefix from the bullet above and none of the host's own `System32` et al. — a defect present in every win32 build since 0.1.0; `micromamba.exe` and the health-check interpreters survived only via `ComSpec`-qualified or already-absolute paths. Second, the health check ran interpreters straight from the ambient host `PATH`, not the `PATH` the product's own persistent kernel actually uses: `kernel-process.ts`/`execution.ts` build the interpreter's `PATH` from a fixed, ordered set of subdirectories under the environment prefix (`Library\mingw-w64\bin`, `Library\usr\bin`, `Library\bin`, `Scripts`, `bin`), because `Scripts\Rscript.exe`'s conda launcher and R's own DLL resolution depend on `Library\bin` preceding the ambient PATH. A health check run under a different PATH than the kernel's own could pass or fail independently of whether the kernel itself can actually start the interpreter.

## Decision

`buildProvisioningEnv` now takes `{ platform, root }` instead of running from `process.env` alone. On win32 it additionally:

- Carries through a `WIN32_AMBIENT_ENVIRONMENT_KEYS` list (`SystemRoot`, `windir`, `SystemDrive`, `ComSpec`, `PATHEXT`, `USERPROFILE`, `APPDATA`, `LOCALAPPDATA`, `PROGRAMDATA`, `NUMBER_OF_PROCESSORS`, `PROCESSOR_ARCHITECTURE`) — a duplicate of science-runtime's list in `kernel-process.ts`, not an import: this application cannot depend on science-runtime, which runs as a separate Host process staged into the package, not a library this carrier links against. Duplication risks the two drifting apart silently, so `provisioning.spec.ts` reads `kernel-process.ts`'s source text directly (no cross-package import) and asserts the two lists match, following the same pattern already established for `interpreter-presence.ts`'s layout tables against science-runtime's `environment.ts` (see the min-sandbox-enforcement and package-cache notes for that precedent).
- Points `TEMP`/`TMP` at `provisioningScratchTempDir(root)` (`<root>/tmp`, under the provisioner root) rather than forwarding the Host's own ambient temp directory. Neither Python's `tempfile` nor R's `tempdir()` consult `TMPDIR` on win32, so leaving `TEMP`/`TMP` unset falls back to `GetTempPath()`, which resolves to the (non-writable, for a standard user) Windows directory whenever `TEMP`/`TMP`/`USERPROFILE` are all absent — exactly the state this application's own allowlist was creating before this fix. The provisioner root already excludes ASCII spaces (the Harness home it derives from rejects them in `harness-home.ts`), so this scratch directory inherits that guarantee without a second check.
- Prepends `dirname(process.execPath)` (the Electron executable's own directory, which ships `vcruntime140.dll`/`msvcp140.dll` next to the application binary) to the child's `PATH`, so a separately spawned `micromamba.exe` can resolve those DLLs through Windows's own search order even on a bare host with no Visual C++ Runtime installed.

`SECRET_ENV_PATTERN`'s credential strip runs first and is unaffected by any of the above — none of the fixed win32 keys are credential-shaped.

The two follow-up defects are fixed at their own two sites. `buildProvisioningEnv` now finds the ambient `PATH` value with a case-insensitive scan of `source`'s own keys (`key.toUpperCase() === 'PATH'`) instead of the allowlist loop's exact-match lookup, and always writes the result back under the single normalized key `PATH`, never the source key's own casing (`Path`) — libuv treats a Windows child's environment block case-insensitively, so one `PATH` key is sufficient and avoids emitting both `PATH` and `Path` into the same block. Non-win32 platforms are unaffected: the case-insensitive lookup and normalized output key only run inside the existing `win32-` branch. Second, `buildProvisioningEnv` takes a new optional `win32HealthCheckPrefix`; when given, it prepends that prefix's own `WIN32_HEALTH_CHECK_PATH_SUBDIRECTORIES` (a duplicate of `execution.ts`'s `WINDOWS_PATH_SUBDIRECTORIES` — `''`, `Library\mingw-w64\bin`, `Library\usr\bin`, `Library\bin`, `Scripts`, `bin` — joined onto the prefix with `path.win32.join`, for the same cross-package reason `WIN32_AMBIENT_ENVIRONMENT_KEYS` is duplicated rather than imported) to `PATH`, after `dirname(process.execPath)` and before the ambient `PATH`. Only the health-check call site passes `win32HealthCheckPrefix`; the `micromamba create` call site does not, since that child installs into the prefix rather than running from it, and its own dependency on the prefix's not-yet-populated subdirectories would be premature. `provisioning.spec.ts` locks `WIN32_HEALTH_CHECK_PATH_SUBDIRECTORIES` against `execution.ts`'s source text the same way it locks `WIN32_AMBIENT_ENVIRONMENT_KEYS` against `kernel-process.ts`'s.

`classifyBootInstallLocationFailure` (`apps/desktop/src/install-location.ts`) now returns a discriminated `BootInstallLocationFailure` (`{ kind: 'space', error }` or `{ kind: 'unavailable-pointer', target }`) instead of a bare target string. A `HarnessHomeSpaceError` always classifies as `'space'`, regardless of whether a pointer is in effect, and `boot()` routes it to a new `showHarnessHomeSpaceRecoveryWindow` instead of rethrowing. That window's page now offers "Choose another location", running the same directory-picker/validate/pointer-write/relaunch flow as onboarding's `desktop:choose-install-location` (extracted into a shared `runChooseInstallLocationFlow`), reloading the same page with an added rejection reason — rather than losing the original error — when the re-selection is itself unusable (also space-containing, for instance). "Quit" remains available. The fix is deliberately **not** to loosen the ASCII-space restriction itself: that restriction exists because R's `tempdir()`/kernel `TMPDIR` genuinely cannot run from a space-containing path (science-runtime, linked above), not because of anything this carrier's own validation invented — the fix gives the user a way out of a bad default, not a way to keep the bad default working.

The vcruntime DLL gap has no code fix in this change beyond the `PATH` prepend above (unverified on real hardware — see Consequences); it is recorded here so the temporary task file that first found it is not the only place this fact lives.

## Alternatives considered

- **Forward the desktop process's entire `process.env` to provisioning children on win32.** Rejected: `buildProvisioningEnv`'s allowlist exists specifically so a credential exported into the desktop process's own environment cannot leak into installer output relayed verbatim to the renderer; forwarding everything on one platform only would make win32 provisioning strictly less safe than darwin's for no reason tied to the actual Winsock/temp-path problem.
- **Ship `vcruntime140.dll`/`msvcp140.dll` alongside the bundled `micromamba.exe`.** Not chosen for this change: it needs real-hardware confirmation that the `PATH` prepend does not already resolve the DLLs (Electron's own directory reliably ships them, since Electron itself is a native binary with the same dependency), and bundling redistributable DLLs directly is a larger packaging decision than this fix's scope. Recorded as the fallback if device testing shows the `PATH` prepend insufficient.
- **Loosen `requireNoAsciiSpace` to warn instead of reject.** Rejected outright: this is exactly the "reduce a user/model-visible capability without consent" pattern the repository's process rules forbid, and the restriction is not this carrier's own invention to relax — R's kernel and TMPDIR probe reject a space-containing scratch path independent of anything the desktop carrier does.

## Consequences

`provisioning.spec.ts` covers `buildProvisioningEnv`'s win32 additions (ambient keys present/absent, `TEMP`/`TMP` pointing at the scratch directory, `PATH`'s first segment being `dirname(process.execPath)`, credential keys still stripped) and darwin's unchanged behavior, all runnable and passing on macOS (the module's `platform: 'win32-x64'` branch is exercised without a real Windows host). It also covers the two follow-up defects: a win32 source with only a `Path` key (no `PATH`) still produces a `PATH` output carrying that value with `dirname(process.execPath)` first and no leftover `Path` key; the health-check call site's `PATH` carries the prefix's six subdirectories, in `execution.ts`'s order, between `dirname(process.execPath)` and the ambient `PATH`; the `micromamba create` call site's `PATH` carries no prefix subdirectories at all; and an end-to-end `DesktopEnvironmentProvisioner.provision` test asserts the health-check children (`python.exe`, `Scripts\Rscript.exe`) receive that same ordered `PATH` while the `micromamba.exe` create child does not. `install-location.spec.ts` and `error-page.spec.ts` cover `classifyBootInstallLocationFailure`'s new routing and `harnessHomeSpaceErrorPage`'s new action/rejection-reason rendering.

None of this has been verified on real Windows hardware. `.agents/tmp/2026-09-06-windows-followups/windows-device-checklist.md` (temporary; deleted once its task completes) now tracks, in addition to its existing items:

- A Windows account whose home directory contains a space: confirm the recovery page opens (not a silent exit), "Choose another location" works end to end (writes the pointer, relaunches), and re-selecting another space-containing path stays on the page with an updated reason instead of writing the pointer.
- `micromamba create` and the Python/R health checks actually starting under the now-populated ambient environment — this is the next failure point after the fix for the unrelated #20/#11 interpreter-layout defect (see the package-cache Agent Note).
- Whether the `PATH` prepend alone resolves `vcruntime140.dll`/`msvcp140.dll` for a standalone `micromamba.exe` spawn on a bare Windows Server host with no Visual C++ Runtime installed, or whether bundling the DLLs directly (see Alternatives) is still needed.
