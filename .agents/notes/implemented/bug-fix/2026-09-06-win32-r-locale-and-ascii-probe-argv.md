# Agent Note: win32 R locale and non-ASCII probe argv both broke R's UTF-8 lossless-output check

Status: implemented

English | [中文](2026-09-06-win32-r-locale-and-ascii-probe-argv.zh.md)

## Problem

A real Windows Server 2022 run, once [the pre-existing scratch-privacy, probe-ordering, and confinement-forwarding defects](2026-09-06-win32-scratch-privacy-and-probe-ordering.md) were fixed, still reported `bindEnvironment`'s R observation as `invalid` with `"interpreter probes did not produce the required lossless output"`, even though the same box's Python observation succeeded. Two independent, compounding root causes:

1. `CHILD_LOCALES.win32` (`execution.ts`) was the POSIX `C.UTF-8`, shared with linux/aix/etc. Under conda-forge's ucrt R 4.5.3, `LC_ALL=C.UTF-8` does not behave the way it does on POSIX: R's own `l10n_info()$"UTF-8"` reported `FALSE` and its active code page reported `0`. Every non-ASCII byte an R process wrote to stdout came back as a literal `<U+XXXX>` escape sequence instead of UTF-8 — the UTF-8 probe's `enc2utf8(UTF8_PROBE_TEXT)` output never matched `UTF8_PROBE_TEXT` byte-for-byte, so `bindEnvironment` classified R as `invalid` before ever reaching the package-inventory probe. `en_US.UTF-8` does not have this problem: R sets its active code page to `65001` (UTF-8) under it and starts with no locale warning. Confirmed directly with a probe script on the real box, isolating this one variable: `LC_ALL=C.UTF-8` reproduced the `<U+79D1><U+5B66>` escape output; `LC_ALL=en_US.UTF-8` reproduced correct UTF-8 bytes; nothing else in the probe environment changed between the two runs.
2. Independently of the locale, the R and Python UTF-8 probe expressions embedded the literal `"dsh-科学-✓"` string directly in the `-e`/`-c` argv. conda-forge's win32 `Scripts\Rscript.exe` is not R itself — it is a small launcher executable that receives the process's command line and re-forwards it to the real R interpreter through `CreateProcessA`, the ANSI (not wide-character) process-creation API. A non-ASCII byte outside the launcher process's active ANSI code page is corrupted in that re-forwarding step, before R's own parser ever sees the expression; R then reported a re-encoding failure (`invalid multibyte string`/re-encoding error) rather than running the expression at all. Python's probe was never affected by this half of the defect: `python.exe` receives the OS's wide-character (UTF-16) argv directly with no ANSI-forwarding launcher in between, so its literal non-ASCII argv worked regardless of the active code page or locale.

Both defects independently make R's UTF-8 probe fail on win32; fixing only one left the other still blocking `bindEnvironment` from ever reporting R `capability: "available"`.

## Decision

**`CHILD_LOCALES.win32` moves from `POSIX_LOCALE` (`C.UTF-8`) to `'en_US.UTF-8'`**, matching darwin (the only other platform in the table that was already not `C.UTF-8`) instead of the POSIX default every Linux-family entry keeps. This is the one value shared by every confined interpreter spawn — persistent kernels and interpreter probes alike — so the fix reaches both without a separate code path for either.

**Both the R and Python UTF-8 probe expressions replace their literal non-ASCII characters with `\u` escapes** (`"dsh-\u79d1\u5b66-\u2713"` in both R and Python source), so the actual argv bytes a launcher or the OS forwards are pure ASCII regardless of code page or locale; the interpreter itself resolves the escape back to the identical Unicode string once it parses the expression. `UTF8_PROBE_TEXT` (`environment.ts`'s expected decoded value for comparison) stays the literal `'dsh-科学-✓'` unchanged — only the wire representation of the request changes, not the expected response. Python's probe did not strictly need this fix on its own (its argv path is unaffected by the ANSI-launcher defect), but is changed for symmetry: both probes now make the identical claim about their own transport-safety, rather than leaving an asymmetry a future platform or launcher change could silently reintroduce for Python without anyone noticing it was ever a live risk there.

## Alternatives considered

- **Deriving the win32 locale from the ambient system code page instead of a fixed `en_US.UTF-8`.** Rejected: this Runtime's fixed environment allowlist and locale values are deliberately not deployment-varying (`docs/cordis-primer.md`'s "no hardcoded tunables" convention is about configurable *deployment* choices, not this — a locale a spawned interpreter needs to behave correctly is a fixed correctness requirement, the same category `TZ: 'UTC'` already is in the same object). Reading the host's live code page would make correctness depend on an ambient host setting this Runtime does not control and cannot verify at spawn time.
- **`C.UTF-8` itself, kept as the win32 value.** Rejected with direct on-device evidence: win32's C runtime `setlocale` does not accept `C.UTF-8` the way glibc does; requesting it either fails outright or silently falls back to the plain `C` locale, reproducing the exact `<U+XXXX>`-escaping defect this change fixes. There is no win32 locale name that gives POSIX `C.UTF-8`'s "no locale-specific behavior, UTF-8 encoding" semantics; `en_US.UTF-8` is the closest available substitute that a real ucrt R build accepts and behaves correctly under.
- **Escaping only the R probe, leaving Python's literal.** Rejected for the symmetry reason above: Python's argv path happens to be safe today because `python.exe` receives wide-character argv directly, but that safety is a fact about the current win32 Python launcher, not a guarantee this codebase enforces anywhere. Escaping both probes removes the need to reason about which interpreter's launcher is ANSI-forwarding today.
- **Detecting the ANSI-forwarding launcher and working around it (e.g., a wrapper batch file, `chcp 65001` before spawn, or a UTF-8-manifest-based launcher override).** Rejected: none of these are within this Runtime's control (conda-forge ships and controls `Rscript.exe`), and an ASCII-only argv is strictly simpler than any workaround that tries to change how a third-party launcher forwards its command line.

## Consequences

`packages/science/science-runtime/src/**/*.ts` per-file coverage stays at 100%. `execution.spec.ts` adds direct coverage of `localeEnvironment()` on win32 (`en_US.UTF-8`) versus linux (`C.UTF-8`), pinning the platform-specific override rather than only exercising it indirectly through `interpreterPathEnv`'s existing win32 tests. `environment.spec.ts` adds an ASCII-only assertion (`/^[\x00-\x7f]*$/`) over every probe argv element for both the Python and R fake-prefix `bindEnvironment` tests, so a future probe expression that reintroduces a literal non-ASCII character fails a test on any platform, not only on a real win32 run.

Confirmed on the real Windows Server 2022 box:

- `kernel-transport-real.spec.ts`'s Python and R real-driver tests both pass end to end over the real TCP loopback transport (`C:\pm\logs\v5-step2.log`, 2/2 passing) — unaffected by this change, confirming no regression to the already-working persistent-kernel path.
- A full `run-science.mts` profile run (`C:\pm\logs\v5-step3.log`) against real `python.exe`/`Rscript.exe` from a Conda `science` prefix: `bindEnvironment` returns `status: "applied"` with R `capability: "available"` (previously `"invalid"`); a `startRun` of `cat(enc2utf8("dsh-科学-✓"),sep="")` returned stdout hex `6473682de7a791e5ada62de29c93`, matching the expected `64 73 68 2d e7 a7 91 e5 ad a6 2d e2 9c 93` exactly (`"dsh-"` + `科学` (`e7 a7 91 e5 ad a6`) + `"-"` + `✓` (`e2 9c 93`)); Python and R each held same-kernel state across two runs on one `kernelEpoch` (Python: `x = 4321` then `print(x)` → `"4321\n"`; R: `y <- 1234` then `cat(y)` → `"1234"`); a 60-second `time.sleep` cancelled after 2 seconds classified `cancelled`; a run after that cancellation succeeded on a fresh `kernelEpoch`.
- A standalone `run-science-py.mts` run (`C:\pm\logs\v5-step3-py.log`) exercised the identical `startRun` sequence Python-only, confirming the same result independent of R's presence in the profile.

`packages/science/science-runtime/README.md`/`README.zh.md`'s "win32 kernel execution is unverified on a real Windows host" Known Limitation is retired: R's `bindEnvironment` probe path now has the same real-hardware confirmation Python's already had.
