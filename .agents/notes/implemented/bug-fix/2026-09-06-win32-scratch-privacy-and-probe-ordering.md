# Agent Note: Pre-existing defects blocked every win32 Science kernel before it could spawn

Status: implemented

English | [中文](2026-09-06-win32-scratch-privacy-and-probe-ordering.zh.md)

## Problem

[The win32 kernel response-transport change](../feature/2026-09-05-win32-kernel-response-transport.md) and [the `minimumEnforcement` change](../architecture/2026-09-05-science-runtime-minimum-sandbox-enforcement.md) made a win32 Science kernel spawn reachable in principle, but a real-Windows-box verification run showed the new code never gets that far: several pre-existing defects, none of them touched by either prior change, stopped every session, probe, and kernel scratch operation before a kernel process could even start.

1. `scratch.ts`'s `privateDirectory()` required `(entry.mode & 0o077) === 0` on every managed directory. Node's win32 `lstat` reports synthetic mode bits that never reflect a prior `chmod`: a freshly created, `chmod(0o700)`'d directory reports `0o666`/`0o777` regardless. This made `ensureSessionScratch` — and therefore every session, probe, and kernel scratch operation — throw `... is not private` unconditionally on win32.
2. `environment.ts`'s `prepareProbeAttempt` planned an interpreter probe's private directory (`planProbeScratch`) and confined it (`sandbox.confine()`, via `confineProbe`) before `createProbeScratch` ever created that directory on disk — confinement ran, at the earliest, before even the owning Session scratch tree existed (`prepareSessionScratch` runs only after every `prepareObservation` call settles). POSIX sandbox backends tolerate confining a workspace root that does not yet exist; the real win32 ACL backend does not — `materializeAclGrant` (`sandbox-local/src/index.ts`) calls `assertPrefixReadOnly`'s sibling `assertTempRootOutsideWorkspace` (`sandbox-windows-acl/src/path-boundary.ts`), which `realpathSync.native`s the workspace root, then adds an ACE to it — both steps need the directory to exist. The observed failure was `ENOENT ... realpath '...\probes\<uuid>'` out of `bindEnvironment`. The persistent-kernel spawn path was unaffected: its policy root is the already-created session scratch root (`execution.ts`), not a not-yet-created probe directory.
3. `kernel-transport-real.spec.ts`'s `resolveRealInterpreter`/`resolveOnPath` were POSIX-only test-harness code: a hardcoded `join(prefix, 'bin', 'python3' | 'Rscript')` executable guess, `PATH` split on `:`, and no `.exe` handling. On win32 this test can never find a real interpreter to run its real-driver assertions against, regardless of whether defects 1 and 2 are fixed.

A real-Windows verification run of the fix for defect 1 surfaced a fourth, symmetric instance of the same root cause: `scratch.ts`'s `privateFile()` carries the identical `(entry.mode & 0o077) === 0` check for a managed regular file (the owner marker JSON, a run's persisted source), and Node's win32 `lstat` synthesizes mode bits for regular files the same way it does for directories. This tripped `scratch.spec.ts` tests on the real box with `... is not private` where a test expected an unrelated, deliberately-injected failure — a collateral failure masking each test's actual scenario, not a defect in the scenario itself.

Fixing defects 1 and 4 exposed a fifth, previously-masked blocker at the same real-box run: `scratch.ts`'s `syncDirectory()` opens a directory read-only and calls `handle.sync()` after every durable managed-file write (the owner marker, a run's persisted source, an artifact input) — a fsync-the-parent-directory step for crash durability. Windows has no equivalent: an `O_RDONLY`-opened directory handle's `sync()` fails there with `EPERM`. This is not novel to this codebase — `dsh-storage-json`'s `fsyncDirectory` and `dsh-session-persistence-jsonl` already document and no-op the identical Windows limitation — but `scratch.ts`'s own `syncDirectory` had not yet been brought in line with that precedent, and this was the single most common failure across the real-box test run (99 of ~320 test failures shared this one `EPERM` root cause) once defects 1 and 4 stopped masking it.

Fixing defects 1, 4, and 5 exposed a sixth blocker at the same real-box run, in a different piece of test scaffolding: `harness.ts`'s `createFakeSandboxRunner()` wrote a `#!/bin/sh` no-policy passthrough runner for `LocalSandboxProvider`'s `runnerCommand`, relying on the OS interpreting the shebang line directly and on `exec "$@"` replacing the wrapper's own process image so the tracked pid became the real interpreter directly. Windows has no POSIX shell to interpret a shebang script, so every test sharing this fixture (`kernel-process.spec.ts`, `kernel-set.spec.ts`, `run.spec.ts`, `loader-composition.spec.ts`, and `kernel-transport-real.spec.ts` itself) failed near-instantly with `science-runtime: kernel process exited before connecting to its response channel` — 64 of 306 failures on the run that first exercised defects 1/4/5's fixes, including the two failures blocking `kernel-transport-real.spec.ts`'s real Python/R driver test that defect 3's fix specifically targeted.

A real-Windows run of `kernel-transport-real.spec.ts` after defects 1–6 were fixed exposed a seventh, narrower blocker: the real driver now spawns, runs user code, and replies over the real TCP loopback transport correctly, but its captured stdout carries `\r\n` where every assertion (and every POSIX run) expects a bare `\n` — `AssertionError: expected 'dsh-tcp-transport-ok\r\n' to be 'dsh-tcp-transport-ok\n'`. Both drivers open `stdoutPath`/`stderrPath` in a mode that performs win32's default LF-to-CRLF translation on write: Python's `execute_run()` used `os.open(stdout_path, os.O_WRONLY | os.O_CREAT | os.O_TRUNC, 0o644)` (no `os.O_BINARY`) plus `rebind_std_streams()`'s `os.fdopen(1, "w", encoding="utf-8", closefd=False)` (no `newline=` override, so Python's own universal-newlines write translation also applies); R's `execute_run` opened both capture files as `file(stdout_path, open = "wt")`. `kernel_python.py`'s own `open_response_channel()` already handles the identical win32 translation correctly for its TCP response channel (`sock.makefile("w", encoding="utf-8", newline="\n")`) — the capture-file path was simply never brought in line with that existing precedent in the same file. Because `readCaptureTail` (`execution.ts`) copies `stdoutPath`/`stderrPath` bytes verbatim into the model-visible run output with no newline normalization, this is not a test-only quirk: identical user code produces different, session-logged output bytes depending on the host platform.

A real-Windows run of `startRun` after defect 7's fix exposed an eighth blocker, once more a real-box confirmation of a fact the transport and `minimumEnforcement` work already on `main` had not fully wired through: `bindEnvironment` accepted a `'partial'`-reporting `sandbox-windows-acl` provider — `confineProbe` (`environment.ts`) already threaded the configured `minimumEnforcement` through to interpreter-probe confinement — but `KernelProcess.start`'s own confinement call still defaulted to `'full'`, because `science-runtime`'s configured `minimumEnforcement` was never forwarded through `KernelSetOptions` into `KernelProcessOptions`. Every `startRun` on a `'partial'`-configured win32 deployment therefore failed at kernel spawn with `CONFINEMENT_UNAVAILABLE` immediately after `bindEnvironment` had already succeeded against the identical sandbox — the same asymmetry between probe and kernel-spawn confinement the `minimumEnforcement` feature's own Known Limitations section had already named as future work before this real-box run made it concrete.

## Decision

**`syncDirectory()` is a no-op on win32.** It follows the exact existing convention (`if (process.platform === 'win32') return`, `/* v8 ignore start/stop */` around the POSIX-only body) already established in `dsh-storage-json`'s `fsyncDirectory` and `dsh-session-persistence-jsonl`, rather than inventing a new pattern for the same platform gap. Scratch bookkeeping's directory-entry durability is unguaranteed on win32 as a result — an accepted, documented trade-off, not a regression: it matches every other package in this codebase that already made the identical call for the identical reason, and it never touches the Session log's own durability, which is unaffected.

**`privateDirectory()` and `privateFile()` both skip the POSIX mode-bit check on win32, keeping their directory/file/symlink kind checks.** Both read `process.platform` directly, the same way `syncDirectory()` does; `scratch.spec.ts` exercises both branches of each by mocking the process-global `process.platform`. Privacy on win32 does not come from POSIX mode bits at all — it comes from the user-profile ACL a Harness home inherits, plus the ACL sandbox's own per-session SIDs (`dsh-sandbox-windows-acl`), neither of which either check ever observed even before this change. `packages/science/science-runtime/README.md`/`README.zh.md` state this explicitly next to the existing mode-0700/mode-0600 description.

**Probe confinement moves from planning time to directory-creation time.** `prepareProbeAttempt` now only plans a probe's directory and builds its three plain, unconfined argv arrays (`version`/`utf8`/`packages`); it confines nothing. `observePrepared` confines all three (`confineProbeAttempt`, in the same fixed version/utf8/packages order the old code confined them in, preserving every test that counts or orders `confine()` calls) immediately after `createProbeScratch` materializes that attempt's directory, and before running any of the three probes. This is symmetric across every platform — no win32-only branch — because a real win32 ACL sandbox is not the only thing that benefits from a policy's `workspaceRoot` actually existing at confinement time; POSIX backends merely tolerated the old, weaker ordering. The existing per-attempt `try`/`finally` around `createProbeScratch`'s directory (`removeProbeScratch`) already covered a probe-run failure; moving confinement inside that same `try` block means a confinement failure (`CONFINEMENT_UNAVAILABLE`, a mocked `SandboxUnavailableError`, or any other `confine()` throw) is caught by the same `finally` and the just-created probe directory is removed exactly as before — no new leak path, and this exact property is pinned by a new test whose fake sandbox's `confine()` asserts `existsSync(policy.workspaceRoot)`.

One second-order consequence follows directly from the reordering and is accepted, not a defect: previously, a probe confinement failure happened during `prepareObservation`, strictly before `prepareSessionScratch` ever ran, so the owning Session's on-disk tree was never created at all. Now that confinement happens inside `observePrepared`, which always runs after `prepareSessionScratch`, a confinement failure rolls back an owning Session tree that was actually created (`rollbackSessionScratch`, already-existing machinery) rather than leaving nothing on disk. `environment.spec.ts`'s two affected assertions (`sandbox` reporting `'partial'` below the configured minimum; a mocked `SandboxUnavailableError`) were updated to check that this exact Session's scratch root and marker are gone, the same assertion shape the pre-existing "rolls back newly owned Session scratch when a retry cannot obtain full confinement" test in `environment.spec.ts` already used for a confinement failure that (even before this change) happened after `prepareSessionScratch`.

**The real-driver test's interpreter discovery now matches the product's own resolution.** `environment.ts`'s `executableCandidate` (the per-platform `EXECUTABLE_LAYOUTS` lookup every static and probe check already used) is exported so `kernel-transport-real.spec.ts` can locate a bound prefix's interpreter the same way `bindEnvironment` does, instead of a hardcoded POSIX-only guess. `resolveOnPath` now splits `PATH` with `node:path`'s `delimiter` and appends `.exe` to the bare command name on win32. `canonicalPrefix` derivation for a PATH-resolved fallback interpreter (used when no `environment-binding.json` prefix exists) walks upward from the resolved executable to the nearest ancestor directory carrying `conda-meta/history`, rather than assuming a fixed number of path segments — this is robust to a Conda R build placing `Rscript.exe` at `Lib\R\bin\x64\Rscript.exe` instead of `WINDOWS_LAYOUT`'s own `Scripts\Rscript.exe`, without needing to special-case that alternate location: a bound prefix whose `executableCandidate` guess misses falls through to this same PATH-based resolution, which finds the real file and derives the correct Conda prefix regardless of how deep under it that file sits.

**`createFakeSandboxRunner()` forwards through Node itself instead of a POSIX shell script.** It now writes a small `.mjs` script and returns `[process.execPath, thatScript]` as a full `runnerCommand` argv (`sandbox-local` spawns `argv[0]` directly with `argv[1..]` as fixed prefix args), so it works identically on every platform without depending on a shell to interpret a shebang line. Because a Node `spawn()` — unlike `exec` — keeps the wrapper script's own process alive as the real interpreter's parent rather than replacing it, `KernelProcess.interrupt()` (which signals only the direct child, by design, never the tree — `subprocess-local`'s `spawn.ts`) now reaches only the wrapper; the wrapper forwards SIGINT to its own child and, by registering a handler at all, suppresses Node's default terminate-on-SIGINT, which would otherwise kill the wrapper before the interpreter's own graceful-interrupt reply and misreport a real interrupt as an abnormal crash. All six `runnerCommand` call sites (a bare array literal in five files, two string-templated `cordis.yml` generators in `loader-composition.spec.ts`) were updated for the new two-element argv.

**Both drivers write run capture files in a mode that performs no line-ending translation.** `kernel_python.py` adds `getattr(os, "O_BINARY", 0)` (a win32-only flag, harmlessly `0` elsewhere) to both `os.open()` calls in `execute_run()`, and `rebind_std_streams()`'s two `os.fdopen()` calls add `newline="\n"`, matching `open_response_channel`'s already-correct TCP wrapper — both layers are fixed together because either one alone can independently reintroduce the translation (the CRT-level text mode on the raw fd, and Python's own io-layer universal-newlines substitution downstream of it). `kernel_r.R`'s `execute_run` opens both capture connections as `"wb"` instead of `"wt"`; `sink()` writes character data through either mode identically, so binary mode only removes the newline translation, matching darwin/linux exactly. No platform branch was needed in R, the same way `getattr`'s POSIX no-op means Python needed none either.

**`minimumEnforcement` is forwarded from `ScienceRuntime` through `KernelSetOptions` into `KernelProcessOptions`, the same path `assetsRoot`/`kernelIdleTimeoutMs`/`kernelStartTimeoutMs` already take.** `KernelProcess.start` passes it to `confineWithEnforcement` (`execution.ts`); the field is required at every layer (`KernelSetOptions`, `KernelProcessOptions`, `confineInterpreterArgv`'s own parameter) rather than optional with a `'full'` default, so a caller cannot silently reach kernel-spawn confinement with no configured minimum. No new option name or forwarding pattern: this closes the one remaining gap between probe confinement (already fully wired) and kernel-spawn confinement (previously wired only as far as `KernelProcess.start`'s own parameter, never actually supplied by its one production caller, `KernelSet`). `kernel-process.spec.ts` covers `KernelProcess.start`'s own parameter directly; `kernel-set.spec.ts`'s `minimumEnforcement forwarding` tests cover the two lines that actually thread `KernelSet`'s configured value into it (`spawnKernel`'s `acquire()` path and `startIsolated`), each proven load-bearing by deleting the forwarding line and confirming the corresponding test turns red; `run.spec.ts` adds one end-to-end case — a `Config.minimumEnforcement: 'partial'` runtime, a partial-reporting sandbox, a real `startRun` kernel spawn — covering the same threading through `ScienceRuntime` itself, not only through a directly constructed `KernelSet`.

## Alternatives considered

- **Also relaxing the Windows chmod-based permission-simulation tests the real box's full suite still fails on (e.g., `chmodSync(dir, 0o000)` to simulate `EACCES`, `run.spec.ts`'s cleanup-failure aggregation tests).** Rejected: these are pre-existing POSIX-only test-harness assumptions unrelated to this change's six root causes — Windows does not restrict directory traversal through POSIX mode bits at all, so a `chmodSync(..., 0o000)`-based simulation has no Windows equivalent to port to, the same category of out-of-scope harness limitation as `harness.ts`'s other `#!/bin/sh` fake-interpreter scripts (`createFakePythonPrefix`/`createFakeRPrefix`), which stay unported: unlike `createFakeSandboxRunner`'s single no-policy passthrough, porting every language-specific fake driver script to Node is a substantially larger, separate undertaking this change does not attempt.
- **Leaving `privateFile()`'s identical `0o077` check untouched until a separate, later change.** Rejected once the real-Windows run produced direct evidence: `privateFile()` fires on the same win32 synthetic-mode-bits fact as `privateDirectory()`, on the same call paths (`ensureOwner`, `rollbackSessionScratch`) that Fix 1 already exists to unblock — deferring it would leave marker-file writes broken on win32 for no reason beyond artificial separation of an already-diagnosed, single-root-cause defect.
- **A win32-only branch inside `prepareProbeAttempt`/`observePrepared` instead of unconditionally moving confinement after directory creation.** Rejected: POSIX backends have no correctness reason to confine before the directory exists either — the old ordering only ever worked because POSIX backends happened to tolerate it, not because it was the right order. One order for every platform is simpler and removes a platform-conditional that would otherwise need its own test matrix.
- **Deriving the real-driver test's `canonicalPrefix` from `EXECUTABLE_LAYOUTS`' fixed segment count (e.g., always two `dirname()` calls up from `Rscript.exe` on win32).** Rejected: a real Conda-forge R build's actual on-disk depth (`Lib\R\bin\x64\Rscript.exe`, three segments) does not match `WINDOWS_LAYOUT`'s own two-segment assumption (`Scripts\Rscript.exe`), so a fixed segment count derives the wrong prefix for exactly the machine this test needs to run on. Walking up to the nearest `conda-meta/history` is correct for any depth and matches how `staticInterpreter` itself already recognizes a Conda prefix.
- **Leaving the win32 CRLF capture difference as an accepted platform quirk instead of fixing it.** Rejected: `readCaptureTail` copies `stdoutPath`/`stderrPath` bytes verbatim into the session-logged, model-visible run output, so this is not a cosmetic terminal-rendering detail — it is identical user code producing different logged bytes depending on host platform, the exact asymmetry the model-visible-input logging convention exists to prevent. The fix is a narrow, two-file change with an existing same-file precedent (`open_response_channel`'s own `newline="\n"` TCP wrapper), not a speculative platform accommodation.

## Consequences

`ensureSessionScratch`, `bindEnvironment`'s probe path, and `KernelProcess.start()`'s confinement now proceed on win32 instead of failing before any scratch or process work — the pre-existing blockers a real Windows Server 2022 verification run found once the transport and `minimumEnforcement` work already on `main` stopped being the limiting factor. `packages/science/science-runtime/src/**/*.ts` per-file coverage stays at 100% (new tests: `scratch.spec.ts` exercises both the POSIX-mode-bit-rejected and win32-mode-bit-skipped branches of both `privateDirectory()` and `privateFile()` against the same real, wrongly-permissioned directory or file; `environment.spec.ts` adds a fake sandbox whose `confine()` asserts its `workspaceRoot` already exists, proving the new ordering directly rather than only by absence of failure). Every `kernel-transport-real.spec.ts` assertion about self-skipping without a usable interpreter is unchanged; only how it locates one changed.

`syncDirectory()` follows the exact `v8 ignore`-exempted pattern `dsh-storage-json`'s `fsyncDirectory` already uses: POSIX coverage of the unconditional-fsync branch (exercised throughout `scratch.spec.ts`) is the same coverage evidence that precedent relies on, and the win32 no-op branch is untestable from a POSIX CI host for the same reason that precedent's `v8 ignore` comment states.

The six `createFakeSandboxRunner()` call sites' existing scenarios exercise it on POSIX, including the SIGINT-forwarding path (`kernel-process.spec.ts`, `run.spec.ts`).

The capture-mode fix in `kernel_python.py`/`kernel_r.R` touches Python/R asset files with no `.ts` coverage surface; POSIX runs of `kernel-transport-real.spec.ts` and every other real-driver test exercise the changed code paths unchanged (the added flags are win32-only or no-ops on darwin/linux), and the win32-specific bytes this fix corrects are observable only from a real Windows-box run of that same spec.

`KernelProcess.start`'s own confinement has the same acceptance-matrix coverage `confineWithEnforcement`'s own suite already gave probe confinement, via the two `kernel-process.spec.ts` cases above. `KernelSet`'s forwarding of that value — the actual defect this Note documents — has its own coverage one layer up: `kernel-set.spec.ts`'s `minimumEnforcement forwarding` tests spawn a real kernel through both `acquire()` and `startIsolated()` against a partial-reporting sandbox, and `run.spec.ts` adds an end-to-end case through `ScienceRuntime.startRun`.

Confirmed on the real Windows Server 2022 box (`C:\pm\logs\v3-step1-final.log` / `C:\pm\logs\v3-step2.log`): after defects 1–6's fixes, `kernel-transport-real.spec.ts`'s Python and R real-driver tests both spawned, ran user code, and replied over the real TCP loopback transport end-to-end, failing only on defect 7's `\r\n`-vs-`\n` stdout mismatch — direct, real-box evidence that defects 1–6 are fully resolved and defect 7 was the single remaining blocker for that spec. Defect 7's own fix (`getattr(os, "O_BINARY", 0)` plus `newline="\n"` in `kernel_python.py`; `"wb"` in `kernel_r.R`) is now also confirmed on the real box: `C:\pm\logs\v4-step2.log` shows `kernel-transport-real.spec.ts`'s Python and R real-driver tests both passing end to end, with no `\r\n` mismatch. Defect 8's fix (`minimumEnforcement` threading) is confirmed end to end on the real box, per [the win32 R locale and probe-argv Agent Note](2026-09-06-win32-r-locale-and-ascii-probe-argv.md): a full `run-science.mts` profile run (`C:\pm\logs\v5-step3.log`) against real `python.exe`/`Rscript.exe` held same-kernel state across two runs on one `kernelEpoch`, cancelled a 60-second run after 2 seconds, and succeeded on a fresh `kernelEpoch` afterward.
