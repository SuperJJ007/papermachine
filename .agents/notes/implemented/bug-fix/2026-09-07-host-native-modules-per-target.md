# Agent Note: package the Host closure with each target's own sharp/koffi native modules

Status: implemented

English | [中文](2026-09-07-host-native-modules-per-target.zh.md)

## Problem

Several Host plugins load a native module at import time: `dsh-attachment-local` imports `sharp` at its top level; `dsh-subprocess-local`'s `windows-inspector.ts` and `dsh-sandbox-windows-acl` both import `koffi` at their top level; `fs-local`, `session-persistence-jsonl`, and `directory-picker-native` import `koffi` dynamically. Any one of these missing at runtime makes the Host process exit before printing its readiness line, which the carrier reports as "Science Host needs attention" — a Restart Host action repeats the same crash every time, since nothing about the packaged closure changes between attempts.

`sharp` and `koffi` both ship their native binaries as per-platform npm `optionalDependencies` (`@img/sharp-<os>-<arch>`, `@img/sharp-libvips-<os>-<arch>`, `@koromix/koffi-<os>-<arch>`). By default pnpm installs only the running machine's own variant of each. `apps/desktop/scripts/stage-host.ts` deploys the Host closure with `pnpm deploy --prod --offline` from this workspace's own `node_modules`, so the closure it produces can only ever contain whichever variants that one `pnpm install` happened to fetch:

- An x64 DMG built on an arm64 mac carried only `sharp-darwin-arm64`/`koffi-darwin-arm64`. Confirmed by running, inside `release/mac/PaperMachine.app/Contents/Resources/host` on a real x64-built app: `ELECTRON_RUN_AS_NODE=1 arch -x86_64 ../../MacOS/PaperMachine --input-type=module -e "await import('sharp'); await import('koffi')"` — both failed (`Could not load the sharp module using the darwin-x64 runtime` / `Cannot find the native Koffi module`); the same command against an arm64-built app succeeded. This means the already-published `papermachine-v0.1.0` `PaperMachine-0.1.0-x64.dmg` (5 downloads at the time this was found) crashes its Host on every real Intel Mac.
- A Windows package cross-built on a mac carries the mac's own darwin-arm64 variants under a win32 app, for the same reason — this is what a real-device smoke test on a Windows cloud box hit (`.agents/tmp/2026-09-06-windows-review/shots/host.log`). A Windows package built natively on `windows-latest` is unaffected, since that runner's own `pnpm install` only ever fetches win32-x64 variants in the first place.

`pnpm-lock.yaml` already lists every platform variant (`@img/sharp-win32-x64@0.35.3`, `@img/sharp-darwin-x64`, `@img/sharp-libvips-darwin-x64@1.3.2`, `@koromix/koffi-win32-x64@3.1.1`, `@koromix/koffi-darwin-x64@3.1.1`, and more) — the lockfile already resolved every variant the workspace's dependency graph could need, so making the install actually fetch all of them for the desktop packaging targets changes no dependency resolution, only which optional variants a given install call downloads.

## Decision

`pnpm-workspace.yaml` gains a `supportedArchitectures` block naming every desktop packaging target's os/cpu (`darwin`, `win32`, `linux`; `x64`, `arm64`) plus `libc: [glibc]` (`linux` covers CI and Linux development machines, independent of desktop packaging; `musl` is not a packaging target and is left out). This makes every `pnpm install` fetch every desktop target's `sharp`/`koffi` variant regardless of which machine runs it, at the cost of downloading platform variants a single machine will never load — not just for sharp/koffi, but for every other optional-native-module package in the workspace (esbuild, oxlint, rolldown, the Claude/Codex agent SDKs, workerd, and others each ship the same per-platform-optionalDependency pattern). `pnpm install --frozen-lockfile` still passes and the lockfile is unchanged, since `supportedArchitectures` only steers which optional variants a given install fetches, not dependency resolution.

`apps/desktop/scripts/native-module-targets.mjs` is a new, framework-independent pure module holding the classification and selection logic both packaging steps below share: `parseNativeModuleEntry` recognizes a `node_modules/@img` or `@koromix` directory name as one of the `sharp-libvips`, `sharp`, or `koffi` families plus its `(os, arch)`, or reports it as unrecognized (for example `@img/colour`); `selectNativeModuleTargets(target, entries)` splits a scope's entries into what a `target` keeps and what it can discard, and throws if a family present anywhere in `entries` has no entry matching `target` exactly, unless a fixed `FAMILY_NOT_SHIPPED_FOR_OS` list exempts that family for `target`'s `os` (currently only `sharp-libvips`/`win32`: `sharp`'s win32 build folds `libvips` in, so no `@img/sharp-libvips-win32-*` package exists at any version). This exemption list is fixed domain knowledge, not inferred from which `os` values happen to appear among `entries` — an os-inferred version of this check shipped first and was caught by this same change's own `stage:host` run against this machine's real, partially-broken install (see Consequences): inferring "does this family ship for this os" from "does any entry of this family name this os" cannot distinguish that fact from "every entry of this family for this os failed to install", and a totally missing target must fail exactly as loud as a partially missing one. This file is plain JavaScript with JSDoc types, not TypeScript: electron-builder's `afterPack` hook loads it directly through Node's ESM loader, never through `tsx`, and `vitest` also loads plain `.mjs` directly, so one file serves both the packaging hook and its unit tests (`apps/desktop/tests/native-module-targets.spec.ts`) without a duplicate implementation. A hand-written `native-module-targets.d.mts` companion gives `stage-host.ts` (a `.ts` file) a typed import: TypeScript's `bundler` module resolution matches a `.mjs` specifier only against a `.d.mts` file of the same basename, never a `.d.ts` one — confirmed in this change by a minimal reproduction (a `.d.ts` companion left the import an implicit `any` with `TS7016`; renaming it to `.d.mts` resolved cleanly).

`stage-host.ts` calls `selectNativeModuleTargets` once per `DESKTOP_PLATFORMS` entry right after deploying and de-symlinking the closure, discarding the `keep`/`remove` result and relying only on the throw: if any of the three desktop targets' sharp or koffi variant is missing from the freshly staged `@img`/`@koromix` scopes, staging fails loud, naming the fix (add `supportedArchitectures` covering every desktop target, then reinstall) rather than silently producing a closure that can only start on some targets. `after-pack.mjs`'s existing `node_modules`-copy step (already required because electron-builder drops `node_modules` from a plain `extraResources` copy) now also calls `pruneNativeModules`, which reads `Arch[context.arch]` from `electron-builder`'s own exported `Arch` enum (`Arch.x64 === 1`, `Arch.arm64 === 3` — confirmed by importing it directly in this change rather than hardcoding the enum's numeric values) and `context.electronPlatformName` (`darwin`/`win32`, which already matches this module's own `os` naming) to compute this specific build's `{os, arch}` target, then deletes every `@img`/`@koromix` directory `selectNativeModuleTargets` returns in `remove`. A packaged app therefore always ships exactly one variant per native module family — the one it can actually load — regardless of which machine or target `electron-builder` is packaging for.

`electron-builder.yml`'s `mac`/`win` `extraResources` entries for `resources/bin` (unrelated `micromamba` binaries, from the 2026-09-07 app-local-CRT change) are untouched by this change — only the Host closure's `node_modules` is pruned here.

## Alternatives considered

- **Package only on each target's own native runner** (build the Windows installer exclusively on `windows-latest`, never cross-build on a mac). Rejected: this would still leave the Intel-mac DMG bug unfixed (an arm64 mac building an x64 DMG is not a cross-OS build, so a "native runner per OS" rule does nothing for it), and it gives up mac-side cross-building entirely rather than fixing the actual defect.
- **electron-builder's `npmRebuild`/`nodeGypRebuild`.** Rejected: both operate on the app's own `node_modules` before asar packaging, not on `extraResources` — the Host closure staged into `resources/host` by `stage-host.ts`/`after-pack.mjs` is invisible to either option.
- **Make sharp/koffi optional at runtime (catch the import failure, degrade the feature).** Rejected outright without investigation: this is a functionality reduction a plugin's users would notice (attachment thumbnailing, Windows subprocess control, or Windows ACL sandboxing silently stops working), and this repository's standing rule is that any user- or model-visible functionality reduction needs the user's explicit agreement first, never a quiet "known limitation."

## Consequences

`apps/desktop/tests/native-module-targets.spec.ts` unit-tests `parseNativeModuleEntry` (each known family, an unrecognized name, and a family-prefixed name with an invalid remainder) and `selectNativeModuleTargets` (correct keep/remove for each of `darwin-arm64`, `darwin-x64`, and `win32-x64`; an unknown directory name left untouched regardless of target; throwing when a family ships for the target's `os` but not its `arch`; throwing when EVERY entry of a required family for the target's `os` is missing, not only some — the case the entries-inferred exemption first missed; not throwing when a family is exempted for the target's `os` — including when that family's entries for a different `os` are present in the same list — covering win32's missing `sharp-libvips` case).

The entries-inferred version of the exemption was caught, not by review, but by actually running this change's own new assertion against a real environment: `pnpm --filter @deepseek-ai/dsh-desktop run stage:host` against this machine's install — every darwin sharp/koffi variant present, `@img/sharp-win32-x64@0.35.3` genuinely missing (undownloadable over this machine's network; see this task's own results section) — exited 0 instead of failing loud, because no entry in `@img`'s listing named `os: 'win32'` at all, which the entries-inferred check read as "sharp doesn't ship for win32" rather than "sharp's win32 entry is missing". Fixed and re-run: the same command now exits 1 with `desktop host staging: @img is missing the win32-x64 native module variant a packaged Host for that target needs (no sharp-win32-x64 entry for the win32-x64 packaging target (no sharp entry for win32 at all))`.

See this task's own results section for the exact verification commands run, their output, and the packaged installer's SHA-256/size.
