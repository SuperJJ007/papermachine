# Agent Note: package the Host closure with each target's own sharp/koffi native modules

Status: implemented

English | [中文](2026-09-07-host-native-modules-per-target.zh.md)

## Problem

Several Host plugins load a native module at import time: `dsh-attachment-local` imports `sharp` at its top level; `dsh-subprocess-local`'s `windows-inspector.ts` and `dsh-sandbox-windows-acl` both import `koffi` at their top level; `fs-local`, `session-persistence-jsonl`, and `directory-picker-native` import `koffi` dynamically. Any one of these missing at runtime makes the Host process exit before printing its readiness line, which the carrier reports as "Science Host needs attention" — a Restart Host action repeats the same crash every time, since nothing about the packaged closure changes between attempts.

`sharp` and `koffi` both ship their native binaries as per-platform npm `optionalDependencies` (`@img/sharp-<os>-<arch>`, `@img/sharp-libvips-<os>-<arch>`, `@koromix/koffi-<os>-<arch>`). By default pnpm installs only the running machine's own variant of each. `apps/desktop/scripts/stage-host.ts` deploys the Host closure with `pnpm deploy --prod --offline` from this workspace's own `node_modules`, so the closure it produces can only ever contain whichever variants that one `pnpm install` happened to fetch:

- An x64 DMG built on an arm64 mac carried only `sharp-darwin-arm64`/`koffi-darwin-arm64`. Confirmed by running, inside `release/mac/PaperMachine.app/Contents/Resources/host` on a real x64-built app: `ELECTRON_RUN_AS_NODE=1 arch -x86_64 ../../MacOS/PaperMachine --input-type=module -e "await import('sharp'); await import('koffi')"` — both failed (`Could not load the sharp module using the darwin-x64 runtime` / `Cannot find the native Koffi module`); the same command against an arm64-built app succeeded. This means the already-published `papermachine-v0.1.0` `PaperMachine-0.1.0-x64.dmg` (5 downloads at the time this was found) crashes its Host on every real Intel Mac.
- A Windows package cross-built on a mac carries the mac's own darwin-arm64 variants under a win32 app, for the same reason — this is what a real-device smoke test hit on a Windows cloud box during an earlier (2026-09-06) acceptance pass, whose Host log recorded exactly this failure. A Windows package built natively on `windows-latest` is unaffected, since that runner's own `pnpm install` only ever fetches win32-x64 variants in the first place.

`pnpm-lock.yaml` already lists every platform variant (`@img/sharp-win32-x64@0.35.3`, `@img/sharp-darwin-x64`, `@img/sharp-libvips-darwin-x64@1.3.2`, `@koromix/koffi-win32-x64@3.1.1`, `@koromix/koffi-darwin-x64@3.1.1`, and more) — the lockfile already resolved every variant the workspace's dependency graph could need, so making the install actually fetch all of them for the desktop packaging targets changes no dependency resolution, only which optional variants a given install call downloads.

## Decision

Desktop packaging's `pnpm install` step passes `--os=darwin --os=win32 --os=linux --cpu=x64 --cpu=arm64 --libc=glibc` (`.github/workflows/desktop-release.yml`'s `macos` and `windows` jobs; `apps/desktop/README.md` documents the same command for local packaging). This widens exactly that one install call to fetch every desktop target's `sharp`/`koffi` variant, at the cost of also fetching every other optional-native-module package's non-current-platform variants for that call (esbuild, oxlint, rolldown, the Claude/Codex agent SDKs, workerd, ripgrep, and others each ship the same per-platform-optionalDependency pattern) — `after-pack.mjs`'s `pruneForeignPlatformVariants` (below) discards those from the packaged output. A first version of this change instead put `supportedArchitectures` permanently in `pnpm-workspace.yaml`, widening every `pnpm install` anyone ever runs — every CI job across the repository, and every developer's machine — for a need only desktop packaging has; this was corrected during acceptance to the per-invocation CLI flags instead, which `pnpm install --frozen-lockfile` (no flags) elsewhere in the repository is unaffected by, and which do not change `pnpm-lock.yaml` (the CLI flags only steer which optional variants a given install fetches, not dependency resolution — the lockfile already resolved every variant the workspace's dependency graph could need). `stage-host.ts`'s own `pnpm deploy --prod --offline` call passes the same six flags: `pnpm deploy` resolves its own closure independently of whatever this workspace's `node_modules` already has linked, re-deriving which optional variant to include per family from the *current* `supportedArchitectures` config the same way a fresh `pnpm install` would — confirmed by acceptance actually running `stage:host` with only the install step widened and watching it stage only this machine's own darwin-x64 variant despite the earlier widened install having already populated the local pnpm store with every target's variant; the install step's widening only guarantees the content is in the local store for this `--offline` deploy to find, not which variant deploy's own resolution picks.

`apps/desktop/scripts/native-module-targets.mjs` is a new, framework-independent pure module holding the classification and selection logic every packaging step below shares. `parseNativeModuleEntry` recognizes a `node_modules/@img` or `@koromix` directory name as one of the `sharp-libvips`, `sharp`, or `koffi` families plus its `(os, arch)`, or reports it as unrecognized (for example `@img/colour`). `selectNativeModuleTargets(scope, target, entries)` splits one scope's entries into what a `target` keeps and what it can discard: every family a fixed `SCOPE_FAMILIES` table lists for `scope` (`@img` → `sharp`, `sharp-libvips`; `@koromix` → `koffi`) must have an entry matching `target` exactly, unless a fixed `FAMILY_NOT_SHIPPED_FOR_OS` list exempts that family for `target`'s `os` (currently only `sharp-libvips`/`win32`: `sharp`'s win32 build folds `libvips` in, so no `@img/sharp-libvips-win32-*` package exists at any version) — otherwise it throws, including when `entries` contains no entry of a required family at all. Both fixed tables (`SCOPE_FAMILIES`, `FAMILY_NOT_SHIPPED_FOR_OS`) exist because this fixed domain knowledge cannot be recovered by inferring it from `entries` itself, at either granularity: inferring "does this scope carry this family at all" from "does any entry of `entries` name this family" cannot distinguish that from "every entry of this family failed to install into this scope", and the same is true one level down for "does this family ship for this os" versus "every entry of this family for this os failed to install" — this change went through both mistakes in turn (see Consequences) before landing on two fixed tables instead of any inference. This file is plain JavaScript with JSDoc types, not TypeScript: electron-builder's `afterPack` hook loads it directly through Node's ESM loader, never through `tsx`, and `vitest` also loads plain `.mjs` directly, so one file serves both the packaging hook and its unit tests (`apps/desktop/tests/native-module-targets.spec.ts`) without a duplicate implementation. A hand-written `native-module-targets.d.mts` companion gives `stage-host.ts` and `after-pack.mjs` a typed import: TypeScript's `bundler` module resolution matches a `.mjs` specifier only against a `.d.mts` file of the same basename, never a `.d.ts` one — confirmed in this change by a minimal reproduction (a `.d.ts` companion left the import an implicit `any` with `TS7016`; renaming it to `.d.mts` resolved cleanly). The same module also exports `parsePlatformVariantEntry`/`selectForeignPlatformEntries`, a second, deliberately weaker pair of functions for every per-platform-optionalDependency package outside `@img`/`@koromix` (ripgrep, `node-addon-require-builtin`, the Landlock launcher, and others the widened install above also fetches every variant of): a family is only pruned when one of its entries actually matches `target`, and a family with no matching entry is left untouched rather than guessed at, since getting this wrong only wastes packaged bytes for a package this module does not know the full shipped-platform set of, never a Host that exits before readiness — the stronger, fail-loud guarantee stays exclusive to `selectNativeModuleTargets`'s fixed `SCOPE_FAMILIES`.

`stage-host.ts`'s `assertNativeModulesForEveryDesktopTarget` reads `@img`/`@koromix` once (throwing immediately if either scope directory does not exist at all, rather than reading it as an empty entry list) and calls `selectNativeModuleTargets` once per `DESKTOP_PLATFORMS` entry per scope right after deploying and de-symlinking the closure, discarding the `keep`/`remove` result and relying only on the throw: if any of the three desktop targets' sharp or koffi variant is missing, staging fails loud, naming the install command above, rather than silently producing a closure that can only start on some targets. `after-pack.mjs`'s existing `node_modules`-copy step (already required because electron-builder drops `node_modules` from a plain `extraResources` copy) now also calls, in order: `pruneNativeModules` (deletes every `@img`/`@koromix` directory `selectNativeModuleTargets` returns in `remove`, computing this build's `{os, arch}` target from `electron-builder`'s own exported `Arch` enum and `context.electronPlatformName`), `pruneForeignPlatformVariants` (the same idea for every other per-platform-optionalDependency package found anywhere under the closure's `node_modules`, scoped or not, using `selectForeignPlatformEntries`), and `assertBundledRuntimePresent` — a new check reading the packaged `resources/bin/<os>-<arch>` directory itself (not the source tree `fetch:micromamba` wrote into) and throwing if the pinned micromamba executable or any of `resources/micromamba.json`'s win32 `runtime.files` CRT DLLs is missing from it. This last check exists because app-builder-lib's `extraResources` copy only warns, never throws, when its `from` path does not exist — a broken `${arch}` macro in `electron-builder.yml`, a renamed directory, or a packaging run that skipped `fetch:micromamba` would otherwise produce a green build whose package is missing micromamba entirely. A packaged app therefore always ships exactly one variant per native module family it needs to run, and packaging itself proves the runtime files it depends on actually reached the package — regardless of which machine or target `electron-builder` is packaging for.

## Alternatives considered

- **Package only on each target's own native runner** (build the Windows installer exclusively on `windows-latest`, never cross-build on a mac). Rejected: this would still leave the Intel-mac DMG bug unfixed (an arm64 mac building an x64 DMG is not a cross-OS build, so a "native runner per OS" rule does nothing for it), and it gives up mac-side cross-building entirely rather than fixing the actual defect.
- **electron-builder's `npmRebuild`/`nodeGypRebuild`.** Rejected: both operate on the app's own `node_modules` before asar packaging, not on `extraResources` — the Host closure staged into `resources/host` by `stage-host.ts`/`after-pack.mjs` is invisible to either option.
- **Make sharp/koffi optional at runtime (catch the import failure, degrade the feature).** Rejected outright without investigation: this is a functionality reduction a plugin's users would notice (attachment thumbnailing, Windows subprocess control, or Windows ACL sandboxing silently stops working), and this repository's standing rule is that any user- or model-visible functionality reduction needs the user's explicit agreement first, never a quiet "known limitation."
- **A permanent `pnpm-workspace.yaml` `supportedArchitectures` block**, widening every desktop target's architecture for every `pnpm install` in the repository. Rejected: `supportedArchitectures` is a single workspace-wide setting with no per-package or per-invocation scope, so it widens every native-binary package with per-platform variants, not just sharp/koffi — roughly 4 GB of additional platform variants per install, on every CI job and every developer machine, for a need only the two desktop packaging CI jobs and local desktop packaging actually have. The per-invocation `--os`/`--cpu`/`--libc` flags achieve the same widened install exactly where it is needed, at no cost anywhere else.
- **`ignoredOptionalDependencies`** to shrink the widened install to only sharp/koffi's own packages. Rejected: this field name-matches and removes an optional dependency from every manifest that declares it, unconditionally — not "every platform variant except the current one" — so excluding, say, `@openai/codex-*` would also remove the current machine's own `@openai/codex-darwin-arm64` variant, breaking whatever in the workspace depends on it. There is no pnpm setting that widens `supportedArchitectures` for one dependency family only.

## Consequences

`apps/desktop/tests/native-module-targets.spec.ts` unit-tests `parseNativeModuleEntry` (each known family, an unrecognized name, and a family-prefixed name with an invalid remainder) and `selectNativeModuleTargets` (correct keep/remove for each of `darwin-arm64`, `darwin-x64`, and `win32-x64`; an unknown directory name left untouched regardless of target; throwing when a family ships for the target's `os` but not its `arch`; throwing when EVERY entry of a required family for the target's `os` is missing, not only some — the case the entries-inferred exemption first missed; not throwing when a family is exempted for the target's `os` — including when that family's entries for a different `os` are present in the same list — covering win32's missing `sharp-libvips` case).

`apps/desktop/tests/native-module-targets.spec.ts` also unit-tests `parsePlatformVariantEntry`/`selectForeignPlatformEntries`: recognizing scoped and unscoped platform-variant suffixes with and without a toolchain qualifier (`-msvc`, `-gnu`), pruning only families with a matching target entry, and leaving a family with no matching entry untouched.

The entries-inferred version of the `selectNativeModuleTargets` exemption was caught, not by review, but by actually running this change's own new assertion against a real environment: `pnpm --filter @deepseek-ai/dsh-desktop run stage:host` against this machine's install — every darwin sharp/koffi variant present, `@img/sharp-win32-x64@0.35.3` genuinely missing (undownloadable over this machine's network at the time) — exited 0 instead of failing loud, because no entry in `@img`'s listing named `os: 'win32'` at all, which the entries-inferred check read as "sharp doesn't ship for win32" rather than "sharp's win32 entry is missing". Fixed and re-run: the same command exited 1 with `desktop host staging: @img is missing the win32-x64 native module variant a packaged Host for that target needs (no sharp-win32-x64 entry for the win32-x64 packaging target (no sharp entry for win32 at all))`.

Decisive packaging verification against the fixed `--os`/`--cpu`/`--libc`-widened deploy, `pruneForeignPlatformVariants`, and `assertBundledRuntimePresent`:

- **mac x64 (`--dir`, `arch -x86_64`):** `release/mac/PaperMachine.app/Contents/Resources/host/node_modules/@img` contained only `colour sharp-darwin-x64 sharp-libvips-darwin-x64`; `@koromix` only `koffi-darwin-x64`; `Resources/bin` only `darwin-x64`; no `win32`/`linux` directory existed anywhere under `host/node_modules` (`pruneForeignPlatformVariants` removed ripgrep's and `node-addon-require-builtin`'s non-darwin-x64 variants alongside sharp/koffi's). Importing `sharp` and `koffi` inside the packaged app under `ELECTRON_RUN_AS_NODE=1 arch -x86_64` both reported `OK`. A real Host process started from the packaged app (`lib/bin.js --profile web --patch … --port 0`) printed `dsh web: http://127.0.0.1:51875` within seconds; the started process was stopped by `kill`ing its own recorded PID only.
- **mac arm64 (`--dir`, native):** same checks against `release/mac-arm64/PaperMachine.app`, all arm64-only; `sharp`/`koffi` both `OK` under native `process.arch === 'arm64'`.
- **Windows x64 installer:** `release/win-unpacked/resources/host/node_modules/@img` contained only `colour sharp-win32-x64`; `@koromix` only `koffi-win32-x64`; `resources/bin/` contained only `win32-x64/`, with 12 files (`micromamba.exe` plus the 11 pinned CRT DLLs) — the same file set `assertBundledRuntimePresent` itself checked before packaging finished. The packaged installer `PaperMachine-0.1.0-x64.exe` is 157,596,632 bytes, SHA-256 `8ae532596c61c460f2d9117b17bed2758d22e4cd3bff5fc94cf23a62a01a1e16` — about 6.9 MB smaller than a build predating `pruneForeignPlatformVariants` (164,519,188 bytes), consistent with that pruning actually removing bytes from the packaged output.
- **`win32-native-patch.tar`** (the win32-x64 `@img`/`@koromix` closure alone, for patching an already-installed cloud device without a full reinstall): 20,292,096 bytes.

This verification ran end to end against the code this note now describes: the widened `pnpm deploy`, `selectNativeModuleTargets`'s keep/remove selection, `stage-host.ts`'s per-target assertion, `pruneForeignPlatformVariants`, and `assertBundledRuntimePresent` all executed for real on all three desktop packaging targets, not only through `apps/desktop/tests/native-module-targets.spec.ts`'s unit tests.
