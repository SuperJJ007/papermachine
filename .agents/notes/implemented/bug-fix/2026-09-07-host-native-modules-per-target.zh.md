# Agent Note：让 Host closure 按打包目标携带自己的 sharp/koffi 原生模块

状态：已实现

[English](2026-09-07-host-native-modules-per-target.md) | 中文

## 问题

有几个 Host 插件在加载期就需要原生模块：`dsh-attachment-local` 在顶层 `import sharp`；`dsh-subprocess-local` 的 `windows-inspector.ts` 与 `dsh-sandbox-windows-acl` 都在顶层 `import koffi`；`fs-local`、`session-persistence-jsonl`、`directory-picker-native` 则动态 import koffi。这几个模块中任何一个在运行时缺失，都会让 Host 进程在打印就绪行之前退出，桌面端会把这个状态显示成"Science Host needs attention"——点 Restart Host 每次都会撞上同一个崩溃，因为打包出来的 closure 在两次尝试之间没有任何变化。

`sharp` 与 `koffi` 都通过 npm 按平台的 `optionalDependencies` 分发原生二进制（`@img/sharp-<os>-<arch>`、`@img/sharp-libvips-<os>-<arch>`、`@koromix/koffi-<os>-<arch>`）。pnpm 默认只会安装运行机器自己那一份变体。`apps/desktop/scripts/stage-host.ts` 用 `pnpm deploy --prod --offline` 从本工作区自己的 `node_modules` 部署 Host closure，所以它产出的 closure 只能带上那一次 `pnpm install` 恰好拉到的变体：

- 在 arm64 mac 上打的 x64 DMG 只带了 `sharp-darwin-arm64`/`koffi-darwin-arm64`。实证：在一个真实打出的 x64 包的 `release/mac/PaperMachine.app/Contents/Resources/host` 目录下跑 `ELECTRON_RUN_AS_NODE=1 arch -x86_64 ../../MacOS/PaperMachine --input-type=module -e "await import('sharp'); await import('koffi')"`——两者都失败（`Could not load the sharp module using the darwin-x64 runtime` / `Cannot find the native Koffi module`）；对 arm64 包跑同样的命令则成功。这意味着已发布的 `papermachine-v0.1.0` 的 `PaperMachine-0.1.0-x64.dmg`（发现问题时已有 5 次下载）在真实的 Intel Mac 上 Host 必崩。
- 在 mac 上交叉打的 Windows 包出于同样的原因，在 win32 应用里带了 mac 自己的 darwin-arm64 变体——这正是更早一次（2026-09-06）验收里一次云机 Windows 实机冒烟撞到的问题，当时的 Host 日志原样记下了这个失败。在 `windows-latest` 上原生打的 Windows 包不受影响，因为那台 runner 自己的 `pnpm install` 本来就只会拉 win32-x64 变体。

`pnpm-lock.yaml` 里已经列出了每一个平台变体（`@img/sharp-win32-x64@0.35.3`、`@img/sharp-darwin-x64`、`@img/sharp-libvips-darwin-x64@1.3.2`、`@koromix/koffi-win32-x64@3.1.1`、`@koromix/koffi-darwin-x64@3.1.1` 等等）——lockfile 早就把依赖图可能需要的每个变体都解析好了，所以让安装期真正拉全这些桌面打包目标的变体，不会改变任何依赖解析结果，只会改变某一次 install 调用具体下载哪些可选变体。

## 方案

桌面打包的 `pnpm install` 步骤会带上 `--os=darwin --os=win32 --os=linux --cpu=x64 --cpu=arm64 --libc=glibc`（`.github/workflows/desktop-release.yml` 的 `macos` 与 `windows` 两个 job；`apps/desktop/README.zh.md` 为本地打包记录了同一条命令）。这只放宽这一次 install 调用本身，让它拉全每个桌面目标的 `sharp`/`koffi` 变体，代价是这次调用也会拉全仓库里其他每个带按平台可选原生模块的包的非当前平台变体（esbuild、oxlint、rolldown、Claude/Codex 的 agent SDK、workerd、ripgrep 等都是同样的模式）——下面 `after-pack.mjs` 的 `pruneForeignPlatformVariants` 会把这些从打包产物里裁掉。本次改动第一版把 `supportedArchitectures` 永久写进了 `pnpm-workspace.yaml`，放宽了任何人跑的每一次 `pnpm install`——仓库里的每一个 CI job、每一台开发机——而这个需求本来只有桌面打包才有；验收阶段把这一处改成了现在这样的一次性 CLI 参数：仓库其余地方的 `pnpm install --frozen-lockfile`（不带参数）不受影响，也不会改动 `pnpm-lock.yaml`（这些 CLI 参数只影响某次 install 拉哪些可选变体，不影响依赖解析本身——lockfile 早就把依赖图可能需要的每个变体都解析好了）。`stage-host.ts` 自己的 `pnpm deploy --prod --offline` 调用带的是同样这六个参数：`pnpm deploy` 会独立于本工作区 `node_modules` 里当前已经链接了什么，按*当前*的 `supportedArchitectures` 配置重新为每个族推导该带哪个可选变体——跟一次全新的 `pnpm install`一样；验收阶段真跑 `stage:host`（只放宽了 install 步骤）时当场撞见并确认了这一点：尽管更早的加宽安装已经把每个目标的变体都拉进了本机的 pnpm store，`stage:host` 暂存出来的却只有这台机器自己的 darwin-x64 变体——install 步骤的放宽只保证内容已经在本地 store 里，供这次 `--offline` 的 deploy 去找，并不决定 deploy 自己的解析会选中哪个变体。

`apps/desktop/scripts/native-module-targets.mjs` 是新增的、与具体框架无关的纯模块，装着下面每个打包步骤共用的分类与选择逻辑。`parseNativeModuleEntry` 把一个 `node_modules/@img` 或 `@koromix` 目录名识别成 `sharp-libvips`、`sharp`、`koffi` 三个族之一并解出它的 `(os, arch)`，或者报告成无法识别（比如 `@img/colour`）。`selectNativeModuleTargets(scope, target, entries)` 把某个 scope 的条目拆成 `target` 该保留的与该丢弃的：一份固定的 `SCOPE_FAMILIES` 表给 `scope` 列出的每个族（`@img` → `sharp`、`sharp-libvips`；`@koromix` → `koffi`）都必须有恰好匹配 `target` 的条目，除非一份固定的 `FAMILY_NOT_SHIPPED_FOR_OS` 列表把这个族在 `target` 的 `os` 上豁免掉（目前只有 `sharp-libvips`/`win32` 这一条：`sharp` 的 win32 构建把 `libvips` 打包在自己内部，所以任何版本都不存在单独的 `@img/sharp-libvips-win32-*` 包）——否则抛错，包括 `entries` 里压根没有某个必需族的任何一条这种情况。这两份固定表（`SCOPE_FAMILIES`、`FAMILY_NOT_SHIPPED_FOR_OS`）之所以都是固定表而不是从 `entries` 推断，是因为这份既有事实在两个层级上都无法从 `entries` 本身恢复：从"`entries` 里有没有任意条目命名了这个族"去推断"这个 scope 是否携带这个族"，分不清那和"这个族的每一条都装失败了"；再往下一层，从"这个族里有没有任意条目命名了这个 os"去推断"这个族是否为这个 os 出货"，同样分不清那和"这个族为这个 os 的每一条都装失败了"。本次改动先后踩过这两个坑（见"影响"一节），才落定成两份固定表而不是任何推断。这个文件是带 JSDoc 类型的纯 JavaScript，不是 TypeScript：electron-builder 的 `afterPack` 钩子直接用 Node 的 ESM 加载器加载它，从不经过 `tsx`，`vitest` 也是直接加载 `.mjs`，所以一份文件同时服务打包钩子与它的单测（`apps/desktop/tests/native-module-targets.spec.ts`），不需要重复实现。一份手写的 `native-module-targets.d.mts` 伴生文件让 `stage-host.ts` 与 `after-pack.mjs` 能拿到有类型的 import：TypeScript 的 `bundler` 模块解析只会拿同名的 `.d.mts` 文件去匹配一个 `.mjs` 说明符，从不会用 `.d.ts`——本次改动用一个最小复现验证过这一点（用 `.d.ts` 伴生文件时该 import 隐式 `any` 并报 `TS7016`；改名成 `.d.mts` 后正常解析）。同一个文件还导出 `parsePlatformVariantEntry`/`selectForeignPlatformEntries` 这一对故意更弱的函数，处理 `@img`/`@koromix` 之外的每一个按平台分发原生模块的包（ripgrep、`node-addon-require-builtin`、Landlock launcher 等，上面加宽的安装同样会把它们的每个变体都拉下来）：只有当某个族确实存在匹配 `target` 的条目时才会裁剪它，找不到匹配条目的族原样保留而不去猜——因为这里猜错的代价只是打包产物多几个字节，而不是一个就绪前退出的 Host；只有 `selectNativeModuleTargets` 那份固定的 `SCOPE_FAMILIES` 才享有这个更强的、失败必响的保证。

`stage-host.ts` 的 `assertNativeModulesForEveryDesktopTarget` 先读一遍 `@img`/`@koromix`（其中任何一个 scope 目录整个不存在就立即抛错，而不是当成空条目列表读），然后对每一个 `DESKTOP_PLATFORMS` 条目、每个 scope 各调一次 `selectNativeModuleTargets`，扔掉 `keep`/`remove` 的返回值、只依赖它的抛错：只要三个桌面目标里任何一个的 sharp 或 koffi 变体缺失，暂存就会报错失败，并指明上面那条安装命令，而不是悄悄产出一个只能在部分目标上启动的 closure。`after-pack.mjs` 里原有的"拷贝 `node_modules`"步骤（本来就必须存在，因为 electron-builder 会从普通的 `extraResources` 拷贝里丢掉 `node_modules`）现在依次还会调用：`pruneNativeModules`（删掉 `selectNativeModuleTargets` 判给 `remove` 的每一个 `@img`/`@koromix` 目录，这次具体打包的 `{os, arch}` 目标是从 `electron-builder` 自己导出的 `Arch` 枚举与 `context.electronPlatformName` 算出来的）、`pruneForeignPlatformVariants`（用 `selectForeignPlatformEntries` 对 closure 的 `node_modules` 下、无论是否带 scope 的其他每个按平台分发原生模块的包做同样的事）、以及新增的 `assertBundledRuntimePresent`——它直接读打包产物里的 `resources/bin/<os>-<arch>` 目录本身（不是 `fetch:micromamba` 写进去的源码树），确认固定版本的 micromamba 可执行文件、以及 `resources/micromamba.json` 里 win32 的每一个 `runtime.files` CRT DLL 都在，缺任何一个就抛错。加这最后一步检查是因为 app-builder-lib 的 `extraResources` 拷贝在 `from` 路径不存在时只会警告、从不报错——`electron-builder.yml` 里的 `${arch}` 宏写坏、目录改了名字、或者某次打包漏跑了 `fetch:micromamba`，都会在没有 micromamba 的情况下打出一个绿色构建。这样一来，不管 `electron-builder` 是在哪台机器上、为哪个目标打包，打出来的 app 永远只带每个原生模块族里真正需要且能加载的那一个变体，而且打包本身就证明了它依赖的运行期文件确实到位。

## 被否决的替代方案

- **只在各自目标的原生 runner 上打包**（Windows 安装包只在 `windows-latest` 上打，mac 上永不交叉打）。否决：这仍然修不了 Intel mac DMG 那个缺陷（arm64 mac 打 x64 DMG 并不是跨操作系统构建，"每个操作系统只用自己的原生 runner"这条规则对它毫无作用），而且这等于彻底放弃 mac 侧的交叉打包，而不是修掉真正的缺陷。
- **electron-builder 的 `npmRebuild`/`nodeGypRebuild`。** 否决：两者都只作用于 asar 打包之前 app 自己的 `node_modules`，不作用于 `extraResources`——`stage-host.ts`/`after-pack.mjs` 暂存进 `resources/host` 的 Host closure 对这两个选项都不可见。
- **让 sharp/koffi 在运行期变成可选（捕获 import 失败，功能降级）。** 未经调查即否决：这是用户或模型可见的功能减少（附件缩略图、Windows 子进程控制、或 Windows ACL 沙箱会悄悄失效），本仓库的既定规则是任何用户或模型可见的功能减少都必须先取得用户明确同意，不能悄悄以"已知限制"收口。
- **永久写进 `pnpm-workspace.yaml` 的 `supportedArchitectures` 块**，为每一次 `pnpm install` 放宽每个桌面目标的架构。否决：`supportedArchitectures` 是一个作用于整个工作区的单一设置，没有按包或按调用的作用域，所以它会放宽每一个带按平台可选原生模块的包，不只是 sharp/koffi——每次安装大约多下载 4 GB 的额外平台变体，落在每一个 CI job 与每一台开发机上，而这个需求实际只有两个桌面打包 CI job 与本地桌面打包才有。一次性的 `--os`/`--cpu`/`--libc` 参数恰好只在真正需要的地方放宽安装，别处零代价。
- **用 `ignoredOptionalDependencies` 把加宽的安装收窄到只剩 sharp/koffi 自己的包。** 否决：这个字段是按名字匹配、从每一份声明了它的 manifest 里无条件删掉这个可选依赖——不是"除了当前平台以外的每个平台变体"，比如排除 `@openai/codex-*` 会连当前机器自己的 `@openai/codex-darwin-arm64` 变体一起删掉，导致工作区里依赖它的东西失效。pnpm 没有"只放宽某一个依赖族的 supportedArchitectures"这种设置。

## 影响

`apps/desktop/tests/native-module-targets.spec.ts` 为 `parseNativeModuleEntry`（每个已知族、一个无法识别的名字、一个族前缀匹配但余下部分不合法的名字）与 `selectNativeModuleTargets`（`darwin-arm64`、`darwin-x64`、`win32-x64` 三个目标各自正确的保留/删除；未知目录名无论目标是什么都保持不动；某个族为目标 `os` 出过货但没有目标 `arch` 时抛错；某个必需的族为目标 `os` 的每一条都缺失时抛错，不只是部分缺失——这正是按 `os` 推断的豁免版本最初漏掉的情形；某个族在目标 `os` 上被豁免时不抛错——即便该族在同一份列表里为另一个 `os` 出过货——覆盖 win32 缺失 `sharp-libvips` 的情形）写了单测。`parsePlatformVariantEntry`/`selectForeignPlatformEntries` 也有单测：识别带 scope 与不带 scope 的平台变体后缀、带与不带工具链限定符（`-msvc`、`-gnu`）；只裁剪存在匹配目标条目的族；某个族没有匹配条目时原样保留。

按 `os` 推断的 `selectNativeModuleTargets` 豁免写法不是靠代码评审、而是靠真跑本次改动新加的这个断言撞见的：对这台机器真实的安装跑 `pnpm --filter @deepseek-ai/dsh-desktop run stage:host`——darwin 的每个 sharp/koffi 变体都在，`@img/sharp-win32-x64@0.35.3` 确实缺失（当时本机网络下不到）——结果退出码是 0 而不是报错失败，因为 `@img` 的目录列表里压根没有任何一条 `os` 是 `win32` 的条目，按 `os` 推断的检查把这读成了"sharp 不为 win32 出货"，而不是"sharp 的 win32 条目缺失了"。修完重跑：同一条命令退出码变成 1，报错 `desktop host staging: @img is missing the win32-x64 native module variant a packaged Host for that target needs (no sharp-win32-x64 entry for the win32-x64 packaging target (no sharp entry for win32 at all))`。

针对修好的加宽 deploy、`pruneForeignPlatformVariants`、`assertBundledRuntimePresent` 三处，跑了决定性的打包验证：

- **mac x64（`--dir`、`arch -x86_64`）：** `release/mac/PaperMachine.app/Contents/Resources/host/node_modules/@img` 只有 `colour sharp-darwin-x64 sharp-libvips-darwin-x64`；`@koromix` 只有 `koffi-darwin-x64`；`Resources/bin` 只有 `darwin-x64`；整个 `host/node_modules` 下不存在任何 `win32`/`linux` 目录（`pruneForeignPlatformVariants` 把 ripgrep 与 `node-addon-require-builtin` 除 darwin-x64 之外的变体和 sharp/koffi 一起裁掉了）。在打包出的 app 内用 `ELECTRON_RUN_AS_NODE=1 arch -x86_64` import `sharp` 与 `koffi` 均报 `OK`。从打包出的 app 真正起一个 Host 进程（`lib/bin.js --profile web --patch … --port 0`），几秒内打出 `dsh web: http://127.0.0.1:51875`；收尾只 `kill` 了记下的那个 PID。
- **mac arm64（`--dir`、原生）：** 对 `release/mac-arm64/PaperMachine.app` 做同样的检查，全部只有 arm64 变体；`sharp`/`koffi` 在原生 `process.arch === 'arm64'` 下均 `OK`。
- **Windows x64 安装包：** `release/win-unpacked/resources/host/node_modules/@img` 只有 `colour sharp-win32-x64`；`@koromix` 只有 `koffi-win32-x64`；`resources/bin/` 只有 `win32-x64/`，里面 12 个文件（`micromamba.exe` 加上固定的 11 个 CRT DLL）——正是 `assertBundledRuntimePresent` 自己在打包完成前检查过的同一份文件集合。打出的安装包 `PaperMachine-0.1.0-x64.exe` 大小 157,596,632 字节，SHA-256 为 `8ae532596c61c460f2d9117b17bed2758d22e4cd3bff5fc94cf23a62a01a1e16`——比 `pruneForeignPlatformVariants` 加入之前的一次构建（164,519,188 字节）小约 6.9 MB，与这项裁剪确实从打包产物里删掉了字节这一点一致。
- **`win32-native-patch.tar`**（单独打包 win32-x64 的 `@img`/`@koromix` closure，供给已经装好的云机设备打补丁而不必整个重装）：20,292,096 字节。

这次验证是对本 note 现在描述的代码端到端真跑的：加宽的 `pnpm deploy`、`selectNativeModuleTargets` 的保留/删除选择、`stage-host.ts` 的按目标断言、`pruneForeignPlatformVariants`、`assertBundledRuntimePresent`，全部在三个桌面打包 target 上真实执行过，不只是走了 `apps/desktop/tests/native-module-targets.spec.ts` 的单测。
