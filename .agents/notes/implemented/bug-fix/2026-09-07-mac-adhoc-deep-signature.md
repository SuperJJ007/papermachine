# Agent Note: ad-hoc deep-sign the packaged mac app so Gatekeeper reports an unidentified developer, not a damaged app

Status: implemented

English | [中文](2026-09-07-mac-adhoc-deep-signature.zh.md)

## Problem

Issue #23 (Livwv, Mac Studio): opening the app inside the 0.1.0 arm64 DMG failed with macOS reporting `"PaperMachine.app" is damaged and can't be opened. You should move it to the Trash`. The README's existing advice ("right-click the app and choose Open") does nothing for this prompt: that fix only applies to Gatekeeper's separate "unidentified developer" verdict, and this device hit "damaged" instead.

Root cause, confirmed on this repository's own packaged output: `electron-builder`'s build log for both local and CI builds reads `skipped macOS application code signing` (no Apple Developer ID identity is configured anywhere in this repository), so the packaged `PaperMachine.app` carries only the ad-hoc signature Electron's own linker step already applied to its binaries — a signature that covers Electron's own code, not this application's bundle resources. `codesign --verify --deep --strict PaperMachine.app` against that package reports `code has no resources but signature indicates they must be present`. Gatekeeper reports that exact condition to a user as "damaged and can't be opened", indistinguishable in the UI from an actually-corrupted download; the only fix a user has for it is `xattr -dr com.apple.quarantine`, never right-click-Open.

Local experiment against the same app confirmed the fix: running `codesign --force --deep --sign - PaperMachine.app` (an ad-hoc signature covering every resource and nested executable) turned the same `codesign --verify --deep --strict` from failing into passing, and turned `spctl --assess --type execute`'s verdict from the "damaged" condition into a plain `rejected` — Gatekeeper's normal "unidentified developer" verdict, which right-click-Open does resolve.

A real Apple Developer ID certificate plus notarization is the actual root fix, and is the user's own (unmade) business decision — out of scope here. This change is the ad-hoc-signing mitigation plus the corresponding README fix, both scoped to 0.1.1.

## Decision

`apps/desktop/scripts/sign-mac-app.mjs` is a new, framework-independent module exporting `signMacApp(appPath, execFile)` and `maybeSignMacApp(electronPlatformName, appPath, execFile)`. `signMacApp` runs `codesign --force --deep --sign - <appPath>` then `codesign --verify --deep --strict --verbose=2 <appPath>` through an injected `execFile`-shaped function (defaulting to a promisified `child_process.execFile`), forwards both invocations' stdout/stderr into the caller's log, and throws — naming the failing step and including that invocation's stderr — on a non-zero exit from either command. `maybeSignMacApp` is the platform gate: it does nothing for any `electronPlatformName` other than `darwin`, so a win32 or linux `afterPack` run never attempts to invoke `codesign` at all. `apps/desktop/scripts/after-pack.mjs`'s `afterPack` hook calls `maybeSignMacApp` as its last step, after `pruneNativeModules`, `pruneForeignPlatformVariants`, and `assertBundledRuntimePresent` have all finished editing or reading the bundle — electron-builder's hook order is `afterPack` → code signing (skipped here, no identity) → `afterSign` → DMG assembly, so nothing after this hook touches the bundle again and the signature applied here is the one the DMG ships.

`--deep` is required, not optional: the packaged app bundles nested executables (the Host under `Contents/Resources/host`, the app-local micromamba binary) that a shallow signature does not cover, and `codesign --verify --deep --strict` fails on any of them left unsigned. `--sign -` (ad-hoc) is the only option available without an Apple Developer ID.

`apps/desktop/electron-builder.yml` gains `mac.identity: null`, so electron-builder's own signing step is skipped unconditionally by explicit configuration rather than by probing the keychain for an identity on every build and finding none. This also means a real identity accidentally present in a build machine's keychain (with no notarization run, since this repository does not run one) cannot get picked up and produce a signed-but-not-notarized package — a distinct Gatekeeper rejection, no better than today's ad-hoc one.

The root `README.md`/`README.zh.md` and `apps/desktop/README.md`/`README.zh.md` installers sections now separate the two Gatekeeper prompts and their two different fixes: "unidentified developer" (right-click, Open) is the prompt a 0.1.1 build should normally produce; "damaged and can't be opened" (only `xattr -dr com.apple.quarantine`, recursive because the app is a directory) is named as the fallback a user might still see. The same edit labels the Windows installer experimental/beta, listing its known limitations (`partial` sandbox enforcement, R edge cases under non-ASCII paths/usernames, Windows 10 64-bit minimum, attach `%USERPROFILE%\.papermachine\logs` to issue reports) — a decision made the same day this change was scoped, independent of the signing fix itself.

## Alternatives considered

- **A real Apple Developer ID certificate plus notarization.** This is the actual root fix and removes the Gatekeeper prompt entirely. Rejected for this change: it requires enrolling in the Apple Developer Program, a business decision the user has not made; ad-hoc signing is the only mitigation available without it.
- **README-only fix (document `xattr -dr` for the "damaged" prompt, ship no signature change).** Rejected: this leaves every user running the terminal command by hand on every install, where an ad-hoc signature removes the "damaged" verdict outright and reduces the remaining prompt to the one right-click-Open already resolves — a strictly better user outcome at the cost of one `codesign` call in `afterPack`.
- **Sign inside `package:mac`/`package:win`'s own script chain instead of `afterPack`.** Rejected: electron-builder's own code-signing step (skipped here) and DMG assembly both run after `afterPack`, so a signature applied any later than `afterPack` risks the DMG assembly step re-touching the bundle after signing; `afterPack` is documented by app-builder-lib as the point after which nothing else edits the bundle's contents.

## Consequences

`apps/desktop/tests/sign-mac-app.spec.ts` unit-tests `signMacApp` (sign runs before verify, both against the given `appPath`, with `codesign` as the command; a failing sign throws with its stderr and never attempts verify; a failing verify throws with its stderr) and `maybeSignMacApp` (signs for `darwin`; invokes `execFile` zero times for `win32` or `linux`) against an injected mock `execFile`, with no real `codesign` invocation. `apps/desktop/tests` (30 files, all passing) and `pnpm exec tsc -b tsconfig.host.json` both ran clean against this change.

Decisive packaging verification, run end to end in this change rather than only through the unit tests above:

- **mac arm64 (`--dir`):** `electron-builder`'s own log recorded `skipped macOS code signing reason=identity explicitly is set to null`, confirming the new `mac.identity: null` config took effect, immediately followed by this change's own `afterPack` signing step's `codesign --force --deep --sign -`/`--verify --deep --strict` output ending `PaperMachine.app: valid on disk` / `satisfies its Designated Requirement`. Re-running `codesign --verify --deep --strict --verbose=2` against the packaged app separately exited 0. `codesign -dv --verbose=2` reported `Signature=adhoc`, `TeamIdentifier=not set`. `spctl --assess --type execute --verbose=2` reported `rejected` (exit 3) — Gatekeeper's normal unidentified-developer verdict, not a damaged-app one. Importing `sharp` and `koffi` inside the packaged app under `ELECTRON_RUN_AS_NODE=1` both reported `OK`; a real Host process (`lib/bin.js --profile web --patch … --port 0`) printed `dsh web: http://127.0.0.1:55048` within seconds and was stopped by `kill`ing its own recorded PID only.
- **mac x64 (`--dir`, `arch -x86_64`):** identical checks against `release/mac/PaperMachine.app`: `codesign --verify --deep --strict` exited 0, `Signature=adhoc`, `spctl --assess` reported `rejected` (exit 3). `sharp`/`koffi` both `OK` under `arch -x86_64`; the Host printed `dsh web: http://127.0.0.1:55261` and was stopped the same way.
- **Quarantine simulation:** a copy of the arm64 `.app` given `com.apple.quarantine` (`0083;00000000;Safari;`) reported `rejected` under `spctl --assess`, and opening it produced `syspolicyd`'s unified-log line `GK evaluateScanResult: 0, PST: (path: …), (team: (null)), (id: com.papermachine.desktop), (bundle_id: com.papermachine.desktop), …` followed by `Prompt shown (6, 0), waiting for response` — the normal unidentified-developer Gatekeeper flow reaching its interactive prompt, not the immediate rejection a damaged-app verdict produces. The quarantined copy's process was stopped by `kill`ing its own recorded PID; the copy was deleted afterward.
- **DMG:** `pnpm exec electron-builder --mac dmg --arm64` produced `release/PaperMachine-0.1.0-arm64.dmg`, 177,487,957 bytes, SHA-256 `e7083564f73075e4d3e843b118675de22ce68326710de26f481cc95c9db483ca`. Mounting it with `hdiutil attach` and running `codesign --verify --deep --strict` against the mounted `PaperMachine.app` exited 0 (`valid on disk`, `satisfies its Designated Requirement`); `hdiutil detach` unmounted cleanly afterward.

What this change has **not** done: no Apple Developer ID or notarization is configured, so a first launch still shows one Gatekeeper prompt (unidentified developer) rather than none. The Windows installer's own signing status is unchanged — it remains unsigned, documented as before.
