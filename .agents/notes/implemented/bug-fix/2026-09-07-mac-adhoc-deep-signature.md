# Agent Note: ad-hoc deep-sign the packaged mac app so Gatekeeper reports an unidentified developer, not a damaged app

Status: implemented

English | [中文](2026-09-07-mac-adhoc-deep-signature.zh.md)

## Problem

Issue #23 (Livwv, Mac Studio): opening the app inside the 0.1.0 arm64 DMG failed with macOS reporting `"PaperMachine.app" is damaged and can't be opened. You should move it to the Trash`. The README's existing advice ("right-click the app and choose Open") does nothing for this prompt: that fix only applies to Gatekeeper's separate "unidentified developer" verdict, and this device hit "damaged" instead.

Root cause, confirmed on this repository's own packaged output: `electron-builder`'s build log for both local and CI builds reads `skipped macOS application code signing` (no Apple Developer ID identity is configured anywhere in this repository), so the packaged `PaperMachine.app` carries only the ad-hoc signature Electron's own linker step already applied to its binaries — a signature that covers Electron's own code, not this application's bundle resources. `codesign --verify --deep --strict PaperMachine.app` against that package reports `code has no resources but signature indicates they must be present`. Gatekeeper reports that exact condition to a user as "damaged and can't be opened", indistinguishable in the UI from an actually-corrupted download; the only fix a user has for it is `xattr -dr com.apple.quarantine`, never right-click-Open.

Local experiment against the same app confirmed the fix: running `codesign --force --deep --sign - PaperMachine.app` (an ad-hoc signature covering every resource and nested executable) turned the same `codesign --verify --deep --strict` from failing into passing, and turned `spctl --assess --type execute`'s verdict from the "damaged" condition into a plain `rejected` — Gatekeeper's normal unidentified-developer verdict. On macOS 15 and later, Apple's own release notes ("Updates to runtime protection in macOS Sequoia", developer.apple.com/news/?id=saqachfa) state that Control-click-Open no longer overrides Gatekeeper for software that is not correctly signed or notarized; an ad-hoc-signed app is both, so the user resolves the verdict from System Settings → Privacy & Security instead. Right-click-Open still works on macOS releases before 15.

A real Apple Developer ID certificate plus notarization is the actual root fix, and is the user's own (unmade) business decision — out of scope here. This change is the ad-hoc-signing mitigation plus the corresponding README fix, both scoped to 0.1.1.

## Decision

`apps/desktop/scripts/sign-mac-app.mjs` is a new, framework-independent module exporting `signMacApp(appPath, execFile)` and `maybeSignMacApp(electronPlatformName, appPath, execFile)`. `signMacApp` runs `codesign --force --deep --sign - <appPath>` then `codesign --verify --deep --strict --verbose=2 <appPath>` through an injected `execFile`-shaped function (defaulting to a promisified `child_process.execFile`), forwards both invocations' stdout/stderr into the caller's log, and throws — naming the failing step and including that invocation's stderr — on a non-zero exit from either command. `maybeSignMacApp` is the platform gate: it does nothing for any `electronPlatformName` other than `darwin`, so a win32 or linux `afterPack` run never attempts to invoke `codesign` at all. `apps/desktop/scripts/after-pack.mjs`'s `afterPack` hook calls `maybeSignMacApp` as its last step, after `pruneNativeModules`, `pruneForeignPlatformVariants`, and `assertBundledRuntimePresent` have all finished editing or reading the bundle. electron-builder's real hook order (app-builder-lib 26.15.3's `platformPackager.js`) runs `afterPack` (this signature) → `sanityCheckPackage` (read-only) → `@electron/fuses` flipping the configured fuse bits, which rewrites `Contents/Frameworks/Electron Framework.framework/…/Electron Framework` → electron-builder's own code-signing step (skipped here, `mac.identity: null`) → `afterSign` → DMG assembly — so the fuse flip runs after this module's signature, not before it, and can invalidate that signature on any build that changes a fuse from Electron's default. `apps/desktop/electron-builder.yml`'s `electronFuses.resetAdHocDarwinSignature: true` closes that gap: `@electron/fuses` re-signs the `.app` (ad-hoc, no verify of its own) immediately after flipping, so the signature the DMG actually ships is the one from that later resign, with this module's verify remaining the only assertion in the chain.

`--deep` is required, not optional: the packaged app bundles nested executables (the Host under `Contents/Resources/host`, the app-local micromamba binary) that a shallow signature does not cover, and `codesign --verify --deep --strict` fails on any of them left unsigned. `--sign -` (ad-hoc) is the only option available without an Apple Developer ID.

`apps/desktop/electron-builder.yml` gains `mac.identity: null`, so electron-builder's own signing step is skipped unconditionally by explicit configuration rather than by probing the keychain for an identity on every build and finding none. This also means a real identity accidentally present in a build machine's keychain (with no notarization run, since this repository does not run one) cannot get picked up and produce a signed-but-not-notarized package — a distinct Gatekeeper rejection, no better than today's ad-hoc one.

The root `README.md`/`README.zh.md` and `apps/desktop/README.md`/`README.zh.md` installers sections now separate the two Gatekeeper prompts and their two different fixes: "unidentified developer" is the prompt a 0.1.1 build should normally produce, resolved from System Settings → Privacy & Security → "Open Anyway" (or right-click-Open on macOS releases before 15); "damaged and can't be opened" (only `xattr -dr com.apple.quarantine`, recursive because the app is a directory) is named as the fallback a user might still see. The same edit labels the Windows installer experimental/beta, listing its known limitations (`partial` sandbox enforcement, R edge cases under non-ASCII paths/usernames, Windows 10 64-bit minimum, attach `%USERPROFILE%\.papermachine\logs` to issue reports) — a decision made the same day this change was scoped, independent of the signing fix itself.

## Alternatives considered

- **A real Apple Developer ID certificate plus notarization.** This is the actual root fix and removes the Gatekeeper prompt entirely. Rejected for this change: it requires enrolling in the Apple Developer Program, a business decision the user has not made; ad-hoc signing is the only mitigation available without it.
- **README-only fix (document `xattr -dr` for the "damaged" prompt, ship no signature change).** Rejected: this leaves every user running the terminal command by hand on every install, where an ad-hoc signature removes the "damaged" verdict outright and downgrades the remaining prompt to Gatekeeper's normal unidentified-developer rejection — a strictly better user outcome at the cost of one `codesign` call in `afterPack`.
- **Sign inside `package:mac`/`package:win`'s own script chain instead of `afterPack`.** Rejected: `afterPack` is the earliest hook electron-builder offers after native-module pruning finishes, and app-builder-lib's own `configuration.d.ts` (`AfterPackContext`, line 393) documents it as running "after pack but before pack into distributable format and sign" — i.e. before electron-builder's own signing step and the `@electron/fuses` flip that follows it, not after. Signing any later than `afterPack` has no earlier hook to move to; the actual ordering risk this change addresses is the fuse flip that runs after `afterPack`, handled by `electronFuses.resetAdHocDarwinSignature` instead of by moving this signature to a later hook.

## Consequences

`apps/desktop/tests/sign-mac-app.spec.ts` unit-tests `signMacApp` (sign runs before verify, both against the given `appPath`, with `codesign` as the command; a failing sign throws with its stderr and never attempts verify; a failing verify throws with its stderr) and `maybeSignMacApp` (signs for `darwin`; invokes `execFile` zero times for `win32` or `linux`) against an injected mock `execFile`, with no real `codesign` invocation. `apps/desktop/tests` (30 files, all passing) and `pnpm exec tsc -b tsconfig.host.json` both ran clean against this change.

Decisive packaging verification, run end to end in this change rather than only through the unit tests above:

- **mac arm64 (`--dir`):** `electron-builder`'s own log recorded `skipped macOS code signing reason=identity explicitly is set to null`, confirming the new `mac.identity: null` config took effect, immediately followed by this change's own `afterPack` signing step's `codesign --force --deep --sign -`/`--verify --deep --strict` output ending `PaperMachine.app: valid on disk` / `satisfies its Designated Requirement`. Re-running `codesign --verify --deep --strict --verbose=2` against the packaged app separately exited 0. `codesign -dv --verbose=2` reported `Signature=adhoc`, `TeamIdentifier=not set`. `spctl --assess --type execute --verbose=2` reported `rejected` (exit 3) — Gatekeeper's normal unidentified-developer verdict, not a damaged-app one. Importing `sharp` and `koffi` inside the packaged app under `ELECTRON_RUN_AS_NODE=1` both reported `OK`; a real Host process (`lib/bin.js --profile web --patch … --port 0`) printed `dsh web: http://127.0.0.1:55048` within seconds and was stopped by `kill`ing its own recorded PID only.
- **mac x64 (`--dir`, `arch -x86_64`):** identical checks against `release/mac/PaperMachine.app`: `codesign --verify --deep --strict` exited 0, `Signature=adhoc`, `spctl --assess` reported `rejected` (exit 3). `sharp`/`koffi` both `OK` under `arch -x86_64`; the Host printed `dsh web: http://127.0.0.1:55261` and was stopped the same way.
- **Quarantine simulation:** a copy of the arm64 `.app` given `com.apple.quarantine` (`0083;00000000;Safari;`) reported `rejected` under `spctl --assess`, and opening it produced `syspolicyd`'s unified-log line `GK evaluateScanResult: 0, PST: (path: …), (team: (null)), (id: com.papermachine.desktop), (bundle_id: com.papermachine.desktop), …` followed by `Prompt shown (6, 0), waiting for response` — the normal unidentified-developer Gatekeeper flow reaching its interactive prompt, not the immediate rejection a damaged-app verdict produces. The quarantined copy's process was stopped by `kill`ing its own recorded PID; the copy was deleted afterward.
- **DMG:** `pnpm exec electron-builder --mac dmg --arm64` produced `release/PaperMachine-0.1.0-arm64.dmg`, 177,487,957 bytes, SHA-256 `e7083564f73075e4d3e843b118675de22ce68326710de26f481cc95c9db483ca`. Mounting it with `hdiutil attach` and running `codesign --verify --deep --strict` against the mounted `PaperMachine.app` exited 0 (`valid on disk`, `satisfies its Designated Requirement`); `hdiutil detach` unmounted cleanly afterward.
- **`resetAdHocDarwinSignature` re-verified after this change** (arm64 `--dir`, same electron-builder invocation as above): `codesign --verify --deep --strict --verbose=2 release/mac-arm64/PaperMachine.app` exited 0 (`valid on disk`, `satisfies its Designated Requirement`); `codesign -dv --verbose=2` reported `Signature=adhoc`, `TeamIdentifier=not set`. `stat -f '%m %N'` on the two files the fuse flip and the afterPack signature both touch: `Contents/_CodeSignature/CodeResources` mtime `1788786055` (21:00:55) is not earlier than `Contents/Frameworks/Electron Framework.framework/Versions/A/Electron Framework` mtime `1788786053` (21:00:53) — the resource seal postdates the framework rewrite, confirming the signature the packaged app ends up carrying is the one `@electron/fuses` applies after flipping, not the `afterPack` one this module applies before it. The build log's own `executing @electron/fuses` / `skipped macOS code signing reason=identity explicitly is set to null` lines bracket the flip as expected; `@electron/fuses` does not log its own `resetAdHocDarwinSignature` `codesign` invocation as a separate line, so its effect is confirmed by this mtime comparison and the outer verify/dv output, not by a distinct log line.

What this change has **not** done, or has not verified: no Apple Developer ID or notarization is configured, so a first launch still shows one Gatekeeper prompt (unidentified developer) rather than none. The Windows installer's own signing status is unchanged — it remains unsigned, documented as before. The unidentified-developer prompt's own text was never captured: the quarantine-simulation check above observed `syspolicyd`'s unified-log entry for the prompt being shown, not the dialog's wording, so the README's three-path guidance is written from Apple's own documentation of the mechanism (cited above) rather than from an on-screen transcript.
