# Agent Note: every provisioning source attempt writes its full micromamba log to disk

Status: implemented

English | [中文](2026-09-07-provisioning-attempt-logs.zh.md)

## Problem

A 2026-09-07 investigation of issue #22 (a TUNA-source install that failed silently, then succeeded seconds later via USTC with no visible error) found `DesktopEnvironmentProvisioner.provision` (`apps/desktop/src/provisioning.ts`) never persisted a failed attempt's output once a later source succeeded. The `for`-loop over `declaration.sources` recorded every `onLine` line into one `logRingBuffer` array, capped at 200 lines and shared across every source attempt in the call; only when **every** source failed did the loop slice its last 200 lines and attach them to the thrown Error's message as `recentLogs`. A source that failed and was followed by a source that succeeded left that `break` on the success path, so the failed-source branch — the only place `logRingBuffer` was ever read — never ran, and the failed source's lines were gone: not written to a file, not surfaced in the UI, not sent as telemetry (`environment.install-failed`'s payload is deliberately limited to `sourceId`/`phase`/`cancelled`, by design). Even in the all-fail case, the shared ring buffer meant only the *last* source's lines survived past 200 total lines across all attempts — an earlier failed source's diagnostic output (the actual `remove_all` MAX_PATH error this investigation was chasing) was already evicted by the next source's own few hundred lines of `create` output before the loop even finished.

The onboarding "copy diagnostic report" button (`onboarding.ts`'s `startConfirmed` catch) and the `environment.install-failed` telemetry event both inherit this gap: neither has anything to show for an intermediate source's failure, only for a `provision()` call that failed outright, and even then only the last source's truncated tail.

## Decision

`provision()` now opens one append-only log file per source attempt — succeeded or failed — at `<root>/logs/provision-<source.id>-<timestamp>.log` (`<root>` is `desktopEnvironmentsRoot(dshHome)`, the existing provisioner root; the `logs` directory is created `mkdir 0o700`, each file `0o600`). A new `AttemptLog` class appends each `onLine` line to that file as it arrives — a real `appendFile` call per line, not assembled in memory and written once — so a process or machine crash mid-attempt still leaves whatever `micromamba create` had already produced on disk; writes are serialized through an internal promise chain so the independently-streamed stdout/stderr lines land in file order. The attempt's own last line is a status marker: `exit ok` on success, or the causing Error's first message line on failure (the *thrown* error, e.g. `desktop provisioning: process stopped (1)` — a summary of why the child stopped, appended after whatever diagnostic text the child itself already streamed via `onLine`). `provision()` clears every `provision-*.log` file left under `logs/` from a prior call before starting its own attempts, so the directory only ever holds the current call's logs rather than accumulating one file per source per reinstall forever; a log write failure (a full disk, say) is swallowed rather than rejecting the provisioning transaction, since this log is a diagnostic side channel, never the thing deciding pass or fail.

`recentLogs` (attached to a total-failure Error, unchanged in shape) is now rebuilt fresh per attempt instead of shared across the whole loop, so it names only the *last* attempt's lines — no longer silently mixed with, or evicted by, an earlier source's output. The same Error also gains `attemptLogs: ProvisioningAttemptLog[]` (`{ sourceId, path }`, one entry per source tried, in attempt order, regardless of which failed) and both `recentLogs` and the new `attemptLogs` paths are folded into the Error's own `message` text — not left as bare object properties — because Electron's `ipcMain.handle` strips every property but `message` off a thrown Error before it reaches the renderer (`electron.d.ts`'s own documented behavior for `handle`), the same reason `recentLogs` already had to travel this way before this change.

An intermediate source's failure is no longer invisible mid-run either: the next source's `phase: 'solving'` "Retrying via …" progress message now appends the prior failure's first error line and its log's full path (bilingual, `buildRetryMessage`), so a user watching the progress panel during a TUNA→USTC fallback sees *why* the run moved on and *where* to find the rest of that failed attempt's output, not only that it did.

`onboarding.ts`'s diagnostic-report button parses an `Attempt logs:` marker out of the caught error's text (`attemptLogPaths`, a small regex over the already-received message string — the only channel available, per the Electron property-stripping fact above) and appends a `完整日志文件 · Full log files:` section listing each path after the existing `- Error:` fenced block, when the failure named any (a capacity or platform-support failure that never reaches the source loop names none, and the report is unchanged in that case). `stripIpcErrorPrefix` (added for issue #22's app-local-CRT fix) is untouched — this section is appended after that stripping already happened, not before.

## Alternatives considered

- **Keep the single 200-line ring buffer, only fix it to reset per attempt.** Rejected: this still discards a failed intermediate attempt's full output the moment the next source runs, leaving nothing on disk to inspect after the fact — the actual gap issue #22 needed closed. A ring buffer bounds what can be *shown inline in an Error message*; it cannot answer "what did the failed attempt actually print" once the run has moved past it.
- **Write to disk only when the whole `provision()` call fails, using the retained per-attempt lines.** Rejected: this is exactly today's behavior with a bigger buffer, and issue #22's own scenario (TUNA fails, USTC succeeds) is precisely the case where the run does *not* fail overall — the failed source's log would still never be written.
- **Thread `attemptLogs` across IPC as structured data (a typed bridge return value) instead of folding it into the Error's message text.** Not pursued in this change: `provision()`/`provisionCustom()` are `Promise<void>` today, and a failure already crosses IPC as a thrown Error whose `message` is the only property Electron preserves — reshaping the bridge's success/failure contract into a discriminated result type is a larger, separately-reviewable change than this fix's scope, and the message-text channel already works (proven by the pre-existing `recentLogs` embedding).
- **Retain unlimited log files instead of clearing the previous round.** Rejected: an environment repeatedly reinstalled or retried would accumulate one file per source per call forever with no cap; clearing at the start of each `provision()` call keeps exactly the current round's evidence without adding a second retention policy to reason about.

## Deferred

The following, from the same investigation, are explicitly out of scope for this change and deferred to 0.1.2:

- Cleaning up a failed attempt's on-disk package cache/prefix residue beyond the existing `rm(prefix, { recursive: true, force: true })` at the top of each loop iteration.
- Re-checking free disk space before each retry (only checked once, before the first attempt).
- Retrying a `CRYPT_E_REVOCATION_OFFLINE` failure with `--ssl-no-revoke` appended.
- Detecting and forwarding a win32 host's system proxy configuration (Electron's `resolveProxy`) into `buildProvisioningEnv` — today only ambient `HTTP_PROXY`/`HTTPS_PROXY`/`NO_PROXY` process environment variables are forwarded.

## Consequences

`provisioning.spec.ts` adds a `per-attempt logs on disk` suite: a TUNA-fails/USTC-succeeds scenario asserts both attempts' log files exist, the failed attempt's file contains its streamed diagnostic lines and ends in the thrown error's first line, the successful attempt's file ends in `exit ok`, and the subsequent "Retrying via" progress message contains both the failure's first line and the failed attempt's log path; an all-sources-fail scenario asserts the thrown Error's `attemptLogs` names all three sources in order, `recentLogs` contains only the last attempt's lines, and every attempt's own log file independently holds that attempt's own lines; a two-call scenario with an injected deterministic clock asserts the `logs/` directory holds only the second call's file once the second `provision()` call starts. `onboarding.spec.ts` adds coverage for the diagnostic report appending a `完整日志文件 · Full log files:` section when the error text names attempt logs, and adds none when it does not. All of `apps/desktop/tests` passes; `tsc -b tsconfig.host.json` and `oxlint` pass clean on every changed file.

Real-machine verification (a genuine win32 TUNA→USTC fallback, confirming the log files and retry message on real hardware) is deferred to this project's next three-platform device pass, per this task's own reduced scope; this change was verified only with an injected `ProcessRunner` (the same test-boundary convention `provisioning.spec.ts` already used for every other fallback scenario) and macOS-local static checks, not a real `micromamba create` invocation.
