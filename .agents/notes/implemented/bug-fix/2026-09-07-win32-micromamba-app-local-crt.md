# Agent Note: win32 ships the MSVC CRT app-local, next to micromamba.exe

Status: implemented

English | [中文](2026-09-07-win32-micromamba-app-local-crt.zh.md)

## Problem

A 2026-09-07 real-device smoke test on a bare aliyun Windows Server 2022 instance (fresh install, no development tools) installed and started PaperMachine and reached onboarding normally, but clicking "Download and install" failed about 45 seconds later with `desktop provisioning: process stopped (3221225781)`. `3221225781` is Node's decimal report of Windows' `0xC0000135` (`STATUS_DLL_NOT_FOUND`). The device's own `host.log`/main-process stderr capture from that run recorded the exact line `Error occurred in handler for 'desktop:provision': Error: desktop provisioning: process stopped (3221225781)`.

The root cause: the bundled `resources/bin/win32-x64/micromamba.exe` (the official `mamba-org/micromamba-releases` 2.9.0-0 win-64 binary) dynamically links the MSVC C/C++ runtime, and its import table names `vcruntime140.dll`, `vcruntime140_1.dll`, and `msvcp140.dll`. A bare Windows install has none of these in `System32`, and this application's own `resources/bin/win32-x64/` directory — the executable's own directory, which Windows' DLL search order checks first — did not carry them either. This is a known, still-open upstream gap: `mamba-org/mamba#2928` (opened 2023-10) and `#3957` (opened 2025-05).

A 2026-09-06 static-review Agent Note (`2026-09-06-win32-desktop-provisioning-env-and-space-path.md`) had already reasoned about this exact exit code from the temporary task file that first found it, and shipped a `dirname(process.execPath)` prefix on the win32 provisioning child's `PATH`, under the premise that "the Electron executable's own directory ships `vcruntime140.dll`/`msvcp140.dll` next to the application binary." That premise was never verified on real hardware, and the 2026-09-07 device run disproved it directly: Electron 43's own application directory carries no such DLLs, because Chromium statically links its own copy of the CRT rather than depending on a system-installed one. The `PATH` prepend was also moot regardless of the DLL question — Windows' DLL search order checks a spawned executable's own directory before consulting `PATH` at all, so placing a directory on `PATH` was never going to change whether `micromamba.exe` could resolve its own dependencies.

A same-day probe on the already-installed cloud device confirmed the actual fix: copying conda-forge's `vc14_runtime` package's `vcruntime140.dll`, `vcruntime140_1.dll`, and `msvcp140.dll` into the installed app's `resources\bin\win32-x64\` (the same directory as `micromamba.exe`) turned `micromamba.exe --version` from the `0xC0000135` failure into the normal `2.9.0` output — with `System32` still carrying none of these DLLs. This confirms Windows' DLL search order finds them next to the executable with no `PATH` entry, environment variable, or system-wide install needed.

The user decided on the app-local approach over the alternatives (below) before this change began: a per-user installer that cannot elevate should not depend on a machine-wide Visual C++ Redistributable install, other conda-family desktop products (JupyterLab Desktop among them) already land `vc14_runtime` app-local for the same reason, and Microsoft's own documentation supports local (non-registry) deployment of these DLLs.

## Decision

`apps/desktop/resources/micromamba.json`'s `win32-x64` entry gains a `runtime` field pinning conda-forge's `vc14_runtime-14.51.36247-habf1de7_41.conda` (`https://conda.anaconda.org/conda-forge/win-64/vc14_runtime-14.51.36247-habf1de7_41.conda`, SHA-256 `4e4cb599cdc41bf2109d1464c127b5bcbddf548ce3e322e612afb691338b48f8` — re-verified against the live URL in this change) and the 11 root-directory `*.dll` names to extract from it: `concrt140`, `msvcp140`, `msvcp140_1`, `msvcp140_2`, `msvcp140_atomic_wait`, `msvcp140_codecvt_ids`, `vcamp140`, `vccorlib140`, `vcruntime140`, `vcruntime140_1`, `vcruntime140_threads`. micromamba itself only hard-depends on three of these; the full set (about 2.4 MB) ships together as insurance against a future satellite DLL dependency, rather than re-deriving the minimal set from a specific micromamba build's import table.

`.conda` is a zip container (stored, not deflated) holding `pkg-<name>.tar.zst` (the package's files, as a zstd-compressed tar) and `info-<name>.tar.zst` (metadata this repository has no use for); `vc14_runtime`'s package also ships a `Library/bin/<name>` duplicate of every root file, for POSIX-style conda environments — deliberately not extracted, since only the root copy sits next to `micromamba.exe`. `apps/desktop/scripts/conda-package.ts` (a new, unit-tested module) unpacks this with fflate's `unzipSync` (already an indirect dependency at this exact version elsewhere in the workspace; added as a direct desktop devDependency), Node's built-in `zlib.zstdDecompressSync` (available across this repository's `^22.19 || >=24` engines range with no new dependency), and `tar-stream` (a new devDependency: actively maintained, and hand-rolling a tar reader for one extraction step would duplicate correctness work — header parsing, PAX extensions — a maintained library already does). `extractCondaPackageFiles` returns the requested files' bytes or throws naming every missing one; `writeCondaPackageFiles` extracts and then writes every file to a `.download`-suffixed temporary path before renaming into place, so a missing file throws before anything is written and a failed call leaves the target directory exactly as found. `scripts/fetch-micromamba.ts` — build-time tooling, which the codebase's own convention keeps out of `src/` since that directory is staged into the Electron package — downloads and SHA-256-verifies the `.conda` file, then calls `writeCondaPackageFiles` into `resources/bin/win32-x64/`, alongside its existing download-and-verify of `micromamba.exe` itself. Non-win32 targets are unaffected: `asset.runtime` is `undefined` for `darwin-arm64`/`darwin-x64`.

`electron-builder.yml`'s top-level `extraResources` no longer stages the whole `resources/bin` directory — a Windows installer previously carried both macOS `micromamba` binaries alongside its own `micromamba.exe` and its now-11 companion DLLs, buried inside every installer for no reason. `mac`/`win` platform sections each add their own `extraResources` entry naming only `resources/bin/darwin-${arch}` / `resources/bin/win32-${arch}`, staged at `to: bin/<platform>-${arch}` — the exact layout `src/main.ts`'s `micromambaPath()` already expects. `${arch}` macro expansion in a platform-specific `extraResources`'s `from`/`to`, and that platform's list merging with (not replacing) the top-level list, were both confirmed by reading `app-builder-lib` 26.15.3's own `macroExpander.js` and `fileMatcher.js` in this change (`FileMatcher`'s constructor macro-expands both `from` and `to`; `getFileMatchers` calls `addPatterns` on both the top-level and platform-specific config for the same `extraResources` key) — not by a real packaging run alone, though a real `--dir` mac build and win32 `electron-builder` invocation in this change also produced the expected `bin/darwin-arm64/` and `bin/win32-x64/` layouts respectively (see Consequences for exact commands and output).

`buildProvisioningEnv` (`src/provisioning.ts`) drops the `dirname(process.execPath)` `PATH` prepend and its now-false JSDoc claim outright — the app-local DLLs make it unnecessary (DLL search order already checks the executable's own directory) and it was never doing anything besides a false claim in the first place. `runProvisioningProcess` now translates a win32 child's exit code `3221225781` into a bilingual, actionable message through the new exported `describeWin32MissingCrtExit` — naming the executable, stating the missing dependency, keeping the original numeric and hex code for diagnosis, and linking `https://aka.ms/vc14/vc_redist.x64.exe` as a manual workaround a user could try if the app-local DLLs were somehow still missing (this application does not run or bundle that installer). Every other exit code and every other platform's message is unchanged; the check only activates when `process.platform === 'win32'`, which is only ever true for a real win32-x64 run of this code. `onboarding.ts` separately strips Electron's `ipcRenderer.invoke` wrapping (`Error invoking remote method '<channel>': Error: <message>`) from a provisioning failure before displaying it — real device evidence (`issues.md`'s captured `Error invoking remote method 'desktop:provision-custom':` failure) showed this wrapping reaching the page unstripped for an unrelated provisioning failure, so the translated CRT message (or any other provisioning error) now displays cleanly regardless.

`.github/workflows/desktop-release.yml`'s Windows job adds a step after the existing micromamba smoke check that asserts every DLL name in `micromamba.json`'s `win32-x64.runtime.files` exists under `resources/bin/win32-x64/`. The smoke check's own `--version` passing proves nothing about the app-local DLLs specifically: the CI runner's own `System32` already carries a system-installed CRT, so `micromamba.exe` would run there even with a broken or empty app-local DLL set.

These DLLs are Microsoft's own build of the Visual C++ 2015-2022 Runtime, distributed by conda-forge under `LicenseRef-MicrosoftVisualCpp2015-2022Runtime` — Microsoft's own redistributable terms permit redistributing exactly the files in this runtime alongside a third-party application, which is what this change does.

## Alternatives considered

- **Embed the official `vc_redist.x64.exe` and run it during install.** Rejected: this installer requires elevation, and this application's Windows installer is deliberately per-user and unelevated (`electron-builder.yml`'s `perMachine: false`) specifically to avoid a UAC prompt on top of the SmartScreen warning an unsigned installer already shows. Running an elevated sub-installer from an unelevated one adds a UAC prompt and a second installer's own failure modes to this application's install path.
- **Statically link micromamba against the CRT.** Rejected: this repository consumes the official `mamba-org/micromamba-releases` binary rather than building micromamba from source, and no statically-linked official win-64 build is published.
- **Rely on the `dirname(process.execPath)` `PATH` prepend (the 2026-09-06 note's original fix).** Disproven on real hardware (see Problem above); retained in no form, since the DLL-search-order fact that made the probe work (executable's own directory checked before `PATH`) means a `PATH` entry could never have been the actual fix even if Electron's directory had carried the DLLs.
- **Extract only the 3 DLLs micromamba's own import table names.** Rejected: the full 11-file set from the same package is about 2.4 MB, and shipping it together removes the need to re-derive the minimal set (and re-verify it stays minimal) against a future micromamba build's own import table.

## Consequences

`apps/desktop/tests/conda-package.spec.ts` unit-tests `extractCondaPackageFiles`/`writeCondaPackageFiles` against a fixture `.conda` file synthesized in the test itself (fflate's `zipSync` around a `zlib.zstdCompressSync`-compressed tar built with `tar-stream`'s own `pack()`), covering: only listed root-directory files are extracted, a `Library/bin/` copy of a listed name is ignored, a missing listed name throws, and a failed `writeCondaPackageFiles` call leaves its target directory empty rather than holding a half-written file. `apps/desktop/tests/provisioning.spec.ts` updates every `buildProvisioningEnv`/`DesktopEnvironmentProvisioner` PATH assertion that previously expected `dirname(process.execPath)` as the first segment, and adds coverage for `describeWin32MissingCrtExit` (the exact exit code, message content, and that every other code returns `undefined`). `apps/desktop/tests/onboarding.spec.ts` adds coverage for the IPC-wrapper stripping. All of `apps/desktop/tests` (312 tests across 27 files at the time of this change) run and pass on macOS.

This change's own automation was exercised for real in this session, not only unit-tested: `pnpm --filter @deepseek-ai/dsh-desktop run fetch:micromamba win32-x64` was run against the live pinned URLs, downloading and verifying the real `micromamba.exe` and all 11 real DLLs from the real `vc14_runtime` package into `resources/bin/win32-x64/` (sizes matched the package's own root-directory listing exactly, confirmed by inspecting the downloaded `.conda` file directly with `unzip`/`tar`/`zstd` outside this application's own code). A `pnpm --filter @deepseek-ai/dsh-desktop run package:win`-equivalent build and a `mac --dir` build were run to confirm the `electron-builder.yml` platform-scoped `extraResources` layout (exact commands, output paths, and installer SHA-256/size are recorded in this task's own results section, not duplicated here).

What this change has **not** done: no code from this change has been installed or run on a real Windows device. The `0xC0000135` failure and the DLL-copy probe that motivated this fix are both real-device evidence, but from before this change (the 2026-09-07 aliyun smoke test and same-day manual-copy probe, both predating any commit in this change); this change's own packaged installer — built with the app-local DLLs from the start, rather than copied in after the fact — has not itself been run on that or any other Windows device. That real-device confirmation is explicitly out of scope for this change (a follow-up task) and this application must not be uploaded to the cloud test box as part of it.
