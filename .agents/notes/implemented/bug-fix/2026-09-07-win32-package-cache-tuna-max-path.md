# Agent Note: TUNA is deterministically over MAX_PATH under the win32 package cache; USTC is the default instead

Status: implemented

English | [中文](2026-09-07-win32-package-cache-tuna-max-path.zh.md)

## Problem

Issue #22 reported a Windows install failing over TUNA and silently retrying, eventually succeeding over USTC after downloading and caching every package a second time. An investigation found the TUNA attempt is not a transient network failure: it fails deterministically, every time, at `libstdcxx-devel_win-64-16.2.0-h230208c_104` — a header pulled in transitively by `r-base`/`r-rcpp`, not one of `general.json`'s 22 declared top-level packages — with `libmamba Error when extracting package: remove_all: The directory is not empty`.

[The 2026-09-05 fix](2026-09-05-win32-package-cache-max-path.md) shrank the win32 package cache root to `<SystemDrive>\pm\pkgs` (10 characters) on the strength of an estimate that the shipped `general` declaration's longest layered relative cache path was "about 245" characters — comfortably under win32's 260-character `MAX_PATH` once added to the 10-character root. That estimate did not account for `libstdcxx-devel_win-64`'s deepest header, the transitive dependency this issue's TUNA failure traces to. Measured directly on the real path structure micromamba 2.x's cache produces — the segment sequence `pkgs/https/<mirror host>/anaconda/cloud/conda-forge/noarch/libstdcxx-devel_win-64-16.2.0-h230208c_104/Library/lib/gcc/x86_64-w64-mingw32/16.2.0/include/c++/ext/pb_ds/detail/cc_hash_table_map_/constructor_destructor_no_store_hash_fn_imps.hpp`, which differs only in `<mirror host>` per source — the relative path is 242 characters for USTC's hostname (`mirrors.ustc.edu.cn`, 19 characters) and 251 for TUNA's (`mirrors.tuna.tsinghua.edu.cn`, 28 characters) — 9 characters longer, purely from the longer hostname in the cache path. Added to the 10-character root: USTC totals 252 (8 characters of margin), TUNA totals 261 — 1 character past `MAX_PATH`. The official channel (`conda.anaconda.org/conda-forge`, no `/anaconda/cloud/` path segment) is 226 characters relative, 236 total. Confirmed by reproducing the identical `create` against the shared cloud Windows box's cache (zero downloads, cache bytes already present): TUNA fails this way every time; USTC and the official channel do not. TUNA is also the default source `source-selection.ts` picked for a mainland-China locale, so this issue's reporter hit it by default, not by explicit selection.

## E1 experiment: the `\\?\` long-path prefix, tried and rejected on real hardware

The 2026-09-05 note's "Alternatives considered" rejected the `\\?\` long-path prefix without a real-hardware test, reasoning it was "not universally honored by every tool in the micromamba/conda toolchain's own path handling." On the shared cloud Windows box, the identical `create` argv/env as the TUNA reproduction was run with `CONDA_PKGS_DIRS` changed to `\\?\C:\pm\pkgs` and the prefix moved aside to avoid touching real cache or installs. It failed immediately (0.15s, before any path length was ever considered):

```
error    libmamba Bad conversion of configurable 'pkgs_dirs' from environment variable 'CONDA_PKGS_DIRS' with value '\\?\C:\pm\pkgs' : yaml-cpp: error at line 1, column 4: unknown token
critical libmamba yaml-cpp: error at line 1, column 4: unknown token
```

micromamba 2.9.0 parses `CONDA_PKGS_DIRS` through its YAML-backed configuration layer (`yaml-cpp`), and `\\?\` is not valid YAML scalar syntax there — the backslash-question-mark sequence is an unrecognized escape token. This is a hard rejection at configuration-load time, independent of and prior to any Win32 path-length behavior; the prefix cannot reach micromamba through this environment variable at all in this version. Full log kept as gitignored review scratch, not committed to the repository.

## Decision

`resolvePackageCacheDir` (`apps/desktop/src/provisioning.ts`) is unchanged: it still returns `<SystemDrive>\pm\pkgs` on win32-x64. Shrinking this root further is not the fix, for two reasons independent of the arithmetic: dropping the `pm` segment for `C:\pkgs` (7 characters) brings TUNA's total to 258 — 2 characters of margin, not a fix that survives the next package with a deeper header or a longer name — and it would orphan every user's existing `C:\pm\pkgs` cache outright, forcing a full re-download of the shipped `general` declaration's ~850MB on the next provisioning attempt for no gain. TUNA's hostname (28 characters, 9 longer than USTC's `mirrors.ustc.edu.cn`) is what accounts for the 9-character gap between USTC's 252-character total and TUNA's 261 at the current 10-character root.

Instead, `general.json`'s `sources` are reordered to `ustc`, `tuna`, `official` (USTC first), and `source-selection.ts`'s `CHINA_MIRROR_SOURCE_ID` changes from `'tuna'` to `'ustc'` — it selects by id, not list position, so the JSON reorder alone would not have changed which source a mainland-China locale actually tries first. TUNA stays listed for manual selection in the confirmation panel; choosing it still fails the same way, since the underlying cache layout is unchanged. Verified end to end on the shared cloud Windows box: a single-source `create` against USTC only, reusing the box's existing cache and the unchanged `CONDA_PKGS_DIRS=C:\pm\pkgs`, completed (`EXITCODE=0`), and both health checks passed — `python.exe -c "import sys;print(sys.version)"` reported 3.13.15, and `Scripts\Rscript.exe -e "library(tidyverse);library(haven);library(lme4);library(survey);library(data.table)"` loaded every declared R package including `libstdcxx-devel_win-64` itself. Logs kept as gitignored review scratch, not committed to the repository.

`general.json`'s `estimatedDownloadBytes` also changes from 520,000,000 to 850,000,000: derived from a real `micromamba clean --dry-run --tarballs` report of both mirrors' cached tarballs on the shared cloud Windows box (~2GB combined across USTC and TUNA), halved to ~0.8GB for a single source; 850,000,000 leaves margin for version drift rather than tracking that estimate exactly.

## Alternatives considered

- **`mirrored_channels` (single `create` attempt, file-level mirror failover across TUNA/USTC/official).** Would address this issue's failure mode more completely — 311 of 312 packages succeed under TUNA, and file-level failover could retry only `libstdcxx-devel_win-64` against a shorter-hostname mirror instead of re-downloading the whole set under a fresh source — but the investigation found a case where the first mirror in a `mirrored_channels` list being unreachable produced an apparent indefinite hang (100+ seconds with no new log output, manually killed) rather than a clean failover, on a configuration deliberately probing a 404. This must be root-caused and verified reliable on real hardware before this application depends on it for every provisioning attempt; deferred to 0.1.2.
- **Hard-link previously downloaded tarballs into a new source's expected cache path before retrying.** Would eliminate the cross-source duplicate-download problem entirely (same package bytes, different mirror). Not attempted: it requires reverse-engineering micromamba's undocumented per-package cache subpath convention with no public API to query it, accepting a maintenance cost tied to micromamba's internal layout. Deferred pending the `mirrored_channels` reliability question above; likely lower priority once file-level failover reduces cross-source duplication to the rare package that actually needs it.
- **Shrink the win32 cache root further (e.g. drop the `pm` segment for `C:\pkgs`).** Rejected: `C:\pkgs` (7 characters) does bring TUNA's total under `MAX_PATH` — 258, 2 characters of margin — but that margin does not survive the next package with a deeper header or a longer name, and shortening the root would orphan every user's existing `C:\pm\pkgs` cache outright, forcing a full re-download on the next provisioning attempt for no gain. The actual lever available is which mirror's hostname the cache path is built from, not how short the shared root is.

## Consequences

Choosing TUNA from the confirmation panel still fails deterministically for the reason described above; this is now documented rather than silently discovered per report. `general.json`'s source order is a live product decision (which mirror a mainland-China user gets by default) now driven by this real measurement rather than the previous unmeasured estimate; `source-selection.ts`'s `CHINA_MIRROR_SOURCE_ID` and `general.json`'s source order are covered by tests asserting `'ustc'` is both the selected id and the shipped list's first entry (`apps/desktop/tests/source-selection.spec.ts`, `apps/desktop/tests/environment-declaration.spec.ts`, `apps/desktop/tests/provisioning.spec.ts`). The `\\?\` long-path prefix is now a closed question for this micromamba version's `CONDA_PKGS_DIRS`, not an unverified rejection — any future consideration of long-path support here needs a different mechanism (e.g. `LongPathsEnabled` at the OS level, previously rejected in the [2026-09-05 note](2026-09-05-win32-package-cache-max-path.md) for requiring elevation this installer does not have).
