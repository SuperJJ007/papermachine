# Agent Note: DSH Science v0.1 R6 settings and Details

Status: implemented

English | [中文](2026-08-17-dsh-science-v01-r6-settings-details.zh.md)

## Problem

The Science line accepted Session, Runtime, model-facing tools, preset, and durable chart/Outcome layers before R6. The shipped Web application had no user-facing way to configure the `science` Runtime profile, see whether that profile was configured, or inspect the current Science Session outside individual tool occurrences. Selecting the Science preset could therefore lead to a first-use Runtime diagnostic without a setup path, and a completed analysis had no current-state side panel.

R6 closes only the `SCI-SETTINGS-SIDEBAR` inventory row. It preserves Runtime ownership of existing Conda prefixes, keeps absolute Host paths out of model and browser-readable state, reuses the durable `science` Session projection, and extends the existing settings and Details plugin points instead of replacing their shells. R6 reopens no accepted R5 decision and does not turn settings into Conda discovery, package installation, environment mutation, Desktop, or release work.

## Decision

R6 ships as five checkpoints: Runtime settings ownership (R6a), generic Details routing (R6b), a path-addressed settings write primitive (R6c-0), a settings-scope secret-presence read (R6c-0b), and the Science settings/Details product surface (R6c). The Web bundle mounts an intentionally unconfigured Science Runtime, exposes a Science settings card in the existing Plugins settings section for the shipped `science` profile, and adds a Science entry to the existing right-side Details column. Headless and custom deployments continue to supply Runtime composition explicitly.

R6 changes setup, not execution authority. A user names existing absolute Python and R Conda prefixes for the fixed `science` profile through the settings card, then restarts the Host. The Runtime continues to observe, confine, and execute those prefixes through the R2 rules; it does not discover, create, clone, solve, install into, update, repair, or delete an environment. The Science Details entry is read-only and derives its mode, environment summary, runs, charts, and latest Outcome from the accepted client-safe Session projection.

R6a and R6b landed on the accepted R5 closure head, before upstream rc.7 was merged into this line. Upstream `4366528a38` (the [plugin-owned settings surface](../../implemented/architecture/2026-08-12-plugin-owned-settings-surface.md) decision) deleted `api-proxy`'s settings-exposure allowlist and made `settings.plugin.item` a slot keyed by namespace, so registering a namespace now serves it by default. Landing R6c's card against the pre-rc.7 allowlist would have meant forking that allowlist inside the Science line or asking a shared package's owner to carry a Science-specific entry ahead of the generic mechanism upstream had already built; the [rc.7 rebaseline](../../implemented/process/2026-08-17-dsh-science-v01-rc7-rebaseline.md) merged upstream rc.7 first so R6c targets the mechanism that remains current after it ships. R6a's and R6b's tree identity changed in that merge — `installSettingsSection` and the `settings.plugin.item` registration path already existed at rc.5 and rc.7 leaves both untouched — so their reviewed identity is the post-rebaseline head, not their pre-rebaseline commits.

### Runtime settings ownership

`@deepseek-ai/dsh-science-runtime/with-settings` provides the same service over the same `Config` as the root entry and additionally treats the existing `profiles` configuration as the composition `base` of a `science-runtime` user-settings namespace. The namespace contains only the profile map; `dshHome`, execution timeout, and artifact-diagnostic bounds remain Cordis configuration, since R6 has no product need to edit them. The root entry keeps its prior behavior and never reads settings.

The settings capability is a declared Cordis injection of the `with-settings` entry, not something the Runtime probes for at load: `attachRuntimeSettings` (`packages/science/science-runtime/src/settings.ts`) runs only once the injected settings provider is ACTIVE, so a deployment that mounts the entry without a settings provider leaves it PENDING on the unmet injection instead of silently resolving profiles from the Cordis map alone.

The settings schema accepts an empty profile map as the intentional unconfigured state. Every declared profile still uses the R2 safe-id grammar, contains at least one of `pythonPrefix` or `rPrefix`, and uses absolute paths; an invalid declared profile fails registration or a settings write, and `parseProfiles` — the same validator the Cordis `configSchema` uses — backs the settings `validate` hook. A missing requested profile continues to fail before provider I/O and before any Science event is appended; it never falls back to another profile or a discovered path.

The `with-settings` entry registers the namespace with `applies: 'restart'`, captures the resolved profile map once during plugin load, and does not watch it. Cordis entry configuration remains the lower-precedence deployment base, while the user settings document can override or remove fields through the existing settings revision and mutation rules. A successful write changes the next Host start only; it cannot swap an environment underneath a live Session.

`pythonPrefix` and `rPrefix` are `role('secret')` fields on the namespace schema (`scienceRuntimeProfilesSchema`), so they are write-only on every browser-facing settings descriptor: no settings response, forwarded event, diagnostic, snapshot, or projection carries the path value, and Host logs and model-visible text stay path-free.

The shipped Web bundle mounts `@deepseek-ai/dsh-science-runtime/with-settings` alongside the base settings, subprocess, sandbox, attachment, and Science Session services with `profiles: {}`; Cordis, not entry order, sequences it after the settings provider. This changes the default Web failure from "Runtime service missing" to the more actionable "science profile missing" until setup and restart complete. CLI/headless bundles gain no such row; their deployment overlay stays authoritative.

### Generic Details routing

`@deepseek-ai/dsh-client-ui-conversation` carries a list slot named `conversation.details.view`. The existing tool-call body is the built-in `tool` entry, retaining its input/output rendering and `conversation.details.tool` child seat. The Details shell owns column geometry, close behavior, title chrome, mounted-on-collapse lifecycle, and fallback behavior.

The per-Session conversation store carries a `detailsView` id and an action that selects it. Tool-row activation selects `tool` and the addressed call before opening the column. The session-header action owner receives an `openDetailsView(id)` callback that selects a registered entry and opens the same column. An absent, removed, or stale id falls back to `tool`; changing Sessions keeps the existing AppFrame behavior of closing the column.

The Details shell derives labels and ordered entries from the slot registry, subscribes to registry/locale changes, and renders only the selected entry. Registrations remain effects; unloading a domain entry removes its label and body and leaves the built-in tool entry usable. No domain package occupies the top-level `details` slot or imports the Details shell implementation.

Title text is the one exception the shell resolves itself rather than reading purely off the registry: while the built-in `tool` entry is active, the shell computes the selected call's own name (falling back to the selection's carried tool name, then the generic label), because a per-session store selection cannot express a registration-time label; every other entry's title is its registered label.

### Path-addressed settings writes (R6c-0) and secret-slot presence (R6c-0b)

`SettingsScopeController.set`/`unset` (`packages/client/ui-settings/src/client/settings-scope.ts`) wrote only a single path segment before R6c-0, while the fields the Science card edits sit two segments deep. R6c-0 adds `setPath(path, value)`/`unsetPath(path)` to the browser-side `SettingsScope<T>` contract and its controller as the PRIMITIVE: `set`/`unset` keep their exact existing single-segment behavior, now implemented as `setPath([field], value)`/`unsetPath([field])`, so the write queue, revision fencing, and stale/rejected-write recovery stay in one place. Neither the wire operation (`SettingsPathOpView` already carries `path: string[]` at any depth) nor the Host settings seam needed a change. This is a generic `ui-settings` change with no Science-owned file touched, landed and reviewed as its own accepted head before any Science file changed.

Before R6c-0b, `role('secret')` fields were stripped from `SettingsNamespaceView.value`/`.base`/`.user` on every wire read, so a browser card editing a write-only field had no way to tell from `SettingsScopeSnapshot` whether the Host held a value for it — which the Science card's "configured" state needs. The wire already answered this separately in `SettingsNamespaceView.secrets` (path from the section root plus whether a value is set), and `SettingsScopeController.accept()` already received that list and dropped it. R6c-0b adds `SettingsSecretPresence` (`packages/client/runtime/src/client/contract/settings-scope.ts`, a minimal structural type with no wire import) and a `secrets: readonly SettingsSecretPresence[]` field to `SettingsScopeSnapshot<T>`, populated by the controller on every accepted view alongside `base`/`user` and left untouched while a namespace is unavailable, matching those two fields' existing treatment. This closed the read-side gap R6c-0's write primitive opened without adding a second `settings.describe` state authority: the Science card's own earlier working-tree mechanism called `api.settings.describe({})` directly, which pulled `dsh-client-connection` and `dsh-client-web-react` into `ui-science`, doubled `describe` traffic on every scope change, and computed the save outcome from a read that bypassed the scope's own write queue and revision fencing. R6c-0b replaced that mechanism before the Science card shipped, so the shipped card reads presence from `scope.getSnapshot().secrets` alone.

### Science settings and Details product surface

`@deepseek-ai/dsh-client-ui-science` is the owner of the Science settings card, Science header action, and Science Details entry, alongside its R5 `save_chart`/`publish_outcome` toolview rows. It registers one **keyed** `settings.plugin.item` card under key `science-runtime` — the namespace R6a registers, not a package or product id — one `conversation.session.header.actions` entry, and one `conversation.details.view` entry with id `science`. Keying on the namespace means the card needs no `settings.section` page, no navigation row, and no Host change to appear: the shipped Web bundle mounts both `ui-science` and `ui-settings-plugins`, the Plugins section's `configurable` tab dispatches one slot key per namespace the Host serves, and a deployment that does not mount the `with-settings` Runtime entry sees no trace of the card, matching the section's existing empty-state behavior.

The card binds the `science-runtime` namespace through `ctx.settingsScope.bind({ namespace: 'science-runtime' })` and writes only `setPath(['science', 'pythonPrefix'], …)`, `setPath(['science', 'rPrefix'], …)`, and `unsetPath(['science'])` — never the section root. The write path's depth is settled by `attachRuntimeSettings`, which registers the namespace with `base: config.profiles`: the section root **is** the profile map itself, not a `profiles` wrapper field, so `['science', 'pythonPrefix']` is the correct coordinate and a `['profiles', 'science', 'pythonPrefix']` coordinate is not. `redactSecrets` walks from the same section root (`packages/settings/settings/src/redact.ts`), so every secret path the card, the wire, and the Host agree on shares this two-segment shape; a real Host run confirms it, writing `science-runtime:\n  science:\n    pythonPrefix: …\n    rPrefix: …` to the settings document. No code path writes the section root itself: doing so would replace every profile a deployment declares with only the one the browser staged, silently erasing profiles the redacted client view never saw.

The card shows loading, an explicit read-only state, unconfigured, configured and in effect, saving, a Host-rejected write, a client-blocked invalid draft, pending-restart, and reset-to-composition. A Host-rejected write (stale revision or Host validation failure) is one indistinguishable `failed` state in the controller, since both recover identically through the scope's own read-back; the plan's separate "stale-revision" and "validation-failure" states collapse to this one shipped state. The running Host's bound state (`ScienceSettingsCardController.hostState`, `'effective' | 'pendingRestart' | 'notConfigured'`) is a pure projection of the bound scope's `effective` snapshot field against its `value` field — the value the namespace's `applies: 'restart'` Science Runtime entry actually read at its own registration compared with what is currently stored — not a client-local flag, so it reports the same state across a page reload rather than only immediately after a save in the tab that made it (see the [Science product gaps Agent Note](../bug-fix/2026-08-18-science-mode-product-gaps.md)). `failed` and `hostState: 'pendingRestart'` can both be true after a save with both fields dirty: a field the Host accepts clears its staged draft and requires a restart, while a field the Host rejects keeps its draft for the user to correct. Blank replacement inputs are no-ops; the explicit remove-override action unsets `['science']`, which returns to unconfigured when no composition base exists and otherwise reveals that base. Other deployment profile ids remain file/configuration concerns and are not a generic profile manager in R6. The "namespace absent" case in the shared card model is unreachable for this card and is not built as UI: the Plugins tab dispatches one slot key per namespace the Host actually serves, so a card mounts only when its namespace is served, and namespace absence renders nothing at the tab level.

The bundle-purity gate forbids the Science card from value-importing `ui-settings-plugins`' card chrome (`PluginCard`) or its staged-form model, so the card owns its own chrome and its own staging/revision fencing. That chrome is built on `@deepseek-ai/dsh-client-ui-primitives` — `Input` for both prefix fields, `Pill` for the Configured/Not configured badge, and `Button` (`primary`/`outline`/`ghost` variants) for Save/Discard/Remove override — plus a hand-rolled collapsed-by-default disclosure header with `aria-expanded` and a "展开设置/收起设置: <name>"-register accessible name. `DisclosureRow` (`@deepseek-ai/dsh-client-ui-primitives`) is deliberately not that header's primitive: it is compact 24px icon-leading chrome used by transcript/tool rows (`ReasoningRow`, `ToolRow`), not by any settings card, and provides no two-line name-over-description header shape; `PluginCard` itself hand-rolls the identical header-button pattern this card mirrors, for that same reason. Collapsed, only the header sits in the accessibility tree — every field, hint, and action button renders only once expanded, matching every sibling card and removing the accessible-name collision the card's initial always-expanded rendering caused with the Terminal card's identically-labeled buttons.

The browser never echoes a stored prefix. A configured field renders a neutral "configured" state; replacing it requires a new absolute path, a blank field changes nothing, and explicit reset removes only the user-layer `science` profile so a composition base can reappear. Settings conflicts reload the current descriptor before another write. R6 adds no browser filesystem picker, path discovery, prefix probing, package inventory, or live apply button.

The Science header action appears only when the current Session summary names the built-in `science` preset. Activating it opens the `science` Details entry. The entry reads the `science` Session projection and renders a client-safe environment summary, ordered run status/history, logical charts with their latest accepted versions, and the latest Outcome with evidence references. Chart thumbnails resolve through the entry's own `science-attachment-loader.ts` rather than the conversation-owned session attachment loader the transcript rows use, because `conversation.details.view`'s owner share (`DetailsViewOwnerProps`) carries nothing and `IConversation`'s outward face exposes no `resolveImage` — the concrete image-resolution service stays inside `ui-conversation`. The loader instead calls `ISession.readAttachment` directly, one of the documented session "behavior verbs" a feature package may call, and converts the returned bytes to a stateless `data:` URI: no `Map`, no `URL.createObjectURL` handle, nothing to revoke on session release, and no second attachment cache — consistent with the "No independent attachment cache" limitation `packages/client/ui-science/README.md` records.

Before the first Science event, the Details entry shows the selected preset and an unbound state. Missing projection support, unavailable attachments, failed Runtime binding, no runs, no charts, and no Outcome each have distinct accessible text; the environment section never reports capability from configuration alone, since any revision whose `status` is not `'applied'` renders the same failed-binding text. Standard and custom non-Science Sessions receive no Science header action and no automatic panel opening. The UI never treats configured prefixes as validated; interpreter capability comes only from a durable environment binding after Host restart and use.

### Runtime row-id ownership

The shipped Web bundle owns the `science-runtime` Cordis entry id: `ScienceRuntime` and its `with-settings` alternative provide the same single-provider `ctx.scienceRuntime` service, so a deployment supplying its own profile map through Cordis configuration overrides that row by id — a same-id patch changing `config`, not swapping which plugin runs — rather than inserting a second Runtime row, which throws `service "scienceRuntime" has been registered` at load. A patch row may not rename an existing row to a different plugin at the same id: the Loader's `applyEntryPatches` strips `name` out of a patch's overrides before applying them, and when a patch's own `name` field disagrees with the target entry's current name it skips the whole patch with a name-mismatch warning rather than partially applying it. Switching the plugin mounted at an id — for example, from the settings-bound entry back to the plain `@deepseek-ai/dsh-science-runtime` entry — therefore is not a same-id override; it is disabling the existing row by id and inserting a new entry under a different id, the same disable-and-insert mechanism every other plugin swap in this repository uses.

## Alternatives considered

**Leave Runtime setup in Cordis files and add only a read-only status page.** Rejected because the shipped Web application would still expose a selectable Science preset without a product setup path. The settings seam already supports composition base plus user override and explicit restart timing, so R6 uses it without taking over execution.

**Bind the namespace on one Runtime entry that checks for a settings service at load.** Rejected because the Cordis Loader creates sibling entries concurrently, so that check reports which module finished importing first, not what the composition declares. Whenever the settings provider's module landed second the namespace went unregistered and the stored profile was silently ignored — the exact restart the user performed to apply it — and cordis.yml entry order did not repair it. A declared injection makes Cordis sequence the two and turns a missing provider into a visible unmet dependency.

**Apply prefix changes live.** Rejected because a live settings write could change profile resolution between environment binding and later runs, or require migrating exact-Session reservations and scratch ownership. Restart-only resolution gives one immutable Runtime configuration to each Host lifecycle.

**Discover or manage Conda environments.** Rejected because discovery, create/clone/install/update/repair/delete, solver output, mutation locks, approval, rollback, quotas, and cleanup form a separate capability. R6 accepts explicit existing prefixes only.

**Return stored prefix paths to the browser.** Rejected because setup status and replacement do not require disclosing an absolute Host path. Secret-path descriptors preserve write and reset operations while keeping browser snapshots and forwarded events path-free.

**Give Science its own `settings.section` page instead of a keyed card.** Rejected once the rc.7 rebaseline made `settings.plugin.item` a namespace-keyed slot and the Host serve every registered namespace. A dedicated page would claim a permanent Settings navigation row for two prefix fields, would have to reimplement the availability logic the tab already derives from what the Host serves, and would appear in deployments that never mount the Science Runtime. A card gets dispatch, availability, and empty-state behavior from the section that owns them, and the shipped Web bundle already mounts both halves. The page remains the right shape if Science settings ever outgrow one profile's two fields.

**Have the settings card poll `settings.describe` for per-field secret presence.** Rejected in favor of R6c-0b's `SettingsScopeSnapshot.secrets` field. A direct `api.settings.describe({})` call pulled two Client packages into `ui-science` that no other read needed, doubled describe traffic on every scope change, and computed the save outcome from a read that bypassed the bound scope's own write queue and revision fencing — a second state authority over one namespace. Extending the scope's own snapshot keeps one settings-state authority per namespace and lets the card derive "landed" from the same write's settlement.

**Let `ui-science` replace the top-level `details` slot.** Rejected because it would remove tool-call Details and make one optional domain own generic column chrome. R6 adds a domain entry behind a conversation-owned routing slot.

**Render Science as another center-column conversation tab.** Rejected because charts and Outcomes already remain in the transcript, while R6 needs a compact current-state surface that can stay beside the conversation. The existing Details column provides that relationship without duplicating the transcript.

**Fold R5 repair into R6.** Rejected because R6 depends on accepted R5 durable chart/Outcome and client-projection semantics. Mixing predecessor repair into R6 would erase the exact accepted base and make R6 evidence unable to distinguish the two inventory rows; a defect found in R5 returns to its own candidate.

## Consequences

An empty Runtime row makes the service present before it is usable. The settings card names the missing `science` profile and the first model-facing use still fails before provider I/O; no UI labels the Runtime ready until a durable binding reports capability. Restart-only settings can surprise a user who expects an immediate change, so the card retains a visible restart-required state after save and never refreshes a live Session into claiming a new prefix is active.

Write-only path fields reduce disclosure but prevent visual confirmation of the stored absolute path; R6 favors Host privacy and provides configured/user-override/reset state instead. Registering a settings namespace now serves it by default for every namespace this line adds, not only `science-runtime`'s: there is no longer an allowlist backstop that would keep an unmarked field off the browser by omission, so a future Science settings field must carry `role('secret')` explicitly, and the redactor's own deferred gap for a secret reachable only through a union, intersection, or transform (recorded in the [plugin-owned settings surface note](../../implemented/architecture/2026-08-12-plugin-owned-settings-surface.md#consequences)) now has a wider blast radius — any registered schema, not only audited ones.

The right Details column is a shared routed surface; the generic checkpoint preserves the tool fallback and HMR behavior independently of Science's entry, so an optional domain unload cannot strand ordinary tool inspection. The shipped Web bundle owns the `science-runtime` row id, and a deployment that wants a different plugin at that id — not merely a different `profiles` config for the same settings-bound entry — must disable the row and insert a replacement under a new id; a same-id override cannot rename the entry's plugin.

Real Python/R acceptance proves the configured interpreters and Runtime lifecycle, not plotting-library availability, scientific correctness, Desktop packaging, installer behavior, signing, notarization, or release readiness. The GUI-change rule's real-model-round GIF requirement is met for the settings card; the session-header action and the Details entry are instead covered by a real-browser e2e scenario rather than a real-model-round GIF, because the composer that would produce a real model round sits behind a workspace-selection surface this pass could not drive headlessly without either an undrivable native dialog or changing the tested entry points. That GIF coverage for the header action and Details entry remains owed to a future pass; the dated evidence names the exact gap.
