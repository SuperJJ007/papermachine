# Agent Note: Science run-row eight states and generic Tool groups

Status: implemented

English | [中文](2026-08-26-science-run-row-states-and-tool-groups.zh.md)

## Problem

Part 3's collapsed `run_python`/`run_r` cell (one line plus expand-on-click code and settled output) treated every settled call the same way, whether the run succeeded, failed on an ordinary exception, or lost its kernel mid-execution — the last two looked identical, and a long or truncated stdout had no distinct affordance from a short one. Separately, an unbroken run of several ordinary Tool calls (a read, a grep, a write) rendered as that many independent one-line cells with no summary, forcing a reader to open each one to learn what the run of steps actually did.

The user named the 8/19 `RunOutput.dc.html` design board as the visual authority for the row's eight states (2026-08-26 decision; the rest of that board — the workbench layout, left navigation, 400px chat column, kernel status bar — is void) and `CS-TURN-RENDERING-SPEC.md` §2/3 as the alignment authority for generic Tool grouping.

## Decision

**Eight states, entirely from existing facts.** `ScienceExecutionRow` derives its state from two already-logged sources: the durable tool-call lifecycle (`scienceToolRowState`, unchanged) and the joined `science` Session projection run entry, matched by `toolCallId === callId` (`useProjection('science')`). A genuine tool-level exception or a turn/session interruption landing mid-call keeps the pre-existing plain folded cell (`FallbackRow`) unchanged. Once the call settles ok, the row also needs the run's raw stdout/stderr text, which the client-safe projection deliberately omits (`ScienceClientRunTerminal`'s doc: "free-text failure output is omitted") — so `run-output.ts`'s `splitRunResultSections` recovers it by locating `tool-science` `formatRunResult`'s two fixed section markers (`--- stdout ---`/`--- stderr ---`) inside the flattened tool-result text every settled call already carries. Byte size and line count are computed client-side off that recovered text (`byteLength`/`countLines`), never off a Host-reported figure that does not exist; truncation and the `KERNEL_DIED` failure code come structurally from the projection run entry, which is authoritative once found. A row degrades to the same plain folded cell whenever either source is missing — no science run entry for this call, or text that does not carry the markers (a hand-built test fixture, or a future format change) — rather than presenting a science-specific state the durable facts do not actually support; several existing web e2e fixtures (`science-chart-outcome.e2e.ts`, `science-artifact-types.e2e.ts`) already construct exactly this non-standard shape and continue to render through the unchanged fallback path, so none of their goldens moved.

The eight states: running (live `mm:ss`, a static "Running…" summary since no stdout-streaming channel exists, and a turn-level Stop reusing the composer's own control through an injected `cancel`); short/long/table/chart success (folded past 8 retained lines, identical whether or not the run captured an artifact — captured artifacts never render a chip in the row, only in the Turn-tail group P3 already built); truncated success (the fold names the retained tail's byte size, with a banner explaining the cap); failed (a tail-first two-line stderr summary, full stack behind its own fold); and kernel-exited (an amber state naming the exited epoch and the next one, `inspect` reused as "View exit reason" since no per-kernel-state-event navigation exists yet).

**Reasoning attaches to its next visible successor, never a bubble of its own.** `chat/reasoning-attach.ts`'s `attachReasoningNodes` walks the flow order once, ahead of `groupAdjacentToolNodes`. A pure-reasoning `assistant-step` Node — only `reasoning` blocks with non-empty text; a `tool-call` placeholder block or a whitespace-only `text` block do not count as other visible content — drops out of the rewritten order, and its text queues onto the next key whose kind is `tool-call` or an `assistant-step` carrying real prose. That successor absorbs the fold instead of the reasoning Node materializing its own row, so a Think step ahead of an otherwise-adjacent `tool-call` run no longer splits that run apart: `groupAdjacentToolNodes` sees the rewritten order, never the removed reasoning key, and its own boundary rule is unchanged — a `tool-call` key still folds into a run, every other kind (assistant prose, a delegate/subagent card, a review card, a completion summary, a compaction prompt, a user message) still breaks one. Several adjacent pure-reasoning keys concatenate onto the same successor, oldest first. A pure-reasoning key with no attachable successor yet — still streaming, the turn closed with nothing after it, or the next key is a non-attachable kind — stays in the order unchanged: today's standalone Think row is the fallback, so no reasoning text is ever silently dropped.

| Chat Node kind | Breaks a `tool-call` run apart | Accepts an attached reasoning fold |
|---|---|---|
| `tool-call` | no (the run member itself) | yes — `ChatNodeSeat`'s leading `ReasoningRow` |
| `assistant-step` carrying prose | yes | yes — synthesized leading `reasoning` blocks |
| `assistant-step` that is pure reasoning | never materializes its own flow key once attached | n/a (source, not target) |
| user / steering / context | yes | no — the reasoning stays standalone instead |
| delegate/subagent, review card | yes | no |
| completion summary (agent-done/compute-done/subtask run) | yes | no |
| compaction prompt | yes | no |

Presentation stays the two forms the spec names, never a third. A fold onto a `tool-call` renders as `ChatNodeSeat`'s own leading `ReasoningRow`, a sibling ahead of that step's card inside the same flow-item wrapper — not a change to `tool.call.toolview` in ui-tool or ui-science, since a cross-plugin value import of `ReasoningRow` from `ui-conversation` would fail the client bundle purity gate (`scripts/client-bundle-purity.spec.ts`); a fold onto prose synthesizes leading `reasoning` blocks into that `assistant-step`'s own `blocks` array, rendered through `AssistantMarkdown`'s existing Think summary row exactly as an in-line reasoning block already is. `ChatNodeSeat` and `ToolGroup` receive each key's own resolved `attachedReasoning: readonly string[] | undefined` slice, never the shared `reasoningByKey` lookup Map itself — the Map's identity changes on every unrelated flow edit (a new streaming partial's synthetic key, another step settling), and passing it as a prop would defeat `ChatNodeSeat`'s `memo` bail-out for every sibling row on every such edit. Both forms are component-local UI state: the fold recomputes from `order` and the Chat Node store on every relevant render, is never logged, and — like every other disclosure here — defaults to collapsed on reload.

**Generic Tool groups, not a Science feature.** `ui-conversation`'s `ChatView` folds an unbroken run of two or more `tool-call` Chat Nodes into one `ToolGroup`; a lone call stays its ordinary single row. Grouping (`chat/tool-group.ts`) and rendering (`ChatView`'s pre-existing `<ChatNodeSeat>` mapping, wrapped rather than replaced) never import `ui-science` or any domain package — classification reads only the call's wire tool name and, for a name it does not recognize directly, its declared render-intent card (`terminal`/`read`/`search`/`diff`/`web`, the same vocabulary `ui-tool`'s card models already use), so Science's own `run_python`/`run_r` rows (registered through the existing `tool.call.toolview` seam) participate correctly with zero Science-specific code in `ui-conversation`. The group title sums each present category's count in a fixed order; the meta line's failure count reads each member's structured `isError`, never guessed text. A group starts expanded (P3b's "collapse everything" default is revised to "group open, member folded" — the P3b Agent Note's final-form statement is updated in place rather than superseded); collapsing it unmounts every member row behind the two-line header. Both levels are component-local view state, never logged.

## Alternatives considered

**Declare a new render-intent card for `run_python`/`run_r` carrying structured stdout/stderr, instead of recovering it from text.** Rejected: a render-intent `view` is a durable field on the tool result, so adding one is a new Host fact the brief explicitly forbids ("不新增 session 事件，不改模型可见内容"); the flattened text already carries everything needed, deterministically, since `formatRunResult` is this same product's own fixed format.

**Read `stdoutBytes`/`stderrBytes` off the projection for the fold's byte-size label.** Rejected in favor of measuring the recovered text directly: those fields report the *original* pre-truncation size, while the fold's truncated-state label needs the *retained* tail's size, and computing it from the text actually shown needs no Runtime constant (`MAX_OUTPUT_BYTES`) exposed to the client at all.

**Classify a Tool group's members by a hardcoded name-to-category table covering every known tool.** Rejected: `ui-tool`'s render-intent card already carries this classification for every tool that bothers to declare one (`read`/`search`/`diff`/`web`), so only the tools with no card need a name literal at all (`run_python`/`run_r`, which never route through `ui-tool`, plus `bash`/`pwsh` for robustness against a windowless call head with no card yet) — a `card`-first design needs far fewer literals and stays generic by construction.

**Give the group wrapper its own `data-chat-anchor-key`.** Rejected: `ChatView`'s scroll/paging anchor logic already treats every `[data-chat-anchor-key]` element as an independently restorable position, and an existing unit test asserts the exact anchor-key list for an ungrouped flow; adding one for the group would grow that list and mildly duplicate the members' own keys for no positioning benefit. A collapsed group's members lose their individual anchor keys until reopened — an accepted, documented degrade (see the `ui-conversation` README's Known Limitations).

**Render the Think fold inside each tool row's own expanded body (`ToolRow`'s `bodyWrap`, or Science's own three toolview components).** Rejected: `ui-tool` and `ui-science` are separate plugins from `ui-conversation`, and neither may take a runtime value import of `ReasoningRow` across that boundary (client bundle purity). Duplicating a second Think-fold presentation inside each toolview package to avoid the import would be exactly the "third Think appearance" the brief forbids. Rendering the fold as `ChatNodeSeat`'s own leading sibling — still inside the same flow-item wrapper, immediately above that step's card — keeps ui-tool and ui-science untouched and reuses the one `ReasoningRow` component unconditionally for every tool-call kind, including Science's own `run_python`/`run_r`.

## Consequences

`ScienceExecutionRow`'s existing e2e coverage needed no golden refresh: every fixture that predates this change either exercises the unchanged fallback branches (`stopped`/`error`, or a settled call whose text does not carry `formatRunResult`'s markers) or captures a Details-column ARIA snapshot the row redesign never touches. `science-stop.e2e.ts` gained three new scenarios against the same real Runtime/subprocess/browser stack the original Stop scenario already used — a settled success (kernel badge, full stdout), two adjacent successful calls folding into one real generated group title, and a real kernel crash rendering the kernel-exited state — proving the redesign end to end without a new fixture family. The eight states' full matrix (including the marker-parse and missing-run degrade paths) is unit-tested at 100% per-file coverage in `ui-science`. `chat/tool-group.ts` and `chat/reasoning-attach.ts` — both pure functions table-tested over every fold/grouping combination, including a Think row folded ahead of what would otherwise be a broken-up tool-call run — reach 100% per file when scanned on their own; `packages/client/ui-conversation/src/client/*` as a whole sits under a standing pre-task coverage exemption (`vitest.config.ts`, "GUI debt exemption") that the project's `pnpm run test:coverage` gate does not lift, so `ChatNodeSeat.tsx`'s and `AssistantNodeView.tsx`'s few remaining gaps are pre-existing branches in code this change did not touch (verified by diffing the uncovered line numbers against the change), not new debt.

Deferred, matching the brief: promoting an in-memory DataFrame result to an artifact-like row waits for the Notebook/Compute data-grounding stage; a "Restart and rerun" action on the kernel-exited state stays out so a rerun is always routed through the model/conversation, never a client control that would break trajectory consistency. Extending the Think fold's presentation into ui-tool's `ToolRow` (a nested sub-disclosure inside that row's own expanded body, matching the literal placement the brief's prose suggests) is deferred: `ChatNodeSeat`'s sibling placement satisfies the same "no independent Think row, no broken grouping, no third appearance" contract without the cross-plugin coupling that placement would need — a future decision to route Think presentation through a shared capability seam (instead of `ui-conversation` alone owning `ReasoningRow`) could revisit which package renders it.
