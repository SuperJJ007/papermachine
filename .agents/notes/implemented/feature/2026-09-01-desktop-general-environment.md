# Agent Note: Desktop onboarding reaches its install path

Status: implemented

English | [中文](2026-09-01-desktop-general-environment.zh.md)

> The bind-an-existing-environment route this note describes is removed; see [PaperMachine owns its environment outright](2026-09-01-desktop-owns-its-environment.md). This note's environment-declaration, custom-environment, and DMG mechanics remain current, except that the declaration's `channels: readonly string[]` field is now `sources: readonly EnvironmentSource[]` (each an id, a display name, and channel URL(s)), described there.

## Problem

`apps/desktop` shipped a bundled micromamba binary, two discipline environment declarations (`social-science`, `biology`), a full `DesktopEnvironmentProvisioner`, and the `desktop:environments`/`desktop:provision`/`desktop:cancel-provisioning` IPC handlers in `main.ts` — all implemented and tested, none reachable. `preload.ts` exposed only `onboardingStatus`/`detect`/`bind`, and `resources/onboarding.html` offered exactly one route: bind an existing conda-family environment already on the machine. This was a deliberate v1 reversal (see [the desktop-product Agent Note](../../proposed/architecture/2026-08-23-science-desktop-product.md)), not an oversight, but it left a user with no conda-family installation at a dead end reading "未检测到可用环境" with no path forward.

The orphaned path was also broken at its end. `launchHost` requires `resolveEnvironmentBindingStatus` to return `bound`, which reads `environment-binding.json`. Provisioning wrote only `applied.json` and never a binding. A user who found and used the install route anyway would have waited out a multi-hundred-megabyte download, watched both health checks pass, and then hit `desktop host: no bound Science environment` — the failure was invisible in the code that ran, because nothing had ever run it.

## Decision

Onboarding now has two routes, both reachable: bind an existing environment (unchanged), or install one. `resources/onboarding.html` adds an install section (summary, package list, advanced editor) and a confirm panel stating download size and disk requirement before anything downloads; a hidden "detected" section replaces the old bare guidance text when nothing was found on the machine. `main.ts`'s `startProvisioning` runs a provisioning operation to completion, then calls the new `bindProvisionedPrefix`, which routes the published prefix through `resolveBindRequest` — the same re-validation the detect-and-bind path uses — before `writeEnvironmentBinding`. A provisioned environment is therefore bound exactly like a detected one; `launchHost`'s routing needed no change.

`preload.ts` adds `environments()`, `provision(id)`, `provisionCustom(packages)`, `cancelProvisioning()`, and `onProvisioningProgress(listener)` to `DesktopOnboardingBridge`, all thin `ipcRenderer.invoke`/`.on` wrappers over the handlers `main.ts` already had (`desktop:provision`) or now adds (`desktop:provision-custom`).

The two discipline declarations are replaced with one, `resources/environments/general.json`, id `general`: the Python analysis stack (numpy, scipy, pandas, matplotlib, seaborn, statsmodels, scikit-learn), the packages that decide whether a researcher's own files can be read at all (openpyxl for Excel, pyreadstat for SPSS/Stata, pyarrow for Parquet, pillow), and the R stack (tidyverse, haven, broom, modelr, lme4, survey, srvyr, data.table, jsonlite). A real `micromamba create --dry-run` solve against this set with the bundled micromamba 2.9.0 resolved 322 packages at 494 MB download with no conflicts, comfortably under the declaration's 520 MB `estimatedDownloadBytes`. `pandas` is pinned to `2.3` rather than the `3.0.5` the solver offers on request, because the models this product runs write pandas 2.x idioms and 3.0's breaking changes would surface as opaque user-visible errors, not a controlled upgrade. `ggplot2` (pulled in by `tidyverse`) is a hard requirement, not a preference: `packages/science/science-runtime/assets/chart_ggplot2.R` calls `ggplot2::ggplot_build` and `ggsave` directly, so an R environment without it fails every R chart, not just ones that ask for it. `pyreadstat` and `haven` are the SPSS/Stata read paths on the Python and R sides respectively; without them, a `.sav` or `.dta` file a social-science researcher hands the product is unreadable regardless of how much of the rest of the stack is present.

`apps/desktop/src/custom-environment.ts` adds a third route past the two fixed ones: a user-authored package list, published as a declaration under the fixed id `custom` through `buildCustomDeclaration`, which routes the token list through the same `parseEnvironmentDeclaration` a shipped declaration goes through, so a typed package spec faces identical validation before it can reach the solver's argv. Its revision is `2026.09.<digest>`, where `digest` hashes the sorted, JSON-canonicalized `(channels, packages)` pair — order-insensitive, so relisting the same set in a different order does not mint a new revision, and content-derived rather than clock-derived, so an unchanged set does not go stale and re-provision on a later calendar month. `writeCustomDeclaration`/`readCustomDeclaration` persist it to `<dshHome>/desktop-environments/custom.json`, read back on `main.ts`'s `declarations()` on every launch. Without this file, `resolveDisciplineStatus` (`discipline-status.ts`) would report `unknown-discipline` for an applied environment whose id no longer appears among the shipped declarations — exactly the state a custom install is in — and a working custom environment would route back to onboarding on every launch with no visible cause.

Drive-by: `scripts/translation-pairing.ts`'s `TRANSLATION_SCOPE_GLOB_EXCLUDES` gains `apps/desktop/.stage/**` and `apps/desktop/release/**`. `verify-translation-pairing` was walking into the packaged Host closure and the built `.app` bundles, both of which carry copies of documentation whose relative links no longer resolve from their new depth, so `pnpm run doc-sync` failed on any machine that had run `package:mac`.

## Alternatives considered

**Delete the provisioning code instead of re-wiring it.** Rejected: the v1 reversal that orphaned it was a considered decision to ship detect-and-bind first, not a decision that installing was wrong — the [desktop-product Agent Note](../../proposed/architecture/2026-08-23-science-desktop-product.md) states install as the intended fallback for a machine with nothing to detect. The code was implemented, tested, and one bug fix away from working; deleting it would have thrown away that work to solve the same problem this change solves.

**Keep separate discipline declarations (social-science, biology) instead of one general environment.** Rejected for this change: a first-time installer with no domain preference yet has no basis to pick a discipline, and the two prior declarations were narrower slices of largely the same Python/R analysis stack. One general environment removes the choice; discipline-specific declarations remain addable later as further entries in the same `declarations()` list without changing how a chosen one is applied or bound.

**Compute the custom revision from the current date instead of a content digest.** Rejected: `resolveDisciplineStatus` treats a revision change as staleness requiring re-provisioning. A date-derived revision would mark an untouched custom set stale every time the calendar rolled over, forcing a re-download of packages that had not changed.

## Consequences

A user with no conda-family environment on their machine now has a path to a working Science workspace without a terminal: install, confirm the download, wait, and land in the workspace, bound the same way a detected environment would be. The confirm panel's stated size and disk requirement are the only warning before a few-hundred-megabyte-to-multi-gigabyte download runs; there is no resumable-download UI distinct from `DesktopEnvironmentProvisioner`'s own retry-from-cache behavior. The advanced editor lets a user remove `python` or `r-base` from the list entirely, which fails the post-install health check with no pre-submission validation catching it earlier — the editor's helper text warns about this rather than the UI preventing it.

Reducing to one shipped declaration removes the two prior discipline names as installable options in this build; nothing currently applied against them is migrated, consistent with the pre-release stance of no on-disk compatibility promise. A custom install's revision digest is a function of the requested package list only, not of what the solver actually resolves — two custom sets that request the same packages but solve differently against a channel that has since republished get the same revision and are treated as interchangeable by `resolveDisciplineStatus`, an accepted imprecision matching the same solver-outcome insensitivity the shipped declaration's fixed revision already carries.

## Verification

`apps/desktop/tests/custom-environment.spec.ts` covers `buildCustomDeclaration`'s id, package passthrough, and health checks; order-insensitive and content-sensitive revisions; token validation rejecting a spec that would reach the solver argv as a flag or a shell-metacharacter payload; an empty package list; and the persistence round-trip, including a corrupt-file read failing loudly instead of silently reporting no custom environment. `apps/desktop/tests/onboarding.spec.ts` drives the renderer against a mocked bridge: the confirm panel states size and disk before any download call fires, confirm/cancel gates both the shipped and custom routes, the custom editor is prefilled from and diffable against the shipped list, progress updates render, a failed download returns the page to a usable state, and an unreadable environment list disables Install with the reason shown. `environment-declaration.spec.ts` pins the single shipped `general` declaration and that its packages include the interpreters and plotting packages the kernel assets require. `main.ts`'s `startProvisioning`/`bindProvisionedPrefix` and the `desktop:provision-custom` handler have no dedicated unit test: `main.ts` is Electron-dependent composition that the existing suite (per the harness-home Agent Note) exercises only indirectly, through `HostLifecycle` and the modules it wires rather than through Electron's own `app`/`ipcMain`.
