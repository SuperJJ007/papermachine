# Agent Note: Desktop usage telemetry: dual-write, no buffer

Status: implemented

English | [中文](2026-09-01-desktop-usage-telemetry.zh.md)

## Problem

PaperMachine shipped with no way for its owner to see install success or active users. Downloads are already counted by the distribution channel, not the app, so the gap was specifically: did an install actually finish, and does anyone keep launching it afterward. `apps/desktop` had no prior telemetry code, and the Host's own session telemetry (`apps/cli/src/profile-boot.ts`) is a separate, unrelated switch that this application's Electron main process never touches.

## Decision

Three metadata-only events, defined in `src/telemetry.ts`: `app.launch` (once per process start), `environment.installed`, and `environment.install-failed`, both carrying the package source (`tuna`/`ustc`/`official`, or a custom declaration's chosen source), and the installed event additionally carrying `durationMs` and `environmentId` (`general`/`custom`); the failed event instead carries the last `ProvisioningProgress.phase` observed and whether the run was cancelled. Every event also carries a fresh `eventId`, the shared anonymous id, an ISO timestamp, `appVersion`, `platform`, `arch`, and `schemaVersion: 1`. No hostname, username, path, package list, or error message text is ever included — error text can carry a path, so it is excluded even from the failure event. `platform` accepts `darwin` and `win32`: wider than `DesktopPlatform` (`environment-declaration.ts`), which stays darwin-only until the Windows port ships its own environment declarations — telemetry's vocabulary tracks what `main.ts` can run the Electron process on, not what conda environments are supported yet.

`ProvisioningProgress` (`provisioning.ts`) gains an optional `sourceId`, populated from the `solving`/`installing` phase onward with the source currently (or, once one succeeds, finally) being attempted; `main.ts`'s `startProvisioning` tracks the latest value across a run's progress callback so a caught failure can report which source it was last attempting. `AppliedEnvironment` gains a required `sourceId`, set from the loop iteration that actually created the prefix — the ordered source fallback (see the [owns-its-environment note](2026-09-01-desktop-owns-its-environment.md)) means the source that succeeds is not always the one first requested.

The anonymous id is the Host's own: `<dshHome>/.anonymous-user-id`, written by the identity plugin (`packages/identity/anonymous-user-id/src/index.ts`) as a bare `${uuid}\n` line via an exclusive-create (`wx`) write, with a reread-then-plain-overwrite fallback on a concurrent winner or a corrupt existing file. `apps/desktop/src/anonymous-id.ts` reimplements this exact algorithm rather than importing the package, matching this application's established pattern (`atomic-write.ts` similarly reimplements durable-write logic rather than depending on `packages/`) of shipping with no runtime dependency on the workspace's product packages. The compatibility contract is the on-disk format, not shared code: desktop's own first `app.launch` fires during onboarding, before any Host process has run, so it is frequently the id's true point of creation, and a Host launched afterward reads the file desktop already wrote.

Receivers are configured at build time in `resources/telemetry.json` (closed record, `schemaVersion: 1`, `endpoints: string[]`), parsed by `src/telemetry-config.ts` against the same strict `https://` URL allowlist `environment-declaration.ts` uses for conda channel URLs — extracted to a shared `src/https-url.ts` so both closed records validate identically rather than maintaining two copies of one parser-boundary regex. A missing or unparseable file throws, surfacing through `main.ts`'s `boot()` as a loud launch failure (`app.exit(1)`) rather than a silent disable; an empty `endpoints` array is the valid, distinct "telemetry off" state. This build ships the deployed Cloudflare Worker (`apps/telemetry-receivers`) as its one endpoint. `TelemetryReporter.report` sends the built event to every configured endpoint independently via `fetch` with a 5-second `AbortSignal.timeout`, wrapping each attempt in its own try/catch so one endpoint's failure, non-2xx response, or hang never affects delivery to another or blocks the caller. `resolveTelemetryEndpoints` reduces `endpoints` to `[]` whenever `DSH_TELEMETRY_DISABLED` is any non-empty value, mirroring `resolveTelemetryPatch`'s interpretation of that same variable for the Host's own telemetry — one environment variable now disables both.

`apps/telemetry-receivers` owns the two deployment targets and one shared strict event validator. Both targets accept only `POST`, stop buffering once a body exceeds 8 KiB, reject malformed or non-canonical records before persistence, return empty responses, expose no authentication or CORS behavior, and never store IP addresses, User-Agent values, or request metadata. The Aliyun target reads only `Content-Length` for the size limit. After validation, the Cloudflare Worker reads `cf-connecting-ip` solely as the key for a 20-event-per-60-second rate limit within each Cloudflare location; invalid requests consume no quota, and the Worker never logs or persists the key. Unknown body fields are invalid because the Aliyun target writes the complete accepted object to SLS; this prevents an accidental client field from expanding what reaches telemetry storage. The Aliyun Node.js web function reads its listening port from `FC_SERVER_PORT`, defaulting to `9000` and refusing to start on a non-integer value, and writes one bare `JSON.stringify(event)` stdout line per accepted request; it keeps no instance-local dedupe state, so SLS queries deduplicate `eventId`. The Cloudflare Worker binds D1 as `DB`, fills `received_at`, and awaits `INSERT OR IGNORE` against the `event_id` primary key before returning `204`, so a duplicate is a successful no-op; an exceeded rate limit instead returns an empty `429` before the insert. The workspace pins Wrangler `4.127.1` for repeatable Worker and D1 deployments and explicitly permits workerd's reviewed prebuilt-platform selector install script. `apps/telemetry-receivers` is a deployment-only package (Worker/Function code pushed straight to a cloud provider, never installed by a consumer), so `scripts/check-workspace-constraints.ts` names it in an explicit `deploymentOnlyAppDirectories` allowlist: it must stay `private: true` and carry no `publishConfig`, and it is exempt from the `apps/*` publication-files policy the other release-member apps must declare.

`main.ts` constructs one `TelemetryReporter` early in `boot()`, right after the Harness home resolves (needed for the anonymous id), and reports `app.launch` there without awaiting (`void telemetry.report(...)`). `startProvisioning` reads the same module-level reporter to report the outcome of each provisioning run. `resources/onboarding.html` states, in the same bilingual style as the rest of the page, that the app reports anonymous usage statistics and that this can be turned off; no toggle UI ships in this version.

## Alternatives considered

- **One endpoint with client-side failover among mirrors.** Rejected: the owner's stated purpose is comparing mainland-China reachability between a Cloudflare Worker and an Aliyun Hong Kong function, which requires each receiver to see its own complete, independent stream from every user who can reach it — a failover client would only ever report to whichever endpoint answered first, hiding the exact signal the owner wants.
- **Depending on `@deepseek-ai/dsh-anonymous-user-id` directly instead of reimplementing its file format.** Rejected: `apps/desktop` ships with no runtime dependency on `packages/` (its `package.json` carries only `devDependencies`), and this application's Electron main process is not part of the Cordis-composed Host the package is designed for. Reimplementing the same read/write algorithm keeps that boundary intact while still guaranteeing the two processes agree on the file.
- **An offline retry queue or buffered send.** Rejected for this version: it adds a persistence format, a replay path, and a growth bound for a metrics feature whose product value is an aggregate trend, not a complete census. A user offline at launch is simply not counted that day; this is stated here as the accepted, deliberate gap rather than left implicit.
- **A settings-panel toggle for turning telemetry off.** Rejected for this version: the task scope is one honest onboarding sentence plus the existing `DSH_TELEMETRY_DISABLED` environment variable, not new settings UI. The sentence states a real, already-working turn-off path (the environment variable), not a promise of a future toggle.

## Consequences

The owner can now see install success (`environment.installed`/`environment.install-failed`, split by source and phase) and active usage (`app.launch`) from two independent receivers, correlatable across them by `eventId` if ever merged, without any event carrying content, file paths, hostnames, or usernames — `error text can contain paths` is why `environment.install-failed` reports a structured `phase` enum value rather than the underlying error's message. The accepted cost is silent undercounting: any user offline, on a blocked network, or running with telemetry disabled contributes zero events for that session, with no queue to catch up later. Users behind one shared IP also share the Cloudflare quota and can therefore be undercounted; the IP key protects ingestion integrity against callers that rotate anonymous ids without adding it to stored telemetry. `resources/telemetry.json` now ships the deployed Cloudflare Worker as its one endpoint; the Aliyun receiver remains available but unlisted until the owner adds its URL and cuts a new build. `DSH_TELEMETRY_DISABLED` still overrides `resources/telemetry.json` at any non-empty value, sending nothing regardless of what ships.

## Verification

`tests/telemetry-config.spec.ts` covers `endpoints: []`, three shipped-style URLs, rejection of a non-`https` and shell-metacharacter/whitespace endpoint (a parser-boundary check), an unknown field, a wrong `schemaVersion`, and the shipped `resources/telemetry.json` itself. `tests/anonymous-id.spec.ts` covers creating the file in the identity package's exact `${uuid}\n` format when absent, reusing an existing valid id, minting and persisting a fresh id over a corrupt existing file (matching the package's reread-then-overwrite fallback), and stability across repeated calls. `tests/telemetry.spec.ts` covers the exact field set of all three event kinds, dual-delivery to every configured endpoint, a failing or hanging endpoint not affecting delivery to or blocking the caller waiting on the others, the `DSH_TELEMETRY_DISABLED` switch (including that any non-empty value disables, matching the Host's interpretation), reporting `win32` as a configured platform, and that `report` never rejects even when every endpoint fails. `tests/provisioning.spec.ts` adds coverage that `AppliedEnvironment.sourceId` and `ProvisioningProgress.sourceId` name the source that actually succeeded (not necessarily the first attempted) through the ordered fallback loop.

`apps/telemetry-receivers/tests` runs the shared validator against every event variant and invalid envelope cases — including accepting `win32` alongside `darwin` and rejecting an unlisted platform such as `linux` — exercises the Aliyun HTTP server's empty `204`/`400`/`405`/`413` responses and stdout payload, and exercises the Cloudflare Worker's D1 insert, duplicate success, post-validation rate-limit allow and reject paths, invalid-request non-write and non-consumption of quota, and empty `500` behavior.

`scripts/check-workspace-constraints.spec.ts` covers `checkDeploymentOnlyAppManifest` accepting a private manifest without `publishConfig` and rejecting one that sets `private: false` or declares `publishConfig`.
