# Agent Note: Deployment-level MCP tool curation

Status: implemented

English | [中文](2026-09-01-mcp-tool-curation.zh.md)

## Problem

`@deepseek-ai/dsh-mcp-client` registered every tool a connected MCP server advertised. A desktop deployment wiring two paper-search MCP servers with a combined 76 tools put every one of them, with its full schema and description, into every model request — 1–2 万 token of tool-selection noise the model paid on every turn regardless of which tools the task actually needed. Nothing in `cordis.yml` could narrow that set, rename a tool the deployment found confusingly named, or replace a description that did not trigger correct tool choice; the only lever was disconnecting the whole server.

## Decision

**Tool curation is a deployment decision, expressed once in `cordis.yml`, never a model or per-request choice.** `StdioConfig`/`StreamableHttpConfig` (`packages/mcp/mcp-client/src/index.ts`) gain an optional `tools` block — `include`, `exclude`, `rename`, `describe`, all keyed by the server's raw MCP tool name (`rawName`) — resolved once by `resolveToolFilter` (`packages/mcp/mcp-client/src/tools.ts`) into a `ResolvedToolFilter` of `Set`/`Map`s that `startConnection` threads through `ToolBridgeOptions` unchanged for the plugin instance's lifetime. Omitting `tools` — or leaving every field empty, which is what Schemastery materializes an omitted field to since `object`/`array`/`dict` schema types default to `{}`/`[]` at construction regardless of an explicit `.default()` call — reproduces the pre-existing behavior of registering every discovered tool exactly as the server describes it.

**`include` then `exclude`, `rename` only changes the public-name suffix, `describe` only changes the registered description.** `syncTools` applies `include` first (non-empty restricts to listed rawNames), then `exclude` (removes rawNames from what remains, independent of whether `include` restricted anything). `rename`'s value substitutes for `rawName` only in the `publicToolName(serverName, suffix)` derivation — normalized through the same DeepSeek function-name contract as any other tool name — while `tools/call` still sends the original `rawName` on the wire; the two names' `(serverName, rawName)` identity relationship the naming contract documents is preserved, `rename` just changes which string plays the `rawName` role in that one derivation. `describe`'s value replaces the server-provided description read at `createDefinition` time.

**Validation splits by what is resolvable when, matching the existing config-resolve-vs-connect split `resolveReconnectPolicy` already uses.** Two different rawNames renaming to the same suffix is a pure function of the config — checked inside `resolveToolFilter` at plugin `apply()`, before any effect registers, alongside the existing reconnect-policy resolution. Whether a rawName named anywhere in `include`/`exclude`/`rename`/`describe` is one the server actually advertises needs a live tool list, so `validateToolFilterReferences` runs inside `syncTools`, on every sync — initial connect, every reconnect, and every `notifications/tools/list_changed` re-sync — against that sync's freshly fetched rawName set, batching every missing reference into one message rather than failing on the first.

**A stale filter reference fails exactly like the pre-existing "server listed one rawName twice" case: `syncTools`'s fetch phase throws.** `syncTools` already threw when the server's own tool list disagreed with what the harness would register (a duplicate rawName resolving to one public name); a filter reference to a rawName the server never advertised is the same shape of problem — the deployment's tool bridge and the server's actual tool list disagree — so it reuses the identical fetch-phase-throw path rather than inventing a new failure mode. That throw's existing consumers determine the practical effect: at initial connect, `connectGeneration` treats it like a failed connection attempt (retried under the reconnect policy, or rejecting plugin activation when `failOnStartupError` is true); at re-sync after `notifications/tools/list_changed`, the notification handler logs `tool re-sync failed` and keeps the previous generation registered untouched, per the pre-existing "fetch-phase failure leaves the previous generation intact" contract. No new failure-handling mechanism exists; a config-vs-server-name mismatch was always going to surface through the mechanism that already recognizes a broken tool list, keeping name-collision and name-not-found diagnostics next to each other in the same `syncTools` phase.

**`syncTools` restructures into three explicit phases** (fetch the full raw listing, validate the filter's references then apply `include`/`exclude`/`rename`/`describe` while building `ToolDefinition`s, swap generations) instead of the prior two (fetch-and-build, swap), so the filter's reference check runs once against the complete server list before any per-tool decision, independent of `include`/`exclude` — an excluded-but-misspelled reference is still caught rather than silently passing because it would never have registered anyway. The duplicate-public-name check inside the build phase now also catches a `rename` landing on another (possibly unrenamed) tool's name, generalizing its message from "server listed tool more than once" to name the resolved public name and both possible causes.

## Alternatives considered

- **A separate model-visible "tool directory" the model expands on demand, deferring full schemas until requested (a deferred-tools pattern).** Rejected for this change: it is a different mechanism — it keeps every tool nominally reachable and shifts the cost from constant schema tokens to a directory-lookup turn, rather than removing tools the deployment never wants reachable at all. It remains a plausible follow-up for a deployment that wants breadth without a fixed curated set, but was out of scope here; recorded so a future change does not rediscover this need from scratch.
- **Validate every `tools` reference at plugin load, before connecting.** Rejected: the server has not been asked for its tool list yet at that point, so there is nothing to validate a reference against; the check would either be vacuous or would need to connect early just to validate, duplicating the connection `syncTools` already performs.
- **Silently drop an `include`/`exclude`/`rename`/`describe` entry that does not match any discovered rawName.** Rejected: a misspelled or renamed-upstream rawName would silently stop taking effect, and the deployment would have no signal that its curation was no longer doing what the `cordis.yml` says — exactly the silent-narrowing failure mode `docs/AGENTS.md`'s "misconfiguration fails loud" convention exists to prevent.
- **A dedicated `ToolFilterMismatch`-style error class or failure path, separate from the existing fetch-phase throw.** Rejected: the existing throw already has well-tested, well-understood consumers across initial connect, reconnect, and re-sync; a second failure shape would need its own handling in three call sites for a distinction (which check produced the reject) that the log message text already carries.

## Consequences

A deployment with `tools.include` covering only the paper-search tools a Science session actually calls turns a 76-tool, ~15–20k-token roster into the handful the deployment names, with the same reduction in tool-selection noise on every turn. `rename` and `describe` let a deployment fix a confusing upstream name or description without forking or patching the MCP server. Every `tools` reference is now a load-bearing part of `cordis.yml`: renaming or removing a tool on the MCP server side without updating the deployment's `tools` config turns a previously-silent no-op into a failed sync, retried under the reconnect policy — a deliberate hardening, not a regression, but an operational fact for whoever maintains the deployment's `cordis.yml` alongside the MCP server's own tool set. The `tools` field's default (all four subfields empty) is indistinguishable at the `Config` level from "curation was never configured," by construction of how Schemastery resolves `object`/`array`/`dict` schema types — this repository accepts that as the necessary and sufficient shape for "omission is a no-op," not a limitation to work around.

## Testing

`packages/mcp/mcp-client/tests/mcp-client.spec.ts` covers `resolveToolFilter` (omission producing an empty no-op filter, `include`/`exclude`/`rename`/`describe` resolving into the expected `Set`/`Map`s, and the rename-target-collision throw) and `syncTools` (`include` alone, `include` then `exclude`, `exclude` alone, `rename` changing the public name while the wire call still uses the original rawName, `describe` overriding the registered description, a stale `include` reference rejecting with every missing name batched into one message across `include`/`exclude`/`rename`/`describe`, and a stale reference on a re-sync leaving the previous generation registered). `packages/mcp/mcp-client/tests/apply.spec.ts` covers the `Config` schema materializing `tools` defaults and keeping explicit values, and `apply()` failing loud on a `tools.rename` collision before any effect registers. `packages/mcp/mcp-client/tests/reconnect.spec.ts` covers a configured `exclude` staying in effect across a reconnect that advertises a different tool list, proving the filter is re-applied rather than reset. Coverage on `packages/mcp/mcp-client/src/**` is 100% per the repository's per-file gate.
