# Agent Note: surfacing store↔session reconciliation health in `scienceLibrary` and the Files panel

Status: implemented

English | [中文](2026-09-02-science-reconciliation-surfacing.zh.md)

## Problem

[T3a](../architecture/2026-09-01-artifact-store-session-reconciliation.md) built the store-side reconciliation algorithm and a pure read interface, `ScienceArtifactStore.getReconciliationSummary(projectId): Promise<ReconciliationSummary>` (`{ orphanCount, reconstructedCount, missingContentCount, items }`), but nothing consumed it: `dsh-api-proxy`'s `scienceLibrary` RPC returned only `{ projectId, artifacts }`, and `dsh-client-ui-science`'s Files panel had no way to learn a version was unhealthy. Separately, `dsh-api-proxy` did not compile at all against this migration's earlier T1/T2 changes — `authorizedScienceArtifact`'s local-session-fold branch read `mediaType`/`byteCount` straight off the `science/artifact-saved` event, both fields [T2a's event slimming](../architecture/2026-09-02-science-artifact-event-slimming.md) removed — a real runtime bug (one apiproxy test asserted an `undefined` value against `'image/png'`), not only a type error.

## Decision

**`scienceLibrary`'s response gains a `health: { orphan, reconstructed, missingContent }` project-wide count, plus a per-artifact `latest.health` mark, both read from one `getReconciliationSummary` call per request — never computed by re-deriving reconciliation state in the BFF.** The aggregate counts are the summary's own `orphanCount`/`reconstructedCount`/`missingContentCount` verbatim. The per-artifact mark (`ScienceVersionHealthFlags`, `{ reconstructed?: true; missingContent?: true }`) is set only when the summary's `items` name that exact `latest.versionId` — an artifact whose *older* version is unhealthy but whose current latest is fine carries no mark, since `scienceLibrary` only ever returns latest rows. `orphan` never appears on a per-item mark, matching T3a's own design: an orphan version is a real, complete version with no session claiming it, an accepted crash-window outcome, not a fact worth flagging on a specific card.

**`authorizedScienceArtifact`'s local-fold branch now resolves `mediaType`/`byteCount` through `store.getVersion(local.projectId, local.versionId)`, keeping only `sha256` from the session event.** This mirrors the client-content-facts-from-store precedent [T2b-2](../feature/2026-09-02-science-tool-receipts-slimming.md) already established for `dsh-tool-science`'s model-facing fields: the event pins `sha256` (verifiable independent of the store), while `mediaType`/`byteCount` are content facts the store alone owns after T1. This was this package's own pre-existing compile break to fix, not new work invented for this task — flagged as in-scope in the T3b task book itself, the same way T2b-2's Note named `dsh-api-proxy` as one of several out-of-boundary breaks for its own task to leave alone.

**The Files-panel banner (`ReconcileBanner`, `dsh-client-ui-science`) never mentions `orphan`, matching the store's own documented stance verbatim.** It renders only when `reconstructed` or `missingContent` is non-zero, states each count, and offers an expandable list built from the artifacts array's own `latest.health` marks — not a second RPC. A library-opened tab whose `latest.health.missingContent` is set shows explicit "content is missing" text in place of `ReadOnlyPreview`, and `ArtifactToolbar` gains a `contentUnavailable` prop that disables Download (via the same `aria-disabled` + `Tooltip` idiom already used for the unavailable Export control) and hides Maximize for an image version — the store's own health mark is sufficient to disable these without a dedicated error code, since the artifact-authority migration's own T4 task (not yet landed on this branch) owns the raw-bytes download endpoint whose error codes a later change can wire in.

**`ScienceDetailsInjected['loadLibrary']`'s type is now declared locally in `dsh-client-ui-science` rather than reused verbatim as `ISession['readScienceLibrary']` (`dsh-client-runtime`), with `health` optional.** `dsh-client-runtime` is outside this task's package boundary — T4's own task book names it explicitly as territory that touches `scienceLibrary`'s consumption again (a `scienceVersions` RPC, unified title/caption sourcing) — so widening its hand-written return type was left alone. The local type is still exactly what the real wire sends: `RpcResult<{ projectId; artifacts; health }>` with `health` marked optional only because the not-yet-widened `ISession['readScienceLibrary']` return (`{ projectId; artifacts }`, no `health` field at all) needs to keep type-checking against it — an object type missing an optional field is assignable to one that declares it, so `session.readScienceLibrary.bind(session)`'s real injected value satisfies this wider local slot today, and will keep doing so once `dsh-client-runtime` catches up and the field stops being effectively-always-present-but-typed-optional.

## Alternatives considered

**Widening `ISession['readScienceLibrary']` in `dsh-client-runtime` directly, so `health` could be declared required** — rejected: outside this task's stated package boundary (`dsh-api-proxy` and `dsh-client-ui-science` only); T4's task book already claims `dsh-client-runtime` for its own `scienceLibrary`-adjacent work, and touching it here would risk colliding with that task's own design for the same surface.

**Deriving the banner's aggregate counts by summing each artifact's own `latest.health` marks client-side, instead of a dedicated response-level `health` field** — rejected: `scienceLibrary` only returns one *latest* row per artifact, while `getReconciliationSummary`'s counts cover every version in the project's store; an older, non-latest unhealthy version would be silently dropped from a client-side sum, understating the true count the banner is supposed to report.

**Giving the missing-content Files-panel card a distinct thumbnail treatment (skip the image loader, show a "content missing" tile)** — deferred, not done: the task's own scope named only the banner (project-wide) and the detail-panel text (per opened version); a card-level thumbnail change was not requested and adds a branch with no test coverage evidence it was needed. `dsh-client-ui-science`'s `ScienceArtifactImage` component already degrades to its own retry affordance on a load failure, so an unmarked card is not silently broken today — it is simply not distinguished from a healthy one until opened.

## Consequences

Scope: `packages/host/apiproxy` (`src/api/sessions.ts`, `src/api/sessions.schema.ts`, `src/api/index.ts`, `src/api-proxy.ts`, `tests/api-proxy-models.spec.ts`, `tests/client-handler.spec.ts`, `tests/fetch-carrier.spec.ts`) and `packages/client/ui-science` (`src/client/library-artifact.ts`, `src/client/ScienceDetailsView.tsx`, `src/client/ScienceDetailsView.module.css`, `src/client/locales.ts`, `tests/ScienceDetailsView.client.spec.tsx`). Both packages' READMEs (+ `.zh.md`) document the new `health` field, the per-item mark, the banner, and the missing-content detail treatment; both are recorded in `verify-translation-pairing`'s per-package `.i18n.yaml` sidecar.

`dsh-api-proxy` now compiles cleanly (`npx tsc -p packages/host/apiproxy/tsconfig.json --noEmit`) and its full test suite passes (392 tests) with 100% per-file statement/branch/function/line coverage on `packages/host/apiproxy/src`. `dsh-client-ui-science` does **not** compile cleanly, and neither `npx tsc -b packages/client/ui-science/tsconfig.json` nor the type-aware `oxlint` pass — both fail on a large, pre-existing break this task did not introduce and does not fix: `ScienceClientArtifactVersion` (`dsh-science-session`) lost `mediaType`/`byteCount`/`origin`/`parent`/`runId`/`producerSessionId`/`createdAt`/`chart` in the same T2a event-slimming pass that motivated this task's own apiproxy fix, and nothing on this branch has yet rewired `dsh-client-ui-science`'s consumption of those fields to source them from the store instead (the same "unified read path" work T4's own task book claims). Every error line checked traces to code this task did not touch (confirmed against `git show HEAD:...` before this task's first edit); this task's own added code was verified by direct review to read only fields `ScienceClientArtifactVersion` still has (`artifactId`, `logicalName`, `version`, `title`, `caption`, `versionId`, `sha256`, `seenAt`) plus the `ScienceLibraryArtifact`/`ScienceLibraryHealth` types this task itself defines, and by 543 passing `dsh-client-ui-science` tests (vitest's esbuild transform does not type-check). Coverage on this task's own changed file, `ScienceDetailsView.tsx`, is 100%; the package-wide run shows one pre-existing gap outside this task's diff (`src/client/index.ts:354`, from an earlier, already-landed commit unrelated to reconciliation).

## Testing

`packages/host/apiproxy/tests/api-proxy-models.spec.ts` gained one dedicated test asserting `scienceLibrary`'s `health` counts and confirming a per-artifact mark appears only for `reconstructed`/`missingContent`, never `orphan`; three existing tests were updated with a `getReconciliationSummary` (or `getVersion`, for the local-fold fix) mock they were missing. `packages/client/ui-science/tests/ScienceDetailsView.client.spec.tsx` gained a `T3 store↔session reconciliation health` suite: the banner appearing with both counts and an expandable list (including a `title`-less artifact's `logicalName` fallback), the banner never appearing for an orphan-only response, and the detail panel's explicit missing-content text plus a disabled Download button that adds no new `loadImage` call when clicked.
