# Agent Note: `saveArtifactAs` — duplicating a committed artifact version into a new logical artifact

Status: implemented

English | [中文](2026-09-02-science-save-artifact-as.zh.md)

## Problem

The artifact-authority acceptance criteria for this migration name a "save as" path — the artifact viewer duplicating one committed version under a new logical name — that did not exist anywhere in the codebase: no Runtime method, no Remote, no request type. Every existing artifact-producing path assumes a producer identity the new version genuinely has (a run's own `producerRunId`/`toolCallId`, a curation's own authorizing call, a style edit's own kernel round trip); a viewer-initiated duplication has none of those, and the T1 store schema's `baseVersionId`/`baseExplicit` split (an explicitly declared content baseline, never defaulted) gives it a fact to declare that none of the three existing write paths needed in quite this shape: a baseline naming a *different* artifact entirely, not a predecessor version of the same one.

## Decision

**`ScienceRuntime.saveArtifactAs({ session, sourceVersionId, newLogicalName, signal })` is a fourth artifact-mutating Runtime operation, alongside capture, `annotateArtifact`, and `commitStyleEdit`, following the same reserve-lease/`assertPrepublication`/append-event shape.** It resolves the owning project through the calling session (`sessionProject`, the same resolution every other mutator uses), reads the source `VersionRecord` and its owning `ArtifactRecord` (for `kind`) from the store, then calls `store.createArtifact` with a fresh `artifactId`, ordinal 1, `baseVersionId: source.versionId` (`baseExplicit` is always `true` here — a save-as always names an explicit baseline, by construction), the source's own `contentOrigin`/`mediaType`/`environmentRevision`/`environmentFingerprint`, and the source's `figure_state` row when one exists (read via `getFigureState`, passed through as `createArtifact`'s `figureState` input). `producerSessionId` is the *calling* session, not the source's own producer — this is a fact the *duplication* originates, not a copy of the source version's producer identity, matching the general rule that provenance is fixed once at content-commit time and a save-as is its own commit. No `producerRunId`/`producerToolCallId`/`producerRequestHeaderSeq` is set — a viewer action, never a model tool, has no authorizing call to record. A separate `actor: 'human'` annotation copies the source's current title/caption forward, mirroring `commitStyleEdit`'s own title-inheritance annotation (three actors — `capture`, `model`, `human` — three call sites, one mechanism, as `2026-09-02-science-runtime-provenance-writes.md` already established for the first two).

**Blob reuse means re-admitting the source's own bytes through the ordinary `createArtifact` write, not skipping the write.** `admitBlob`'s rename-onto-a-content-addressed-path is idempotent by SHA-256 (`blobs.ts`'s own doc: "always byte-identical for the same digest, so admission is idempotent by hash without an existence pre-check") — re-admitting bytes already present in the project's blob store costs one filesystem rename onto an unchanged target, not a second copy. This keeps `saveArtifactAs` a single ordinary call into the store's existing write path instead of a bespoke shortcut that would need its own dedicated blob-linking mechanism the store does not otherwise have.

**`sourceVersionId` is resolved against the project's store, not the calling session's own projection.** Every other mutator (`annotateArtifact`, `applyChartEdit`) resolves its target from `this.assertSession(request.session)`'s live projection, because their targets are things that session's own fold already knows about (a `logicalName` the session captured, an `artifactId` the session's history names). A viewer-initiated save-as has no such constraint — the artifact library it operates over is project-wide (T1's own `listArtifacts`/D7 cross-session-continuation reasoning), so a source version any session in the project produced is a legitimate target, checked with a direct `store.getVersion(projectId, sourceVersionId)` read.

**Two new `ScienceRuntimeErrorCode` values, one store error translated, one store error surfaced directly.** `ARTIFACT_VERSION_NOT_FOUND` (source lookup returns `undefined`) and `ARTIFACT_LOGICAL_NAME_CONFLICT` (the store's own `ProjectArtifactStoreError` with code `LOGICAL_NAME_CONFLICT`, caught and re-thrown as a `ScienceRuntimeError`) are the only two rejections specific to this operation; every other store or infrastructure failure propagates through the same `prepublicationError` classification every mutator already uses. The Remote (`ScienceEditService.saveArtifactAs`, `dsh-tool-science`) translates these two onto its own `SAVE_AS_SOURCE_NOT_FOUND`/`SAVE_AS_NAME_CONFLICT` `ScienceEditErrorCode` values and passes every other error through unchanged — the same shape `translateChartRuntimeError` already uses for `applyChartOps`/`previewChartOps`, kept as a separate inline translation here rather than folded into that shared helper, since the two operations' error vocabularies do not overlap.

**No model tool.** `saveArtifactAs` is registered only as a Typert `@Remote` method on the existing `ScienceEditService` (`edit-message.ts`), reached exclusively through the Web Host's `./edit-service` entry the artifact viewer calls — `dsh-tool-science`'s model-facing tool roster (`get_science_state`, `run_python`, `run_r`, `annotate_artifact`, `install_science_packages`) is unchanged. The viewer's own save-as button and UI flow are T4's scope; this task delivers the Runtime method, the Remote, and their tests only.

## Alternatives considered

**Skip the `createArtifact` write entirely and insert a `versions` row directly aliasing the source's blob path** — rejected: it would need a second, bespoke write path parallel to `createArtifact`'s own (transaction discipline, ordinal assignment, the `UNIQUE(owningProjectId, logicalName)` conflict check) for a byte-cost saving `admitBlob`'s own idempotent-rename design already delivers for free.

**Default `producerSessionId` to the source version's own producer, treating save-as as a re-stamp of existing provenance** — rejected: this is exactly the shape T1's authority rule and the T2b-1 provenance-writes note reject for curation (D2 — a metadata operation's own actor must never impersonate the content's original producer). A save-as is a new fact this session originates; recording it as the source's own producer would let one save-as attribute new bytes-adjacent metadata to a session that never touched this exact new artifact.

**Resolve `sourceVersionId` against the calling session's own live projection, matching `annotateArtifact`'s pattern** — rejected: a viewer-driven duplication has no reason to be scoped to what one session happens to have captured, and the whole point of a project-wide artifact library (T1's `listArtifacts`, D7's cross-session continuation) is that any session viewing the project can act on any version in it.

## Consequences

Scope: `packages/science/science-runtime` (the method, its request/error-code types) and `packages/science/tool-science` (`ScienceEditService.saveArtifactAs`, its request/receipt types) only. `packages/science/science-runtime/tests/save-as.spec.ts` (new) and the `scienceEdits saveArtifactAs` cases in `packages/science/tool-science/tests/tool-science.spec.ts` cover it at 100% per-file coverage on both packages' `src`. The artifact viewer's save-as button, its request wiring through the generated Typert client, and any keyless snapshot exercising it end to end are T4/T5's scope — this task adds no UI and touches no example bundle.

`pnpm run duplication` flags the new method's `assertPrepublication`/append/`catch`/`finally` tail (`saveArtifactAs`'s and `annotateArtifact`'s closing ~9 lines) as a clone. This is the same boilerplate shape two other pre-existing pairs in this file already share unextracted (`bindEnvironment`'s and `installPackages`'s revision-append tails; `startRun`'s and `applyChartEdit`'s pre-publication guard blocks) — every Runtime mutator wraps genuinely different logic in an identical lease/prepublication/append/release template, and this file's own prior authors have consistently left that wrapper unextracted rather than parameterizing it over the differing body. This task follows the existing convention rather than introducing a new one unilaterally; a shared-tail extraction, if wanted, is a repo-wide style decision spanning all four existing pairs, not a change local to this one addition.

**T4b-2 delivered the viewer's own save-as button** (`packages/client/ui-science/src/client/ScienceDetailsView.tsx`'s `ArtifactToolbar`/`SaveAsForm`): a toolbar toggle opens an inline name input calling the injected `saveArtifactAs` Remote with the open version's `versionId`, `SAVE_AS_SOURCE_NOT_FOUND`/`SAVE_AS_NAME_CONFLICT` get dedicated localized text in the form, and a successful call switches the active tab to the receipt's new `artifactId`/`version` — the Files panel picks up the new artifact on its own next mount rather than through an explicit invalidation signal.
