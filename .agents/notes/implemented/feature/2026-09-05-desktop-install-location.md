# Agent Note: A chosen Harness home persists as a pointer file, applied by relaunch

Status: implemented

English | [中文](2026-09-05-desktop-install-location.zh.md)

## Problem

`resolveHarnessHome` (`harness-home.ts`) already accepted a `customHomeDir` argument taking precedence over `PAPERMACHINE_HOME` and `DSH_HOME`, but nothing in the application ever passed one: a Windows user whose `C:` drive cannot hold the roughly 6 GB shipped environment had no way to install elsewhere short of setting an environment variable before launching a GUI application — not a workflow a packaged installer's user can follow. Separately, the "Copy Diagnostic Report" button onboarding's failed-install path already offered named platform, user agent, time, and the error text, but not the Harness home path or which package source had been attempted — exactly the facts a maintainer triaging a report needs first, and the two gaps a filed issue asked for by name.

## Decision

A new module, `install-location.ts`, owns a pointer file directly under the OS home directory, `<osHomeDir>/.papermachine-home` — an ASCII-only filename chosen deliberately so it stays readable even when the home directory's own path is otherwise problematic (non-ASCII, containing a space). The file holds exactly one absolute path, written atomically through the existing `writeFileAtomic` (`atomic-write.ts`) shared with the environment-binding and applied-environment pointers. `readInstallLocationPointer` returns `undefined` for a missing file — the ordinary case — and throws, naming the file, for one that exists but is empty, whitespace-only, or names a relative path: silently falling back to the default Harness home for a corrupt pointer would run the Host and every kernel against the wrong drive without any indication why. `main.ts`'s `harnessHome()` reads this pointer and passes it as `resolveHarnessHome`'s `customHomeDir`, so a pointer file now outranks both `PAPERMACHINE_HOME` and `DSH_HOME` — it is the one precedence tier a GUI user reaches without an environment variable, and `harness-home.ts`'s JSDoc documents this application's specific source for that argument.

Onboarding's environment-choice screen gained an install-location row, rendered from a new `desktop:install-location` IPC call, showing the resolved path plus a "Change…" button and, only while a pointer file is in effect, a "Use default" button, with a line stating that changing it restarts the application and does not move an already-installed environment. "Change…" opens `dialog.showOpenDialog` from the main process (never `window.prompt`, which this application's renderer forbids) defaulting to the current Harness home's parent directory; a cancelled dialog is reported as `cancelled` and changes nothing. An accepted directory is validated by calling `resolveHarnessHome` itself before anything is written — a candidate that would throw `HarnessHomeSpaceError` is reported `rejected` with that error's message, never partially applied. A path containing a non-ASCII character (an unconfirmed risk for some conda and R packages, per the filed issue) triggers a bilingual `dialog.showMessageBox` warning that the user can accept or decline; declining reports `cancelled` the same as dismissing the picker. Acceptance writes the pointer file, then calls `app.relaunch()` followed immediately by `app.quit()` — `relaunch()` only schedules the restart, and `quit()` is what actually starts shutdown, so the existing `before-quit` handler still runs `coordinator.beforeQuit()` (aborting any provisioning run, stopping the Host, flushing telemetry) before the process exits and Electron restarts it fresh against the new home. "Use default" clears the pointer file and relaunches the same way. Both handlers report `restarting`, on which the renderer disables the two buttons and shows a restarting message rather than trying to return to a ready state that is about to be torn down anyway.

The diagnostic report gained a `desktop:diagnostics` IPC call returning the app version, `${platform}-${arch}`, the resolved Harness home, and whether it is customized. Onboarding now tracks the most recently attempted package source across `onProvisioningProgress` updates (seeded from the confirmed choice, the same rule `main.ts`'s own `lastSourceId` tracking already applied for telemetry) and, on a failed install, fetches diagnostics before building the report so it can add the app version, an upgraded platform line (`darwin-arm64` rather than the browser's generic `navigator.platform`), the Harness home path with a customized/default note, and the last source attempted — alongside the existing user agent, time, and fenced error text.

## Alternatives considered

- **Persist the choice under Electron's `userData`.** Rejected outright: `apps/desktop/tests/no-userdata-regression.spec.ts` forbids any `getPath('userData')` call in `src/`, and `userData`'s own macOS path containing a space is the exact defect `harness-home.ts` already routes around — storing the pointer to a space-free Harness home inside a space-containing directory would make the pointer's own location the next instance of the same bug class.
- **Require an environment variable (`PAPERMACHINE_HOME`) instead of a GUI control.** This is the status quo the filed issue calls out as unusable: a packaged GUI application's user has no ordinary way to set a process environment variable before launch, and the two existing environment variables remain available for the workflows that do.
- **Re-resolve the Harness home live, without a relaunch, and hot-swap the running Host.** Rejected: the Host, every kernel subprocess, the watchdog, and in-memory state such as `activeOrigin` and `hostLogPath` are all keyed to the home directory at the moment they were created; tearing all of that down and recreating it in place duplicates most of `boot()`'s own startup sequence for a rare, deliberate user action, where a relaunch reuses the exact code path every ordinary launch already exercises and is proven correct.
- **Skip the non-ASCII warning and simply accept the path.** Rejected: the filed issue names non-ASCII paths as a real, if unconfirmed, cause of failures for some conda and R packages under Chinese usernames; warning without rejecting keeps the choice with the user while surfacing a risk they would otherwise discover only after a failed multi-minute install.

## Consequences

A user on a small system drive can redirect the entire ~6 GB environment to another drive from onboarding itself, with no environment variable and no command line. The pointer file is a new on-disk format this pre-release codebase makes no compatibility promise about; a future format change may replace it outright per the repository's pre-release stance. Every install-location change costs one full application relaunch (a few seconds), accepted because it reuses the same startup path as an ordinary launch rather than a second, less-exercised in-place teardown path. A failed install's diagnostic report now names the exact Harness home and package source involved, which a filed issue can otherwise only guess at from the error text alone.

## Verification

`apps/desktop/tests/install-location.spec.ts` covers the pointer file path, `readInstallLocationPointer` returning `undefined` for a missing file and throwing (naming the file) for empty, whitespace-only, and relative content, a write-then-read round trip, atomic replacement leaving no temp file behind, `clearInstallLocationPointer` removing an existing file and no-op on a missing one, and `hasNonAsciiCharacters` for an ASCII path, a CJK path, and a space-only path (false — a distinct, separately checked risk). `apps/desktop/tests/onboarding.spec.ts` covers the install-location row rendering the resolved path, "Use default" appearing only when customized, a `rejected` result surfacing its reason and re-enabling the controls, a `restarting` result disabling both buttons, and the diagnostic report string containing the app version, Harness home, and last attempted source. `apps/desktop/tests/harness-home.spec.ts` and `apps/desktop/tests/no-userdata-regression.spec.ts` stay green unchanged. `main.ts`'s IPC wiring and the `dialog` calls are Electron-only and untested, per this package's existing testing boundary.
