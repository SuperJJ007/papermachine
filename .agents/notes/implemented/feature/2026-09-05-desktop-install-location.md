# Agent Note: A chosen Harness home persists as a pointer file, applied by relaunch

Status: implemented

English | [中文](2026-09-05-desktop-install-location.zh.md)

## Problem

`resolveHarnessHome` (`harness-home.ts`) already accepted a `customHomeDir` argument taking precedence over `PAPERMACHINE_HOME` and `DSH_HOME`, but nothing in the application ever passed one: a Windows user whose `C:` drive cannot hold the roughly 6 GB shipped environment had no way to install elsewhere short of setting an environment variable before launching a GUI application — not a workflow a packaged installer's user can follow. Separately, the "Copy Diagnostic Report" button onboarding's failed-install path already offered named platform, user agent, time, and the error text, but not the Harness home path or which package source had been attempted — exactly the facts a maintainer triaging a report needs first, and the two gaps a filed issue asked for by name.

## Decision

A new module, `install-location.ts`, owns a pointer file directly under the OS home directory, `<osHomeDir>/.papermachine-home` — an ASCII-only filename chosen deliberately so it stays readable even when the home directory's own path is otherwise problematic (non-ASCII, containing a space). The file holds exactly one absolute path, written atomically through the existing `writeFileAtomic` (`atomic-write.ts`) shared with the environment-binding and applied-environment pointers. `readInstallLocationPointer` returns `undefined` for a missing file — the ordinary case — and throws, naming the file, for one that exists but is empty, whitespace-only, or names a relative path: silently falling back to the default Harness home for a corrupt pointer would run the Host and every kernel against the wrong drive without any indication why. `main.ts`'s `harnessHome()` reads this pointer and passes it as `resolveHarnessHome`'s `customHomeDir`, so a pointer file now outranks both `PAPERMACHINE_HOME` and `DSH_HOME` — it is the one precedence tier a GUI user reaches without an environment variable, and `harness-home.ts`'s JSDoc documents this application's specific source for that argument.

Onboarding's environment-choice screen has an install-location row, rendered from a `desktop:install-location` IPC call, showing the resolved path plus a "Change…" button and, only while a pointer file is in effect, a "Use default" button. Its note states plainly that changing the location restarts the application and starts over as if newly installed: sessions, the environment binding, and any environment already installed stay behind at the previous location — nothing is moved — so the new location needs its environment installed again. "Change…" opens `dialog.showOpenDialog` from the main process (never `window.prompt`, which this application's renderer forbids) defaulting to the current Harness home's parent directory; a cancelled dialog is reported as `cancelled` and changes nothing. Confirming the picker without navigating anywhere would otherwise reuse that parent directory itself — `~` by default, or a Windows drive root — as the new Harness home outright, so `resolveChosenInstallLocationPath` (`install-location.ts`) appends a fixed `PaperMachine` subdirectory to the chosen directory before it becomes anything else, skipped only when the chosen directory's own basename already names it — compared case-insensitively on darwin and win32, whose default filesystems are themselves case-insensitive — so an existing `PaperMachine` directory under the chosen location is reused rather than duplicated, and the function is idempotent on its own output. The resolved target is validated by calling `resolveHarnessHome` itself before anything is written — a candidate that would throw `HarnessHomeSpaceError` is reported `rejected`, with a reason rewritten around "the chosen folder" rather than that error's own message (which names "your user home directory", accurate for the default-location failure it was written for but wrong for a folder the user just picked). A path containing a non-ASCII character (an unconfirmed risk for some conda and R packages, per the filed issue) triggers a bilingual `dialog.showMessageBox` warning that the user can accept or decline; declining reports `cancelled` the same as dismissing the picker. A second bilingual dialog (`installLocationConfirmationDialog` builds its text; `confirmsInstallLocation` is the pure decision over its response) then names the exact resolved target and asks for a final "确定 · OK" / "取消 · Cancel" confirmation before anything is written, so a user who confirmed the picker's own default still sees, and can still decline, the exact directory about to become the Harness home. Acceptance writes the pointer file, then calls `app.relaunch()` followed immediately by `app.quit()` — `relaunch()` only schedules the restart, and `quit()` is what actually starts shutdown, so the existing `before-quit` handler still runs `coordinator.beforeQuit()` (aborting any provisioning run, stopping the Host, flushing telemetry) before the process exits and Electron restarts it fresh against the new home. "Use default" clears the pointer file and relaunches the same way. Both handlers report `restarting`, on which the renderer disables the two buttons and shows a restarting message rather than trying to return to a ready state that is about to be torn down anyway; an IPC call that instead rejects (a caught exception, not a reported `rejected` result) is caught by both click handlers, which show the error and re-enable the controls, symmetric with the row's own `installLocation()` load.

Choosing "Change…" or "Use default" while a provisioning run is in progress is refused outright rather than relaunching mid-download: relaunching aborts the run and discards its downloaded bytes with no confirmation, so `onboarding.ts`'s `setBusy` — the single function that already disables every control starting new work for a run's lifetime — now disables these two buttons as well, and `main.ts`'s choose/reset handlers independently reject with a named reason whenever the module-level `provisioning` `AbortController` is set, so the refusal holds even for a click that reached the handler before the renderer's own disable took effect.

A pointer whose value is a well-formed absolute path but whose target cannot be reached at launch — an unplugged drive, an unmounted network share, a permission change — gets its own recovery page rather than the general Host error page. `boot()` resolves the Harness home itself, before registering anything else, so this is the first launch failure any of this application's code can hit; `isInstallLocationUnavailable` (`install-location.ts`) is the pure classifier deciding whether a `resolveHarnessHome` failure qualifies (a pointer is in effect, and the failure is not the already-handled `HarnessHomeSpaceError`), and `installLocationUnavailableErrorPage` (`error-page.ts`) renders the page, naming the pointer file and the unreachable target, with "Use default location" (clears the pointer and relaunches, reusing the same main-world navigation guard `error-page.ts`'s `RESTART_URL` already used) and "Quit" in place of the ordinary Restart Host action, which would only retry the same broken pointer.

The diagnostic report has a `desktop:diagnostics` IPC call returning the app version, `${platform}-${arch}`, the resolved Harness home, and whether it is customized. Onboarding tracks the most recently attempted package source across `onProvisioningProgress` updates (seeded from the confirmed choice, the same rule `main.ts`'s own `lastSourceId` tracking already applied for telemetry) and, on a failed install, fetches diagnostics before building the report so it can add the app version, an upgraded platform line (`darwin-arm64` rather than the browser's generic `navigator.platform`), the Harness home path with a customized/default note, and the last source attempted — alongside the existing user agent, time, and fenced error text.

## Alternatives considered

- **Persist the choice under Electron's `userData`.** Rejected outright: `apps/desktop/tests/no-userdata-regression.spec.ts` forbids any `getPath('userData')` call in `src/`, and `userData`'s own macOS path containing a space is the exact defect `harness-home.ts` already routes around — storing the pointer to a space-free Harness home inside a space-containing directory would make the pointer's own location the next instance of the same bug class.
- **Require an environment variable (`PAPERMACHINE_HOME`) instead of a GUI control.** This is the status quo the filed issue calls out as unusable: a packaged GUI application's user has no ordinary way to set a process environment variable before launch, and the two existing environment variables remain available for the workflows that do.
- **Re-resolve the Harness home live, without a relaunch, and hot-swap the running Host.** Rejected: the Host, every kernel subprocess, the watchdog, and in-memory state such as `activeOrigin` and `hostLogPath` are all keyed to the home directory at the moment they were created; tearing all of that down and recreating it in place duplicates most of `boot()`'s own startup sequence for a rare, deliberate user action, where a relaunch reuses the exact code path every ordinary launch already exercises and is proven correct.
- **Skip the non-ASCII warning and simply accept the path.** Rejected: the filed issue names non-ASCII paths as a real, if unconfirmed, cause of failures for some conda and R packages under Chinese usernames; warning without rejecting keeps the choice with the user while surfacing a risk they would otherwise discover only after a failed multi-minute install.
- **Let the user type or edit the appended subdirectory's name instead of a fixed `PaperMachine`.** Rejected: a free-text name reopens the exact validation surface (spaces, non-ASCII characters) this feature already runs against the *directory* the user picks, for a name with no functional effect on Science — a second input surface with the same failure modes and no real capability behind it.
- **Skip the final confirmation dialog and rely on the install-location row's resolved-path display instead.** Rejected: that display only renders after the relaunch this same action triggers has already run and the pointer has already been written; naming the resolved path before it is written is the only point at which a user can still decline it.

## Consequences

A user on a small system drive can redirect the entire ~6 GB environment to another drive from onboarding itself, with no environment variable and no command line. The pointer file is a new on-disk format this pre-release codebase makes no compatibility promise about; a future format change may replace it outright per the repository's pre-release stance. Every install-location change costs one full application relaunch (a few seconds), accepted because it reuses the same startup path as an ordinary launch rather than a second, less-exercised in-place teardown path. A failed install's diagnostic report now names the exact Harness home and package source involved, which a filed issue can otherwise only guess at from the error text alone. Confirming the directory picker on its own opening default no longer hands that container directory to Science outright: `resolveChosenInstallLocationPath` appends `PaperMachine` to it, and the final confirmation dialog gives the user one more chance to see, and decline, the resolved path before it is written.

## Verification

`apps/desktop/tests/install-location.spec.ts` covers the pointer file path, `readInstallLocationPointer` returning `undefined` for a missing file and throwing (naming the file) for empty, whitespace-only, and relative content, a write-then-read round trip, atomic replacement leaving no temp file behind, `clearInstallLocationPointer` removing an existing file and no-op on a missing one, `hasNonAsciiCharacters` for an ASCII path, a CJK path, and a space-only path (false — a distinct, separately checked risk), `resolveChosenInstallLocationPath` appending the subdirectory, skipping an already-named one, comparing case-insensitively on darwin and win32 versus case-sensitively on linux, idempotence on its own output, and a Windows drive root (parsed with `node:path`'s `win32` module regardless of the test host), `installLocationConfirmationDialog`'s bilingual text naming the resolved target and its OK/Cancel buttons, `confirmsInstallLocation` for both button responses, and `isInstallLocationUnavailable` for a pointer-set target that does not exist, one that is not writable, no pointer in effect, and a space-containing path (`false` — `HarnessHomeSpaceError` keeps its own page). `apps/desktop/tests/error-page.spec.ts` covers `installLocationUnavailableErrorPage` naming the pointer file, the target, and the reason, and offering "Use default location"/"Quit" instead of Restart Host. `apps/desktop/tests/onboarding.spec.ts` covers the install-location row rendering the resolved path, "Use default" appearing only when customized, a `rejected` result (including the provisioning-in-progress reason) surfacing it and re-enabling the controls, a `restarting` result disabling both buttons, both buttons staying disabled for a provisioning run's duration and re-enabling if it fails, an IPC rejection from either button being caught and recovered the same way, and the diagnostic report string containing the app version, Harness home, and last attempted source. Fixtures in both spec files standing in for a customized install location use `/Volumes/Data/PaperMachine` rather than the pre-subdirectory `/Volumes/Data/.papermachine`, matching the shape a real pointer now takes. `apps/desktop/tests/harness-home.spec.ts` and `apps/desktop/tests/no-userdata-regression.spec.ts` stay green unchanged. `resolveChosenInstallLocationPath`, `installLocationConfirmationDialog`, and `confirmsInstallLocation` all live in `install-location.ts` rather than `main.ts` for the same reason `isInstallLocationUnavailable` does: each is tested directly, independent of the untested `main.ts`/`dialog` boundary that only wires them together.
