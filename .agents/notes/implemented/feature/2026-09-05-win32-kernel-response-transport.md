# Agent Note: A pluggable kernel response-channel transport makes win32 Science kernel execution possible

Status: implemented

English | [中文](2026-09-05-win32-kernel-response-transport.zh.md)

## Problem

`@deepseek-ai/dsh-science-runtime`'s persistent kernel read every response frame (`READY`/`DONE`/`CHART`) from a POSIX FIFO the Host created in the kernel's private scratch, forwarded through an owned `cat` subprocess so idle reads never occupied a Host filesystem worker. `mkfifo` and named-pipe blocking-open semantics have no win32 equivalent, so `startRun` (`index.ts`) and `prepareObservation` (`environment.ts`) both rejected pre-publication on win32 with `ScienceRuntimeError('KERNEL_UNSUPPORTED_PLATFORM', …)` before any scratch or process work — Science kernel execution, and therefore the whole Science Runtime, did not run on Windows at all (papermachine issue [#14](https://github.com/SuperJJ007/papermachine/issues/14)).

## Decision

The response channel is now a seam, `KernelResponseTransport` (`kernel-transport.ts`), with two implementations selected once per kernel by `selectKernelTransportKind(platform = process.platform)`: `FifoTransport` on darwin/linux (exactly the prior FIFO-plus-`cat` mechanism, moved into this module unchanged — same frames, same quiescence and teardown ordering, same error messages) and `LoopbackTcpTransport` on win32. Both hand `KernelProcess` the same thing — a readable byte stream carrying the identical wire-protocol frames, plus a `faulted` signal — so the frame parser and the `KernelProcess` state machine never know which transport produced them; only `kernel-process.ts`'s own spawn/teardown sequencing changed to call through the seam (`transport.endpointArg`, `transport.connect()`, `transport.end()`, `transport.endStartFailure()`) instead of owning FIFO paths and a `cat` reader directly. `KernelProcessOptions.transportKind` lets a caller force a specific transport instead of the platform default; every production caller omits it, and only a test uses it, to exercise `LoopbackTcpTransport` on a POSIX host without mocking `process.platform` globally. `kernel-process.ts`'s line-buffering frame parser now strips exactly one trailing `\r` before splitting a line's fields, since R's `socketConnection` text mode may emit CRLF on win32 even though Python's `makefile(newline="\n")` never does.

`LoopbackTcpTransport` listens via `node:net` on `127.0.0.1` port 0 (an OS-assigned ephemeral port) and accepts connections until one presents the correct token; only that connection stops the listener, so a second connection is refused from then on. A connection presenting a wrong or missing token, ending before any line arrives, or otherwise erroring is destroyed, but the listener keeps accepting further connections until `connect()`'s own deadline elapses or the kernel process itself exits: the token is 128 bits of CSPRNG output, so an indefinite guessing channel is not a realistic threat, while closing the listener on the first connection regardless of its token would let any other unrelated local process fail kernel startup outright by winning the race to connect first. A long-lived listener-level `'error'` handler and `'connection'` handler are installed once, at construction, rather than only for the duration of one `connect()` call: the window between `create()` returning (its address must be embedded in the kernel driver's argv before the kernel spawns) and a caller invoking `connect()` is real wall-clock time in which either a listener fault or the kernel's own connection attempt can already land, and neither may go unhandled — a fault with no listener crashes the Host process as an uncaught `'error'` event, and a connection with no listener is accepted and leaked open with nothing ever reading from it. The first line the kernel writes on the connection that does present a valid token must be a 32-hex-char random token minted fresh per kernel (`randomBytes(16).toString('hex')` — no dependency added for this); token-line parsing uses the `'readable'`+`socket.read()` loop (the same pattern Node's own HTTP module uses for protocol-upgrade sniffing) and `socket.unshift()` to hand any bytes read past the token's newline back to the stream unconsumed: a `'data'` listener does not preserve already-buffered bytes across the flowing-to-paused transition, so the paused-mode `'readable'`/`read()` pattern is required.

The driver argv's single positional endpoint argument is now either an absolute FIFO path (unchanged) or `tcp:127.0.0.1:<port>:<token>`. `kernel_python.py`'s new `open_response_channel(endpoint)` branches on an `endpoint.startswith("tcp:")` prefix: the TCP branch does `socket.create_connection((host, int(port)))`, wraps it with `sock.makefile('w', encoding='utf-8', newline='\n')`, writes the token line first, then uses the file object exactly like the FIFO handle for every later `send()`. `kernel_r.R` does the same with `socketConnection(host=, port=, open='w', blocking=TRUE)` and `writeLines(token, con)`. Both drivers keep every existing hardening flag (`--vanilla --encoding=UTF-8` for R's UTF-8 probe path is unrelated here; the kernel argv itself keeps `-B -u -X utf8` for Python and the same R flags as before) — the endpoint argument's shape is the only change to either driver's own argv contract.

Named pipes were rejected as the win32 mechanism even though they are the more literal FIFO analog: a Windows ACL sandbox may not grant the write-restricted kernel process token write access to a Host-created named pipe (the two ends can be created under different, non-inheriting security contexts), while a loopback socket is not an ACL-securable object at all — there is nothing for the sandbox to deny. POSIX keeps the FIFO/`cat` mechanism rather than moving to loopback TCP everywhere: the existing sandbox network policy is untouched by this change (a POSIX kernel remains network-denied except for whatever a user's own code opens), and rewriting a working, already-tested mechanism to chase transport symmetry was rejected as unjustified churn under the pre-release "foundation over blast radius" stance — the two transports are already fully decoupled behind one seam, so there is no shared-code cost to keeping them different.

`kernelEnvironment()` (`kernel-process.ts`) now carries through a fixed set of ambient win32 variables from the Host's own environment when `process.platform === 'win32'`: `SystemRoot`, `windir`, `SystemDrive`, `ComSpec`, `PATHEXT`, `USERPROFILE`, `APPDATA`, `LOCALAPPDATA`, `PROGRAMDATA`, `NUMBER_OF_PROCESSORS`, `PROCESSOR_ARCHITECTURE`, plus `TEMP`/`TMP` set to the kernel's own scratch temp directory (neither Python's `tempfile` nor R's `tempdir()` consult `TMPDIR` on Windows). A win32 process started with none of the first group cannot initialize Winsock (`WinError 10106`), which the loopback TCP response channel and the interpreter's own standard library both depend on; the existing POSIX allowlist (`PYTHONUSERBASE`/`R_LIBS_USER`, `HOME`, `TMPDIR`, `PATH`, `SCIENCE_STATE_DIR`, `SCIENCE_WORKSPACE_DIR`) is unchanged. `interpreterPathEnv()` (`execution.ts`) now branches on `process.platform === 'win32'` to build a `;`-joined `PATH` from `<prefix>`, `<prefix>\Library\mingw-w64\bin`, `<prefix>\Library\usr\bin`, `<prefix>\Library\bin`, `<prefix>\Scripts`, `<prefix>\bin` — the same order `conda activate` itself uses on Windows — via `node:path`'s `win32` submodule so the value is deterministic independent of the host platform actually running the function (tests exercise it on macOS, mirroring the win32 `PATH`-resolution precedent in [the package-cache MAX_PATH note](../bug-fix/2026-09-05-win32-package-cache-max-path.md)). POSIX's `<prefix>/bin:/usr/bin:/bin` is unchanged.

Cooperative interrupt did not gain any new win32 mechanism. `SubprocessHandle.interrupt()` is already a documented no-op on win32 (`dsh-subprocess-local`'s `spawn.ts`); this change makes no attempt to add a `CTRL_BREAK_EVENT`-based equivalent. A cancelled or timed-out win32 run therefore always falls through the existing "kernel did not prove it caught the interrupt within the grace window" path straight to `run-escalation`, ending the kernel and losing its in-memory state — the same code path a POSIX kernel only reaches when `SIGINT` goes unanswered. This is accepted as a v1 Known Limitation, not a defect to fix in this change: building a distinct win32 interrupt mechanism is materially separate work with its own design questions (whether `GenerateConsoleCtrlEvent` is even reachable through this Runtime's process-group spawn shape) that this change's own scope — making kernel execution possible on win32 at all — does not require answering first.

The two pre-publication win32 rejections were removed outright: `startRun`'s block in `index.ts` and `prepareObservation`'s block in `environment.ts`. `ScienceRuntimeErrorCode`'s `'KERNEL_UNSUPPORTED_PLATFORM'` member is removed from the closed union (`types.ts`) along with its call site in `run.spec.ts`, which asserted exactly the `startRun` rejection this change removes and has no adapted replacement — with the preflight rejection gone, a win32 `startRun` call now proceeds identically to darwin/linux, already covered by every other non-platform-specific test in that file. The `environment.ts` rejection was independently rewritten in flight by a sibling PR (`#17`, "refuse Science onboarding on Windows"; same session, merged into `main` while this branch was in progress) to a different message under the same `KERNEL_UNSUPPORTED_PLATFORM` code, exactly the trivial conflict this shared surface was expected to produce; reconciling this branch onto that merge kept this change's full removal of the block, per its own explicit design intent. `environment.spec.ts`'s corresponding test survived that reconciliation adapted rather than deleted: it still builds the same Windows-shaped Conda prefix (`python.exe` at the prefix root, matching `WINDOWS_LAYOUT`) and forces `process.platform`, but now asserts `bindEnvironment` completes (`status: 'applied'`) and that every probe spec's argv targets `python.exe`, since this harness's fully-faked subprocess provider does not care whether that file is a real executable — keeping the file the union's only remaining exercise of the win32 candidate-selection branch (`WINDOWS_LAYOUT`) `environment.ts` already had before this change.

Every accepted socket retains an error listener from acceptance through destruction, including the queued interval before token parsing and the interval after token handoff when startup cleanup can still run. The listener destroys a failed socket; token and frame consumers continue to observe the same error event and classify it. A subprocess handle missing requested stdin is rejected before response-channel handoff. Removing listeners between those owners can turn a peer reset during startup failure into an uncaught Host exception. Unit regressions cover queued and handed-off socket resets, and the assembled Runtime covers rejected startup with a missing stdin handle.

## Alternatives considered

- **Windows named pipes (`\\.\pipe\...`) instead of loopback TCP.** Rejected: the ACL/sandbox-token mismatch above is a plausible, unverified-until-real-Windows failure mode this change cannot afford to build on without a real Windows host to test against; a loopback socket sidesteps the whole ACL question.
- **One transport for every platform (loopback TCP everywhere, retiring the FIFO).** Rejected: it would touch the sandbox's POSIX network policy for no behavioral gain, and discards a mechanism that is already fully tested and unrelated to this change's actual goal (making win32 possible, not making POSIX different).
- **A win32 `CTRL_BREAK_EVENT`-based cooperative interrupt in the same change.** Rejected as separate scope: it needs its own process-group/console-subsystem design work this change's brief did not ask for, and shipping win32 kernel execution does not require it — it only requires being honest that interrupt on win32 always loses kernel state, which is now documented.
- **Keep fake JS drivers FIFO-only.** Rejected: Windows then skips supported execution, artifact, and chart paths. The shared fixtures support authenticated TCP alongside FIFO; cooperative-interrupt state-machine tests inject a provider acknowledgement, while native SIGINT delivery remains POSIX-specific.

## Consequences

`kernel-transport.ts` has a dedicated unit suite (`tests/kernel-transport.spec.ts`) against a real `node:net` client: token acceptance, wrong-token rejection, a second connection being refused, EOF classified the same way FIFO EOF is, and listener teardown leaving no open handle. A separate real-driver suite (`tests/kernel-transport-real.spec.ts`) forces `transportKind: 'tcp'` (never mocking `process.platform`) and runs the actual shipped `kernel_python.py`/`kernel_r.R` through a full RUN/DONE/EXIT cycle against this machine's own bound (`~/.papermachine/environment-binding.json`) or PATH-resolved interpreter, self-skipping per language with a stated reason when neither exists; both languages ran on the machine this change was built on. Every prior FIFO-path kernel-process and kernel-set test still passes unchanged, proving POSIX behavior is byte-for-byte the same. `packages/science/science-runtime/src/**/*.ts` per-file coverage stays at 100% (`npx vitest run --coverage packages/science/science-runtime/tests --coverage.include='packages/science/science-runtime/src/**/*.ts' --coverage.reportOnFailure`; `--coverage.reportOnFailure` is required only because of the pre-existing, unrelated `kernel-set.spec.ts` same-ID-conflict flake below, which otherwise suppresses vitest's coverage report entirely).

What remains unverified without a real Windows host: the true behavior of `interrupt()`-as-no-op against a real win32 process tree under this Runtime's actual confinement, and whether any further ambient environment variable proves necessary that this change's fixed allowlist did not anticipate. A real Windows Server 2022 run has since confirmed the rest — an actual `micromamba`/Conda-provisioned win32 kernel spawn end to end (real interpreter, real sandbox enforcement, real Winsock initialization under the new environment allowlist) — per [the win32 scratch-privacy and probe-ordering Agent Note](../bug-fix/2026-09-06-win32-scratch-privacy-and-probe-ordering.md) and [the win32 R locale and probe-argv Agent Note](../bug-fix/2026-09-06-win32-r-locale-and-ascii-probe-argv.md). A pre-existing, unrelated flake was found and is not fixed by this change: `kernel-set.spec.ts`'s `discards the losing kernel through EXIT/quiesce after a same-id byId conflict, never leaving it running unregistered` fails the same way on an unmodified baseline checkout (confirmed via `git stash`), so it is out of this change's scope.
