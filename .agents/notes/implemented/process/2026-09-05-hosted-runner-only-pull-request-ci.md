# Agent Note: Hosted-runner-only pull-request CI

Status: implemented

English | [中文](2026-09-05-hosted-runner-only-pull-request-ci.zh.md)

## Problem

This repository is a fork published as a separate private GitHub repository, and it inherited [CI](../../../../.github/workflows/ci.yml), [CI master](../../../../.github/workflows/ci-master.yml), [e2e](../../../../.github/workflows/e2e.yml), [release](../../../../.github/workflows/release.yml), and [release-vendor](../../../../.github/workflows/release-vendor.yml) unchanged from the upstream project. Those workflows assume infrastructure only the upstream project has: `ci.yml`'s four primary jobs selected the enterprise runner labels `dsh-ubuntu-24-04-16core` and `dsh-windows-2025-16core`, with a `vars.DSH_CI_FAILOVER_*`-gated fallback onto an in-house self-hosted pool ([CI failover runbook](2026-07-26-ci-failover-runbook.md)); `e2e.yml` triggered on every pull request, push, and a nightly schedule and required the repository secret `DEEPSEEK_API_KEY_EXTERNAL`; `release.yml` and `release-vendor.yml` packed the npm package family on every pull request; and `ci-master.yml`, `sandbox.yml`, and `landlock-run.yml` triggered on `push: branches: [master]`, a branch this repository's default branch (`main`) never produces. None of the enterprise runners, the self-hosted pools, the `DEEPSEEK_API_KEY_EXTERNAL` secret, or a `master` branch exist here, so the affected jobs stayed queued forever or failed outright, and `all-checks-passed` never resolved on real pull requests.

## Decision

`ci.yml`'s five runner selectors that read `vars.DSH_CI_FAILOVER_LINUX` / `vars.DSH_CI_FAILOVER_WINDOWS` are plain `ubuntu-latest` (the three required Linux jobs and the `all-checks-passed` verdict) or `windows-latest` (`windows-native`); every dead failover branch — the cache-restore `if:` conditions, the failover Playwright install step, and the `DSH_SNAPSHOT_MAX_CONCURRENCY` ternary — is removed along with the comments describing the enterprise/self-hosted topology. `windows-native`'s only remaining Windows-specific note is that a clean install is faster than restoring a many-file pnpm store cache on a hosted runner. `pnpm run check:ci:static`, `check:ci:coverage`, `check:ci:consumers`, and `check:ci:windows-complete` keep gating the same commands on the same `DSH_GATE_CONCURRENCY` and `DSH_COVERAGE_*` budgets; only the runner pool changed.

`e2e.yml` keeps only `workflow_dispatch:` as its trigger. A comment above `on:` states that push, pull-request, and nightly triggers are off until the repository secret `DEEPSEEK_API_KEY_EXTERNAL` exists, and that restoring them is a one-line addition back to `on:`; the job-level `if:` and the preflight secret check are left as they were; the SECURITY warning against `pull_request_target` stays for whenever the trigger returns.

`release.yml` and `release-vendor.yml` each keep only `workflow_dispatch:`, with a one-line comment that this repository does not publish the npm package family on pull requests, so both workflows stay runnable by hand from a `dsh-v*` / `vendor-*` tag through their companion `-publish.yml` workflows exactly as before.

`ci-master.yml` drops its `push` trigger and keeps `workflow_dispatch` with its `suite` input unchanged, with a comment that the serial standby drills and the two benchmark suites need self-hosted runners this repository does not have. Its `wine-apt-cache`, `serial-linux-selfhosted`, and `serial-windows` jobs keep their own `if: github.event_name == 'push' && github.ref == 'refs/heads/master'` guard unedited, so they are now dormant — reachable by neither the removed push trigger nor `workflow_dispatch` — until this repository regains both a push trigger and the self-hosted `vm-backup`/`dsh-win-ci` pools those jobs assume. Only `larger-runner-benchmark` and `consolidated-runner-benchmark`, gated on `workflow_dispatch` with a matching `inputs.suite`, are reachable today.

`sandbox.yml` and `landlock-run.yml` rename their `push: branches:` target from `master` to `main`, the repository's actual default branch, with every other trigger, `paths` filter, and job body unchanged.

`.github/AGENTS.md` and `scripts/ci-workflow.spec.ts` are updated to match: the spec's `ci.yml`/`ci-master.yml` assertions drop every `DSH_CI_FAILOVER_*`/enterprise-label check in favor of asserting the plain hosted `runs-on` values, and new assertions pin that (a) no workflow file references `dsh-ubuntu-24-04-16core`, `dsh-windows-2025-16core`, `dsh-win-ci`, `vm-backup`, or `DSH_CI_FAILOVER` outside `ci-master.yml`, whose matching jobs are reachable only through `workflow_dispatch`; (b) `e2e.yml`, `release.yml`, `release-vendor.yml`, and `ci-master.yml` each have `workflow_dispatch` as their only trigger; and (c) no workflow's `push.branches` names `master`.

## Alternatives considered

**Retarget the failover selectors onto a real self-hosted pool this repository stands up.** Rejected for now: nothing in this fork operates the always-on VMs or Windows runner fleet the upstream failover mechanism assumes, and building that is a separate, larger undertaking than making pull-request CI resolve at all.

**Delete the dormant `ci-master.yml` standby jobs and the `2026-07-26-ci-failover-runbook.md` Agent Note instead of leaving them dormant.** Rejected: this change's scope is making pull-request CI pass with hosted runners, not redesigning the master/serial-standby topology. Leaving the jobs' own push-gated `if:` in place documents the exact condition a future push trigger would need to reintroduce; deleting them would erase that scaffold along with jobs and rationale that remain valid if this repository ever adds the assumed runners back. The failover runbook itself is left unedited per the standing rule against editing existing Agent Notes in this change; it now describes a mechanism absent from the live workflow files until a future change either restores hosted-enterprise-pool failover or retires the runbook.

**Restore `e2e.yml`'s automatic triggers with a soft-fail on the missing secret instead of `workflow_dispatch`-only.** Rejected: the preflight step already hard-fails on a missing key by design, so it would fail on every pull request rather than simply not running, and downgrading that guard to tolerate the missing secret would mask a real misconfiguration the day the secret is actually added elsewhere.

## Consequences

Every job pull-request CI can currently satisfy now resolves on a plain GitHub-hosted runner, so `all-checks-passed` can succeed on a real pull request in this repository for the first time. `e2e.yml`, `release.yml`, `release-vendor.yml`, and `ci-master.yml`'s benchmark suites are reachable only by a maintainer manually dispatching them; nothing currently runs the real-API e2e suite, packs a release tarball, or benchmarks a larger runner automatically. `ci-master.yml`'s `wine-apt-cache`, `serial-linux-selfhosted`, and `serial-windows` jobs are unreachable by any trigger this workflow now has — restoring them requires both a decision to reintroduce `push` (or another trigger satisfying their `if:`) and the self-hosted pools they exercise. `sandbox.yml` and `landlock-run.yml` resume running on every push to `main`, this repository's actual default branch. Restoring any manual-only workflow to automatic triggers, or restoring the removed failover mechanism, is a one-line change to each workflow's `on:` block plus its runner selector, as the comments left in place state.
