# Agent Note: Spec-first chart artifacts for Science

Status: proposed

English | [中文](2026-08-22-science-spec-first-charts.zh.md)

## Problem

[The artifact-domain and image-edit note](2026-08-22-science-artifact-domain-and-image-edit.md)'s S4 slice designed region-selected editing over normalized pixel regions on captured raster PNGs — the only chart representation Science produced at the time. On 2026-08-21 the product decision changed the default chart-authoring path: a chart artifact should be a declarative spec, rendered to SVG in the browser, with elements a viewer can select by structure (a mark, an encoding) rather than by pixel coordinates, plus a lightweight editor that changes style attributes directly on that spec. That decision leaves S4's raster region-select and the S1–S3 `artifact_inputs`/`edit_of` pipeline in place for photographic content and for chart libraries with no spec equivalent, but it upgrades what "the default chart" means and adds a second, human-only editing entry point the prior note never designed for: a save that commits new bytes with no run and no model turn behind it. Six decisions block the next slice of Science chart work — the spec format, how the agent produces one, how a human style edit is recorded without breaking the run-centric provenance every other artifact version carries today, how a selection reaches the model as a structured message, where deterministic export renders, and whether raster region-select still has a job. Each is decided here against the two rules the prior note already established: the kernel drivers do not change, and every model-visible input stays reconstructable from a session event.

## Proposal

Chart artifacts gain a second content family — declarative specs — alongside the raster PNGs Science already captures; nothing about `run_python`/`run_r`, the kernel wire protocol, or the `.png`-only image capture path changes. A spec is an ordinary run output the same way a PNG is: the agent's plotting code writes it under `SCIENCE_ARTIFACT_DIR`, and auto-capture admits it through the same walk. A human style edit is a separate, new provenance path: the lightweight editor commits a new artifact version with no run behind it, so `ScienceArtifactVersion`'s current run-centric fields cannot describe it as written today, and the type gains a discriminated branch. Everything else in the domain — artifact identity as `{artifactId, version}`, `parent` as ancestry, `publish_outcome` evidence, the notebook projection — is unchanged.

### 1. Spec format: Vega-Lite, authored from Python through Altair

Vega-Lite is the spec format: a JSON document, a maintained SVG/canvas renderer (`vega`/`vega-lite`, embedded through `vega-embed`), and marks/encodings addressable by structural path (`mark`, `encoding.color`, …) — exactly the "select by structure, not pixels" requirement. [R5](../../implemented/feature/2026-08-16-dsh-science-v01-r5-charts-outcome.md) explicitly rejected "a generic chart specification or plotting dependency" because at that time Python/R code already produced raster output the attachment service validated; adopting Vega-Lite now is choosing a maintained renderer over hand-rolling one, the same preference [the dependency-over-hand-rolling policy](../../implemented/process/2026-07-26-dependencies-over-hand-rolling.md) states for harness code — see § Supersession check below for how this reopens that one alternative without touching R5's shipped decisions. On the Python side, Altair is the idiomatic Vega-Lite binding: `chart.save('fig.vl.json')` (or `.to_json()` plus a file write) emits the spec directly. This is agent guidance, not a harness dependency: the conda environment a kernel runs in is user-provisioned, so nothing here adds Altair to any `package.json`; static Science guidance recommends it the same way it already names `SCIENCE_ARTIFACT_DIR` without shipping the libraries that write there. R has no comparable maturity: no widely maintained package emits Vega-Lite JSON with coverage close to Altair's, and translating ggplot2's grammar onto Vega-Lite's encoding model has no accepted lossless mapping. R charts stay ggplot2/base-R raster PNG for v1, captured and edited through the existing raster path (decision 6) — an explicit degrade, not a placeholder for a bridge.

### 2. How the agent produces a spec: an ordinary run output, no kernel or tool change

[`capture.ts`](../../../../packages/science/science-runtime/src/capture.ts)'s `CAPTURE_MEDIA_TYPE_BY_EXTENSION` keys on `extname()` (the path's last suffix only); `.json` already maps to `application/json`, so a `.vl.json` file is technically capture-eligible today, but it would collapse onto the same generic media type as any other JSON output (`meta.json` in the shipped example fixture), leaving the viewer no way to tell a Vega-Lite spec from an arbitrary result file. The proposal: recognize the two-part suffix `.vl.json` ahead of the existing single-suffix lookup — a local change inside `isCaptureEligible` and the media-type lookup, not the directory walk or the kernel — mapped to a new `TextMediaType` member on [`dsh-attachment`'s closed union](../../../../packages/attachment/attachment/src/types.ts): the unversioned `application/vnd.vega-lite+json`. Vega-Lite's own convention already pairs the `.vl.json` filename with a `$schema` field carrying the exact spec version inside the document, so the media type does not also pin a version — a versioned media type would force an allowlist and union change on every Vega-Lite major upgrade while adding no information the spec bytes do not carry. The spec's bytes flow through the existing `saveText` admission path unchanged: JSON text carries none of the EXIF/sRGB/resize normalization questions captured images do, so this needs no new byte-exactness carve-out. No new tool: the agent already writes to `SCIENCE_ARTIFACT_DIR`; capture, `annotate_artifact`, `publish_outcome`, and the `edit_of` baseline mechanics already operate on capture-relative paths and media types generically and apply to a spec file exactly as they apply to a `.csv` or `.md` today.

### 3. Human style-edit provenance: a discriminated `origin` branch

Every field on [`ScienceArtifactVersion`](../../../../packages/science/science-session/src/types.ts) beyond identity and content is run-centric and required: `runId`, `toolCallId`, `requestHeaderSeq`, `environmentRevision`, `environmentFingerprint` all authorize the version against a specific model-issued run. A style edit made by a human directly in the editor has none of those facts — synthesizing fake ones would misrepresent authorization that never happened and break every consumer (`publish_outcome`, replay, the notebook projection) that currently trusts those fields as literal. The fix widens `ScienceArtifactOrigin` with a third value, `'human-edit'`, and splits `ScienceArtifactVersion` into a discriminated union on `origin`: the existing `'auto' | 'model'` branch keeps every current field unchanged (including `parent` staying optional, populated only when an edit baseline named one), and the new `'human-edit'` branch drops `runId`/`toolCallId`/`requestHeaderSeq` and makes `parent` required — a style edit always names the spec version it re-styled, never opens a first version. `environmentRevision`/`environmentFingerprint` are copied from that required parent rather than dropped, so `publish_outcome`'s environment-revision derivation and every other reader that assumes those two fields keeps working without a branch of its own; the values describe the environment the underlying data came from, which a style-only edit does not change. Ordering and durability need no `requestHeaderSeq` substitute: the `science/artifact-saved` event's own session-log `seq` already places a human edit in time relative to every other fact, and `requestHeaderSeq` exists specifically to authorize a *model-issued* action against a specific request, which a direct UI edit is not. Strict-fold validation mirrors [S1's rule](2026-08-22-science-artifact-domain-and-image-edit.md) for `parent`/`inputs`: an unresolvable parent on a `'human-edit'` version fails the fold loud, exactly like an unresolvable `edit_of` baseline does today. `SESSION_FORMAT_VERSION` stays `0`; the pre-release stance means this widens the schema without a compatibility shim.

### 4. Selection and edit messages: reuse the existing structured-message and image-block extension points

The structured payload is one durable, model-visible `user/message`: `{targets: readonly {artifactId, version, target: specPath | normalizedRegion}[], instruction}`, no new event type. Two extension points already carry exactly these fields. [`ContentBlockMap`](../../../../packages/llm/llm/src/types.ts) already has a role-neutral `ImageBlock` (`{type: 'image', attachment}`) valid in user content, which [the DeepSeek wire adapter](../../../../packages/llm/llm-deepseek/src/types.ts) turns into an `image_url` content part. [`MessageSourceMap`](../../../../packages/llm/llm/src/message.ts) is a merge-extensible sum type for producer-specific structured data, so `tool-science` adds a `'science-edit'` key carrying the durable `{targets, instruction}` companion. `serialize.ts` never sends `source` to the model; message `content` renders all selected paths or regions, their exact artifact versions, and the one instruction as text. Each region target also contributes its exact selected version as an `ImageBlock`, in target order, while spec-path targets remain text-only.

### 5. Finalize export: client-side rendering, a derived attachment, not a new version

PNG/PDF rendering runs client-side, reusing the same Vega-Lite/Vega renderer C1 mounts in the Web viewer (`view.toImageURL(...)`/`toSVG()`), rather than adding a Host-side headless renderer. The export is a derived attachment, not a new artifact version: [`ScienceArtifactVersion`'s own contract](../../../../packages/science/science-session/src/types.ts) states "a version is what one request turn produced," and an export renders bytes a request turn already produced and already logged — it creates no new content, matching the prior note's S5 notebook bundle, which stays "a pure projection... no Artifact is created unless the user explicitly saves the bundle." Export's reproducibility bar is deliberately lower than capture's: captured images are byte-exact scientific evidence (verbatim admission, no normalization); an export is a rendering of already-logged spec and data for human consumption, so viewer-to-viewer font or canvas variance is an accepted cost of a convenience deliverable, not a violation of the byte-exactness rule capture draws. Science ships more than the Web Client — the automation-only ACP server and the headless CLI examples have no browser to render in — so a Host-side deterministic exporter would be needed for parity there; this note defers building one until a non-Web Client actually asks for PNG/PDF export rather than adding a new Host rendering dependency (a headless browser or native canvas binding) against no current consumer.

### 6. Raster region-select stays

S1–S3's `artifact_inputs`/`edit_of` pipeline and the prior note's raster region-select entry point stay exactly as designed, covering photographic/pixel content and every degraded raster chart (matplotlib, ggplot2, or any library with no spec output). They share decision 4's message format, differing only in `target`: `specPath` for a spec-backed chart, `normalizedRegion` for everything raster.

## Supersession check

[R5](../../implemented/feature/2026-08-16-dsh-science-v01-r5-charts-outcome.md)'s Alternatives-considered section rejected "a generic chart specification or plotting dependency" because "Python/R code already creates the output and the attachment service validates raster bytes." This note reopens exactly that alternative for the default Python chart-authoring path only (decision 1); R5's shipped publication, provenance, and presentation decisions (`annotate_artifact`, `publish_outcome`, the Outcome revision model) are unaffected and stay authoritative, so this is a partial supersession of one alternative, not of R5's decision — R5 stays active, not archived. [The artifact-domain and image-edit note](2026-08-22-science-artifact-domain-and-image-edit.md) stays active for its S1–S3 slices (already shipped) and its domain records (artifact identity, dependency edges, the notebook projection); this note supersedes only that note's S4 slice scope, narrowing S4 to the raster/degraded-chart path (decision 6) while spec-first charts follow the pipeline decisions 1–5 design. No other active Agent Note covers spec formats, human-edit provenance, or Science message structure.

## Implementation slices

1. **C1 — spec capture and viewer render** (`science/s4a-spec-capture`). The decision-2 allowlist/media-type change, plus a client-side Vega-Lite renderer mounted in the Web viewer. Acceptance: a real session's Altair output is captured, renders as vector SVG, and is version-switchable; keyless snapshot and a GIF (product-visible GUI change).
2. **C2 — select → structured edit message** (`science/s4b-select-message`), closing the prior note's S4 acceptance criterion with a raster fallback. The viewer emits the decision-4 message for both a spec-path selection and a region selection; the agent closes the loop with `artifact_inputs`/`edit_of` exactly as S1–S3 already support. Acceptance: a GIF'd real server/model flow, a keyless snapshot of the structured message; if C0/C1 slip, C2 lands on the raster path alone first so the prior note's S4 acceptance criterion is still met.
3. **C3 — style editor** (`science/s4c-style-editor`). Selecting an element opens a property panel restricted to a safe style subset (color, font size, labels — never data transformations, which stay agent territory); finalizing commits a decision-3 human-edit version. Acceptance: a GIF, unit and snapshot coverage of the new discriminated schema branch and its strict-fold validation.
4. **C4 — export** (`science/s4d-export`). Implements decision 5. Acceptance: the exported PNG/PDF is a plausible rendering of the exact spec version, not byte-identical across environments (decision 5's accepted cost); a GIF.

## Sign-off record (2026-08-22)

The user accepted decisions 1–6 and resolved the three questions this note had left open:

- **Media type**: the unversioned `application/vnd.vega-lite+json`, folded into decision 2; the spec's `$schema` field is the version authority.
- **Host-side deterministic export**: stays deferred with a concrete trigger — build it when a specific non-Web Client commits to Science chart support, not before.
- **Human-edit attribution**: no finer granularity than the `'human-edit'` origin. The deployment is anonymous and single-user ([`dsh-anonymous-user-id`](../../../../packages/identity) is deployment-scoped); a per-person attribution field would have no consumer.

The exact rendered wording of the structured edit message's `text` block (decision 4) is pinned by C2's keyless snapshot and the C2 implementation evaluation below.

## C1 dependency evaluation (2026-08-23)

C1 pinned `vega-embed@7.1.0` (closure: `vega@6.4.0`, `vega-lite@6.4.3`) as `dsh-client-ui-science`'s only new runtime dependency; `THIRD_PARTY_NOTICES.md` lists the direct dependency (BSD-3-Clause) and the lockfile carries the closure. Measured cost: `lib/client.js` grows to ~2.0 MB (~475 KB gzip), roughly 4.5× the next-largest client plugin, imported statically whenever the plugin mounts. Accepted for v1 against the maintained-dependency bar — the renderer replaces an entire hand-rolled charting surface — with deferred-loading recorded in the ui-science README's Known Limitations rather than built speculatively. C3 closes the external-loading risk: ui-science passes `vega-embed` a custom loader whose `sanitize` rejects HTTP(S) and protocol-relative URIs. `sanitize` is the seam every Vega resource resolution funnels through — `load`'s own default implementation calls it before fetching, and an image mark's `href`/`url` is sanitized directly with no call to `load` at all — so the restriction covers a remote `data.url`, an image mark, and an href alike. Only the data-loading path's rejection propagates out of `embed()`, so a remote `data.url` degrades to the JSON tree with an explanation; vega-scenegraph's `ResourceLoader` catches the `sanitize` rejection for an image mark or href internally (`loadImage` resolves to an empty placeholder image, `sanitizeURL` resolves to `null`) rather than rejecting, so that reference is simply not resolved and the chart renders without it. Inline values still render.

## C2 implementation evaluation (2026-08-23)

C2 adds one `scienceEdits` Typert Remote in `dsh-tool-science`; Web mounts its `./edit-service` entry in the Host root shared with the Typert Gateway, while the agent preset mounts only the model-facing Consumer. The browser submits one non-empty ordered target array and one instruction, while the Host resolves the live Agent and folds its complete session before admission. Every selected version must be its artifact's current committed version: a missing reference, malformed target, media mismatch, or stale version identifies the failing array position and rejects the whole request with a stable `SCIENCE_EDIT_*` code; no branch substitutes latest or partially enqueues. The admitted `user/message` carries the full request under `source.kind: 'science-edit'`; its text lists the targets, one instruction, and the requirement to use each exact version as the corresponding `artifact_inputs` source and `edit_of` parent. Each raster target additionally attaches its exact selected image in array order. The keyless Science runnable snapshot submits both target kinds in one structured message to the assembled agent, whose mock model issues `run_python` with matching `artifact_inputs` and `edit_of`. The real-server/model browser GIF remains C2's final product acceptance evidence.

C2's real-server flow also surfaced one adjacent defect in `dsh-science-runtime`: `assertSession` still keyed on the session's frozen creation header (`header.agentPreset === 'science'`), refusing every Web session recomposed into the science preset through the `agent-preset/selected` mechanism [the per-session preset design](../../implemented/architecture/2026-08-03-per-session-agent-presets.md) already ships. The guard now keys on the durable `science/mode-bound` fact alone: that fact is appended only by the science preset's own Consumer, so mode binding — not the creation header — is the authorization the Runtime actually relies on, and a recomposed session qualifies exactly when a natively-science one does. Recorded here because the C2 acceptance path is its first consumer; the README and an environment regression test carry the behavior.

## C3 reader review (2026-08-23)

The required pre-implementation review resolves every `ScienceArtifactVersion` reader before the discriminated branch lands:

| Reader | `human-edit` behavior |
|---|---|
| `science-session` `types.ts` / `codec.ts` | The durable and client values become strict discriminated unions. The human branch requires `parent`, environment fields, Vega-Lite text, and no run/tool/request fields; the run-produced branch remains unchanged. |
| `science-session` `fold-state.ts` / `domain.ts` / `invariant.ts` | These retain or dispatch the whole version and need no origin-specific policy; the invariant continues to run the same strict transition before publication. |
| `science-session` `transition.ts` | A human edit must open the next contiguous version, resolve its parent to the same artifact's current committed Vega-Lite version, retain Vega-Lite media type, copy that parent's environment fields, and commit no earlier than its parent fact. It cannot open v1, supersede in place, or consume run/request/tool provenance. |
| `science-session` projection value/schema | The browser receives the human branch's exact parent, attachment, environment preview, and commit time, with no synthetic run link; projection validation mirrors the strict durable union. |
| `science-runtime` capture / inputs / public types | Capture continues to create only run-produced versions. Input and edit-baseline materialization already depends on exact identity plus attachment bytes, so it accepts a human version unchanged; the shared environment fields keep downstream run capture and `edit_of` ancestry exact. |
| `science-runtime` annotation | `annotate_artifact` rejects a human version: converting it to the existing `model` branch would erase the direct-edit discriminator, while retaining `human-edit` cannot carry the model tool authorization that annotation currently proves. A later mixed-provenance design must be explicit rather than inferred from an ancestor run. |
| `tool-science` run / state / artifact schema | Run receipts remain run-produced. Model state makes `runId` conditional, reports `parent` for human versions, and names the direct-edit origin instead of inventing a source run. |
| `tool-science` edit message | Exact-version selection already depends only on artifact identity, attachment media type, and target, so a human Vega-Lite version remains selectable for another agent edit without fallback to latest. |
| `publish_outcome` | Chart evidence continues to derive `environmentRevision` from the cited exact version; the copied parent environment makes human versions valid evidence without a special case. |
| Notebook projection | No notebook artifact projection exists in the current tree; the deferred C5 bundle therefore has no C3 reader to modify. The durable/client projection remains its future input. |
| `tool-cordis` API catalog | The generated declaration must be regenerated from the new public union; it is never edited as an independent reader. |

The style-subset restriction belongs to the editor UI, not Host admission. A person can already ask the agent to run arbitrary code, and arbitrary Vega-Lite JSON has no reliable Host-side classification of “style-only” diffs; the Host therefore validates JSON object form, size, exact current parent, and media type, while the panel exposes only the bounded v1 controls.

## C3 implementation evaluation (2026-08-23)

C3 implements `ScienceArtifactVersion` and its client projection as strict `origin`-discriminated unions. Run-produced versions retain their existing provenance; a direct edit has `origin: 'human-edit'`, a required exact parent, Vega-Lite text, copied environment provenance, and no run/tool/request fields. The fold accepts only the next contiguous version over the same artifact's current committed Vega-Lite parent, with matching logical name and environment and parent-to-commit timing. The Host `scienceEdits.commitStyleEdit` Remote replays that fold before admitting a complete JSON-object spec through the attachment store and appending the event. The Host intentionally does not attempt a semantic “style-only” JSON diff: the Viewer owns that workflow constraint through color, font-size, and axis/legend-title controls, while Host admission owns exact-version concurrency, JSON structure, media type, and attachment bounds.

The Viewer edits an immutable working copy and re-embeds it for live preview; a successful commit selects the returned version and renders direct-edit ancestry instead of a fabricated run. The custom Vega loader rejects HTTP(S) and protocol-relative data loads and falls back to the JSON tree with an explanation. The assembled keyless Science snapshot commits one human version through the Remote, proves the event has exact ancestry and no run fields, then proves the next model call uses that version in both `artifact_inputs` and `edit_of`. That scenario exposed a stale-workspace edge: a later run could otherwise recapture the unchanged pre-edit file as a spurious next version. Auto-capture now skips bytes matching the latest run-produced ancestor when the current version is human-edited and the path is not an explicit edit baseline; an explicit baseline still permits a deliberate model edit or revert.

## Alternatives considered

- **Bridge R charts to Vega-Lite.** Rejected for v1: no maintained R package emits Vega-Lite JSON with coverage close to Altair's, and a hand-built bridge would itself be the hand-rolled infrastructure the dependency policy warns against; R charts already have a working raster path.
- **A new dedicated tool for saving a spec (e.g. `save_chart_spec`).** Rejected for the same reason the prior note rejected a dedicated edit tool: a spec is an ordinary run output, and a save-tool would duplicate the capture walk's accounting and the provenance the run already carries.
- **Keep `ScienceArtifactVersion` a single flat shape and synthesize a fake run for human edits.** Rejected: a synthetic run would misrepresent `runId`/`toolCallId`/`requestHeaderSeq` as authorizing facts that never happened, breaking every consumer that currently trusts those fields as literal.
- **Host-side headless export from day one.** Rejected for v1: no current non-Web Client needs it, and it would add a new Host rendering dependency with no present consumer; see § Sign-off record for the deferred trigger.
- **A new `ContentBlockMap` entry for structured edit targets, instead of a new `MessageSourceMap` key.** Rejected: a new content-block type needs "adapter, UI, and compaction support" across every provider (per its own doc comment), while `MessageSourceMap` is designed for exactly this producer-specific structured companion and already has five packages exercising the pattern.

## Acceptance criteria

- Decisions 1–6 are pinned as stated here before C1 starts; a later change to any of them is a new decision, recorded by amending this note while it is still proposed or by a follow-up note once building begins.
- C1 captures an Altair-produced `.vl.json` as a versioned artifact under the new media type and renders it as version-switchable SVG in the viewer, with a keyless snapshot and a GIF.
- C2 emits the decision-4 structured message from both a spec-path selection and a region selection, closing the prior note's S4 acceptance criterion; the agent's resulting edit carries `parent` set to the exact selected version.
- C3 commits a human-edit version whose `origin` discriminates it from every run-produced version, strict-fold-validated per decision 3, with a GIF and full coverage of the new schema branch.
- C4 exports PNG/PDF as a derived attachment, never a new artifact version, per decision 5.

## Risks

- No R-side spec path (decision 1) permanently limits R charts to the raster/degraded pipeline; if R adoption grows relative to Python this becomes a recurring product gap, not a one-time cost.
- The discriminated `ScienceArtifactVersion` schema (decision 3) is the first branch on `origin` whose shape actually diverges from the run-centric base; every current reader of the type (`publish_outcome`, `annotate_artifact`, capture, the notebook projection, presentation rendering) needs an explicit review for the new branch before C3 starts, not just a type-level narrowing.
- A client-side Vega-Lite/Vega renderer (decisions 1–2) is a new Web dependency with real bundle-size and supply-chain surface; evaluate it against [the maintained-dependency bar](../../implemented/process/2026-07-26-dependencies-over-hand-rolling.md) when C1 pins the exact package versions, not merely assumed acceptable because this note recommends the format.
- Deferring Host-side export (decision 5) risks a later non-Web Client needing it under time pressure instead of as a planned slice; the § Sign-off record trigger is the mitigation — build it as soon as a second Client commits to Science chart support.
- A structured edit message referencing a version since superseded (a stale selection) needs explicit handling in C2; the prior note's pre-publication `INPUT_NOT_FOUND`-style rejection is the template, not a silent fallback to latest.
