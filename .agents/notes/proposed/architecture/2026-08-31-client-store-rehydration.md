# Agent Note: Snapshot-store rehydration merges over `init()` instead of replacing it

Status: proposed

English | [中文](2026-08-31-client-store-rehydration.zh.md)

## Problem

`attachPersistence()` in `packages/client/runtime/src/client/contract/store.ts` rehydrated a persisted store with `api.setState(JSON.parse(raw), true)` — a wholesale replace, `init()` discarded entirely, no validation of any kind on a value read from `localStorage`, a durable boundary where `AGENTS.md` requires it. A field added to a store's state after its persist key was minted is absent from every payload an older build wrote; reading it back returns `undefined` regardless of what `init()` declares.

Two shipping stores hit this. `ui-science`'s `selection-store.ts` persists under `dsh.science.selection.v1`; `libraryCollapsed` and `libraryTabs` were added to `ScienceSelectionState` after that `.v1` suffix was minted, and the suffix was never bumped. A pre-existing payload rehydrates with `libraryCollapsed === undefined`; `ProjectLibrary`'s `collapsed[sessionId] === true` and `rememberLibraryArtifact`'s `draft.libraryTabs[...] = ...` both throw a `TypeError` on read/write — the reported "刷新后详情栏选中标记与折叠状态可能不一致". `ui-conversation`'s `stores.ts` persists `dsh.conversation.chat` with no version suffix at all; `inspect` was added to `ChatStoreState` on 2026-08-31 (`6d13ded908`) with the same exposure.

Separately, `ScienceSelectionState`'s `lightboxOpen` and `view` are transient UI state: a lightbox or provenance drill-in left open when a tab closed reopens over the content on the next load, a rough edge logged as known debt on 2026-08-30. Nothing in the persistence engine could exclude a field from storage short of hand-rolling per-store JSON pre/post-processing.

## Proposal

Rehydration takes `init()`'s value as the base and overlays only the persisted payload's own top-level keys that the base already has: a key absent from the payload keeps its init value, and a key the payload carries that the base does not declare is dropped rather than reappearing. This is a shallow, one-level merge — nested shape drift (a field whose own internal shape changed) is not reconciled and stays the version suffix's job, stated in the module JSDoc. A payload whose top level does not match the base's kind (not a plain object where the base is one; not the same primitive/array kind otherwise) is rejected outright and `init()` is kept, through the same non-fatal `console.error` path a storage or JSON-parse failure already used.

`defineStore`'s `StoreSpec` (`packages/client/ui-slots/src/store.ts`, the framework-neutral contract) gains an optional `transient?: readonly (keyof T)[]`: top-level fields excluded from both directions of persistence — never written to storage, and a stored value for one (including a legacy payload predating the declaration) is ignored on read, always restored from `init()`. The exclusion set is a declaration on the store spec, checked against the state's own keys by `keyof T`, not a hidden rule inside the persistence helper. `selection-store.ts` declares `transient: ['lightboxOpen', 'view']`; no other store's spec changes. The `.v1` persist suffix is not bumped — the merge already makes the two added fields rehydrate correctly, and bumping would discard every user's real open tabs for no reason.

The two lower-level `createSnapshotStore(init, { persist })` callers that bypass `defineStore` — `sessions/service.ts`'s `SessionSelection` and `ui-trajectory`'s `duration-store.ts` — get the same merge for free: `attachPersistence` reads the base from `api.getState()` at attach time, which already equals the `init` value passed in, so no second init parameter is needed. `SessionSelection`'s two fields were optional (`sessionId?: SessionId`) with no own keys present on the `{}` literal passed as `init`, so the merge's "keys the base already has" test would never restore them; its fields are now `sessionId?: SessionId | undefined` / `subagentAddress?: SubagentAddress | undefined` and `init` passes both keys explicitly as `undefined`, giving the merge real keys to overlay onto while `exactOptionalPropertyTypes` still accepts every existing call site (`{}`, and the conditional-spread `set()` calls) unchanged. `duration-store.ts`'s scalar `boolean` state needs no such change: a non-plain-object base accepts a payload of the same primitive/array kind whole, which is what a scalar store's whole-value persistence already meant.

## Alternatives considered

**Keep the version-suffix discipline and require a bump on every added field.** This is the status quo the bug demonstrates failing: bumping is a social process (someone has to remember), not a mechanical one, and it throws away every user's real persisted state — including fields that did not change — on every bump. The merge makes an additive field change free and confines the suffix to what it is actually needed for: a field whose own internal shape changed incompatibly.

**Deep-merge nested objects instead of a shallow top-level overlay.** A deep merge would let a stale nested payload silently resurrect an old sub-shape one level down (a renamed or restructured nested field reappearing under its old name), trading one silent-drop bug for a silent-resurrection bug at one more level of nesting, and it still cannot save a genuinely incompatible nested shape from needing a version bump. A shallow merge keeps the exact scope the class of bug lives in (top-level fields added or removed) and states the boundary explicitly rather than pushing it deeper.

**Bring in a runtime schema-validation library (e.g. zod) at the storage boundary.** Every current store's persisted shape is "the same top-level keys as `init()`", not a shape with independent field types, ranges, or nested invariants to check; a schema library would validate a boundary this shallow at the cost of a new dependency with no current field-level rule to enforce. `packages/AGENTS.md`'s "prefer maintained dependencies over hand-rolling" applies once there is owned validation logic and tests a library would delete — there is not yet, since the entire check is "is this key present in the base object."

## Acceptance criteria

Unit tests in `packages/client/runtime` cover the merge (a payload missing a field keeps the init value; a payload carrying an unknown field drops it; a non-object payload — `null`, an array, a string, a number — is discarded and `init()` kept; an absent payload keeps `init()`; a scalar-state payload of a mismatched kind is discarded) and the transient exclusion (a written payload omits the declared field; a stored value for it is ignored on read, both directly on `createSnapshotStore` and through a `defineStore` declaration). A `ui-science` test seeds a legacy payload lacking `libraryCollapsed`/`libraryTabs`, renders `ScienceDetailsView`, and asserts it does not throw, the library group renders expanded, and opening a library artifact still records it in `libraryTabs`. `selection-store.client.spec.ts` asserts the store spec declares `transient: ['lightboxOpen', 'view']` and keeps `persist: 'dsh.science.selection.v1'` unbumped.

## Risks

A store built directly on `createSnapshotStore` (bypassing `defineStore`) whose state is an object with optional fields left unset in its `init` literal — the `SessionSelection` shape this note fixed — loses those fields on rehydration unless its `init` explicitly assigns them (even as `undefined`) so they exist as the base's own keys; this is a footgun for any future low-level caller with the same pattern, not mechanically enforced. The merge is deliberately shallow: a nested field whose internal shape changes incompatibly still needs a version-suffix bump, and nothing in this change detects that case — an incompatible nested payload merges in as-is and fails downstream, the same failure mode the version suffix already exists to prevent.
