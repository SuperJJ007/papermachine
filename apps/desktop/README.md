# dsh-desktop

English | [中文](README.zh.md)

`@deepseek-ai/dsh-desktop` is the Electron carrier for the Science desktop product, shipping macOS (arm64, x64) and Windows (x64) installers. It starts the existing Web profile as a separate Host process, assigns `~/.papermachine` as the Harness home (`DSH_HOME`), and loads the Host's OS-assigned loopback URL inside a locked-down BrowserWindow. The Harness home is resolved by `src/harness-home.ts` under the OS user home directory, deliberately independent of Electron's own `userData` directory (which keeps holding only Electron's cookies, caches, and similar state): R refuses to run with an ASCII space anywhere in its scratch `TMPDIR`, and macOS's `userData` path (`~/Library/Application Support/PaperMachine`) contains one, so resolution fails loud instead if the OS user home itself has a space in its path.

A fresh home opens desktop onboarding before the workspace. PaperMachine owns its Python and R environment outright: onboarding installs the shipped `general` environment (or an advanced-editor package list of the user's own), never a conda-family environment already on the machine. Installing writes `<dshHome>/environment-binding.json`, and opens the workspace; the generated Host overlay binds the provisioned prefix to the fixed `science` Runtime profile, hands the Host the bundled micromamba executable and the ordered install channels `install_science_packages` uses, makes Science the session default, removes the generic product-mode picker, disables the shared module-reload `hmr` row, and swaps the sidebar/hero brand slots from the official occupant to the PaperMachine one. On `win32-x64` only, the same overlay also lowers `science-runtime`'s `minimumEnforcement` to `partial` (`src/runtime-overlay.ts`'s `renderDesktopRuntimeOverlay`): the shipped Windows sandbox backend, [`dsh-sandbox-windows-acl`](../../packages/sandbox/sandbox-windows-acl/README.md) (see its "Verified boundaries" section), cannot reach full enforcement; every `darwin-*` target omits the field and keeps the Config default (`full`). See the [minimum-sandbox-enforcement Agent Note](../../.agents/notes/implemented/architecture/2026-09-05-science-runtime-minimum-sandbox-enforcement.md) for why that acceptance is a deployment decision rather than a code fix. The following existing Models onboarding remains the only API-key writer, through the credentials service. See "Onboarding and environment binding" below.

## Development

Build the repository Web artifacts first, then run:

```sh
pnpm --filter @deepseek-ai/dsh-desktop dev
```

Development requires the pinned micromamba asset for the current machine:

```sh
pnpm --filter @deepseek-ai/dsh-desktop fetch:micromamba darwin-arm64
```

Pass `darwin-x64` on an Intel Mac and `win32-x64` on Windows; `DESKTOP_PLATFORMS` (`src/environment-declaration.ts`) is the list, and the script refuses a target outside it. The download is accepted only when its SHA-256 digest matches `resources/micromamba.json`, and lands as `micromamba.exe` for a Windows target. `fetch:micromamba win32-x64` additionally downloads conda-forge's `vc14_runtime` package and lands its 11 root-directory DLLs beside `micromamba.exe`: the bundled `micromamba.exe` dynamically links the MSVC C/C++ runtime, and a bare Windows host has neither the DLLs in `System32` nor, before this, anywhere Windows' DLL search order would find them — see the [app-local CRT Agent Note](../../.agents/notes/implemented/bug-fix/2026-09-07-win32-micromamba-app-local-crt.md).

The carrier never opens the system browser. External HTTPS links are handed to the operating system, while every other navigation outside the active Host origin is refused. An unexpected Host exit leaves the Harness home intact and replaces the page with a restart action.

## Process lifecycle

The Host owns its own POSIX process group. Normal Electron shutdown sends `SIGTERM` so the Host can dispose Cordis and its subprocess tree, then escalates to `SIGKILL` after a bounded grace period. A sibling plain-Node watchdog observes Electron and stops the Host group if Electron is forcibly terminated.

## Host diagnostics

Electron persists the Host's stderr at `<dshHome>/logs/host.log`; Host output never enters the renderer. The shipped `resources/host.json` config has schema version 1, a 5 MiB `logMaxBytes` active-file bound, and `logMaxRotatedFiles: 2`. Both bounds are strict safe integers (`logMaxBytes` from 1 KiB through 50 MiB; retained rotations from 1 through 20), and a missing, unreadable, malformed, or extra-field config fails launch. Before any line reaches disk, the writer replaces exact values from credential-named Host environment variables and common bearer, API-key, authorization, credential, password, secret, token, and `sk-…` forms. The log directory and files are forced to modes `0700` and `0600`; non-regular files and symlinks are rejected; rotation keeps only `host.log`, `host.log.1`, and `host.log.2` under the shipped config. A single line larger than the active-file bound becomes a fixed omission marker rather than retaining an unbounded buffer or writing part of a credential.

## Host port

The Host is launched on the port it last bound successfully, remembered at `<dshHome>/host-port.json` (`src/host-port.ts`), rather than always requesting a fresh OS-assigned port. Browser-side state is keyed by origin, and an OS-assigned port changes the origin on every launch — silently discarding whatever the client had persisted to `localStorage` under the previous one. Today that is the sidebar's details-panel width, the current session selection, the trajectory-duration preference, the workspace browser's grouping/ordering/expansion state, the per-session chat draft and view selection, and the Science artifact viewer's open tabs and library state (`packages/client/*/src/**/stores.ts`, wherever `defineStore`/`createSnapshotStore` opts into `persist`); the sidebar width itself is deliberately excluded from persistence upstream and unaffected by this. A stable origin across ordinary launches keeps all of that intact. Moving this state out of `localStorage` into the settings service is the real long-term fix — it would survive a fallback too — but it reaches across client packages and is out of scope here.

The Host reports no bind failure this carrier can distinguish from any other startup failure: a taken port and an unrelated boot error both surface identically, as the child process exiting before it prints its readiness line. `src/host-launch.ts`'s `launchHostOnRememberedPort` therefore does not try to diagnose the cause — a launch failure on the remembered port (another process holding it, or a second PaperMachine instance already running) is retried once on an OS-assigned port (`0`), and the port the Host actually reports is what gets remembered afterward, never the port that was requested. A missing, unreadable, or corrupt `host-port.json` degrades the same way, to an OS-assigned port, rather than blocking or failing launch. The residual case — an occasional fallback launch — still loses the state above for that one session; this narrows the loss from every launch to the exceptional one, not to zero.

## Onboarding and environment binding

Startup routes solely on `<dshHome>/environment-binding.json` (`src/environment-binding.ts`): a missing file is an ordinary first run that opens onboarding. A file that fails to parse, names a prefix that has since disappeared, or names a prefix outside this application's own provisioned environments root (`<dshHome>/desktop-environments/environments/`) also routes to onboarding with a loud status message — the last case covers a binding written before this application owned its environment outright, or any other foreign conda-family install, and is never silently kept. A valid binding opens the workspace directly. The binding also records the id of the package source the install succeeded through (`sourceId`); a binding without one is invalid. The discipline-package `applied.json` pointer described under Environment declarations below plays no role in this routing.

Onboarding has exactly one route: install. PaperMachine does not offer to bind a conda-family environment already on the machine — one environment it provisions and owns is the only reproducible code path, so first run needs no conda knowledge and a package install into a prefix this application owns can re-solve freely without risking a user's own Anaconda setup. `src/interpreter-presence.ts`'s `qualifyingInterpreters` re-validates a just-provisioned prefix by the same rule Science Runtime's own interpreter check requires (a regular, non-symlinked `conda-meta/history` file plus at least one of the two interpreters at that module's `interpreterLayout` — `bin/python` and `bin/Rscript` on macOS, `python.exe` and `Scripts\Rscript.exe` on Windows) immediately before `main.ts`'s `bindProvisionedPrefix` writes the binding — a defense-in-depth re-check of the same health checks provisioning just ran, at the exact path about to be written. `DesktopEnvironmentProvisioner`'s own health-check step (Environment declarations, below) resolves each check's executable through that same `interpreterLayout` function rather than a fixed path, so the two never risk disagreeing on where an interpreter lives. The application menu's "Change Environment…" action reopens onboarding while the active Host keeps serving the current environment. Onboarding shows the applied id, revision, `applied` or `stale` status, and prefix at the top; "Keep current environment" returns to the workspace by relaunching the Host. When the applied revision matches the standard declaration, the primary action is "Reinstall" and states that it downloads the advertised 850 MB again. Only explicit install confirmation stops the Host before provisioning can modify the prefix.

Onboarding's install-location row lets a user redirect the Harness home to another drive before installing — the one GUI path onto `resolveHarnessHome`'s `customHomeDir` (`src/harness-home.ts`), needed on Windows machines whose `C:` drive is too small for the roughly 6 GB environment. The choice is persisted as a single absolute path in `<osHomeDir>/.papermachine-home` (`src/install-location.ts`), an ASCII-only filename read before either `PAPERMACHINE_HOME` or `DSH_HOME` and ahead of the `<osHomeDir>/.papermachine` default, so it is the precedence tier a GUI user reaches without setting an environment variable. A pointer file that exists but is empty, whitespace-only, names a relative path, or otherwise cannot be read routes to a dedicated recovery page rather than failing silently or leaving the app to vanish with no window at all. The same recovery page opens when a pointer that did read fine instead names a target that becomes unreachable at launch — an unplugged drive, an unmounted network share, a permission change. Either way the page names `<osHomeDir>/.papermachine-home` directly and offers a "Use default location" button; deleting that file by hand has the same effect. The picker's own default is the current Harness home's own parent directory, so confirming it without navigating anywhere would otherwise reuse that parent directory itself — `~` by default, or a Windows drive root — as the new Harness home outright; `resolveChosenInstallLocationPath` (`src/install-location.ts`) instead appends a fixed `PaperMachine` subdirectory to the chosen directory, skipped only when the chosen directory's own basename already names it (case-insensitively on darwin and win32, whose default filesystems are case-insensitive), so an existing `PaperMachine` directory under the chosen location is reused as-is rather than duplicated. The resolved path warns, without rejecting, when it contains non-ASCII characters, then names itself in a confirmation dialog; declining that confirmation, like a dismissed picker or a declined non-ASCII warning, changes nothing on disk. Only after that confirmation is the resolved path validated through `resolveHarnessHome` itself — a candidate that would trip `HarnessHomeSpaceError` is rejected there, still before the pointer file is written — so a decline at any earlier step never leaves behind a directory this handler created just to check it. Accepting relaunches the application so every already-open Host and window picks up the new home from a clean start; nothing at the previous location is moved, which means sessions, the environment binding, and any environment already installed there stay behind and the app starts over as if newly installed, needing its environment installed again at the new location. "Use default" clears the pointer file and relaunches the same way. Choosing "Change…" or "Use default" while a provisioning run is in progress is rejected outright, naming the run rather than relaunching mid-download and silently discarding it.

## Environment declarations

`resources/environments/*.json` is a closed, data-only format: schema version, discipline id and revision, supported platform-architecture pairs, an ordered list of package sources, packages, honest capacity fields, an operation timeout, and exactly one Python plus one R health check. It admits no executable installation hook. The operation timeout bounds both each `micromamba create` attempt and each health check: a cold disk, a Windows real-time scanner walking thousands of newly written `.pyd`/`.dll` files, or an x86_64 wheel's first import under Rosetta translation can each hold a health check past two minutes, so declarations size this field for that case rather than a shorter fixed timeout applying only to health checks. Each revision installs directly at the prefix path it publishes under (`environments/<discipline>/<revision>`), so every health check runs against the exact path `applied.json` will point to — Conda/micromamba installs are not relocatable, so verifying one path and publishing another would prove nothing about what ships. A failed solve, cancellation, or health check leaves the previous `applied.json` pointer unchanged for a fresh or different-revision provision; the same-revision repair path clears that pointer before touching the prefix (see below), so a failure there leaves no applied revision at all. Retry reuses micromamba's package cache and clears the unready prefix directory before recreating it, since a prefix with no matching `applied.json` entry is never ready.

`DesktopEnvironmentProvisioner.provision` (`src/provisioning.ts`'s `resolvePackageCacheDir`) resolves that shared package cache directory explicitly, rather than letting micromamba derive it from `MAMBA_ROOT_PREFIX`, and passes it as `CONDA_PKGS_DIRS` to every `create` attempt. On macOS it is `<dshHome>/desktop-environments/micromamba/pkgs`, the same path micromamba would have used implicitly. On Windows it is `<SystemDrive>\pm\pkgs` instead of a path under `<dshHome>`: micromamba 2.x lays the cache out per source host and channel, and the longest such relative path for the shipped `general` declaration is 251 characters for the TUNA mirror, 242 for USTC, and 226 for the official channel — added to the 10-character `C:\pm\pkgs` root, 261, 252, and 236, so TUNA alone overruns Windows's 260-character `MAX_PATH` while USTC and the official channel stay under it — see [issue #4](https://github.com/SuperJJ007/papermachine/issues/4), the [2026-09-05 package-cache Agent Note](../../.agents/notes/implemented/bug-fix/2026-09-05-win32-package-cache-max-path.md), and the [2026-09-07 TUNA-`MAX_PATH` Agent Note](../../.agents/notes/implemented/bug-fix/2026-09-07-win32-package-cache-tuna-max-path.md). The directory is created before the first `create` attempt; provisioning fails loud, naming the path, if it cannot be created. Because this path sits outside `<dshHome>`, nothing in this application currently removes it, matching the fact that no code path here deletes `<dshHome>/desktop-environments/micromamba` either — Harness home cleanup is left to the user on every platform.

This build ships one declaration, `general`: the Python analysis stack (NumPy, SciPy, pandas, Matplotlib, seaborn, statsmodels, scikit-learn), the file formats research data actually arrives in (openpyxl for Excel, pyreadstat for SPSS and Stata, PyArrow for Parquet), and the R stack (tidyverse, haven, broom, modelr, lme4, survey, srvyr, data.table, jsonlite). ggplot2 arrives with tidyverse and is required, not optional: the kernel's R chart capture calls it directly (`packages/science/science-runtime/assets/chart_ggplot2.R`). Discipline declarations are added beside this one; a prefix holds both interpreters, so a provisioned environment binds `pythonPrefix` and `rPrefix` to the same path.

`general`'s packages are downloaded from three sources, tried in order as whole, independent `micromamba create` attempts rather than merged into one searched channel list: the USTC mirror, the TUNA mirror, then the official `conda.anaconda.org` channel. A source that fails for any reason is abandoned entirely and the next is tried against a freshly cleared prefix, reusing the shared micromamba package cache; the confirmation panel states which source is being tried. The confirmation panel defaults to the USTC mirror when the system timezone is `Asia/Shanghai` or a preferred system language is Chinese (`src/source-selection.ts`, decided from locale settings alone, never a network probe), otherwise the official channel; the user can pick any of the three before confirming, and that choice becomes the first attempt in the fallback order above. The same ordered fallback carries into the workspace: the Host overlay's `science-runtime` row sets `micromambaPath` to the bundled executable and `installChannels` to the shipped sources' channel URLs starting from the bound source, so `install_science_packages` first tries the mirror the environment itself came from, then the remaining sources in order, each as a whole, independent `micromamba install` attempt. The same row sets `installTimeoutMs` to one hour (`renderDesktopRuntimeOverlay`'s fixed `INSTALL_TIMEOUT_MS`), matching the bound this Host's own provisioning already gives micromamba work, so a real multi-minute solve is never misreported as timed out. See the [environment-ownership Agent Note](../../.agents/notes/implemented/feature/2026-09-01-desktop-owns-its-environment.md) for the full rationale.

A user-authored package set (`src/custom-environment.ts`) is published as one further declaration under the id `custom`, built through the same parser so a typed package token faces exactly the validation a shipped declaration faces before it can reach the solver's argv. It carries the same ordered sources as the shipped declaration; its revision is `YYYY.MM.<digest of the sorted package set>`, deliberately excluding sources from that digest since they describe where packages come from, not which packages the resulting environment has. An unchanged package set keeps its prefix and stays `current` across launches, while an edited set provisions into a prefix of its own. The declaration is persisted to `<dshHome>/desktop-environments/custom.json` and re-read at launch, without which `resolveDisciplineStatus` would report `unknown-discipline` for a working custom install and route back to onboarding every time.

Every source attempt writes its own full `micromamba create` output to `<dshHome>/desktop-environments/logs/provision-<sourceId>-<timestamp>.log` (directory mode `0700`, file mode `0600`), whether that attempt succeeded or failed. A failed attempt's log path and its first error line are named in the next source's "Retrying via …" progress update and, if every source fails, in the thrown Error's diagnostic report so a user can locate them. These logs are written unredacted and with no size bound, unlike the bounded, credential-redacting `<dshHome>/logs/host.log` above, because each one lives for a single `provision()` call: `clearStaleAttemptLogs` deletes every prior call's `provision-*.log` file at the start of the next call, so a user must save or copy a log before retrying. If `logs/` cannot be created or cleared (a locked leftover file, say), that call disables attempt logging entirely rather than failing installation over it.

## Installers

`package:mac` and `package:win` each build the repository, download the pinned micromamba assets for their own targets, stage a symlink-free production Host closure, and ask Electron Builder for that platform's installers — arm64 and x64 DMGs on macOS, an x64 NSIS installer on Windows. Both run only on their own platform, and both select the official client profile through `pnpm -w run build --profile official` rather than a leading environment assignment, which the shell pnpm runs a script through on Windows does not accept. Neither publishes: `--publish never` keeps Electron Builder from reading the `repository` field and reaching for a GitHub token, since the release workflow creates the release itself. `scripts/write-update-metadata.ts` then records name, architecture, size, and SHA-256 for that run's installers, and rejects a run that produced fewer than the platform's complete set.

The staged Host closure needs every desktop packaging target's `sharp`/`koffi` native module variant, not just the running machine's own — otherwise an x64 DMG built on an arm64 mac, or a Windows package cross-built on a mac, ships the host machine's own darwin-arm64 binaries under a different platform's app, and the packaged Host exits before readiness with no build-time signal, since sharp and koffi are both loaded at Host startup. `pnpm install` fetches only the running machine's own variant by default, so **before staging, install with every desktop target's architecture widened for this one call**: `pnpm install --frozen-lockfile --os=darwin --os=win32 --os=linux --cpu=x64 --cpu=arm64 --libc=glibc` (`.github/workflows/desktop-release.yml` runs the same flags; local packaging needs them too, before the first `stage:host`). This is a per-invocation CLI override, not a permanent `pnpm-workspace.yaml` setting, because every other native-binary package in the workspace with per-platform variants (ripgrep, `node-addon-require-builtin`, the Landlock launcher, and more) would otherwise widen on every `pnpm install` anyone runs, not just desktop packaging's. `scripts/stage-host.ts` asserts all three desktop targets' sharp/koffi variants are present right after staging and fails loud, naming this install command, if any are missing; `scripts/after-pack.mjs` then deletes every sharp/koffi/ripgrep/etc. variant that is not this specific electron-builder invocation's own platform and architecture, and asserts the packaged `resources/bin/<os>-<arch>` itself carries the pinned micromamba executable and (win32 only) every app-local CRT DLL (`scripts/native-module-targets.mjs` holds the pure selection logic both steps share). See the [native-module-per-target Agent Note](../../.agents/notes/implemented/bug-fix/2026-09-07-host-native-modules-per-target.md).

The Windows installer is per-user (`%LOCALAPPDATA%`, no elevation); it carries no code signature. Neither does `electron-builder.yml` configure an Apple Developer ID for macOS (`mac.identity: null`), so `scripts/after-pack.mjs`'s `afterPack` hook ad-hoc deep-signs the packaged `.app` itself (`codesign --force --deep --sign -`) once every other packaging step has finished editing its contents, then verifies the result with `codesign --verify --deep --strict`: this is the one signature the mac package ships, and it makes Gatekeeper report an unidentified developer instead of a damaged app on a downloaded copy. See the [mac ad-hoc signature Agent Note](../../.agents/notes/implemented/bug-fix/2026-09-07-mac-adhoc-deep-signature.md). The Windows package's `resources/bin/win32-x64/` also carries the MSVC C/C++ runtime DLLs `fetch:micromamba win32-x64` lands there, app-local, next to `micromamba.exe`: a per-user, unelevated installer cannot require or run the machine-wide Visual C++ Redistributable install a bare Windows host is otherwise missing (see the [app-local CRT Agent Note](../../.agents/notes/implemented/bug-fix/2026-09-07-win32-micromamba-app-local-crt.md)). `.github/workflows/desktop-release.yml` builds both platforms and collects the artifacts into one draft GitHub release; a draft creates no tag and stays invisible outside the repository's writers until someone publishes it.

The Windows installer is experimental/beta: `dsh-sandbox-windows-acl` only reaches `partial` sandbox enforcement, not the `full` isolation macOS gets (see its README's "Verified boundaries"); R has known edge cases under non-ASCII install paths or usernames; Windows 10 64-bit or later is required; and an issue report should attach `%USERPROFILE%\.papermachine\logs`.

The generated app owns its Host, environment declarations, and micromamba executable; the Harness home and applied environments stay under `~/.papermachine`, outside the application payload and outside Electron `userData`.

## Bundled default skills

The DMG ships three default Science skills — `scientific-visualization`, `statistical-analysis`, and `scientific-writing` — vendored read-only under `resources/skills/` from the upstream `K-Dense-AI/scientific-agent-skills` repository (exact commit and license in `resources/skills/SOURCES.md`). Electron Builder's `extraResources` stages the directory unmodified at `process.resourcesPath/skills`, outside the asar archive. The generated Host overlay's `skill-filesystem` row (`src/runtime-overlay.ts`) mounts that path as an isolated, global-scope skill provider (`bundledSkillDir`, `includeDefaultRoots: false`, so it discovers nothing else).

A user's own skill of the same name wins. The `science` agent preset's own `skill-filesystem` row keeps discovering project, custom, and `~/.papermachine/skills` roots in the preset's own scope layer, and `dsh-skill`'s registry resolves a duplicate name by nearest scope layer first — the preset's layer is nearer than this bundled row's global layer, so it always shadows a same-named bundled skill regardless of either root's discovery rank. Adding a new skill or overriding a bundled one is a matter of dropping a `<name>/SKILL.md` (or `<name>.md`) under `~/.papermachine/skills`; nothing under `resources/skills` needs editing, and re-copying the bundled set from upstream never touches a user's own skills.

## Usage telemetry

PaperMachine reports three metadata-only events, never content: `app.launch` (once per process start), `environment.installed`, and `environment.install-failed` (a provisioning run's package source, duration or last phase, and whether it was cancelled). Every event carries a fresh `eventId`, the anonymous id shared with the Host's identity plugin (`<dshHome>/.anonymous-user-id`; `src/anonymous-id.ts` creates it in that plugin's exact format when desktop's own first `app.launch` runs before any Host has), a timestamp, `appVersion`, `platform`, `arch`, and `schemaVersion: 1` — no hostnames, paths, package lists, or error text.

Receivers are configured at build time in `resources/telemetry.json` (`schemaVersion: 1`, `endpoints: string[]` of `https://` URLs; parsed by `src/telemetry-config.ts`, which rejects a missing or malformed file loudly rather than silently disabling). Every configured endpoint receives every event independently — no failover, no retry queue, no offline buffer. This build ships one endpoint, the deployed Cloudflare Worker (`apps/telemetry-receivers`); an empty `endpoints: []` is the valid, distinct "telemetry off" state a future build can ship instead. Setting `DSH_TELEMETRY_DISABLED` to any non-empty value — the same switch and interpretation the Host's own session telemetry uses (`resolveTelemetryPatch`, `apps/cli/src/profile-boot.ts`) — sends nothing.

Quitting (`before-quit`) waits for every already-enqueued report to finish sending, bounded by the reporter's own per-endpoint request timeout, so a `void report(...)` fired from a just-cancelled provisioning run (`environment.install-failed`, `cancelled: true`) is not lost to process exit.

## Limitations

The UI still uses the Web HTTP carrier on private loopback. The packaged `file://` plus Electron IPC carrier and automatic update application remain outside this implementation. The Windows installer is built and its carrier tests run on a Windows runner, but no release of it has been accepted on a Windows device. See the [desktop product decision](../../.agents/notes/proposed/architecture/2026-08-23-science-desktop-product.md).

Two known Windows gaps, neither implemented here: micromamba's `create` does not pass `--ssl-no-revoke`, so on a machine whose certificate-revocation check is itself unreachable (plausible for the USTC mirror this build defaults to under a Chinese locale, `src/source-selection.ts`) a package download can fail on a revocation-check error that flag would work around — not passed by default because it weakens TLS certificate validation, a security trade-off this repository has not decided to make. And the Windows CI job that exercises this application's real install path provisions under a short `C:\mm\science` prefix to stay under `MAX_PATH` (`.github/workflows/ci.yml`), not the roughly 99-character prefix a real per-user install uses (`<user>\.papermachine\desktop-environments\environments\general\<revision>`) — that signal covers the package-cache `MAX_PATH` fix (see the [package-cache Agent Note](../../.agents/notes/implemented/bug-fix/2026-09-05-win32-package-cache-max-path.md)) but does not exercise the full real-world prefix length.
