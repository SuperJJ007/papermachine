# 0.1.1

English | [中文](0.1.1.zh.md)

`0.1.1` is PaperMachine's first release built for Windows as well as macOS, superseding `0.1.0` and folding in every earlier `0.1.1` candidate's own history — see [0.1.1-rc.3](0.1.1-rc.3.md) and [0.1.1-rc.4](0.1.1-rc.4.md) for the fixes already recorded there, and [0.1.0](0.1.0.md) for the fixes that shipped between rc.4 and the first public release.

This record covers only what changed after the `papermachine-v0.1.1-rc.4` tag and was not yet in `0.1.0`: 127 commits, most of them building and hardening the Windows port, plus a handful of macOS packaging fixes found this week.

**The Windows installer is experimental/beta**, shipped to gather real-device data rather than as a finished platform: its sandbox only partially enforces file-write confinement (not the full isolation macOS gets — see [`dsh-sandbox-windows-acl`](../../packages/sandbox/sandbox-windows-acl/README.md)'s "Verified boundaries" section), R has known edge cases under non-ASCII install paths or usernames, Windows 10 64-bit or later is required, and an issue report should attach `%USERPROFILE%\.papermachine\logs`; cancelling or timing out a run on Windows always restarts its kernel and loses every variable that kernel held, where macOS usually survives an interrupt.

**On macOS**, the app is now ad-hoc signed at build time, so Gatekeeper should give a plain "unidentified developer" rejection rather than reporting the app damaged; depending on which prompt actually appears, three fixes apply, matching the [README](../../README.md)'s install section: on current macOS, accept the warning from System Settings → Privacy & Security; on older macOS, right-click the app and choose Open; if macOS instead reports the app "is damaged and can't be opened", run `xattr -dr com.apple.quarantine /Applications/PaperMachine.app` once instead — neither of the other two fixes that prompt.

**Download and default source.** The bundled 22-package general science environment is about 850 MB to download and needs 6 GB of free disk; USTC is preselected when the system language or timezone looks like mainland China, otherwise the official conda-forge channel, and on Windows TUNA is not offered as the default because it fails deterministically past a path-length limit (`MAX_PATH`) partway through every install — picking it manually still works only for the packages that stay under the limit, and fails on the same package every time otherwise.

## 改了什么

### 新增

- **Windows installer and first Windows support.** `apps/desktop` ships a `win32-x64` NSIS installer alongside the macOS DMGs, per-user and requiring no administrator rights; `.github/workflows/desktop-release.yml` builds both platforms into one draft GitHub release. See [the desktop Windows installer](../../.agents/notes/implemented/feature/2026-09-04-desktop-windows-installer.md).
- **A pluggable kernel response transport makes Science kernel execution possible on Windows at all.** The persistent kernel's response channel is a seam with a POSIX FIFO implementation and a new win32 loopback-TCP implementation, replacing the win32 preflight rejection that previously refused every kernel spawn outright. See [the win32 kernel response transport](../../.agents/notes/implemented/feature/2026-09-05-win32-kernel-response-transport.md).
- **`science-runtime` accepts a `'partial'`-enforcing sandbox by explicit configuration.** A validated `minimumEnforcement` config field, defaulting to `'full'`, lets a deployment accept Windows's honestly-weaker ACL sandbox instead of hard-rejecting it; the accepted level is recorded on every environment binding. See [minimum sandbox enforcement](../../.agents/notes/implemented/architecture/2026-09-05-science-runtime-minimum-sandbox-enforcement.md).
- **Windows launch no longer shows the unsupported-platform page.** Once the two items above closed the gap that motivated it, the interim block in `openInitialSurface()` was removed; onboarding now starts on Windows like it does on macOS. See [Windows launch unblock](../../.agents/notes/implemented/bug-fix/2026-09-06-windows-launch-block-removed.md).
- **A configurable install location.** Onboarding's environment-choice screen can redirect the roughly 6 GB Harness home to another drive — the fix a Windows user whose `C:` drive is too small needs, applying through a relaunch and validated at every step (non-ASCII warning, confirmation dialog, unreachable-target recovery page). See [install location](../../.agents/notes/implemented/feature/2026-09-05-desktop-install-location.md).
- **Every provisioning attempt's full micromamba log is kept on disk**, and a failed source's own log path is named in the retry message and the diagnostic report, instead of the previous shared, capped ring buffer silently losing an intermediate source's failure once a later source succeeded. See [provisioning attempt logs](../../.agents/notes/implemented/bug-fix/2026-09-07-provisioning-attempt-logs.md).
- **A real Windows CI signal for Science**, and pull-request CI runs on GitHub-hosted runners rather than infrastructure only the upstream project has. See [Windows Science CI signal](../../.agents/notes/implemented/process/2026-09-06-windows-ci-science-signal.md) and [hosted-runner-only pull-request CI](../../.agents/notes/implemented/process/2026-09-05-hosted-runner-only-pull-request-ci.md).

### 修复

- **Every desktop target ships its own `sharp`/`koffi` native module variant instead of whichever variant happened to be installed on the build machine.** An arm64-built x64 DMG or a mac-cross-built Windows package previously carried the wrong platform's binaries and crashed the Host on launch; this affected the already-published `papermachine-v0.1.0` x64 DMG. See [native modules per target](../../.agents/notes/implemented/bug-fix/2026-09-07-host-native-modules-per-target.md).
- **The packaged macOS app is ad-hoc deep-signed**, so Gatekeeper reports an unidentified developer instead of "damaged and can't be opened"; the README's guidance now covers both prompts instead of only the one right-click-Open fixes. See [mac ad-hoc deep signature](../../.agents/notes/implemented/bug-fix/2026-09-07-mac-adhoc-deep-signature.md).
- **Windows ships the MSVC C/C++ runtime app-local, next to `micromamba.exe`.** A bare Windows install had none of `vcruntime140.dll`/`vcruntime140_1.dll`/`msvcp140.dll` and failed provisioning with `STATUS_DLL_NOT_FOUND`; the fetch script now stages all three next to the binary that needs them. See [win32 app-local CRT](../../.agents/notes/implemented/bug-fix/2026-09-07-win32-micromamba-app-local-crt.md).
- **The Windows micromamba package cache stays under `MAX_PATH`, and TUNA is no longer the default mainland-China source.** Moving the cache root to `<SystemDrive>\pm\pkgs` fixed the general case; TUNA's longer hostname still pushes one transitive R dependency's deepest header path over the 260-character limit, so `general.json` now lists USTC first. See [package cache MAX_PATH](../../.agents/notes/implemented/bug-fix/2026-09-05-win32-package-cache-max-path.md) and [the TUNA measurement](../../.agents/notes/implemented/bug-fix/2026-09-07-win32-package-cache-tuna-max-path.md).
- **win32 provisioning children get the ambient system environment, and a Harness home containing a space recovers instead of failing silently.** Neither `SystemRoot`/`USERPROFILE`/etc. nor a dedicated recovery page for a space-containing default home (`C:\Users\John Smith`) existed before; both were found by static review before either was reported from a device. See [provisioning environment and space-path recovery](../../.agents/notes/implemented/bug-fix/2026-09-06-win32-desktop-provisioning-env-and-space-path.md).
- **Eight pre-existing defects blocked every win32 Science kernel before it could spawn**, found one after another on a real Windows Server 2022 run once the transport and sandbox-config work above made a win32 kernel spawn reachable in principle: win32's synthetic `lstat` mode bits broke the scratch-privacy check for both directories and files, probe confinement ran before its own scratch directory existed, a fake test-only sandbox runner and the package-cache test harness carried POSIX-only assumptions, a directory handle's `fsync` has no win32 equivalent, captured run output was CRLF-translated, and the configured `minimumEnforcement` never reached kernel-spawn confinement. See [scratch privacy and probe ordering](../../.agents/notes/implemented/bug-fix/2026-09-06-win32-scratch-privacy-and-probe-ordering.md).
- **win32 R's UTF-8 output and non-ASCII probe arguments both work now.** `C.UTF-8` does not give conda-forge's win32 R a working UTF-8 locale the way it does on POSIX (`en_US.UTF-8` does); separately, the win32 `Rscript.exe` launcher re-forwards argv through an ANSI, not wide-character, API that corrupted a literal non-ASCII probe string before R ever saw it. Both blocked `bindEnvironment` from ever reporting R available on Windows. See [R locale and probe argv](../../.agents/notes/implemented/bug-fix/2026-09-06-win32-r-locale-and-ascii-probe-argv.md).
- **A shared Conda prefix drifting under a running session is now detected and re-observed per run**, instead of leaving every session but the one that ran the install permanently reporting a stale environment fingerprint. See [shared prefix drift](../../.agents/notes/implemented/bug-fix/2026-09-06-science-shared-prefix-drift.md).
- **Each health check gets the declaration's own timeout, not a hidden 120-second cap.** An Intel or Apple Silicon-Rosetta install's first import of `general.json`'s native-extension-heavy Python packages, or a cold disk's or Windows Defender's first scan of a fresh R library, can each run well past two minutes; a health check that hits the old cap failed with `desktop provisioning: timed out` even though the interpreter was still working. See [health check timeout follows declaration](../../.agents/notes/implemented/bug-fix/2026-09-08-health-check-timeout-follows-declaration.md).
- **Every Windows Science task now spawns a real interpreter instead of a phantom app instance.** The win32 ACL sandbox re-execs `process.execPath` — the packaged `PaperMachine.exe` — to run its Node runner, but never gave that spawn `ELECTRON_RUN_AS_NODE=1`; the packaged binary booted itself as a second, complete desktop app instead, which then raced the real Host for its remembered port while the real `python.exe`/`Rscript.exe` never ran, hanging every task to its 120-second timeout. `ConfinedArgv` now carries the required env entries its backend's runner invocation needs, merged by every consumer before spawning; `apps/desktop`'s single-instance lock adds defense in depth. See [win32 ACL runner env](../../.agents/notes/implemented/bug-fix/2026-09-08-win32-acl-runner-electron-run-as-node.md).

### 已知

- **Windows sandbox enforcement is `partial`, not `full`.** An externally Everyone-writable object stays writable through it, and an NTFS hard link aliases a granted workspace file onto an external path; see [`dsh-sandbox-windows-acl`](../../packages/sandbox/sandbox-windows-acl/README.md)'s "Verified boundaries" section.
- **No cooperative interrupt on Windows.** `SubprocessHandle.interrupt()` is a documented no-op there; a cancelled or timed-out run always restarts its kernel and loses every variable that kernel held.
- **The Windows-specific 9/7 packaging fixes have not been reconfirmed on a real Windows device.** The app-local CRT fix, the per-target native-module fix, and the per-attempt provisioning log fix were each verified through unit tests and, for the native-module fix, real packaged-output inspection on macOS and a Windows build's file layout — but none has been installed and run on Windows since landing. Windows kernel execution itself (Python and R spawn, run, cancel, and same-kernel state persistence) was confirmed end to end on a real Windows Server 2022 box, before these three fixes.
- **No repeatable Windows CI gate against real hardware.** The new `windows-native` CI job has no Python or R installed, so `kernel-transport-real.spec.ts`'s real-driver cases still self-skip there; today's only real-hardware signal is the manual verification runs each note above cites.
- **The Windows desktop first-launch flow (onboarding, environment download and install) has not been verified end to end on Windows hardware since the 9/7 packaging fixes landed.** Kernel execution has.
- **0.1.0's known limitations are otherwise unchanged**: no in-app telemetry switch, the Alibaba Cloud FC telemetry receiver is not deployed, a nature-figure-style color palette stays deferred, and no systematic accessibility pass has run. See [0.1.0](0.1.0.md)'s 已知 section.

## 实机验了什么

No formal on-device checklist pass ran against a `0.1.1` build; the [device checklist](../product/device-checklist.md) still has no Windows-specific items to run against.

**macOS** carries forward `0.1.0`'s own delta-pass record unchanged (see [0.1.1-rc.4](0.1.1-rc.4.md)'s table), plus two of this release's fixes verified directly against real packaged output on this machine: the ad-hoc-signed app's Gatekeeper verdict (`spctl --assess` reporting `rejected` — the normal unidentified-developer path, not "damaged" — on both an arm64 and an x64 `--dir` build, a mounted DMG, and a quarantine-simulated copy) and the per-target native-module packaging (a real Host process starting and printing its ready line under `ELECTRON_RUN_AS_NODE=1` on both architectures, with `sharp`/`koffi` importing cleanly and no foreign-platform files present in either package).

**Windows** verification is a chronological sequence of ad hoc real-device runs against a cloud-hosted Windows Server 2022 instance during this week's development, each tied to a specific defect found and then fixed, not a single end-to-end pass: kernel spawn, run, cancel, and same-kernel state persistence were confirmed working for both Python and R after the transport, sandbox-config, scratch-privacy, and R-locale fixes landed. The three fixes that landed afterward — app-local CRT, per-target native modules, and per-attempt provisioning logs — have each been verified locally (unit tests, and for the CRT fix, a real download-and-verify of the pinned DLL package) but not yet reinstalled and run on that or any other Windows device.

## 遗留

- **Real-device confirmation of the app-local CRT, per-target native-module, and per-attempt provisioning-log fixes on Windows.** Each is unit-tested and, for the native-module fix, verified against real packaged output, but none has been installed and run on a Windows device since landing.
- **A full on-device checklist pass covering Windows**, once the [device checklist](../product/device-checklist.md) gains Windows-specific items.
- **A Windows cooperative interrupt mechanism.** Building a `CTRL_BREAK_EVENT`-based equivalent to POSIX `SIGINT` is separate, undesigned work; today every Windows cancel or timeout loses the kernel's state.
- **A repeatable Windows CI gate against real hardware**, replacing today's manual verification; the `windows-native` CI job still has no Python or R interpreter to drive `kernel-transport-real.spec.ts`'s real-driver cases.
- **`0.1.1-rc.4`'s three pending owner decisions and post-release queue are unchanged**: see [0.1.1-rc.4](0.1.1-rc.4.md)'s 遗留 section.
- **`0.1.0`'s own unresolved items are unchanged**: an in-app telemetry switch, the Alibaba Cloud FC receiver, a nature-figure-style palette, and a systematic accessibility pass. See [0.1.0](0.1.0.md)'s 遗留 section.
