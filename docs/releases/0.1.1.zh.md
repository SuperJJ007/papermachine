# 0.1.1

[English](0.1.1.md) | 中文

`0.1.1` 是 PaperMachine 第一个同时为 Windows 和 macOS 构建的版本,取代 `0.1.0`,并纳入此前每一个 `0.1.1` 候选版本自己的历史——已经记录过的修复见 [0.1.1-rc.3](0.1.1-rc.3.zh.md)和[0.1.1-rc.4](0.1.1-rc.4.zh.md),rc.4 到首个公开发布之间落地的修复见 [0.1.0](0.1.0.zh.md)。

这份记录只覆盖 `papermachine-v0.1.1-rc.4` 这个 tag 之后、还没进 `0.1.0` 的改动:127 个 commit,绝大多数在构建和加固 Windows 移植,外加本周发现的几个 macOS 打包修复。

**Windows 安装包是 experimental/beta**,发出去是为了拿真实设备的数据,不是一个已完工的平台:它的沙箱只做部分的文件写入限制(不是 macOS 那种完整隔离——见 [`dsh-sandbox-windows-acl`](../../packages/sandbox/sandbox-windows-acl/README.zh.md)的"已验证边界"一节),R 在非 ASCII 安装路径或用户名下有已知边缘情况,要求 Windows 10 64 位及以上,报 issue 时请附上 `%USERPROFILE%\.papermachine\logs`;在 Windows 上取消或超时一次运行总会重启内核,丢掉那个内核持有的每一个变量,而 macOS 上一次中断通常能保留下来。

**在 macOS 上**,应用现在构建时做了 ad-hoc 签名,所以 Gatekeeper 应该给出一个干净的"未识别开发者"拒绝,而不是报告应用已损坏;具体出现哪个提示,对应三条修复,与 [README](../../README.zh.md) 的安装段一致:在较新的 macOS 上,从系统设置→隐私与安全性里接受警告;在较旧的 macOS 上,右键点应用选择"打开";如果 macOS 报告应用"已损坏,无法打开",改为运行一次 `xattr -dr com.apple.quarantine /Applications/PaperMachine.app`——另外两条修复对这个提示都不起作用。

**下载体积与默认源。** 内置的 22 个包的通用科学环境大约要下载 850 MB,需要 6 GB 可用磁盘空间;当系统语言或时区看起来像中国大陆时,USTC 会被预选,否则用官方 conda-forge 源,而在 Windows 上 TUNA 不作为默认源提供,因为它会在安装过程中因路径长度限制(`MAX_PATH`)确定性地失败——手动选它对没超限的包仍然有效,但同一个包每次都会失败。

## 改了什么

### 新增

- **Windows 安装包,首次支持 Windows。** `apps/desktop` 现在除了两个 macOS DMG,还打出一个按用户安装、不需要管理员权限的 `win32-x64` NSIS 安装包;`.github/workflows/desktop-release.yml` 把两个平台都构建进同一个草稿版 GitHub release。参见[桌面端 Windows 安装包](../../.agents/notes/implemented/feature/2026-09-04-desktop-windows-installer.zh.md)。
- **一条可插拔的内核响应传输,让 Science 内核在 Windows 上真的能跑起来。** 持久内核的响应通道现在是一个抽象接口,POSIX 上是 FIFO 实现,新增了 win32 上的回环 TCP 实现,取代了此前直接拒绝所有 win32 内核启动的预检拦截。参见 [win32 内核响应传输](../../.agents/notes/implemented/feature/2026-09-05-win32-kernel-response-transport.zh.md)。
- **`science-runtime` 现在可以按显式配置接受一个 `'partial'`(部分)强度的沙箱。** 新增一个校验过的 `minimumEnforcement` 配置字段,默认 `'full'`,可以让部署方接受 Windows 那个诚实报告为较弱的 ACL 沙箱,而不是硬性拒绝它;实际接受的强度会记录在每一次环境绑定上。参见[最低沙箱强度](../../.agents/notes/implemented/architecture/2026-09-05-science-runtime-minimum-sandbox-enforcement.zh.md)。
- **Windows 启动不再显示"不支持的平台"页面。** 上面两项补上缺口之后,`openInitialSurface()` 里那个临时拦截被移除;onboarding 现在在 Windows 上和在 macOS 上一样能启动。参见 [Windows 启动解锁](../../.agents/notes/implemented/bug-fix/2026-09-06-windows-launch-block-removed.zh.md)。
- **可配置的安装位置。** onboarding 的环境选择界面现在能把大约 6 GB 的 Harness 主目录重定向到另一块盘——这正是一个 `C:` 盘太小的 Windows 用户需要的修复,通过一次重启应用生效,每一步都有校验(非 ASCII 警告、确认对话框、目标不可达时的恢复页面)。参见[安装位置](../../.agents/notes/implemented/feature/2026-09-05-desktop-install-location.zh.md)。
- **每一次置备尝试完整的 micromamba 日志都会落盘**,失败源自己的日志路径会出现在重试提示和诊断报告里,而不再是此前那种共享、有上限的环形缓冲区——一旦后面的源成功了,前一个失败源的记录就悄悄没了。参见[置备尝试日志](../../.agents/notes/implemented/bug-fix/2026-09-07-provisioning-attempt-logs.zh.md)。
- **Science 有了真实的 Windows CI 信号**,拉取请求 CI 也改成跑在 GitHub 托管的 runner 上,不再依赖只有上游项目才有的基础设施。参见 [Windows Science CI 信号](../../.agents/notes/implemented/process/2026-09-06-windows-ci-science-signal.zh.md)和[仅托管 runner 的拉取请求 CI](../../.agents/notes/implemented/process/2026-09-05-hosted-runner-only-pull-request-ci.zh.md)。

### 修复

- **每个桌面构建目标现在都打包自己那份 `sharp`/`koffi` 原生模块变体,而不是构建机上恰好装了哪个就打包哪个。** 一个在 arm64 上构建的 x64 DMG,或者在 mac 上交叉构建的 Windows 包,此前都会带上错误平台的二进制,导致 Host 一启动就崩溃;这影响了已经发布的 `papermachine-v0.1.0` x64 DMG。参见[按目标平台打包原生模块](../../.agents/notes/implemented/bug-fix/2026-09-07-host-native-modules-per-target.zh.md)。
- **打包后的 macOS 应用现在做 ad-hoc 深度签名**,所以 Gatekeeper 报告的是"未识别开发者",不再是"已损坏,无法打开";README 的指引现在覆盖两种提示,而不只是右键"打开"能解决的那一种。参见 [mac ad-hoc 深度签名](../../.agents/notes/implemented/bug-fix/2026-09-07-mac-adhoc-deep-signature.zh.md)。
- **Windows 把 MSVC C/C++ 运行时以 app-local 方式和 `micromamba.exe` 放在一起。** 一台干净的 Windows 装机没有 `vcruntime140.dll`/`vcruntime140_1.dll`/`msvcp140.dll` 中的任何一个,导致置备以 `STATUS_DLL_NOT_FOUND` 失败;现在下载脚本会把这三个 DLL 和需要它们的二进制放在同一目录下。参见 [win32 app-local CRT](../../.agents/notes/implemented/bug-fix/2026-09-07-win32-micromamba-app-local-crt.zh.md)。
- **Windows 上 micromamba 的包缓存保持在 `MAX_PATH` 以内,中国大陆默认源也不再是 TUNA。** 把缓存根目录挪到 `<SystemDrive>\pm\pkgs` 解决了一般情况;但 TUNA 更长的主机名仍然会让某个 R 传递依赖最深的头文件路径超过 260 字符的上限,所以 `general.json` 现在把 USTC 排在第一位。参见[包缓存 MAX_PATH](../../.agents/notes/implemented/bug-fix/2026-09-05-win32-package-cache-max-path.zh.md)和 [TUNA 的实测](../../.agents/notes/implemented/bug-fix/2026-09-07-win32-package-cache-tuna-max-path.zh.md)。
- **win32 置备子进程拿到了系统的环境变量,一个路径含空格的 Harness 主目录也不再静默失败,而是能恢复。** 此前既没有把 `SystemRoot`/`USERPROFILE` 等环境变量传给置备子进程,也没有给一个含空格的默认主目录(`C:\Users\John Smith`)配专门的恢复页面;两处都是靠静态审查发现的,发现时都还没有设备报告过。参见[置备环境变量与空格路径恢复](../../.agents/notes/implemented/bug-fix/2026-09-06-win32-desktop-provisioning-env-and-space-path.zh.md)。
- **八个已存在的缺陷曾让每一个 win32 Science 内核在启动前就被挡住**,是在上面两项传输/沙箱配置工作让 win32 内核启动理论上可达之后,在一台真实的 Windows Server 2022 上一个接一个发现的:win32 合成的 `lstat` 权限位让目录和文件的私密性检查都失败、探测的沙箱限制在自己的暂存目录创建之前就执行、一个仅测试用的假沙箱运行器和包缓存测试脚手架都带着 POSIX 独有的假设、目录句柄的 `fsync` 在 win32 上没有对应机制、捕获的运行输出被做了 CRLF 转换,以及配置的 `minimumEnforcement` 从没传到内核启动的沙箱限制那一步。参见[暂存区私密性与探测顺序](../../.agents/notes/implemented/bug-fix/2026-09-06-win32-scratch-privacy-and-probe-ordering.zh.md)。
- **win32 上 R 的 UTF-8 输出和非 ASCII 探测参数现在都正常了。** `C.UTF-8` 在 conda-forge 的 win32 R 上不像在 POSIX 上那样给出一个能用的 UTF-8 locale(`en_US.UTF-8` 可以);另外,win32 的 `Rscript.exe` 启动器会经由一个 ANSI(而非宽字符)API 转发命令行参数,在 R 看到之前就把一个字面的非 ASCII 探测字符串弄坏了。这两个问题都会让 `bindEnvironment` 在 Windows 上永远报告不出 R 可用。参见 [R locale 与探测参数](../../.agents/notes/implemented/bug-fix/2026-09-06-win32-r-locale-and-ascii-probe-argv.zh.md)。
- **一个共享的 Conda 前缀在会话运行期间发生漂移时,现在会被逐次运行检测并重新观测**,而不是让除了跑安装那个会话之外的所有会话永久报告一份过时的环境指纹。参见[共享前缀漂移](../../.agents/notes/implemented/bug-fix/2026-09-06-science-shared-prefix-drift.zh.md)。
- **每一条 health check 现在使用声明自己的超时,而不是一个隐藏的 120 秒上限。** 在 Intel 或 Apple Silicon 的 Rosetta 环境下首次 import `general.json` 里那些原生扩展较重的 Python 包,或者一块冷盘、Windows Defender 首次扫描一个刚装好的 R library,都可能远超两分钟;此前撞上这个旧上限的 health check 会以 `desktop provisioning: timed out` 失败,即便解释器其实还在正常工作。参见[health check 超时改随声明](../../.agents/notes/implemented/bug-fix/2026-09-08-health-check-timeout-follows-declaration.zh.md)。

### 已知

- **Windows 的沙箱强度是 `partial`,不是 `full`。** 一个对 Everyone 可写的外部对象透过它仍然可写,一条 NTFS 硬链接能把一个已授权的工作区文件别名到一个外部路径;见 [`dsh-sandbox-windows-acl`](../../packages/sandbox/sandbox-windows-acl/README.zh.md)的"已验证边界"一节。
- **Windows 上没有协作式中断。** `SubprocessHandle.interrupt()` 在那里是一个有文档说明的空操作;一次取消或超时的运行总会重启内核,丢掉那个内核持有的每一个变量。
- **9/7 这批 Windows 专属打包修复还没有在真实 Windows 设备上复验过。** app-local CRT 修复、按目标平台的原生模块修复、逐次置备日志修复,各自都通过了单测,原生模块修复还对照过真实打包产物(在 macOS 上检查,以及一次 Windows 构建的文件布局),但落地以来都还没有在 Windows 上装上跑过。Windows 内核执行本身(Python 和 R 的启动、运行、取消,以及同一内核状态的持久化)在这三项修复之前,已经在一台真实的 Windows Server 2022 上端到端验证过。
- **没有对真实硬件的、可重复的 Windows CI 门禁。** 新增的 `windows-native` CI job 上没有装 Python 或 R,所以 `kernel-transport-real.spec.ts` 里真正驱动解释器的用例在那里仍然会自跳过;今天唯一的真实硬件信号,是上面每篇笔记各自引用的那些人工验收记录。
- **9/7 打包修复落地之后,Windows 桌面端的首次启动流程(onboarding、环境下载与安装)还没有在 Windows 硬件上端到端验证过。** 内核执行部分已经验证过。
- **0.1.0 的已知限制其余不变**:没有应用内的遥测开关,阿里云 FC 遥测接收端未部署,一套 Nature 风格配色方案仍然搁置,也没有跑过系统性的无障碍验收。参见 [0.1.0](0.1.0.zh.md) 的"已知"一节。

## 实机验了什么

没有针对 `0.1.1` 构建跑过正式的实机 checklist;[实机验收清单](../product/device-checklist.zh.md)目前也还没有 Windows 专属的条目可跑。

**macOS** 原样带着 `0.1.0` 自己的增量验收记录不变(见 [0.1.1-rc.4](0.1.1-rc.4.zh.md) 的表格),外加本轮两项修复直接对照真实打包产物在这台机器上做的验证:ad-hoc 签名之后应用的 Gatekeeper 判定(`spctl --assess` 在一次 arm64 和一次 x64 的 `--dir` 构建、一个挂载的 DMG、以及一份模拟隔离属性的副本上都报告 `rejected`——正常的未识别开发者路径,不是"已损坏"),以及按目标平台打包原生模块(两种架构下打包出的真实 Host 进程都能启动并打印就绪行,`sharp`/`koffi` 都能正常导入,两个包里都没有混进其他平台的文件)。

**Windows** 的验证是本周开发过程中,针对一台云上 Windows Server 2022 实例做的一串按时间顺序的人工实机验收,每一次都对应一个被发现并随即修复的具体缺陷,不是一次端到端通验:在传输、沙箱配置、暂存区私密性、R locale 这几项修复落地之后,Python 和 R 的内核启动、运行、取消,以及同一内核状态的持久化都已确认可用。随后落地的三项修复——app-local CRT、按目标平台的原生模块、逐次置备日志——各自都在本地验证过(单测,以及 CRT 修复那次对固定 DLL 包的一次真实下载与校验),但还没有在那台或任何其他 Windows 设备上重新装上跑过。

## 遗留

- **app-local CRT、按目标平台原生模块、逐次置备日志这三项修复在 Windows 上的真机复验。** 每一项都有单测覆盖,原生模块修复还对照过真实打包产物,但落地以来都还没有在 Windows 设备上装上跑过。
- **一次覆盖 Windows 的完整实机 checklist 通验**,等[实机验收清单](../product/device-checklist.zh.md)有了 Windows 专属条目之后再跑。
- **一套 Windows 的协作式中断机制。** 做一个基于 `CTRL_BREAK_EVENT`、对应 POSIX `SIGINT` 的机制是另一块还没设计的独立工作;目前 Windows 上的每一次取消或超时都会丢掉内核状态。
- **一道对真实硬件的、可重复的 Windows CI 门禁**,取代今天的人工验收;`windows-native` CI job 仍然没有 Python 或 R 解释器去驱动 `kernel-transport-real.spec.ts` 里那些真正的解释器用例。
- **`0.1.1-rc.4` 的三个待裁决问题和发布后队列不变**:见 [0.1.1-rc.4](0.1.1-rc.4.zh.md) 的"遗留"一节。
- **`0.1.0` 自己未解决的项目不变**:应用内遥测开关、阿里云 FC 接收端、Nature 风格配色方案,以及系统性的无障碍验收。参见 [0.1.0](0.1.0.zh.md) 的"遗留"一节。
